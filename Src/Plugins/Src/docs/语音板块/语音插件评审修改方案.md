## 一、总体结论

三件套已经完成新插件开发文档中的主要"发布方"升级项：

- `Startup` 均使用 `[Plugin]` 声明 `voice.kws` / `voice.stt` / `voice.tts` 能力。
- 已使用 `[PublishesEvent]` 声明 `voice.*.v1` 事件契约。
- 运行时事件发布已通过共享 `PluginBusClient.PublishEventAsync(op, JsonElement)`，payload 使用插件本地 `JsonSerializerContext`。
- Process 插件宿主已在 `ProcessPluginHost` 中统一注册 `PluginBusClient`，并以 `PluginInfoData.Id` 作为 `sourcePluginId`，语音插件自身无需再手工注册共享客户端。
- `.csproj` 已启用 `<PublishAot>true</PublishAot>` 与 `<JsonSerializerIsReflectionEnabledByDefault>false</JsonSerializerIsReflectionEnabledByDefault>`。
- 模型目录已作为 `Content` 复制到输出和发布目录。

本轮已按该评审完成实现修复，重点结果：

1. **架构契约缺口已补齐**：KWS/STT 已声明 `[SubscribesEvent]` 并注册插件内 `BackgroundService`，通过共享 `PluginBusClient.SubscribeEventAsync` 订阅协同事件；TTS 仍默认不订阅 voice 事件。
2. **运行期 bug 已修复**：STT stopped 不再由工具层重复发布；TTS `Finish` 不再冒充 completed；TTS 模型缺失时不再伪造 started/subtitle/completed/greeting_ready；KWS/STT 真实事件链路会同步写 runtime state；PluginBus 类型化包装层捕获并记录发布异常。
3. **配置和文档已对齐**：KWS/STT 模型目录改用 `PluginSettings.PluginDirectory`；TTS `speed` 改为 `float?`；TTS 模型校验补 `dict/`；语音指南补齐宿主转发机制、协同订阅、模型文件要求和 `Diagnostics/`。
4. **框架层兼容修复**：`Netor.Cortana.Plugin.Process.Generator` 已修复可空值类型参数生成逻辑，省略或传 `null` 时不会再被解析成 `0` 或抛 `GetDouble/GetInt32` 异常；`DebuggerArgs` 增加 `AddIfNotNull` 支持调试器正确省略可空值类型参数。

## 二、架构级变更：语音三件套应只改插件侧使用 PluginBus 做协同

宿主现已支持 PluginBus 的插件间协调，具体链路是：

1. 插件通过 `PluginBusClient.PublishEventAsync(op, JsonElement)` 发送 `type=event` 帧。
2. `WebSocketPluginBusServerService` 识别 `type=event` 后交给 `PluginBusBroadcastDispatcher`。
3. `PluginBusBroadcastDispatcher` 从 op 首段提取 topic，例如 `voice.kws.detected.v1` 的 topic 是 `voice`。
4. `PluginBusSubscriptionRegistry` 找到订阅该 topic 的连接，再按运行帧 `subscribedOps` 二次过滤，并排除 source client，避免自回环。
5. 对 `voice.*` 事件，宿主同步调用 `VoiceEventBridge` 桥接到宿主 `IPublisher` / UI 事件；同时仍按订阅关系转发给其他插件。
6. `PluginBusClient.SubscribeEventAsync(op, handler)` 会自动发送 `subscribe` 帧，携带 topics 和已注册的 `subscribedOps`。

因此，语音三件套之间的基础协同可以在现有框架下完成：KWS/STT/TTS 仍是独立插件，通过一对多事件广播互相感知状态，不需要为了这条协同链路修改宿主程序。只有以下情况才需要另行评审宿主改动：新增宿主级 UI 事件、新增受保护 RPC op、要求事件持久化/重放、要求强安全绑定或跨插件事务语义。

语音功能不是单个工具调用能完整表达的场景，KWS / STT / TTS 天然是一条事件驱动流水线，因此应作为插件侧架构改变处理，不能只把 PluginBus 当成"向宿主 UI 发事件"的传输细节。

目标架构调整为：

- KWS、STT、TTS 均是独立语音能力插件，通过 `voice.*.v1` 事件协调，不直接互相持有引用，也不依赖宿主硬编码串联。
- 宿主负责提供 PluginBus 路由、弱声明校验、订阅过滤、EventHub 桥接和 UI 状态同步。
- 插件之间通过 `[PublishesEvent]` / `[SubscribesEvent]` 显式声明协同契约，生成到 `plugin.json.publishedOps` / `plugin.json.subscribedOps`。
- 高频状态变化走 PluginBus 事件（唤醒、识别 partial/final、TTS started/subtitle/completed/error）。
- 需要明确结果的动作仍走工具调用或后续 RPC 型 op，不把 PluginBus 事件误用成同步 RPC。

建议的语音协同链路：

1. KWS 检测到唤醒词后发布 `voice.kws.detected.v1`。
2. STT 订阅 `voice.kws.detected.v1`，进入识别会话或准备态，并发布 `voice.stt.partial.v1` / `voice.stt.final.v1` / `voice.stt.stopped.v1`。
3. STT 订阅 `voice.tts.started.v1` / `voice.tts.completed.v1`，在 TTS 播放期间暂停或降低识别敏感度，避免把系统朗读再次识别成用户输入。
4. KWS 订阅 `voice.tts.started.v1` / `voice.tts.completed.v1`，在播放期间调整唤醒策略，避免自唤醒。
5. **TTS 默认不订阅 `voice.stt.final.v1`**：识别结果不等于要朗读的内容，朗读队列应由对话编排层（`conversation.*` 事件或宿主直接调用 `voice_tts_speak`）驱动；如果产品上确有"识别即朗读"的回声功能，应在产品层评审后再加订阅，并写明触发条件。
6. 字幕、桌宠、日志归档等后续插件只订阅需要的 `voice.*` op，不再要求宿主为每个扩展点写专用集成代码。

当前代码只完成了"发布方"升级，"插件间协同"升级还没动：

- KWS 没有声明或实现对 TTS 状态事件的订阅。
- STT 没有声明或实现对 KWS detected、TTS started/completed 的订阅。
- TTS 默认无订阅契约，文档没把这个"默认不订阅"明确写下来，留出语义模糊。
- 原 `Docs/三方对接文档/插件开发指南/语音插件开发指南.md` 只写了发布事件和第三方消费语音事件，缺少宿主 plugin->plugin 转发机制、三件套协同订阅关系和"只改插件侧即可完成协同"的边界说明；本次文档修正应把这些内容补齐。

## 三、代码逻辑问题

### 1. 语音三件套缺少 PluginBus 插件间协同订阅

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Kws.Sherpa/Startup.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Stt.Sherpa/Startup.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Tts.Melo/Startup.cs`

现状：

- 三个插件均声明了 `[PublishesEvent]`。
- 三个插件均未声明 `[SubscribesEvent]`。
- 当前协同主要依赖宿主桥接到 EventHub/UI 或外部工具主动调用，而不是插件之间通过 PluginBus 订阅协同。

问题：

- 新宿主已经支持 PluginBus 插件间协调，语音流水线应使用这个能力作为主架构。
- 没有订阅契约时 `plugin.json.subscribedOps` 为空，宿主无法做订阅审计，后续字幕、桌宠、语音仲裁、降噪等插件也缺少稳定协作入口。
- STT 无法根据 KWS detected 自动进入会话；KWS/STT 无法根据 TTS 播放状态调整监听策略，容易出现自唤醒、回声识别、状态不同步。
- 当前缺口在插件侧：需要声明 `[SubscribesEvent]`、注册 `BackgroundService`、调用 `PluginBusClient.SubscribeEventAsync` 并实现轻量 handler。宿主的转发、订阅过滤和 voice 桥接能力已经具备。

修改方案：

- STT 入口增加：
  - `[SubscribesEvent("voice.kws.detected.v1", Reason = "唤醒后启动或准备一次语音识别会话")]`
  - `[SubscribesEvent("voice.tts.started.v1", Reason = "TTS 播放期间暂停或降低语音识别敏感度")]`
  - `[SubscribesEvent("voice.tts.completed.v1", Reason = "TTS 播放结束后恢复语音识别策略")]`
- KWS 入口增加：
  - `[SubscribesEvent("voice.tts.started.v1", Reason = "TTS 播放期间避免系统朗读触发唤醒")]`
  - `[SubscribesEvent("voice.tts.completed.v1", Reason = "TTS 播放结束后恢复唤醒监听策略")]`
- TTS 入口默认不增加 `[SubscribesEvent]`；如果产品需要自动朗读，订阅 `conversation.*` 而不是 `voice.stt.final.v1`，并在订阅前评审。
- 为 KWS/STT 新增 `BackgroundService`（插件内生命周期服务），在启动时调用共享 `PluginBusClient.SubscribeEventAsync` 注册 handler。
- 不需要在三件套 `Startup` 中重新注册 `PluginBusClient`；Process 插件宿主已经统一注册，并会作为 `IHostedService` 管理连接生命周期。
- handler 内只做轻量状态切换，不执行长耗时合成/识别；需要长任务时投递到内部队列。

实现状态：

- 已新增 `KwsVoiceCoordinator`、`SttVoiceCoordinator`，handler 只写入有界 Channel，后台单消费者串行处理 start/stop 策略。
- KWS 订阅 `voice.tts.started.v1` / `voice.tts.completed.v1`；STT 订阅 `voice.kws.detected.v1` / `voice.tts.started.v1` / `voice.tts.completed.v1`。
- TTS 未增加订阅契约，保持由对话编排层或工具调用驱动朗读。

### 2. STT stopped 事件可能重复发布

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Stt.Sherpa/Tools/VoiceSttTools.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Stt.Sherpa/Engine/SttEngine.cs`

现状：

- `VoiceSttTools.Stop` 调用 `state.Stop()` 后立即 `PublishStoppedAsync(sessionId)`。
- `SttEngine.RunLoop` 的 `finally` 也会 `PublishStoppedAsync(sessionId)`。

问题：

- 正常停止时工具层和引擎线程都可能发布 `voice.stt.stopped.v1`。
- UI/订阅插件可能收到重复停止事件，导致状态机重复收尾或日志噪声。

修改方案：

- 由引擎统一发布真实会话结束事件。
- `VoiceSttTools.Stop` 只负责停止和返回状态，不再主动发布 stopped。
- `SttEngine.Stop` 只停止真实会话；无活跃会话时不再伪造 stopped，避免无会话重复收尾。

### 3. TTS Stop / Finish 的 completed 重复与语义混淆

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Tts.Melo/Tools/VoiceTtsTools.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Tts.Melo/Engine/TtsMeloEngine.cs`

现状：

- 历史实现中 `VoiceTtsTools.Stop` 调用 `_engine.StopStreaming()` 后立即 `PublishCompletedAsync`，引擎取消路径也可能发布 completed。
- `VoiceTtsTools.Finish` 的语义容易和播放完成混淆。
- 若 TTS 引擎和工具层同时发布 completed，订阅方会收到重复收尾。

问题：

- `Finish` 语义是"输入流结束"（不再追加文本），不是"播放结束"。skeleton 模式下提前发 completed 会让订阅者误判播放完成。
- `Stop` 模式下工具层与引擎并发发 completed，订阅方收到双发或乱序。

修改方案：

- 真实播放完成由引擎统一发布 `voice.tts.completed.v1`，工具层 stop 只请求停止和清空状态。
- `voice_tts_stop` 作为用户主动停止动作，由后台取消路径按播放代次发布一次 `completed(reason=stopped)`；非用户主动取消发布 `completed(reason=cancelled)`。
- 播放失败或合成无可播放音频时发布 `voice.tts.error.v1`，并以 `completed(reason=error)` 完成状态收尾，不再伪造自然完成。
- `Finish` 在所有分支都不发 completed，只更新状态并返回结果；如果产品需要"输入流结束"信号，单独走 `voice.tts.input_finished.v1` 这类新 op，不要复用 completed。
- skeleton 模式（无模型）下不要走 started → subtitle → completed 的伪生命周期；详见下文 §三.7。

### 4. KWS/STT 后台线程 fire-and-forget 与空 catch 吞噬异常

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Kws.Sherpa/Engine/KwsEngine.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Stt.Sherpa/Engine/SttEngine.cs`

现状：

- KWS 使用 `_ = pluginBus.PublishDetectedAsync(...)`。
- STT 使用 `_ = pluginBus.PublishPartialAsync(...)`、`_ = pluginBus.PublishFinalAsync(...)`、`_ = pluginBus.PublishStoppedAsync(...)`。
- KWS Stop / Dispose 路径多处 `try { ... } catch { /* ignore */ }`（如 `KwsEngine.Stop` 的 cts cancel、StopUnsafe 的 thread.Join）。

问题：

- `PluginBusClient.PublishEventAsync` 内部会捕获并记录发送失败，但序列化、`ObjectDisposedException`、调用前异常仍可能变成未观测任务异常。
- 后台线程无法等待异步发布，当前代码也没有统一的 fire-and-forget 错误处理。
- 空 catch 把音频设备拔出、ONNX 崩溃等真实故障静默吞掉，运行期问题只能从应用日志推测。

修改方案：

- 在 `KwsPluginBusClient` / `SttPluginBusClient` / `TtsPluginBusClient` 类型化包装层用 try-catch 包住整次 publish 并记录 `LogWarning`。
- 后台线程改为 `await PublishSafelyAsync(...)` 或 `_ = bus.PublishSafelyAsync(...)`；前者要求 RunLoop 异步化，后者保持现有同步线程模型，二选一。
- 不直接 `.Wait()` / `.Result`，避免阻塞和死锁。
- KWS Stop / Dispose 路径的空 catch 改为 `LogWarning` 记录，仅在确实可忽略的极端情况（例如 `cts.Cancel()` 抛 `ObjectDisposedException`）保留并附注释说明。

### 5. STT 状态没有同步真实识别结果

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Stt.Sherpa/Runtime/SttRuntimeState.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Stt.Sherpa/Engine/SttEngine.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Stt.Sherpa/PluginBus/SttPluginBusClient.cs`

现状：

- `SttRuntimeState.SetPartial` / `SetFinal` 只在调试工具 `EmitPartial` / `EmitFinal` 中调用。
- 真实识别链路直接由 `SttEngine` 调用 `pluginBus.PublishPartialAsync` / `PublishFinalAsync`，没有更新 runtime state。
- `voice_stt_status` 因此不能反映真实识别链路的 `lastPartialText` / `lastFinalText`。

问题：

- 调试工具与真实引擎表现不一致。
- `SttEngine` 直接注入 `SttRuntimeState` 会形成循环依赖（state 已构造时持有 engine 引用）。

修改方案：

- 为避免 `SttRuntimeState -> SttEngine -> SttPluginBusClient -> SttRuntimeState` 循环依赖，包装层通过 `IServiceProvider.GetService<SttRuntimeState>()` 延迟取得状态对象。
- `PublishPartialAsync` / `PublishFinalAsync` / `PublishStoppedAsync` 内部先更新状态，再走原 `bus.PublishEventAsync`。
- 调试工具与真实链路共用同一条状态写入路径。

### 6. KWS 状态没有同步真实唤醒时间

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Kws.Sherpa/Runtime/KwsRuntimeState.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Kws.Sherpa/Engine/KwsEngine.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Kws.Sherpa/PluginBus/KwsPluginBusClient.cs`

现状：

- `KwsRuntimeState.MarkDetected` 只在调试工具 `EmitDetected` 中调用。
- `KwsEngine.RunLoop` 检测到关键词后直接 `_ = pluginBus.PublishDetectedAsync(...)`，没更新 `_lastDetectedAt`。

问题：

- `voice_kws_status.LastDetectedAt` 不能反映真实唤醒。

修改方案：

- 与 §三.5 同构：`KwsPluginBusClient` 通过 `IServiceProvider.GetService<KwsRuntimeState>()` 延迟取得状态对象，`PublishDetectedAsync` 内部先 `state.MarkDetected()`，再发事件。

### 7. TTS 无模型时仍发布完整生命周期，且 greeting_ready 误发

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Tts.Melo/Tools/VoiceTtsTools.cs`

现状：

- `Speak` / `Enqueue` / `GreetingPlay` 在 `ModelFilesReady == false` 时仍发布 started/subtitle/completed，并返回 Success。
- `GreetingRegen` 无论模型是否就绪都会调用 `PublishGreetingReadyAsync`。

问题：

- 骨架兼容行为与"提供 TTS 能力"的插件描述冲突，订阅者会误以为真实音频已播放。
- `voice.tts.greeting_ready.v1` 在指南 §6.7 被定义为 TTS 模型就绪自检信号；模型未就绪时仍发该事件，破坏自检语义。

修改方案：

- 模型缺失时改为返回 `model_not_ready` 失败结果，不再发 started/subtitle/completed。
- 必要时发布 `voice.tts.error.v1`（payload 带 `reason = "model_not_ready"`）让订阅方有可观测信号。
- `GreetingRegen` 仅在 `ModelFilesReady && 缓存生成成功` 时才发 greeting_ready；模型未就绪发 error（`reason = "model_not_ready"`），并保留欢迎语文本但不标记 `GreetingReady`。
- 如果确实需要保留无模型自测路径，改用工具结果中的显式标记（例如 `mode = "skeleton_only"`），不再走真实事件发布；并在文档中标注降级用途。

### 8. KWS/STT 模型目录解析未使用 PluginSettings

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Kws.Sherpa/Runtime/KwsRuntimeState.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Stt.Sherpa/Runtime/SttRuntimeState.cs`

现状：

- KWS/STT 默认通过 `AppContext.BaseDirectory` 解析 `models/KWS`、`models/STT`。
- TTS 已注入 `PluginSettings`，优先使用 `settings.PluginDirectory`。

问题：

- 新指南明确语音插件运行时读取 `PluginSettings`，其中包含 `PluginDirectory`。
- Process 插件运行环境中，`AppContext.BaseDirectory` 与插件安装目录通常一致，但不是框架契约；后续宿主改变启动方式、单文件发布或调试器工作目录变化时，KWS/STT 可能找错模型目录。

修改方案：

- 为 `KwsRuntimeState` 和 `SttRuntimeState` 注入 `PluginSettings`。
- 保存 `_pluginDirectory = string.IsNullOrWhiteSpace(settings.PluginDirectory) ? AppContext.BaseDirectory : settings.PluginDirectory`。
- 将 `ResolvePluginPath` 改为实例方法，使用 `_pluginDirectory` 解析相对模型目录；保留绝对路径直通逻辑。

### 9. KWS 监听循环不响应取消信号

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Kws.Sherpa/Engine/KwsEngine.cs`

现状：

- `KwsEngine.RunLoop` 用 `Thread.Sleep(50)` 等待下一轮解码，不感知 `cancellationToken`。
- `SttEngine.RunLoop` 用 `cancelHandle.WaitOne(100)`，能立即响应取消。

问题：

- KWS Stop 时最差需要 50ms 才能感知，与 STT 行为不一致。
- 在并发停止/重启场景下增加竞争窗口。

修改方案：

- 把 `Thread.Sleep(50)` 改为 `cancellationToken.WaitHandle.WaitOne(50)`，与 STT 对齐。

### 10. TTS configure 的 speed 可选语义和类型不一致

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Tts.Melo/Tools/VoiceTtsTools.cs`

现状：

- `speed` 参数标注 `[Parameter(... Required = false)]`。
- 方法签名是 `float speed`，不可空。
- 逻辑通过 `speed > 0 ? speed : null` 判断是否保持当前值。

问题：

- 工具协议把参数标记为可选，但类型不可空；调用侧省略参数时反序列化层会给默认值 `0`，与"用户明确传 0"无法区分。
- 文档语义是"为空或小于等于 0 时保持当前值"，代码只能表达"0 或负数保持"。

修改方案：

- 将签名改为 `float? speed`。
- 传入 `_state.Configure(speed, voice, modelDirectory)`，工具层先校验 `speed` 在 `0.25..4` 范围内；省略时保持当前值。
- 同步修复 Process Generator 对可空值类型参数的生成逻辑，确保省略或 JSON null 不会被解析为 `0`。

### 11. TTS completed / error 事件缺少结构化 reason

位置：

- `Plugins/Src/Cortana.Plugins.Voice.Tts.Melo/PluginBus/TtsPluginBusEvent.cs`
- `Plugins/Src/Cortana.Plugins.Voice.Tts.Melo/Tools/VoiceTtsTools.cs`

现状：

- `voice.tts.completed.v1` payload 仅 `text` + `sessionId`。
- `voice.tts.error.v1` payload 仅 `text`（错误消息）+ `sessionId`。

问题：

- 订阅者无法区分播放自然完成、用户停止、错误后收尾。
- 错误事件无法区分 `model_not_ready` / `greeting_not_ready` / `synthesis_failed` / `synthesis_empty` / `playback_failed`。
- UI 收尾、日志归档、桌宠动作和未来插件联动都缺少精确语义。

修改方案：

- v1 兼容方式：在两个 payload 中追加可选字段 `reason`：
  - completed：`completed` / `stopped` / `cancelled` / `error`
  - error：`model_not_ready` / `greeting_not_ready` / `synthesis_failed` / `synthesis_empty` / `playback_failed`
- 因为新增可选字段向后兼容，不需要升到 v2；订阅方未读取 reason 时行为不变。
- `TtsPluginBusEventPayload` 与 `PluginJsonContext` 同步更新。

### 12. KWS/STT/TTS 配置参数缺少范围校验

位置：

- `VoiceKwsTools.Configure`
- `VoiceSttTools.Configure`
- `VoiceTtsTools.Configure`

现状：

- KWS 阈值、奖励分、尾部空白帧、STT 超时、线程数等参数直接接收。

问题：

- 负数、0、极大值可能导致 sherpa-onnx / Melo 初始化或运行异常。
- 错误以底层异常暴露给工具调用方，不利于插件协议稳定。

修改方案：

- 在工具层做输入校验并返回结构化失败结果（`code = "invalid_argument"`）。
- 建议范围：
  - KWS threshold：`0 < value <= 1`
  - KWS score：`value > 0`
  - KWS blanks：`value >= 0`
  - STT silence/timeout：`value > 0`
  - STT num_threads：`1 <= value <= Environment.ProcessorCount`
  - TTS speed：`0.25 <= value <= 4`
