# 软件插件模式对比传统 MCP 的优势

> 更新时间：2026-06-20  
> 参考范围：`Docs/三方对接文档/插件开发指南/`、仓库 `README.md`、`Plugins/docs/参考文档/plugin-mcp.md`

## 一、结论

当前软件的插件模式不是为了替代 MCP，而是把 MCP 擅长的“外部工具服务接入”之外的能力补齐成“可安装、可治理、可调试、可联动的软件能力包”。

一句话概括：

> MCP 更像一条标准工具连接协议；当前软件的 Native / Process 插件模式更像完整的软件扩展机制。

传统 MCP 的核心价值是让宿主作为 MCP Client 连接外部 MCP Server，通过 `stdio`、`sse` 或 `streamable-http` 自动发现远程工具并调用。这非常适合接入已有生态、远程服务和跨语言工具。

当前软件插件模式在此基础上更进一步：插件不仅能暴露工具，还能声明能力、声明所需宿主权限、生成设置界面 schema、携带本地模型和资源、接入 PluginBus 事件总线、调用宿主授权模型、运行后台服务，并通过统一发布目录或 zip 包安装更新。

因此，两者的最佳定位是：

| 类型 | 最适合解决的问题 |
| --- | --- |
| MCP | 连接已有外部工具服务、远程系统、社区 MCP Server、跨客户端共享工具能力 |
| Native / Process 插件 | 把能力作为本软件的一部分分发、安装、治理、调试、事件联动和深度集成 |

## 二、当前软件插件模式是什么

当前软件支持三条扩展路线：

| 通道 | 形态 | 适用场景 | 宿主加载方式 |
| --- | --- | --- | --- |
| Native | AOT `.dll` | 本地轻量能力、高性能本地工具、严格部署体积 | 宿主加载原生库，调用 Generator 导出的入口 |
| Process | `.exe` 子进程 | 需要进程隔离、完整 .NET JIT 生态、模型、外部 SDK、长任务服务 | 宿主启动子进程，通过 stdin/stdout 单行 JSON 协议调用 |
| MCP | 外部 MCP Server 连接配置 | 已有 MCP Server、远程服务、跨语言工具生态 | 宿主按配置连接，不生成 `plugin.json`，不走 zip 插件安装 |

本文重点比较的是当前软件的 Native / Process 插件模式与传统 MCP 工具接入模式的差异。

Native / Process 插件通过 Attribute 声明：

- `[Plugin]`：插件 ID、名称、版本、说明、标签、能力。
- `[Tool]` / `[Parameter]`：工具、参数和说明。
- `[RequiredHostCapability]`：插件希望宿主提供的能力，例如宿主 LLM 调用。
- `[PluginSetting]`：插件设置项和敏感配置 schema。
- `[PublishesEvent]` / `[SubscribesEvent]`：PluginBus 事件发布和订阅契约。

Generator 会自动生成：

- `plugin.json`。
- 工具路由。
- Process 插件入口。
- 强类型 Debugger。
- 设置 schema、能力声明、事件契约声明。

这意味着插件开发者主要写业务代码和声明元数据，不需要手写宿主协议、工具路由或清单文件。

## 三、传统 MCP 模式是什么

本文中的传统 MCP 指常见的 MCP Server 接入方式：

1. 外部工具以 MCP Server 运行。
2. 宿主配置 `Command` / `Arguments` / `Url` / 环境变量 / 认证信息。
3. 宿主通过 `stdio`、`sse` 或 `streamable-http` 连接。
4. 连接成功后调用 `ListToolsAsync()` 获取工具列表。
5. AI Agent 把远程工具纳入可调用工具链。

这种模式的优点很明确：

- 可直接接入社区 MCP Server。
- 不要求工具服务用 C# 编写。
- 适合远程部署和多客户端复用。
- 宿主只要知道连接方式，不需要参与工具服务内部实现。

但传统 MCP 通常只解决“工具如何被发现和调用”的问题，不负责一个能力在当前软件中的完整生命周期，例如插件安装包、版本、设置界面、宿主能力授权、事件联动、插件数据目录、后台服务生命周期、发布自测和本地资源管理。

## 四、核心对比

| 维度 | 当前软件 Native / Process 插件 | 传统 MCP |
| --- | --- | --- |
| 定位 | 软件扩展包，面向本软件深度集成 | 外部工具服务连接协议 |
| 分发方式 | 发布目录或 zip 插件包，可携带 `plugin.json`、可执行文件、模型、模板、依赖 | 配置命令、参数、URL、环境变量或远程地址 |
| 元数据 | `plugin.json` 统一描述插件、工具、能力、设置、事件、最低宿主版本 | 连接后由 MCP Server 返回工具列表；安装包和宿主治理信息不属于核心接入链路 |
| 开发体验 | Attribute 声明 + Generator 生成入口、路由、清单、调试器 | MCP Server 自行实现协议和工具定义，宿主按标准发现 |
| 配置体验 | `[PluginSetting]` 生成设置 schema，支持 Secret、Path、Enum、Json 等类型 | 通常依赖命令参数、环境变量、远程服务配置或宿主自定义配置表单 |
| 权限治理 | `[RequiredHostCapability]` 明确申请宿主能力，写明 purpose、required、reason | 常见做法是 MCP Server 自行持有 token、路径、远程凭据，宿主只能管理连接配置 |
| 运行上下文 | 宿主注入 `DataDirectory`、`WorkspaceDirectory`、`PluginDirectory`、`PluginBusEndpoint` 等 | MCP Server 通常只知道自身启动参数、环境变量和协议请求上下文 |
| 事件协作 | PluginBus 支持插件间发布/订阅事件，并可桥接 UI / EventHub | 当前软件的 MCP 通道不参与 PluginBus 事件总线 |
| 后台服务 | Process 插件支持 `IHostedService` / `IHostedLifecycleService` 生命周期 | MCP Server 可以常驻，但宿主通常只把它视为外部工具服务 |
| 本地资源 | 插件包可携带模型、模板、原生运行时和数据目录约定 | MCP Server 可以自行管理资源，但不属于宿主插件包标准 |
| 调试验证 | 生成 Debugger、`--self-test`、Native Debug Console、发布前最小工具验证 | 主要验证连接可达和工具可发现，具体自测由 MCP Server 自行设计 |
| 模型调用 | 插件可申请 `host.llm.invoke.v1`，通过宿主授权模型调用，不直接持有模型密钥 | MCP Server 通常需要自己接模型或通过自定义方式接收凭据 |
| 安装更新 | 可按插件包卸载、覆盖安装、重载 | 可启停连接，但服务安装、依赖下载、版本更新通常在 MCP Server 侧 |
| 典型优势 | 产品化、本地化、治理、事件联动、深度宿主能力 | 标准生态、远程服务、跨语言、跨客户端 |

## 五、插件模式的主要优势

### 1. 从“工具连接”升级为“软件能力包”

MCP 的主要抽象是 Server 暴露工具，宿主连接后使用工具。当前软件插件模式的抽象更大：插件是一个带元数据、运行时、资源、设置、能力声明和生命周期的能力包。

一个插件发布目录可以包含：

```text
plugin.json
Your.Plugin.exe
Your.Plugin.dll
Your.Plugin.deps.json
models/
templates/
```

这对语音识别、TTS、Office、本地脚本、SSH、宝塔运维、记忆引擎这类能力很重要。它们不是简单的远程 API 调用，而是需要携带模型、模板、依赖、运行目录、日志和状态的完整本地功能。

### 2. 宿主能在启动前理解插件

Native / Process 插件会生成 `plugin.json`，其中包含：

- 插件唯一 ID、名称、版本、说明。
- `providedCapabilities`：插件提供的能力。
- `requiredHostCapabilities`：插件申请的宿主能力。
- `settingsSchema`：插件需要的设置项。
- `publishedOps` / `subscribedOps`：插件发布和订阅的事件契约。
- `runtime`、`command` 或 `libraryName`。
- `minHostVersion`。

这让宿主不必等工具调用失败后才知道插件需要什么。宿主可以提前展示配置、做能力筛选、检查最低版本、做弱声明校验，并在用户授权前解释插件为什么需要某项能力。

传统 MCP 也能在连接后列出工具，但“插件包级别”的安装治理、设置 schema、事件契约、宿主能力申请通常不属于 MCP Server 连接协议本身。

### 3. Generator 降低协议和工具声明错误

当前插件开发不要求开发者手写宿主协议、工具路由或 `plugin.json`。开发者使用 Attribute 声明，Generator 自动完成：

- Process 消息循环入口。
- 工具路由字典。
- 工具名生成和冲突检测。
- `plugin.json` 生成。
- 强类型调试辅助代码。
- 诊断错误输出。

这带来两个实际收益：

1. 常见错误能在编译期暴露，例如工具方法不是 public、参数类型不支持、工具名冲突、插件 ID 格式不合法、返回自定义类型但缺少 `JsonSerializerContext`。
2. 插件代码和宿主协议保持一致，减少“文档写一套、清单写一套、运行时又是一套”的漂移。

传统 MCP 的优势是通用标准，但具体 Server 的工具 schema、调试入口、打包方式、配置方式和自测机制通常由每个 Server 自己维护。

### 4. 设置项可以产品化展示

插件可以通过 `[PluginSetting]` 声明配置项：

- `String`
- `Secret`
- `Number`
- `Boolean`
- `Enum`
- `Path`
- `Json`

同时还能声明是否必填、是否敏感、校验规则、作用域、是否需要重启。宿主可以基于 `settingsSchema` 自动生成设置界面，并用统一方式处理敏感值。

传统 MCP 常见配置方式是命令行参数、环境变量、URL、API Key。它足够灵活，但对终端用户不一定友好：用户需要知道如何拼接命令、如何传环境变量、哪个 token 对应哪个 Server。当前插件模式更适合面向普通用户和应用商店分发。

### 5. 宿主能力申请更明确

当前插件模式把“插件提供什么”和“插件需要宿主提供什么”分开：

- `[Plugin].Capabilities`：插件提供给宿主或模型层的能力。
- `[RequiredHostCapability]`：插件申请宿主能力。

例如插件需要调用宿主授权的大模型，可以申请：

```csharp
[RequiredHostCapability(
    Id = "host.llm.invoke.v1",
    Purpose = "summary.generate",
    Required = true,
    Reason = "需要调用宿主授权的大模型生成摘要。")]
```

运行时插件通过 PluginBus 的 `model.capability.request` 调用宿主模型。这样模型密钥、模型选择、审计和授权留在宿主侧，插件不直接读取模型供应商密钥。

对用户来说，这比把模型 API Key 分散写进多个 MCP Server 环境变量更容易治理。

### 6. PluginBus 让插件能协作，而不只是被调用

当前插件模式支持 PluginBus 事件总线。插件可以声明自己发布或订阅哪些事件：

```csharp
[PublishesEvent("voice.stt.partial.v1", Description = "实时识别中文本")]
[SubscribesEvent("voice.tts.subtitle.v1", Reason = "显示 TTS 字幕")]
```

这解决的是 MCP 工具调用以外的问题：插件之间、插件和宿主 UI 之间需要状态通知。

典型场景：

- KWS 插件检测到唤醒词，发布 `voice.kws.detected.v1`。
- STT 插件发布 `voice.stt.partial.v1` 和 `voice.stt.final.v1`。
- TTS 插件发布字幕、播放开始、播放完成和错误事件。
- 宿主把语音事件桥接到 UI 状态、字幕、桌宠或其他插件。
- 记忆、工作流、会议等模块可以通过统一 topic 形成后续扩展。

传统 MCP 的强项是工具调用。工具调用是“请求-响应”；PluginBus 事件是“一对多、单向、不等响应”。这两类能力服务的场景不同。当前软件插件模式同时支持工具和事件，因此更适合需要实时状态联动的本地插件。

### 7. 更适合长任务和后台服务

Process 插件可以在 DI 中注册服务，并支持 `IHostedService` / `IHostedLifecycleService`。宿主在 `init` 后启动后台服务，在 `destroy` 或进程退出时停止。

这适合：

- 语音唤醒常驻监听。
- STT / TTS 引擎预热。
- 长期记忆索引维护。
- 文件变更监听。
- 定时提醒。
- 本地窗口状态监听。

MCP Server 当然也可以常驻运行，但传统 MCP 视角下，宿主主要管理“连接是否可用”和“工具是否可发现”。当前插件模式把后台服务纳入插件生命周期，便于统一停止、重载、日志和运行上下文注入。

### 8. 本地优先和离线可控

当前软件面向本地优先使用场景。Native / Process 插件包可以把模型、模板、原生依赖和工具程序一起发布。安装后只要本地环境满足运行时要求，就不需要每次通过 `npx`、`uvx` 或远程 HTTP 服务拉起外部生态。

这对以下场景更稳：

- 语音模型文件很大，需要和插件版本绑定。
- 企业或个人用户希望离线运行。
- 工具依赖原生库或固定版本 SDK。
- 不希望首次运行时联网下载包。
- 希望发布包经过测试后再分发。

MCP 在远程服务和社区生态上更灵活，但如果目标是“一个用户安装后就能稳定使用的软件功能”，插件包方式更容易控制版本和依赖。

### 9. 隔离和崩溃影响更可控

当前软件插件模式有两类隔离策略：

- Native：适合 AOT、本地轻量和高性能能力，配合宿主加载机制和发布验证。
- Process：独立子进程承载，通过 stdin/stdout 单行 JSON 协议通信。插件崩溃不会直接把主程序业务对象带崩，宿主可以销毁和重载进程。

对于语音、脚本、Office、SSH、外部 SDK 这类容易引入复杂依赖的能力，Process 插件可以把运行时依赖和崩溃边界隔离在插件进程内。

MCP 的 stdio 模式同样有进程隔离，HTTP 模式也有网络隔离。但 MCP 侧隔离的是外部 Server；当前插件模式额外把插件安装目录、数据目录、设置 schema、宿主能力和事件契约纳入同一治理模型。

### 10. 调试、测试和发布门禁更贴近插件开发

当前插件开发指南要求发布前进行本地调试：

- Native：Debug Console 能发现插件，每个工具至少调用一次。
- Process：`dotnet run -- --self-test`，先 `InitAsync()`，每个 `[Tool]` 至少调用一次。
- Process Generator 生成 `{PluginClass}Debugger`，便于强类型调用工具。
- 发布前检查 `plugin.json`、`.exe`、`.dll`、`.deps.json`、`models/`、`templates/`。

这些约束让插件开发者能在进入宿主前先发现问题。传统 MCP 通常能做连接测试和工具发现，但每个 Server 的自测深度、日志路径、版本校验和发布门禁并不统一。

### 11. 更适合应用商店和资源中心

当前软件资源中心可以把资源安装到用户数据目录下的 `plugins`、`skills`、`agents`、`solutions` 等目录。插件包天然适合成为应用商店资源：

- 有插件 ID。
- 有版本号。
- 有说明和标签。
- 有最低宿主版本。
- 有设置 schema。
- 有能力声明。
- 有事件契约。
- 有固定发布目录结构。

MCP Server 更适合“配置一个外部服务”。如果要把一个能力做成可审核、可安装、可更新、可展示的商品或资源，插件模式的元数据和包结构更完整。

## 六、从用户角度看优势

对普通用户来说，插件模式的优势是少做环境配置：

| 用户动作 | 插件模式 | 传统 MCP |
| --- | --- | --- |
| 安装 | 安装插件包或从资源中心安装 | 找到 MCP Server，安装 Node/Python/uv/npx 依赖，配置命令或 URL |
| 配置 | 宿主按 `settingsSchema` 展示表单 | 配命令、参数、环境变量、URL、Token |
| 授权 | 宿主展示插件申请的能力和原因 | 通常通过环境变量或 Server 文档表达 |
| 使用 | 插件工具、能力、事件进入宿主体系 | 工具进入 Agent 工具链 |
| 排错 | 看插件日志、自测、清单、宿主插件状态 | 看 MCP Server 日志、连接状态、工具发现结果 |
| 更新 | 卸载/覆盖安装/重载插件 | 更新外部 Server 包或服务部署 |

如果目标用户不是开发者，插件模式更容易做成“安装即用”的体验。

## 七、从开发者角度看优势

对插件开发者来说，当前插件模式减少了重复基础设施工作：

1. 不用手写 `plugin.json`。
2. 不用手写工具路由。
3. 不用手写 Process 宿主消息循环。
4. 不用自己设计设置 schema 格式。
5. 不用自己定义宿主模型密钥传递方式。
6. 不用把事件订阅契约写在外部文档里再手工同步。
7. 可以通过生成的 Debugger 做本地自测。
8. 可以通过 `PluginSettings` 拿到标准运行上下文。

开发者更专注于业务能力本身：

- 语音引擎怎么初始化。
- Office 文档怎么读写。
- 远程服务器怎么执行命令。
- 记忆索引怎么建立。
- 工作流事件怎么消费。

## 八、从架构角度看优势

当前软件插件模式把扩展能力拆成三个层次：

1. **工具层**：AI Agent 能调用的函数。
2. **能力层**：插件向宿主声明自己提供什么、需要什么。
3. **事件层**：插件、宿主 UI、工作流、会议、记忆等模块之间的状态广播。

传统 MCP 主要覆盖工具层，部分 MCP Server 也会提供资源、提示词等能力，但它们作为外部服务接入时，仍然和当前软件的插件安装、设置、宿主能力、事件总线、应用商店资源体系存在边界。

当前插件模式的优势就在于它把这些边界收进了同一个宿主治理模型。

## 九、MCP 仍然更适合的场景

插件模式有优势，但不意味着所有扩展都应该做成插件。下面场景仍然优先考虑 MCP：

1. 已经有成熟的社区 MCP Server，例如 GitHub、数据库、浏览器自动化、搜索、文件系统等。
2. 能力部署在远程服务器上，需要多个客户端共用。
3. 工具由 Python、Node.js、Go 等语言生态维护，且不需要深度接入当前软件的 PluginBus、设置 schema 或宿主能力。
4. 团队希望按 MCP 标准对外提供服务，让其他 MCP Client 也能使用。
5. 只是快速接入一个外部 API，不需要安装包、模型文件、后台服务或事件联动。

换句话说：

- 要接入开放生态，用 MCP。
- 要做成本软件的一等扩展能力，用 Native / Process 插件。

## 十、推荐选型

| 需求 | 推荐方式 | 理由 |
| --- | --- | --- |
| 接入已有 MCP Server | MCP | 最省成本，直接配置连接 |
| 接入远程工具服务 | MCP | HTTP / SSE / streamable-http 更自然 |
| 本地高性能能力 | Native 插件 | AOT、启动快、部署体积可控 |
| 复杂本地 SDK / JIT / 反射 / 动态编译 | Process 插件 | 完整 .NET 运行时和进程隔离 |
| 语音 KWS / STT / TTS | Process 插件 | 模型目录、后台服务、PluginBus 实时事件更合适 |
| 需要宿主模型能力但不想暴露模型密钥 | Native / Process 插件 | 通过 `host.llm.invoke.v1` 申请宿主模型调用 |
| 需要插件间事件协作 | Native / Process 插件 | 支持 `[PublishesEvent]` / `[SubscribesEvent]` 和 PluginBus |
| 面向应用商店分发 | Native / Process 插件 | 有插件包、版本、设置、能力声明和安装更新路径 |
| 多个 AI 工具客户端共用同一能力 | MCP | MCP Server 可被多个 MCP Client 复用 |

## 十一、当前软件的组合策略

当前软件最合理的策略不是“插件模式 vs MCP 二选一”，而是组合使用：

1. **Native / Process 插件负责本软件的一等能力**
   - 语音三件套。
   - 记忆引擎。
   - Office 文档工具。
   - 本地脚本运行。
   - 应用启动和窗口管理。
   - 需要 PluginBus 联动的能力。

2. **MCP 负责外部生态接入**
   - GitHub、数据库、浏览器、搜索等已有 Server。
   - 远程运维平台。
   - 跨语言团队维护的工具服务。
   - 希望同时服务其他 MCP Client 的能力。

3. **宿主统一装配给智能体**
   - 智能体可以同时绑定插件工具和 MCP 工具。
   - 插件负责深度集成。
   - MCP 负责开放生态。

这种组合能保留 MCP 标准生态的灵活性，又能让当前软件拥有可控的本地插件产品化能力。

## 十二、总结

当前软件插件模式相对传统 MCP 的优势集中在八个方面：

1. **产品化**：插件是完整安装包，不只是连接配置。
2. **可治理**：`plugin.json` 声明能力、设置、事件、宿主权限和版本。
3. **开发效率**：Generator 自动生成清单、入口、路由和调试器。
4. **用户体验**：设置 schema 可生成界面，减少命令行和环境变量配置。
5. **安全边界**：宿主能力申请、敏感设置和模型调用统一由宿主管理。
6. **事件协作**：PluginBus 支持插件间和宿主 UI 的实时联动。
7. **本地可控**：模型、模板、依赖和数据目录可随插件包管理。
8. **生命周期完整**：安装、更新、卸载、自测、后台服务和销毁都有明确路径。

MCP 仍然是接入外部工具生态的关键通道；插件模式则是把关键能力沉淀成本软件扩展体系的关键通道。两者一起使用，才能同时获得开放生态和本地深度集成。
