# 00. 方案总览

## 重写原因

前一版方案重点写了 LayUI table、抽屉和筛选接口，但没有把后台外壳、菜单功能面、页面操作链路和当前项目已有业务能力完整纳入方案。执行结果容易变成“表格换成 LayUI 了”，但用户进入后台后仍感觉和旧版差不多。

本方案从当前 `Netor.Cortana.Platform.Admin` 代码、控制器、视图和数据库实体重新出发，重新定义 Madorin 后台 LayUI 界面体系。

## 改造目标

1. 后台首屏呈现 Madorin 资源市场运营工作台，而不是通用管理模板。
2. 菜单按业务场景组织：待办、用户钱包、资源市场、订单权益、创作者收益、系统运维。
3. 所有新增、修改、查看统一从右侧抽屉完成。
4. 关联明细统一从底部抽屉打开，例如用户交易记录、创作者资源、创作者结算、订阅下载、订单流水。
5. 主列表全部使用 LayUI `table.render()` 对接 JSON 数据。
6. 筛选项必须来自当前数据库字段和关联关系，不能只做关键词和状态。
7. 操作能力不能弱化，发布、下架、审核、充值、改密、结算、批量处理等必须保留。
8. 所有界面、表单、控件用 Razor `.cshtml` 编写，并使用 LayUI 标准 class。
9. 暂不使用 `Netor.Operates.LayuiHelpers`。

## 本轮执行原则

1. 先写清楚方案和执行计划，再按计划推进代码。
2. 每个阶段必须包含验收点，不能只记录“已修改文件”。
3. 能落到现有控制器的入口必须做成真实链接、真实筛选或真实抽屉。
4. 当前项目没有后端能力的入口，只能写入后续计划，不能在菜单里伪造。
5. 每轮提交只包含本轮方案或 Admin UI 相关文件，不混入数据库连接串和 provider 配置改动。
