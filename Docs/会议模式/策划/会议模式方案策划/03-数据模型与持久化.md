# 03 - 数据模型与持久化

> 会议模式的数据库表结构、WS 分发协议、附件存储
>
> **核心原则**：AOT 安全、轻量持久化、与 ChatSession 弱关联（会议是封闭事件）

---

## 一、设计原则

### 1.1 状态归属

| 状态 | 谁拥有 | 怎么读 |
|------|--------|--------|
| Workflow 运行时状态（GroupChat history） | AF 框架（in-process，不做 Checkpoint） | 不需要——会议关闭即散会，无需恢复 |
| 会议元数据（Topic / RunId / Status / PendingRequest） | Cortana（`MeetingSessions`） | `SELECT FROM MeetingSessions WHERE Id = ?` |
| 会议消息（每条发言） | Cortana（`MeetingMessages`） | UI 重建 + WS 分发 |
| 用户插话 | Cortana（`MeetingPendingInputs`） | `MeetingHostManager.UpdateHistoryAsync` 消费 |
| 会议附件 | Cortana（`MeetingAttachments`） | 智能体打开文件时通过工具读取 |
| 会议结束总结 | 写一条 assistant 消息到 `ChatMessages` | 对话模式可见 |

### 1.2 与 ChatSession 的关系（弱关联）

- `MeetingSessions.SessionId` 关联到 `ChatSessions`，仅用于"打开历史会议"的入口
- **会议不写 `ChatMessages` 中间过程**，只在结束时写一条总结消息（含 meetingId + 主题 + 参会者 + 总结正文）
- 与工作模式"永续对话"语义不同：会议是封闭事件，**关闭即散会，不可恢复**

### 1.3 AOT 安全

- 所有 JSON 列（ParticipantsJson / ToolCallsJson / AttachmentsJson 等）由 `MeetingJsonContext` 源生成
- 数据访问保持 Cortana 既有风格：`CortanaDbContext.Execute` + `SqliteCommand` 显式参数
- 不使用 ORM、不使用反射映射

---

## 二、数据边界

### 2.1 复用现有表

| 表 | 会议模式如何使用 |
|----|---------------|
| `ChatSessions` | `MeetingSessions.SessionId` 关联，仅做归类 |
| `ChatMessages` | 会议结束时写**一条** assistant 消息（总结） |
| `Agents` / `AiProviders` / `AiModels` | 参会者由现有 `AgentEntity` 配置驱动 |

### 2.2 新增表

| 表 | 用途 | 行数级别 |
|----|------|---------|
| `MeetingSessions` | 会议元数据 + RunId + Status + PendingRequest | 每会议 1 条 |
| `MeetingMessages` | 每条发言（含主持人/智能体/用户）—— **永远不删除，原始消息保留全量用于回放** | 每会议 N 条 |
| `MeetingPendingInputs` | 用户插话队列 | 短暂存活 |
| `MeetingAttachments` | 会议级附件 | 每会议 0~N 条 |
| `MeetingCompactionSegments` | 会议上下文压缩段（仅服务 LLM history，不影响 UI 回放） | 每会议 0~N 条 |

## 三、表结构

### 3.1 MeetingSessions

```sql
CREATE TABLE IF NOT EXISTS MeetingSessions (
    Id                  TEXT PRIMARY KEY,            -- GUID(N)
    SessionId           TEXT NOT NULL,               -- 关联 ChatSessions.Id
    WorkspaceId         TEXT NOT NULL DEFAULT '',
    Topic               TEXT NOT NULL,               -- 会议主题（用户输入）
    HostAgentId         TEXT NOT NULL DEFAULT 'system-meeting-host',
    ParticipantsJson    TEXT NOT NULL,               -- [{agentId,name,joinOrder}, ...]
    Status              INTEGER NOT NULL DEFAULT 0,  -- 0=进行中 / 1=等待用户回复 / 2=已结束 / 3=已取消(散会)
    RunId               TEXT,                        -- AF StreamingRun.RunId
    PendingRequestId    TEXT,                        -- HITL 挂起的 RequestId（征询时非空）
    PendingRequestKind  TEXT,                        -- 'ask_user'（v1.0 仅此一种）
    PendingRequestData  TEXT,                        -- HitlPendingRequestSnapshot JSON
    FinalSummaryMd      TEXT,                        -- 最终总结（用户确认后写入）
    Provider            TEXT NOT NULL DEFAULT '',    -- 主持人 Agent 用的 provider(会议建立时锁定,中途不可变)
    Model               TEXT NOT NULL DEFAULT '',    -- 主持人 Agent 用的 model(会议建立时锁定,中途不可变)
    CreatedAt           INTEGER NOT NULL,
    UpdatedAt           INTEGER NOT NULL,
    EndedAt             INTEGER,                     -- 结束/取消时间
    FOREIGN KEY (SessionId) REFERENCES ChatSessions(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_meeting_session ON MeetingSessions(SessionId);
CREATE INDEX IF NOT EXISTS idx_meeting_status ON MeetingSessions(Status, UpdatedAt DESC);

-- 修复缺陷 11：同 SessionId 下最多只能有一条活跃会议（Status IN (0,1)）
-- 利用 SQLite 部分唯一索引 + WHERE 子句
CREATE UNIQUE INDEX IF NOT EXISTS idx_meeting_active_unique
    ON MeetingSessions(SessionId)
    WHERE Status IN (0, 1);
```

**Status 取值约束**：

| 值 | 含义 | 何时进入 |
|----|------|---------|
| 0 | 进行中 | INSERT 时 |
| 1 | 等待用户回复 | `ask_user` 工具调用时 |
| 2 | 已结束 | 用户确认结束时 |
| 3 | 已取消(散会) | 用户主动取消 / 软件关闭时未结束 |

**ParticipantsJson 结构**：

```json
[
  { "agentId": "agt-001", "name": "财务张三", "joinOrder": 0 },
  { "agentId": "agt-002", "name": "法务李四", "joinOrder": 1 }
]
```

> 主持人不出现在此列表里——它是固化的 `system-meeting-host`。

**Provider / Model 锁定语义（修复缺陷 26）**：

`MeetingSessions.Provider` / `MeetingSessions.Model` 字段在**会议建立时一次性写入**，会议进行中**禁止修改**。即使用户在输入区切换 Model，也只影响"下次新建会议"，不影响当前进行中的会议。

理由：

- AF GroupChatHost 持有 hostAgent + participants 实例引用，中途切 model 需要重建整个 workflow，复杂度太高
- 主持人和参会者状态（`_lastSpeakerId` / `_terminationFlag` / TCS 等）不便迁移
- 会议是封闭事件，模型一致性优于灵活性
- 用户想换模型的本质是"用不同模型继续讨论"，等价于结束当前会议 + 新开会议（带主题继承）

UI 实现：会议进行中点击 Model 按钮 → 显示 toast 提示"当前会议已锁定模型，下次新建会议生效"（详见 [04 §3.5](./04-界面交互设计.md)）。

### 3.2 MeetingMessages

```sql
CREATE TABLE IF NOT EXISTS MeetingMessages (
    Id                  TEXT PRIMARY KEY,            -- GUID(N)
    MeetingId           TEXT NOT NULL,
    Sequence            INTEGER NOT NULL,            -- 单调递增
    SpeakerKind         TEXT NOT NULL,               -- 'agent' / 'host' / 'user'
    SpeakerId           TEXT NOT NULL,               -- agentId / 'system-meeting-host' / 'user'
    SpeakerName         TEXT NOT NULL,               -- 冗余存储（防 Agent 改名导致历史失真）
    ContentMd           TEXT NOT NULL DEFAULT '',    -- Markdown 正文
    ThinkingMd          TEXT,                        -- 思维链（智能体用）
    ToolCallsJson       TEXT,                        -- [{callId,name,args,result,exception,durationMs}, ...]
    AttachmentsJson     TEXT,                        -- 用户消息引用的附件 [{name,path,mime}, ...]
    MessageRole         TEXT NOT NULL DEFAULT 'normal',  -- 'normal' / 'summary' / 'inquiry'
    AwaitingUserReply   INTEGER NOT NULL DEFAULT 0,  -- 1 = 此条之后工作流挂起等用户
    IsPartial           INTEGER NOT NULL DEFAULT 0,  -- 1 = 流式中途异常,只保留了部分内容(修复缺陷 14)
    ErrorMessage        TEXT,                        -- IsPartial=1 时的错误描述,可空
    CreatedAt           INTEGER NOT NULL,
    FOREIGN KEY (MeetingId) REFERENCES MeetingSessions(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_meeting_msg ON MeetingMessages(MeetingId, Sequence);

-- 修复缺陷 10：confirm_meeting_end 工具需要快速查最近一条 summary 消息
CREATE INDEX IF NOT EXISTS idx_meeting_msg_summary
    ON MeetingMessages(MeetingId, Sequence DESC)
    WHERE MessageRole = 'summary';

-- 修复缺陷 24：保证同会议内 Sequence 唯一,防止并发写入冲突
CREATE UNIQUE INDEX IF NOT EXISTS uk_meeting_msg_sequence
    ON MeetingMessages(MeetingId, Sequence);
```

**新字段说明**：

| 字段 | 含义 | 何时写 |
|------|------|--------|
| `IsPartial` | 流式输出中途因网络断开/超时仅保留部分文本 | `MeetingStreamProcessor` 在 catch 路径调用 `AppendPartialAsync`（修复缺陷 14） |
| `ErrorMessage` | 异常类型 + 简短描述，便于排查 | 同上，由调用方传入 `ex.Message` |

**用途**（修复缺陷 14）：参会者流式发言到一半网络断开 → UI 已经看到"小李说了一半" → 落库时把累积文本写入 `IsPartial=1` 的消息 → 后续重试由主持人决定（让小李重说 / 跳过）。同一条消息**不会**被 retry 后的完整版本覆盖（保持只读历史），重试产生新的 Sequence。

**SpeakerKind / MessageRole 矩阵**：

| SpeakerKind | MessageRole | 场景 |
|-------------|-------------|------|
| `host` | `normal` | 主持人开场白、轮次衔接 |
| `host` | `summary` | 主持人输出总结（结束流程的第一步） |
| `host` | `inquiry` | 主持人调用 `ask_user` 征询（AwaitingUserReply=1） |
| `agent` | `normal` | 普通参会者发言 |
| `user` | `normal` | 用户主题（首条）/ 用户插话 / 用户对征询的回复 |

**ToolCallsJson 结构**（每条记录可对应多个工具调用）：

```json
[
  {
    "callId": "call_abc",
    "name": "file_read",
    "args": { "path": "report.xlsx" },
    "result": "...",
    "exception": null,
    "durationMs": 245
  }
]
```

### 3.3 MeetingPendingInputs

```sql
CREATE TABLE IF NOT EXISTS MeetingPendingInputs (
    Id                  INTEGER PRIMARY KEY AUTOINCREMENT,
    MeetingId           TEXT NOT NULL,
    Content             TEXT NOT NULL,
    AttachmentsJson     TEXT,                        -- 插话时也可以贴附件
    Kind                TEXT NOT NULL DEFAULT 'interrupt',  -- 'interrupt' / 'reply'
    EnqueuedAt          INTEGER NOT NULL,
    Consumed            INTEGER NOT NULL DEFAULT 0,
    ConsumedAt          INTEGER,
    FOREIGN KEY (MeetingId) REFERENCES MeetingSessions(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_meeting_pending ON MeetingPendingInputs(MeetingId, Consumed, EnqueuedAt);
```

**Kind 区分**：

- `interrupt`：用户主动插话（`MeetingHostManager.UpdateHistoryAsync` 在下一轮 `SelectNextAgent` 之前合并到 history）
- `reply`：用户对 `ask_user` 征询的回复（直接 `run.SendResponseAsync` 注入 HITL，不走队列；本字段仅用于审计）

> 实际上 `reply` 不入此队列——它走的是 AF Workflow 的 HITL 通道。这里设计 `Kind` 字段是为了未来如果要做"延迟回复"等场景留扩展位。v1.0 实际只用 `interrupt`。

### 3.5 MeetingCompactionSegments（上下文压缩段）

**这是会议模式区别于工作模式的关键设计**——会议天然容易超长（多人发言 + 长议题 + 用户多次插话补充），必须做上下文压缩。直接借鉴 [CompactionSegments](../../../Src/Netor.Cortana.Entitys/CortanaDbContext.cs#L309) 的"段落式不可变摘要"机制。

```sql
CREATE TABLE IF NOT EXISTS MeetingCompactionSegments (
    Id                      TEXT PRIMARY KEY,            -- GUID(N)
    MeetingId               TEXT NOT NULL,
    SegmentIndex            INTEGER NOT NULL,            -- 段落序号（0 起，单调递增）
    StartSequence           INTEGER NOT NULL,            -- 覆盖 MeetingMessages.Sequence 起点
    EndSequence             INTEGER NOT NULL,            -- 覆盖 MeetingMessages.Sequence 终点
    Summary                 TEXT NOT NULL,               -- LLM 生成的段落摘要
    OriginalMessageCount    INTEGER NOT NULL,            -- 原始覆盖的消息条数
    ModelName               TEXT NOT NULL DEFAULT '',    -- 生成摘要时使用的模型
    CreatedAt               INTEGER NOT NULL,
    UpdatedAt               INTEGER NOT NULL,
    FOREIGN KEY (MeetingId) REFERENCES MeetingSessions(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS idx_meeting_compact ON MeetingCompactionSegments(MeetingId, SegmentIndex);
```

**核心设计原则**（与对话模式压缩段一致）：

1. **段落不可变**：一旦生成永不修改、永不删除，避免递归信息丢失
2. **覆盖范围用 Sequence 锚定**：`MeetingMessages.Sequence` 单调递增，是天然主键
3. **MeetingMessages 永不删除**：原始消息全量保留，压缩段只是 LLM 上下文的"摘要叠加层"

## 三-bis、上下文构建（双路径）

会议模式有**两条独立的消息读取路径**：

| 路径 | 谁用 | 内容 | 为什么 |
|------|------|------|--------|
| **A. UI 回放路径** | 用户回看历史会议 | `MeetingMessages` 全量，按 Sequence 排序 | 老板要看到完整的群聊记录，包括思考/工具调用 |
| **B. LLM 上下文路径** | `MeetingHostManager.UpdateHistoryAsync` 调用 | `MeetingCompactionSegments` 摘要 + 尾部原始消息 + 用户插话队列 | 防止 token 爆炸，长会议也能继续讨论 |

### B 路径调用点（修复缺陷 3）

**关键认知**：AF GroupChatHost 维护着自己的 message buffer，每轮调用 agent 之前会先调 `GroupChatManager.UpdateHistoryAsync(buffer)` 给我们一次过滤历史的机会。但 AF 的 buffer 与我们的 `MeetingMessages` DB 是两份不同步的数据 —— **AF 完全不知道我们的压缩段存在**。

正确做法：`UpdateHistoryAsync` 完全无视 AF 传入的 `history` 参数，**直接从 DB 重建**（含压缩段 + 尾部原文），再合并用户插话队列：

```csharp
// MeetingHostManager.cs（详见 02-AF编排集成.md §2.2）
protected internal override async ValueTask<IEnumerable<ChatMessage>> UpdateHistoryAsync(
    IReadOnlyList<ChatMessage> history,    // 完全无视
    CancellationToken ct = default)
{
    var rebuilt = await _historyProvider.BuildLlmHistoryAsync(_meetingId, ct);
    var pending = _pending.DrainAsUserMessages(_meetingId);
    if (pending.Count > 0) rebuilt.AddRange(pending);
    return rebuilt;
}
```

这意味着：

- **`BuildLlmHistoryAsync` 的调用点是 `UpdateHistoryAsync` 钩子**，不是 `MeetingExecutor.ExecuteAsync` 启动时
- 每一轮 agent 发言之前都会重建一次（保证最新一条消息已落库就立刻可见）
- AF 自己的 buffer 只是"提供给 agent 的载体"，不是"真相"

### B 路径核心算法（仿 [ChatHistoryDataProvider.ProvideChatHistoryAsync](../../../Src/Netor.Cortana.AI/Providers/ChatHistoryDataProvider.cs#L381)）

**修复缺陷 23 + 27**：

- **缺陷 23**：BuildLlmHistoryAsync 内部全部读操作放在同一个 `BEGIN DEFERRED` 事务，确保读到一致快照（避免段落已写但尾部消息正在并发写入的部分状态）
- **缺陷 27**：尾部原文用 `ListCompleteBySequence`，过滤 IsPartial=1 消息，避免半截发言污染 LLM 上下文

```csharp
public async Task<List<ChatMessage>> BuildLlmHistoryAsync(string meetingId, CancellationToken ct)
{
    // 修复缺陷 23:同一事务内读取段落 + 尾部消息,保证快照一致性
    return await _db.QueryInTransactionAsync(conn =>
    {
        var segments = _compactService.GetByMeetingIdOnConnection(conn, meetingId);
        var result = new List<ChatMessage>();

        if (segments.Count > 0)
        {
            // 1) 滑动窗口:只加载最近 N 个段落(旧段落不删除,只是不再注入 LLM 上下文)
            var maxDisplay = _settings.GetValue("Meeting.Compaction.MaxDisplaySegments", 10);
            var displaySegments = segments.Count > maxDisplay
                ? segments.Skip(segments.Count - maxDisplay).ToList()
                : segments;

            // 2) 摘要作为 system 消息注入
            foreach (var seg in displaySegments)
            {
                result.Add(new ChatMessage(ChatRole.System,
                    $"[会议摘要 #{seg.SegmentIndex + 1}]\n{seg.Summary}"));
            }

            // 3) 加载最后段落之后的原始消息(修复缺陷 27:过滤 IsPartial=1)
            var tailStart = segments[^1].EndSequence + 1;
            var tailMessages = _messageService.ListCompleteBySequenceOnConnection(
                conn, meetingId, tailStart);
            result.AddRange(ConvertToChatMessages(tailMessages));
        }
        else
        {
            // 没压缩过:全部完整原始消息(过滤 IsPartial=1)
            var allMessages = _messageService.ListCompleteByMeetingOnConnection(conn, meetingId);
            result.AddRange(ConvertToChatMessages(allMessages));
        }

        return result;
    }, transactionMode: SqliteTransactionMode.Deferred, ct);
}
```

> **关键约束**：UI 回放路径仍调 `ListByMeeting` 显示全部消息（含 `IsPartial=1` 半截消息 + "未完成"角标），保留历史完整性给老板。LLM 上下文路径调 `ListCompleteByMeeting` 过滤 IsPartial，让主持人 / 参会者只看到完整发言，避免重试场景下 history 中残留半截消息让主持人决策困惑（详见 [04 §5.5](./04-界面交互设计.md)）。

`ConvertToChatMessages`：把 `MeetingMessageEntity` 转成 AF 的 `ChatMessage`，根据 `SpeakerKind` 映射 `ChatRole`：

| SpeakerKind | ChatRole | AuthorName |
|-------------|----------|----------|
| user | User | "用户" |
| host | Assistant | "主持人" |
| agent | Assistant | AgentName（区分谁说话） |

> **注意**：所有智能体发言都映射成 `Assistant` 角色（这是 GroupChat 的内部协议——参考 [GroupChatWorkflowBuilder.cs:78-82](file:///E:/OpenSourse/agent-framework-main.v1.6.0/dotnet/src/Microsoft.Agents.AI.Workflows/GroupChatWorkflowBuilder.cs)，AF 内部 `AIAgentHostOptions.ReassignOtherAgentsAsUsers = true` 让每个 agent 在自己视角下把别人重新分类为 user）。我们这里仅用于 `MeetingHostManager.SelectNextAgentAsync` 的决策提示，AF 内部的协议转换由框架完成。

### 触发压缩的时机（修复缺陷 23）

仿 [CompactAndReplaceAsync](../../../Src/Netor.Cortana.AI/Providers/ChatHistoryDataProvider.cs#L728) 的策略，但加 SemaphoreSlim 互斥避免同会议并发触发：

```csharp
private readonly ConcurrentDictionary<string, SemaphoreSlim> _compactionLocks = new();

// 在每条消息写入 MeetingMessages 后异步检查
private async Task TryCompactAsync(string meetingId, CancellationToken ct)
{
    // 修复缺陷 23:同一会议同时只能有一个 TryCompactAsync 在跑,避免并发压缩
    var sem = _compactionLocks.GetOrAdd(meetingId, _ => new SemaphoreSlim(1, 1));
    if (!await sem.WaitAsync(0, ct))
    {
        // 已有压缩在跑,跳过本次触发(下次消息写入时会再次尝试)
        return;
    }

    try
    {
        var segmentSize = _settings.GetValue("Meeting.Compaction.SegmentSize", 30);
        var rawTailSize = _settings.GetValue("Meeting.Compaction.RawTailSize", 20);

        var totalCount = _messageService.CountByMeeting(meetingId);
        var coveredEndSeq = _compactService.GetMaxEndSequence(meetingId);    // -1 表示没压缩过
        var unsummarizedCount = totalCount - (coveredEndSeq + 1);

        // 触发条件：未摘要消息超过"段落大小 + 尾部保留数"
        if (unsummarizedCount <= segmentSize + rawTailSize) return;

        // 取最早的 segmentSize 条未摘要消息
        var batch = _messageService.ListBySequenceRange(
            meetingId,
            coveredEndSeq + 1,
            coveredEndSeq + segmentSize);

        // 调用压缩专用 LLM
        var summary = await _compactionClient.SummarizeAsync(batch, ct);
        if (string.IsNullOrWhiteSpace(summary)) return;

        _compactService.Add(new MeetingCompactionSegmentEntity
        {
            MeetingId = meetingId,
            SegmentIndex = _compactService.GetMaxSegmentIndex(meetingId) + 1,
            StartSequence = batch[0].Sequence,
            EndSequence = batch[^1].Sequence,
            Summary = summary,
            OriginalMessageCount = batch.Count,
            ModelName = _compactionModel.Name,
        });
    }
    finally
    {
        sem.Release();
    }
}
```

**主持人记忆"摘要切换"是预期行为**：从"全量原文"到"摘要+尾部"的瞬间跳变是预期可观察现象——下游摘要质量足够高时，主持人不需要看全文。这是性能/质量的设计权衡，不是 bug。如果摘要质量出现问题（决策连贯性下降），调高 `MaxDisplaySegments` 或 `RawTailSize`。

### 压缩用的 LLM

**Append 事务保证（修复缺陷 24）**：

```csharp
public string Append(MeetingMessageEntity msg)
{
    return _db.ExecuteInTransaction(conn =>
    {
        // BEGIN IMMEDIATE 保证此事务获得写锁,其他写入等待
        // → GetNextSequence + Insert 原子化,避免并发写时同 Sequence 冲突
        msg.Sequence = ExecuteScalarOnConnection<int>(conn,
            "SELECT IFNULL(MAX(Sequence), -1) + 1 FROM MeetingMessages WHERE MeetingId = @m",
            cmd => cmd.Parameters.AddWithValue("@m", msg.MeetingId));

        InsertOnConnection(conn, msg);
        return msg.Id;
    }, transactionMode: SqliteTransactionMode.Immediate);
}
```

**额外保险**：`uk_meeting_msg_sequence` UNIQUE 索引（详见 §3.2）让并发冲突被 SQLite 拦截后立即抛异常，不会出现"两条同 Sequence 但都成功"的数据腐坏。

### 4.5 MeetingCancellationRegistry（修复缺陷 15）

仿 [WorkTaskCancellationRegistry](../../../Src/Netor.Cortana.AI/WorkMode/WorkTaskCancellationRegistry.cs) 设计。每个会议注册一个 CTS，`MeetingExecutor.CancelAsync` 调用时取消 CTS 让所有 in-flight 的 `RunStreamingAsync` 抛 `OperationCanceledException`，工作流自然结束（散会路径）。

```csharp
namespace Netor.Cortana.AI.MeetingMode;

public sealed class MeetingCancellationRegistry
{
    private readonly ConcurrentDictionary<string, CancellationTokenSource> _registry = new();

    /// <summary>
    /// 在 MeetingExecutor.ExecuteAsync 入口调用,失败说明已有运行中的执行轮次。
    /// 配合 §3.1 表的 idx_meeting_active_unique 唯一索引,实现"同 session 单活跃会议"的保证。
    /// </summary>
    public bool TryRegister(string meetingId, CancellationTokenSource cts)
        => _registry.TryAdd(meetingId, cts);

    public void Unregister(string meetingId)
        => _registry.TryRemove(meetingId, out _);

    /// <summary>取消会议:同时唤醒 MeetingHostManager 内部的 _userReplyTcs,避免泄漏。</summary>
    public void Cancel(string meetingId)
    {
        if (_registry.TryRemove(meetingId, out var cts))
        {
            cts.Cancel();
        }
    }
}
```

**关键约束**：

- `MeetingExecutor.ExecuteAsync` 用 `using var linkedCts = CTS.CreateLinkedTokenSource(externalCt)` + `TryRegister` 注册
- `MeetingExecutor.CancelAsync(meetingId)` 调用 `_registry.Cancel(meetingId)`
- `MeetingHostManager.SelectNextAgentAsync` 的 TCS 必须传 `linkedCts.Token` 给 `WaitAsync`，CTS 取消时 TCS 自动 throw `OperationCanceledException`，避免泄漏
- catch 路径写 `MeetingSessions.Status=3` + 发 `meeting.cancelled` 事件

## 九、生命周期总结

| 阶段 | 数据库写入 |
|------|----------|
| 用户提交主题 | INSERT MeetingSessions (Status=0) + INSERT MeetingAttachments |
| 主持人/参会者发言完成 | INSERT MeetingMessages |
| 每写入一条消息 | 异步 TryCompactAsync → 满足条件时 INSERT MeetingCompactionSegments |
| 用户插话 | INSERT MeetingPendingInputs (Kind=interrupt) |
| 主持人调用 ask_user | UPDATE MeetingSessions (Status=1, PendingRequest*) + INSERT MeetingMessages (summary) + INSERT MeetingMessages (inquiry, AwaitingUserReply=1) |
| 用户回复征询 | UPDATE MeetingSessions (ClearPending) + INSERT MeetingMessages (user normal) |
| 用户确认结束 | UPDATE MeetingSessions (Status=2, FinalSummary, EndedAt) + INSERT ChatMessages (assistant 总结) |
| 用户取消 / 软件关闭未结束 | UPDATE MeetingSessions (Status=3, EndedAt) |

**所有阶段都不删除 MeetingMessages / MeetingCompactionSegments**——历史回放和上下文压缩是两条独立路径，原始数据全量保留。

### 9.1 启动时孤儿会议清理（修复缺陷 7）

应用关闭可能不是用户主动操作（崩溃、系统重启、电源故障），此时 `MeetingSessions.Status` 仍是 `0`（进行中）或 `1`（等待用户回复），但根本没有进程在跑。下次启动时如果不清理，UI 会显示"进行中"但点开毫无反应。

**对策**：新增 `MeetingStartupService : IHostedService`，应用启动时把所有遗留的活跃会议标记为已散会：

```csharp
namespace Netor.Cortana.AI.MeetingMode;

public sealed class MeetingStartupService : IHostedService
{
    private readonly MeetingSessionService _sessions;
    private readonly IPublisher _publisher;
    private readonly ILogger<MeetingStartupService> _logger;

    public Task StartAsync(CancellationToken ct)
    {
        var orphans = _sessions.GetAllInProgress();    // Status IN (0, 1)
        if (orphans.Count == 0) return Task.CompletedTask;

        _logger.LogInformation("检测到 {Count} 个未正常结束的会议,自动散会", orphans.Count);

        foreach (var meeting in orphans)
        {
            _sessions.MarkAsAdjourned(meeting.Id);    // UPDATE Status=3, EndedAt=now
            _publisher.Publish(
                Events.OnMeetingCancelled,
                new MeetingCancelledArgs(meeting.Id, "auto_adjourn_on_startup"));
        }
        return Task.CompletedTask;
    }

    public Task StopAsync(CancellationToken ct) => Task.CompletedTask;
}
```

DI 注册：

```csharp
services.AddSingleton<MeetingStartupService>();
services.AddSingleton<IHostedService>(sp => sp.GetRequiredService<MeetingStartupService>());
```

> **与工作模式的差异**：工作模式有 [WorkModeStartupService](../../../Src/Netor.Cortana.AI/WorkMode/WorkModeStartupService.cs) 做孤儿任务检测，但工作模式有"恢复"语义（基于 AF Checkpoint）。**会议模式没有恢复机制——孤儿一律散会**，与 [README §7.2](./README.md) 的决策一致。

### 10.2 LoadMeetingHistory 流程

```csharp
public void LoadMeetingHistory(string meetingId)
{
    var session = _sessions.GetById(meetingId);
    var messages = _messageService.ListByMeeting(meetingId);     // 全量原始消息

    MessageList.Items.Clear();

    // 渲染第一条 user 主题
    AddUserBubble(session.Topic);

    // 按 Sequence 顺序逐条还原
    foreach (var msg in messages)
    {
        var avatar = ResolveAvatar(msg.SpeakerKind, msg.SpeakerId);
        var bubble = MeetingBubbleBuilder.Build(new MeetingBubbleArgs(
            MessageId: msg.Id,
            SpeakerKind: msg.SpeakerKind,
            SpeakerId: msg.SpeakerId,
            SpeakerName: msg.SpeakerName,
            Avatar: avatar,
            Markdown: msg.ContentMd,
            MessageRole: msg.MessageRole,
            Timestamp: DateTimeOffset.FromUnixTimeMilliseconds(msg.CreatedAt)));

        // 还原思考卡（如果有）
        if (!string.IsNullOrEmpty(msg.ThinkingMd))
            AppendThinkingCard(bubble, msg.ThinkingMd);

        // 还原工具调用卡（如果有）
        if (!string.IsNullOrEmpty(msg.ToolCallsJson))
        {
            var calls = JsonSerializer.Deserialize(
                msg.ToolCallsJson, MeetingJsonContext.Default.ListMeetingToolCallRecord);
            foreach (var call in calls ?? [])
                AppendToolCard(bubble, call);
        }

        MessageList.Items.Add(bubble);
    }

    // 已归档/散会的会议仍保留历史上下文，允许用户继续讨论、保存记录或开启下一轮
    if (session.Status is MeetingStatus.Ended)
    {
        _view.MeetingInputArea.IsEnabled = true;
        UpdateStatusHint("本轮会议已归档，可继续讨论、保存记录或开启下一轮");
    }
    else if (session.Status is MeetingStatus.Cancelled)
    {
        _view.MeetingInputArea.IsEnabled = true;
        UpdateStatusHint(session.Status);
    }
}
```

### 10.3 关键设计点

1. **原始消息全量加载**：不读 `MeetingCompactionSegments`，因为压缩段是给 LLM 看的，不是给老板看的
2. **思考/工具卡完全还原**：从 `ThinkingMd` 和 `ToolCallsJson` 重建，与实时渲染视觉一致
3. **状态指示明确**：进行中的会议可继续讨论；已归档的会议保留当前上下文，允许继续讨论、要求保存文档或开启下一轮；已散会的会议也可输入历史续接指令
4. **附件可点击**：从 `AttachmentsJson` 解析，提供"打开文件"按钮（调用 `IAppPaths.WorkspaceResourcesDirectory` 拼绝对路径）

### 10.4 进行中会议的"恢复"语义

用户从历史列表点开一个**进行中**（`Status=0` 或 `Status=1`）的会议：

- 加载历史消息（同上）
- 如果 `Status=1`（等待用户回复）→ 状态提示行变 "主持人在等您回复"，输入框走马灯加亮
- 用户可以直接输入回复或继续插话，逻辑与活跃会议一致

> **关键约束**：v1.0 不做跨进程恢复（关闭软件 = 散会），所以"进行中"的会议只可能是当前进程仍在跑的那一个。如果发现重启后还有 `Status ∈ {0, 1}` 的会议（孤儿），统一置为 `Status=3 已散会`，不做恢复尝试。这与 [README §7.2](./README.md) 的决策一致。
