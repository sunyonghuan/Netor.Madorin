# 架构决策：当前版商用化 与 多任务并发版重建

> 状态：决策草案（仅方案，不涉及代码改动）
> 关联文档：`Docs/存储优化/对话记录文件化存储方案.md`
> 适用范围：Netor.Cortana 从"单对话/单工作区"演进到"多任务并发 / 多智能体并发 / 多工作区并行"

---

## 1. 背景与问题

当前软件是**单对话、单工作区**模式：全局只认一个"当前工作区"和一个"当前活跃会话/任务"。这套模型正常运行、即将具备商用条件（前提是完成对话记录文件化，见关联文档）。

下一步的产品目标是行业标配能力：

- **多工作区并行**：同时打开 N 个工作目录，各自独立跑。
- **单工作区内多对话并行**：同一目录里同时进行多个对话/任务。
- **多智能体并发**：多个 streaming run 同时执行。
- UI 上表现为多窗体或界面内分栏。

核心矛盾：这些能力要改动的是**最底层的假设**（全局工作区静态、单会话上下文、DI 作用域、AI 流水线并发），改动会渗透全局。在一个即将商用的稳定体上做这种手术，会把"稳定可卖"和"高风险重构"两条生命线绑死。

---

## 2. 三条路径与取舍

### 路径 A：在当前软件上原地改造
- **做法**：直接在现有工程里增加并发能力。
- **优点**：不新建工程，短期看"省事"。
- **致命缺点**：并发改动渗透到每个角落，商用版与半成品架构互相拖累；每个 bug 修复都要在动荡的架构里趟一遍。即用户所说的"增增改改改乱了"。
- **结论**：**否决**。不应为并发去动一个即将商用的稳定体。

### 路径 B：从零重写
- **做法**：全新工程，从头实现。
- **优点**：架构最干净。
- **致命缺点**：丢弃现有代码中**用时间换来的隐性知识**（各 AI provider 的怪脾气、插件框架边界情况、PowerShell 会话坑、流式异常半截消息处理等，这些在代码里、不在文档里）。典型 second-system effect，会用数月重踩同样的坑；重写期间无新价值产出，存在漫长空窗期。
- **结论**：**否决**（除非满足第 6 节的翻转条件）。

### 路径 C（推荐）：新组合根 + 旧类库复用
- **做法**：另起新工程，但**把现有代码当作类库来引用复用**。改动集中在"组合根（composition root）"这一层——应用生命周期、DI 作用域、工作区上下文、UI 外壳。
- **本质**：不是"从零重写"，而是"**在现有类库之上重建一层新的外壳和编排层**"。
- **结论**：**采纳**。既不原地动稳定体，也不从零丢弃已有资产。

---

## 3. 推荐方案（路径 C）详解

### 3.1 分层：复用 vs 重建

| 层 | 处理方式 | 说明 |
|----|---------|------|
| 应用生命周期 / 组合根 | **重建** | 去掉全局静态，改为按工作区/按对话的作用域上下文 |
| DI 作用域 | **重建** | 引入 scoped container，每个工作区/对话一套 |
| UI 外壳（多窗体/分栏） | **重建** | 每个 pane 一套独立 VM，独立生命周期 |
| AI 编排（并发 run） | **重建** | 独立取消、独立 provider/限流、并发 streaming run |
| UI 控件 / 样式 | **复用** | 项目引用整体搬运 |
| 插件框架 | **复用**（含中层解耦，见 3.2） | |
| AI provider / 模型客户端 | **复用** | 需确认线程安全 |
| 实体模型 + 文件化存储层 | **复用** | 每工作区物理隔离正是并发地基 |

工作量分布：重建部分约占 **两三成**，其余七八成是引用复用。这正是路径 C 相对"从零"省下的部分。

### 3.2 全局状态解耦清单（中层耦合）

耦合已渗到中间层（AI/插件层），不只在 UI 顶层。以下为需要从"全局静态"改造为"注入的作用域上下文"的已知点：

1. **`App.WorkspaceDirectory`（全局静态）** — 头号障碍。`AppPaths` 的所有路径都从它派生。需改为 per-workspace 的 `WorkspaceContext` 注入。
2. **`AppPaths`** — 派生自上述静态，需随之作用域化。
3. **"当前会话/当前任务"单例假设** — UI 的 VM、AI 流水线（`ChatTurnPreparationService` 那条链）默认单上下文，需按对话/工作区作用域化。
4. **`ExecutionSession` / 插件状态（共享）** — 工作区内多对话并行时的资源竞争点。
5. **AI 流水线并发** — 多个 streaming run 同时跑，需各自独立取消、provider/限流处理、模型客户端线程安全。

> 关键推论：这些中层全局的解耦**无论选哪条路都躲不掉**（原地改要解、重写要重做、路径 C 是"边往上搬边重构成 scoped"）。既然是共同成本，而底层（控件、provider、实体）又干净可复用，天平就倒向路径 C。

### 3.3 存储地基：每工作区一个 writer

- 内容按工作区落在各自 `.cortana` 里，物理隔离，天然支持多工作区并行。
- **不要用单一全局 Channel**：单 Channel + 单消费线程是串行点，会造成 head-of-line blocking（A 工作区写大文件堵住 B）。
- **正确形态**：**每个工作区（或每个对话）一个 Channel + 一个 writer**。
- 索引也需下沉到每个工作区的 `.cortana`（每工作区一个小索引库/索引文件），否则全局 `madorin.db` 仍是所有并发工作区的共享写入点，耦合未真正消除。

### 3.4 关于"数据库是并发灾难"的校准

- **被高估的部分**：SQLite WAL 支持"多读并发 + 单写串行"，单次写入毫秒级。桌面应用同时几个对话的量级，写竞争可忽略（配合 `busy_timeout` + 串行写队列即可）。"database is locked"通常是多连接乱写的用法问题，非引擎能力问题。
- **真正成立的部分**：`madorin.db` 是 exe 目录下的**全局单库**，所有工作区共用、靠 `Categorize` 区分。这才是真正耦合点。文件化 + 每工作区索引正是解决这一条。
- **Channel 的价值**：不是"千万级吞吐"（并发规模是个位数对话，吞吐从不是问题），而是**解耦 + 单消费者串行安全写**。

## 4. 两个降低风险的关键动作

### 4.1 先把当前版作为商用发布
完成文件化后即发布。发布后它从"必须小心呵护的半成品"变为"有营收的稳定基座"，新架构重建无时间压力，可从容挑选旧代码成熟部分搬运。**几乎消除重写最大的风险（空窗期）**。

### 4.2 文件化投资是共享的、不浪费
即将做的文件化 + 每工作区 Channel/索引，是"多工作区并发"的地基，新架构直接复用。因此现在可以放心先把文件化做完。

---

## 5. "多任务并发"目标分层（需先定方向）

该目标其实是隔离强度不同的两件事，方向决定工作量：

### 5.1 多工作区并行（推荐先做）
- N 个目录各开一摊，隔离最自然，文件化收益最大。
- 需：de-globalize 工作区状态 + 每工作区索引 + 每工作区 writer。
- 与文件化方案**强协同**，可顺序衔接。

### 5.2 单工作区内多对话并行（更后期的独立阶段）
- 同一目录里同时几个对话，共享同一份文件、同一 PowerShell 会话、同一套插件状态。
- 文件化帮不上忙，重心在**工作区内的资源隔离**（会话池、插件/执行会话按对话作用域化）。
- 难度更高，建议后置。

---

## 6. 决策翻转条件

推荐（路径 C）成立的前提是全局状态**主要集中在可搬运的边界**。若实施中发现全局假设**深深焊死在业务逻辑里、拆一个带出一串**，复用价值会打折，天平会往"从零重写（路径 B）"偏移。就目前所见结构（耦合止于 AI/插件中层，底层控件/provider/实体干净），尚未到该程度。

判定信号：
- ✅ 倾向 C：底层类库能独立编译/引用，全局静态可用注入替换。
- ⚠️ 倾向 B：解耦一个全局静态会连带修改大量业务分支、无法隔离。

---

## 7. 结论与推荐路线

**一句话结论**：当前版做完文件化就发布商用；并发版作为**新组合根 + 外壳项目**另起，把现有底层类库整体复用，在往上搬的过程中把全局状态重构成按工作区/按对话的作用域上下文。既不原地动稳定体，也不从零丢弃已有资产。

**推荐时间线（阶段化，各阶段可独立交付）**：

1. **阶段 0 — 文件化 + 每工作区 Channel/索引**（在当前工程完成）→ 达成商用条件，同时打好并发地基。
2. **阶段 1 — 当前版商用发布** → 形成稳定营收基座，为重建争取从容空间。
3. **阶段 2 — 新工程搭建：组合根 + DI 作用域 + `WorkspaceContext`** → 去 `App.WorkspaceDirectory` 全局静态，引用复用底层类库。
4. **阶段 3 — 多工作区并行**（对应 5.1）→ 每工作区独立 scope/writer/索引，UI 外壳（多窗体/分栏）。
5. **阶段 4 — 并发 AI 编排** → 多 streaming run、独立取消、provider 线程安全。
6. **阶段 5 — 单工作区内多对话并行**（对应 5.2）→ 工作区内资源隔离，难度最高，最后做。
