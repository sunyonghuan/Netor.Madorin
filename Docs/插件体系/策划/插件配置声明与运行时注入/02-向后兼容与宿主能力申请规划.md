## 1. 背景

当前插件体系已经存在多类能力：

- 普通工具能力：由 `[Tool]` 方法暴露给 AI 调用。
- 语音能力：如 STT、TTS、KWS，由主程序适配层选择具体插件。
- PluginBus 能力（运行时连接维度）：如 `conversation.v1`、`memory.v1`、`workflow.v1`，由 `PluginBusSubscriptionRegistry.SetCapabilities` 在 subscribe 帧解析后写入。
- 宿主大模型能力：当前已有插件大模型授权页、`PluginModelCapabilityService`、`PluginBusModelCapabilityDispatcher`。

新的配置声明机制会进一步引入：

- `settingsSchema`：插件需要用户配置哪些字段。
- `requiredHostCapabilities`：插件申请主程序提供哪些能力。

这些字段不能成为强制协议，否则老插件会因为缺少新字段或新方法而加载失败。

### 1.1 与现状的差距（不能默认为已存在）

下表澄清"已存在"和"需要从零新增"的现状，避免误把待建能力当作演进起点：

| 字段/能力 | Native 通道现状 | Process 通道现状 |
|-----------|------------------|------------------|
| `PluginAttribute.Capabilities` | **不存在**（`Netor.Cortana.Plugin.Native.PluginAttribute` 只有 Tags / Instructions） | 已存在（`Netor.Cortana.Plugin.PluginAttribute.Capabilities`） |
| Generator `PluginClassInfo.Capabilities` | **不存在**（`Native.Generator.Analysis.PluginClassInfo` 没有该字段） | 已存在 |
| plugin.json `capabilities` 输出 | **不存在**（`Native.Generator.PluginJsonEmitter` 只输出 id / name / version / description / runtime / libraryName / minHostVersion） | 已存在（`Process.Generator.PluginJsonEmitter` 写 tags / capabilities） |
| `get_info` 返回 capabilities | **不存在**（`InfoJsonEmitter` 只输出 tags / tools，不输出 capabilities） | 已存在（`PluginInfoData.Capabilities` 字段，但当前被 Native 通道共用基类的 `NativePluginInfo` 反序列化静默丢弃，详见 §1.3） |
| PluginBus subscribe `capabilities` 字段 | 已存在（运行时连接维度，参考 `PluginBusSubscriptionRegistry`） | 已存在（同上） |

也就是说本规划"插件 capabilities 元数据声明"在 Native 通道上其实是**从零新增**，不是演进。Process 通道则是把已有 `Capabilities` 字段进一步规范化为 `providedCapabilities`。

> **PluginBus subscribe 的 `capabilities` 与 manifest `capabilities` 是两个不同维度**：前者是运行时单连接的能力声明（用于 dispatcher 路由），后者是插件包的能力分类（用于 UI 展示与授权 UI 决策）。本规划只处理后者，**不收敛 PluginBus subscribe 的 capabilities**——两者并行不悖。详见 §10。

### 1.2 plugin.json 现状不只是缺 capabilities — tags / tools 也缺

代码现状：

| 字段 | Native plugin.json（`Native.Generator/PluginJsonEmitter`） | Process plugin.json（`Process.Generator/PluginJsonEmitter`） | PluginManifest 反序列化字段 |
|------|------------------------------------------------------------|-------------------------------------------------------------|------------------------------|
| `tags` | **不输出** | 输出（仅当 `Tags.Length > 0`） | `PluginManifest.Tags`（缺失时为空数组） |
| `capabilities` | **不输出** | 输出（仅当 `Capabilities.Length > 0`） | `PluginManifest.Capabilities`（缺失时为空数组） |
| `tools` | 不输出（`PluginManifest` 也没有 `Tools` 字段，tools 是通过 get_info 协议拿到） | 不输出（同上） | 不存在 |

所以"主程序仅通过 plugin.json 即可识别插件能力"在 Native 通道当前**完全不成立**：UI 拿到的 `LoadedPluginInfo.Manifest.Tags` 永远为空，`Manifest.Capabilities` 也永远为空。

落地工作不仅是加 `settingsSchema` / `requiredHostCapabilities`，而是连同 tags / capabilities 一并补齐——否则 §6.1 的"按申请展示"以及 §6 中"按 tags 过滤插件"等 UI 都无法工作。具体改造点见 §11.1。

### 1.3 NativePluginInfo / PluginInfoData 协议层不对称 — 影响 get_info 通道

代码现状：

| DTO | 文件 / 行 | 含 `capabilities` 字段 | 含 `requiredHostCapabilities` 字段 |
|-----|----------|------------------------|------------------------------------|
| Process 通道 `PluginInfoData` | `Src/Plugins/Netor.Cortana.Plugin.Process/Protocol/PluginInfoData.cs:36-37` | 是 | 否 |
| Native 通道 `NativePluginInfo` | `Src/Netor.Cortana.Plugin/Native/NativePluginInfo.cs:7-28` | **否** | 否 |

问题：`Native` 与 `Process` 共用 `ExternalProcessPluginHostBase` 基类，基类在 `InitializePluginAsync` 里只反序列化为 `NativePluginInfo`（`Src/Netor.Cortana.Plugin/Core/ExternalProcessPluginHostBase.cs:181`）。

也就是说 Process 通道宿主侧通过 get_info 拿到的 JSON 里**即便有** `capabilities` 字段，也会被当作未知字段静默丢弃——只有 plugin.json 这一条路能让 capabilities 真正进到主程序内存。get_info 当前的"二次校验通道"作用名存实亡。

落地本规划时，必须**同时**改 Native 端 `NativePluginInfo` 增加 `Capabilities` / `RequiredHostCapabilities` 字段（以及配套的 `NativePluginJsonContext` 注解），让两通道的 get_info 也对齐 plugin.json 的字段集合。详见 §11.1。

## 2. 核心原则

### 2.1 新字段全部可选

老插件没有声明新字段时，主程序必须正常加载。

兼容规则：

| 缺失内容 | 主程序行为 |
|----------|------------|
| `settingsSchema` | 视为该插件没有设置项 |
| `requiredHostCapabilities` | 视为该插件不申请宿主能力 |
| `providedCapabilities` | 仅按旧有工具、tags 或现有能力字段处理 |
| 新版 `extensions` 字段 | 使用旧初始化逻辑 |
| 未知字段 | 忽略 |
| 未知 capability token | 忽略或 warning，不阻断加载 |

### 2.2 不强制调用新方法

主程序不能为了新能力而强制调用老插件不存在的方法，例如：

- `get_settings_schema`
- `get_host_capabilities`
- `get_required_capabilities`
- `get_authorization_schema`

初版应优先让 Generator 把声明写入插件元数据，主程序读取不到就降级。

### 2.3 声明不等于授权

插件声明“我需要某项宿主能力”，只表示主程序应该在 UI 中展示这项申请。

是否真的允许使用，必须经过：

1. 主程序识别插件申请。
2. 用户或系统策略授权。
3. 主程序保存授权配置。
4. 插件初始化时收到授权摘要。
5. 插件调用宿主能力。
6. 宿主在每次调用时再次强校验。

插件不能仅凭声明获得权限。

## 3. 能力方向区分

插件能力需要区分两个方向。

### 3.1 插件提供能力

插件提供能力表示“插件能为主程序做什么”。

建议字段名：

```json
{
  "providedCapabilities": [
    "voice.stt.v1",
    "voice.tts.v1",
    "memory.supply.v1"
  ]
}
```

用途：

- 主程序识别语音插件、记忆插件、特殊能力插件。
- 设置页展示插件类型和可用能力。
- 非 AI 工具调用场景下，由主程序内部服务选择具体插件。

#### 3.1.1 Tags vs Capabilities 区分

代码现状里两个字段常被混用——例如 Memory 插件 `Tags = ["memory", "ingest", "plugin-bus"]` 既包含分类标签也含技术术语；Voice STT 插件 `Tags = ["voice", "stt", "sherpa"]` 同时声明了 `Capabilities = ["voice.stt"]`。落地时应以下面规则区分：

| 字段 | 角色 | 消费者 | 典型值 |
|------|------|--------|--------|
| `Tags` | 给**用户**看的分类/搜索标签，自然语言、风格化 | 设置页搜索、列表分组 UI、用户感知 | `"搜索"`、`"Google"`、`"提醒"`、`"日程"` |
| `Capabilities` / `providedCapabilities` | 给**主程序**用的能力 token，机器识别、稳定 ID | 主程序内部服务选型（KWS/STT/TTS 选插件）、授权 UI 决策、插件作者声明面向系统的能力 | `"voice.stt"`、`"voice.tts.v1"`、`"memory.supply.v1"` |

判定标准：

- 主程序代码里要按值做 `string.Equals(..., StringComparison.Ordinal)` 比较的属于 capability，用稳定带版本号的小写点分 token；
- 只供 UI 显示、用户搜索/筛选的属于 tag，自由形式（中英文、空格、风格化都允许）。

迁移指引（针对现有插件）：

| 当前写法 | 应当迁移为 |
|----------|------------|
| Memory `Tags = ["memory", "ingest", "plugin-bus"]` | `Tags = ["记忆", "长期记忆"]`（用户视角）+ `Capabilities = ["memory.supply.v1"]`（机器视角） |
| Voice STT `Tags = ["voice", "stt", "sherpa"]` + `Capabilities = ["voice.stt"]` | `Capabilities` 已经对了，`Tags` 建议改为 `["语音识别", "Sherpa"]`，把 `voice` / `stt` 这类机器 token 从 Tags 移除 |

迁移**不强制**——老插件保留现状仍能加载，但新插件作者按本节写就避免混用。

### 3.2 插件申请宿主能力

插件申请宿主能力表示“插件希望主程序提供什么资源或服务”。

建议字段名：

```json
{
  "requiredHostCapabilities": [
    {
      "id": "host.llm.invoke.v1",
      "purpose": "memory.extract",
      "required": false,
      "reason": "用于从对话中提取长期记忆候选"
    }
  ]
}
```

用途：

- 主程序授权页按需展示能力申请。
- 用户理解插件为什么需要该能力。
- 主程序生成授权配置和运行时授权摘要。
- 宿主服务按能力、插件、purpose 做运行时校验（purpose 是否落到设置 key 取决于阶段，详见 §8.1.1）。

### 3.3 命名空间约定

为避免"提供"与"申请"两个方向语义混淆，强制以下命名约定：

- **`host.*` 前缀仅用于 `requiredHostCapabilities`**：表示插件向宿主申请使用的能力（例如 `host.llm.invoke.v1`、`host.events.conversation.v1`、`host.notification.v1`）。
- `providedCapabilities` 中的能力**不带 `host.` 前缀**：表示插件向宿主供应的能力（例如 `voice.stt.v1`、`voice.tts.v1`、`memory.supply.v1`）。
- 同一能力名不允许同时出现在两侧（除非概念上确实是双向，且两端各自带不同前缀）。

按此约定，"记忆插件向宿主供应长期记忆上下文"是 `providedCapabilities: ["memory.supply.v1"]`，不写成 `host.memory.supply.v1`——`host.*` 表示的是"插件作为消费者"。这条约定在 §4 中体现。

### 3.4 reason 与 purpose 的角色区分

`reason` 与 `purpose` 维度完全不同，插件作者必须填对：

| 字段 | 类型 | 角色 | 消费者 |
|------|------|------|--------|
| `reason` | 自然语言（中/英文） | 给用户看的说明，"我为什么需要这个能力" | 授权 UI 展示 |
| `purpose` | 短 token（小写、点分） | 路由/限流键，"我把这个能力用在哪个用途" | 宿主侧授权配置（按阶段决定是否落到 setting key）、限流 |

错误示例：

- `purpose: "用于提取长期记忆候选"` ❌（reason 写到了 purpose）
- `reason: "memory.extract"` ❌（purpose 写到了 reason）

正确示例：`purpose: "memory.extract"`、`reason: "用于从对话中提取长期记忆候选"`。

## 4. 宿主能力分类建议

初版可以先定义少量标准能力，避免能力名失控。所有 ID 都带 `host.*` 前缀（参考 §3.3）：

| 能力 ID | 说明 | 典型插件 |
|---------|------|----------|
| `host.llm.invoke.v1` | 调用宿主配置的大模型 | 记忆插件、分析插件 |
| `host.events.conversation.v1` | 订阅对话事件 | 记忆插件、审计插件 |
| `host.events.workflow.v1` | 订阅 workflow 事件 | 任务插件、记忆插件 |
| `host.memory.context.v1` | 请求宿主允许该插件向系统注入长期记忆上下文 | 记忆插件 |
| `host.notification.v1` | 向主程序发送通知 | 提醒插件、监控插件 |
| `host.file.browse.v1` | 请求主程序提供文件选择或受控文件访问 | 文件类插件 |

> 注意 `host.memory.context.v1` 与 `providedCapabilities` 中的 `memory.supply.v1` 是配套关系：插件**提供** `memory.supply.v1`（包能力声明），同时**申请** `host.memory.context.v1` 让宿主允许它把记忆推到对话上下文里。两者方向不同，前缀不同。

注意：

- 能力 ID 用版本号结尾，方便后续扩展。
- 能力申请不直接暴露给 AI。
- 权限检查发生在宿主服务或 PluginBus 控制面。

## 5. 记忆插件示例

记忆插件既提供能力，也申请宿主能力。

> 本示例仅声明**一个** `host.llm.invoke.v1` 申请项，对应"是否允许调用宿主大模型"的总开关。**初版不按 `purpose` 拆分授权**（理由见 §8.1.1）；后续若启用按 purpose 分开授权，再扩展为多个申请项。

```json
{
  "providedCapabilities": [
    "memory.supply.v1"
  ],
  "requiredHostCapabilities": [
    {
      "id": "host.events.conversation.v1",
      "required": true,
      "reason": "用于接收对话事件并摄取长期记忆"
    },
    {
      "id": "host.events.workflow.v1",
      "required": false,
      "reason": "用于从任务执行事件中提取可沉淀记忆"
    },
    {
      "id": "host.memory.context.v1",
      "required": false,
      "reason": "用于把长期记忆注入到对话上下文中"
    },
    {
      "id": "host.llm.invoke.v1",
      "required": false,
      "reason": "用于离线提取与摘要长期记忆"
    }
  ]
}
```

这里的 `host.llm.invoke.v1` 可以**未来按 `purpose` 拆开**配置不同模型、限额或开关；初版只按一个 capability ID 走总开关。

## 6. 主程序 UI 规划

插件详情页建议拆成多个区块：

```text
基础信息
工具列表
插件设置
插件提供能力
宿主能力申请
授权与限额
运行状态
```

老插件缺少声明时：

```text
插件设置：该插件未声明设置项
宿主能力申请：该插件未声明宿主能力申请
```

不要提示错误，不要求升级。

### 6.1 大模型授权 UI 的兼容降级路径

当前 `PluginAuthorizationPage.RefreshPlugins` 对所有 Loaded Plugin **以及所有 MCP Server**一视同仁地展示 LLM 授权 UI（参考 `Src/Netor.Cortana.UI/Views/Settings/PluginAuthorizationPage.axaml.cs:33-48`，`AuthorizablePlugin.FromMcpServer` 与 `FromLoadedPlugin` 进同一渲染路径）。本规划要切到"按申请展示"，但：

- Native 通道历史插件几乎都没有 capabilities 声明（参见 §1.1 / §1.2）；
- MCP Server 当前没有任何元数据声明协议，没法天然加 `host.llm.invoke.v1`。

直接切换会让 Native 老插件 + 全部 MCP Server 瞬间失去 LLM 授权入口。

为此采用**三态展示规则 + MCP 兼容子规则**，由 `PluginAuthorizationPage` 在渲染时按以下顺序判定：

> **类型识别**：判定时按 `AuthorizablePlugin.Kind` 区分两类条目（参考 `Src/Netor.Cortana.UI/Views/Settings/PluginAuthorizationPage.axaml.cs:443-453`）。当前 `Kind` 是字符串字面量 `"本地插件"` / `"MCP 服务"`，分别由 `FromLoadedPlugin` / `FromMcpServer` 设置。落地 P2 时建议把这两个字符串提到 `AuthorizablePluginKind` 静态常量类（或改为 enum），避免 §6.1.1 / §6.1.2 的判定散落写魔法字符串。

#### 6.1.1 本地插件（LoadedPluginInfo）

| 条件 | 展示策略 |
|------|----------|
| 插件元数据已声明 `host.llm.invoke.v1` | 按新规则展示授权卡片（标记“按申请展示”） |
| 插件未声明，但 `Plugin:{pluginId}:Capability:llm:Enabled = true` 已存在历史授权 | 进入兼容模式：继续展示授权卡片，标记“历史兼容入口（建议升级元数据）” |
| 都不满足 | 不展示 LLM 授权卡片 |

兼容模式只针对 LLM 授权这种已存在历史授权状态的能力。其它新增能力（事件订阅、文件、通知）没有历史 setting，未声明时直接不展示。

> **判定陷阱**：判定依据是 `Plugin:{pluginId}:Capability:llm:Enabled` 的**值**为 `'true'`，而**不是 setting 是否存在**。`PluginAuthorizationPage.EnsureAuthorizationSettings`（参考 `Src/Netor.Cortana.UI/Views/Settings/PluginAuthorizationPage.axaml.cs:243-254`）会在用户首次打开授权页时自动 `EnsureSetting(... defaultValue: "false" ...)` 预创建一组 key——这只表示用户曾打开过授权页，不代表用户曾经授权过该插件使用大模型。实施时使用 `SettingsService.GetValue<bool>(key, false)` 读真实值，`true` 才视为"历史已授权"。

兼容模式什么时候退出由后续阶段决策；本规划只保证不破坏存量。

#### 6.1.2 MCP Server

MCP Server 没有 plugin.json，也没有 `host.llm.invoke.v1` 声明协议。本规划下采用**永久兼容模式**：

| 条件 | 展示策略 |
|------|----------|
| MCP Server 已存在 `Plugin:{mcpServerId}:Capability:llm:Enabled` 设置（无论 true/false） | 兼容模式展示授权卡片，标记“MCP 服务（兼容模式）” |
| MCP Server 从未保存过该 setting | 仍展示一次默认禁用的授权卡片，让用户首次开关；不视为"按申请"、不视为"未声明" |

理由：

- MCP 协议层不归 Cortana 控制，要求 MCP 主动声明 capabilities 不现实。
- 从 UI 体验看，MCP Server 与本地插件在同一列表，让 MCP 突然消失会比让 Native 老插件消失更困惑。

是否给 MCP 增加自身的能力声明协议（例如在 `McpServerEntity` 上加 `RequiresHostLlm` 字段，或读取 MCP 服务器返回的 `serverInfo.capabilities`）作为 §15 待确认问题，不阻塞初版。

## 7. 授权流程

推荐流程：

```text
插件元数据声明 requiredHostCapabilities
  -> 主程序读取声明
  -> 设置页展示申请项
  -> 用户授权或拒绝
  -> 主程序保存授权配置
  -> 插件 init 时下发授权摘要
  -> 插件按授权摘要决定是否启用相关功能
  -> 插件调用宿主能力
  -> 宿主每次调用再次校验授权
```

授权配置和插件普通配置不同：

- 普通配置解决“插件如何执行”。
- 授权配置解决“插件能否使用宿主能力”。

两者可以展示在同一插件设置页，但存储和运行时校验应分离。

## 8. 运行时授权摘要

可以继续使用现有 `PluginSettings.Extensions` 作为下发槽位。

建议新增字段：

```json
{
  "extensions": {
    "pluginConfigJson": "{...}",
    "hostCapabilityGrantsJson": "{...}"
  }
}
```

`hostCapabilityGrantsJson` 示例：

```json
{
  "version": "1.0",
  "grants": [
    {
      "id": "host.llm.invoke.v1",
      "enabled": true,
      "limits": {
        "maxInputTokens": 128000,
        "maxOutputTokens": 4096,
        "timeoutMs": 30000,
        "maxConcurrency": 2
      }
    },
    {
      "id": "host.events.conversation.v1",
      "enabled": true
    }
  ]
}
```

授权摘要只用于插件运行时判断和降级，不是安全边界。

### 8.1 注入字段值类型约定

`pluginConfigJson` 与 `hostCapabilityGrantsJson` 在 init 通道下发时**值类型固定为 JSON 字符串**（与 01 文档 §8.1.1 一致）：

- Process 通道 `InitExtensions : Dictionary<string, string>` 只能放字符串值；
- Native 通道虽然可以接受嵌套对象，但同样按字符串约定，避免两通道协议规则不对等。

### 8.1.1 初版授权配置：不按 purpose 拆分

当前 `PluginModelCapabilityService.ReadSettings` 按 `Plugin:{pluginId}:Capability:llm` 单一前缀写值（一个开关、一组限额、一组限流），**没有 purpose 维度**。

为避免 settings、UI、限流三处同时改造，初版按以下口径处理：

- 授权配置 setting key 不引入 purpose 维度，继续沿用 `Plugin:{pluginId}:Capability:llm:*`。
- `requiredHostCapabilities` 中可以保留 `purpose` 字段供插件作者声明（用作日志、限流上下文标签），但不影响授权决策。
- `hostCapabilityGrantsJson` 也按单 capability ID 输出，不按 purpose 拆 grant。
- 是否在后续阶段引入 purpose 拆分作为正式开关，列入 §15 待确认问题。

这样：

- 保留向后扩展余地（grants 的 schema 已经是数组，未来加 purpose 字段不破坏现有插件）。
- 当前 UI / SystemSettingsService / 限流逻辑不需要为 purpose 改造。
- §5 记忆插件示例只声明一个 `host.llm.invoke.v1` 申请项，与本节口径一致。

#### 8.1.1.1 与 ModelPurposeKeys / ModelPurposeResolver 的并行关系

代码现状：项目里**已经存在**一套基于 setting key 的"按 purpose 选模型"机制：

- `Src/Netor.Cortana.AI/Providers/ModelPurposeKeys.cs` 定义常量：`Compaction.ModelId` / `Memory.ModelId` / `Memory.AbstractionModelId` / `Memory.ConflictModelId`
- `Src/Netor.Cortana.AI/Providers/ModelPurposeResolver.cs` 通过 `TryResolve(string settingKey)` 解析为 `IChatClient`
- 但这套机制只播种了 `Compaction.ModelId`；`Memory.ModelId` 已被 `App.axaml.cs:520 DeleteSetting("Memory.ModelId")` 删除；`Memory.AbstractionModelId` / `Memory.ConflictModelId` 从未播种

也就是说当前代码里**有两套并行的"按 purpose 选模型"机制**：

| 机制 | 位置 | 当前用途 |
|------|------|----------|
| `ModelPurposeResolver` + `ModelPurposeKeys` | `Src/Netor.Cortana.AI/Providers/` | 仅 `Compaction.ModelId` 真正在用，其它 key 是占位 |
| `PluginModelCapabilityService` + `Plugin:{pluginId}:Capability:llm:*` | `Src/Netor.Cortana.AI/Providers/PluginModelCapabilityService.cs` | 插件大模型能力授权与限额 |

两套机制设计目标不同：

- `ModelPurposeResolver` 解决"宿主自身某个内部任务用哪个模型"（例如对话压缩用专用模型）。
- `PluginModelCapabilityService` 解决"某个插件能不能用大模型 / 用哪个 / 配多少额度"。

本规划的 `requiredHostCapabilities` / `hostCapabilityGrantsJson` 落在第二条机制（`PluginModelCapabilityService`）上。**初版不合并这两套机制**：

- `Compaction.ModelId` 等"宿主自用"的 purpose 继续走 `ModelPurposeResolver`，与插件授权无关。
- 插件大模型能力一律走 `Plugin:{pluginId}:Capability:llm:*`，不再扩展 `Memory.*ModelId` 系列。
- `Memory.AbstractionModelId` / `Memory.ConflictModelId` 等未播种 key 视为历史遗留，不在本规划落地，也不要新加。后续如果 Memory 插件确实需要按 purpose 拆模型，应当走 `Plugin:cortana_memory:Capability:llm:Purpose:{purposeName}:ModelId` 这类带 plugin 前缀的 key（具体形态作为 §15 待确认问题）。

安全边界必须在宿主侧：

- `PluginModelCapabilityService` 读取授权配置并校验。
- PluginBus dispatcher 校验插件 ID、能力 ID（purpose 仅作日志维度，不参与决策）。
- 文件、通知、事件等宿主能力也应由对应宿主服务强校验。

## 9. 和 AI 上下文的关系

宿主能力申请和授权摘要不得进入：

- 系统提示词
- 智能体提示词
- 会话上下文
- 长期记忆
- 工具描述
- 工具参数 Schema

AI 只知道工具能做什么，不知道插件是否获得了某项宿主授权。

如果插件因未授权无法执行，应返回业务错误：

```text
该插件尚未获得大模型能力授权，请到插件授权设置中启用。
```

不要把授权配置、模型 ID、Provider ID、内部端点等信息返回给 AI。

## 10. 与现有实现的对齐

当前已有基础：

- `PluginSettings.Extensions`
- 插件授权页中的大模型授权配置（`PluginAuthorizationPage` + `Plugin:{pluginId}:Capability:llm:*` 前缀）
- `PluginModelCapabilityService`
- `PluginBusModelCapabilityDispatcher`
- `plugin.json` 中的 `capabilities` 字段生成逻辑（**仅 Process 通道**；Native 通道当前 plugin.json 不输出该字段，参见 §1.1）
- `PluginBusSubscriptionRegistry.SetCapabilities` 维护的 PluginBus subscribe `capabilities`（**运行时连接维度，不参与 manifest capabilities 收敛**）

后续要做的是**把 manifest capabilities 收敛为统一模型**：

```text
插件元数据声明申请
  -> 主程序授权 UI 展示
  -> SystemSettingsService / 配置存储保存授权
  -> init.extensions 下发授权摘要
  -> PluginBus / 宿主服务调用时强校验
```

> PluginBus subscribe 的 `capabilities` 字段是另一个维度（单连接动态能力声明，由 dispatcher 派发帧时使用），**不在本规划的收敛范围内**。两套 capabilities 并行存在，不互相替代。

### 10.1 init extensions 字段命名分裂的处理

Native 通道（`ExternalProcessPluginHostBase`）下发 `pluginBusEndpoint` / `pluginBusPort` / …；Process 调试通道已经进入迁移期，`PluginDebugger` 同时下发 `pluginBusEndpoint` 体系与旧 `chatWsEndpoint` / `conversationFeedEndpoint` 体系，`PluginSettings` 按新名优先、旧名回退读取。两通道的 init key 命名分裂是历史遗留。

> **注意**：这里的"分裂"历史上曾导致 §0.1 描述的真实 bug。当前 §0.1 兼容修复已落地，Process 插件可以拿到 PluginBus 字段。本节的"不在本期统一"专指**键命名规范层面**的统一（例如把 `chatWsEndpoint` 这类旧名彻底废弃）；**让两套 key 都能工作**属于兼容修复，不属于"统一"范畴。

本规划**不在本期推动键命名规范层面的统一**，原因：

- 与配置声明能力没有直接耦合，强行收敛会扩大改动面。
- 新增字段（`pluginConfigJson` / `hostCapabilityGrantsJson`）是命名空间隔离的独立 key，不卷入 PluginBus / ConversationFeed 字段命名分歧。

后续若启动 init key 统一迁移，建议作为独立提案处理：迁移期内同时下发新旧两套 key（消费端按优先级读取），避免存量插件被破坏。

## 11. 对 Generator 的要求

Generator 新增能力时必须保持兼容：

- 没有声明 `settingsSchema` 时不生成该字段。
- 没有声明 `requiredHostCapabilities` 时不生成该字段。
- 旧插件生成的 `plugin.json` 仍可被主程序识别。
- `providedCapabilities` 和现有 `capabilities` 字段的关系需要明确。

### 11.1 Native 通道的从零新增项

Native 通道当前**没有** `Capabilities` 链路（参见 §1.1）。新增 `providedCapabilities` 时需要**同时**完成以下改造：

| 位置 | 改动 |
|------|------|
| `Netor.Cortana.Plugin.Native.PluginAttribute` | 新增 `Capabilities` 属性，与 `Netor.Cortana.Plugin.PluginAttribute` 对齐 |
| `Native.Generator.Analysis.PluginClassAnalyzer` | 解析 `Capabilities` 命名参数，写入 `PluginClassInfo` |
| `Native.Generator.Analysis.PluginClassInfo` | 新增 `Capabilities` 字段 |
| `Native.Generator.Emitters.PluginJsonEmitter` | 输出 `tags` / `capabilities` / `settingsSchema` / `requiredHostCapabilities` 字段 |
| `Native.Generator.Emitters.InfoJsonEmitter` | 同步输出 `capabilities` / `requiredHostCapabilities`（与 plugin.json 不一致时以 plugin.json 为准） |

Process 通道已有 `Capabilities` 字段，重点改造点是：把现有 `capabilities` 输出迁移为 `providedCapabilities`，并在过渡期同时输出两个字段。

### 11.1.1 配套的协议层 / Wrapper / UI 改造

仅改 Generator + plugin.json 不够，capabilities 要从插件作者声明一直流到主程序 UI，需要按下表把整条链路打通：

**协议层注意点**：

- `Native` 与 `Process` 共用 `ExternalProcessPluginHostBase` 基类，基类只反序列化为 `NativePluginInfo`（`Src/Netor.Cortana.Plugin/Core/ExternalProcessPluginHostBase.cs:181`）。如果新字段只加到 `PluginInfoData` 不加到 `NativePluginInfo`，则 Process 通道 get_info 返回的字段会被静默丢弃。
- 真正的"权威 capabilities"以 plugin.json 为准（参见 01 文档 §11.1.1）：UI 渲染、§6.1 判定都读 `LoadedPluginInfo.Manifest.Capabilities`，`info.Capabilities` 仅作为 init 后的二次校验。两者不一致时记 warning，但不阻断。
- `requiredHostCapabilities` 设计为对象数组（id / required / reason / purpose），所以 `PluginManifest` 必须新增 `RequiredHostCapability` record；上述三处 `JsonSerializerContext`（PluginManifestJsonContext / NativePluginJsonContext / ProcessProtocolJsonContext）都要追加 `[JsonSerializable]`，否则 AOT 模式下 `JsonSerializer.Deserialize` 在三条路径中任意一条都会运行时抛错。
- `PluginManifest.Validate` 当前只校验 `Id` / `Name` / `Runtime`（参考 `Src/Netor.Cortana.Plugin/Core/PluginManifest.cs:101-132`），新增字段**不进 Validate**，按 §12 兼容加载策略宽松读取——格式错误记 warning、忽略字段，不阻断插件加载。

### 11.2 与现有 `capabilities` 字段的过渡

- 初期保留现有 `capabilities` 字段。
- 新增 `providedCapabilities` 作为更明确的方向性字段。
- 主程序读取时兼容两者：优先读 `providedCapabilities`，缺失时回退 `capabilities`。
- 后续再决定是否把 `capabilities` 标记为历史兼容字段。

### 11.3 手写 plugin.json 的特殊插件

并非所有插件都走 Generator 输出 plugin.json。当前已知例外：

| 插件 | 现状 |
|------|------|
| `Plugins/Src/Cortana.Plugins.ScriptRunner/plugin.json` | 仓库直接维护，不引用 `Netor.Cortana.Plugin.Process.Generator` |

这类插件**不会随 Generator 升级自动获得新字段**。规划落地时需要：

1. 通知作者按下面"手写 plugin.json 字段参考"补全字段；
2. 提供完整 schema 文档（建议 P1 配套交付）；
3. 落地 P1 时全仓搜索一遍，把所有手写 plugin.json 列入清单，避免遗漏。

**手写 plugin.json 字段参考**（与 Generator 输出口径一致）：

```jsonc
{
  // —— 必填核心字段（缺失阻断加载） ——
  "id": "your_plugin_id",
  "name": "Your Plugin",
  "version": "1.0.0",
  "runtime": "process",          // dotnet / native / process
  "command": "your-plugin.exe",  // process 必填
  // "libraryName": "your.dll",  // native 必填
  // "assemblyName": "Your.dll", // dotnet 必填

  // —— 可选元数据 ——
  "description": "...",
  "minHostVersion": "1.0.0",
  "abstractionsVersion": "1.0.0",
  "tags": ["category1", "category2"],

  // —— 本规划新增字段（可选，缺失视为空） ——
  "capabilities": ["voice.tts.v1"],            // 历史字段，过渡期保留（§11.2）
  "providedCapabilities": ["voice.tts.v1"],    // 新方向性字段（§3.1）
  "settingsSchema": [                           // 配置声明，参考 01 文档 §6
    {
      "key": "apiKey",
      "type": "secret",
      "required": true,
      "sensitive": true
    }
  ],
  "requiredHostCapabilities": [                 // 宿主能力申请（§3.2）
    {
      "id": "host.llm.invoke.v1",
      "purpose": "...",
      "required": false,
      "reason": "用户可见的中文说明"
    }
  ]
}
```

不必声明的字段全部**省略**，不要写空数组或 `null`——按 §12 兼容加载策略，缺失即视为空，含错误格式的字段会被忽略并记 warning。

## 12. 兼容加载策略

主程序加载插件元数据时建议采用宽松读取：

1. 识别已知字段。
2. 忽略未知字段。
3. 缺失可选字段时使用空集合。
4. 字段格式错误时记录 warning，并忽略该字段。
5. 只有核心字段错误才阻断加载，例如插件 ID 为空、runtime 无法识别、启动命令缺失。

不应因为配置声明或能力申请字段异常阻断整个插件加载。

## 13. 风险与防护

| 风险 | 防护 |
|------|------|
| 老插件缺少新字段导致加载失败 | 所有新字段可选，缺失视为空 |
| 插件伪造授权摘要 | 宿主每次调用强校验，摘要只作提示 |
| 能力名失控 | 建立标准能力 ID 表，未知能力忽略 |
| AI 上下文泄露授权信息 | 授权摘要不进入提示词和工具描述 |
| 用户看不懂插件为什么申请能力 | `reason` 必填或强建议填写 |
| 大模型授权被过度展示 | 只对申请 `host.llm.invoke.v1` 的插件展示 |
| required 能力未授权时插件行为异常 | 插件 init 后应检测 grants 并进入降级或禁用状态 |

## 16. 初步结论

这部分可以定义为“插件宿主能力申请与授权兼容机制”。

核心边界是：

> 新插件可以声明配置和宿主能力申请；老插件不声明也能继续运行。声明用于主程序展示和授权，真正权限由宿主运行时强校验。
