# 插件配置声明与运行时注入规划

> 状态：规划草案  
> 目标：在不大面积破坏现有 Native / Process / MCP 插件开发规则的前提下，让主程序统一承载插件设置界面、配置保存和运行时注入，并确保配置值不污染 AI 提示词、聊天上下文和长期记忆。

## 1. 背景

当前插件运行时已经具备基础初始化配置：

- `dataDirectory`
- `workspaceDirectory`
- `pluginDirectory`
- `wsPort`
- `extensions`

其中 `extensions` 已经用于下发 PluginBus 等运行时字段，例如：

- `pluginBusEndpoint`
- `pluginBusPort`
- `pluginBusProtocol`
- `pluginBusVersion`

这说明现有框架已经有“宿主在 init 阶段向插件注入运行时参数”的基础能力。新的插件配置能力应在这个方向上增量扩展，而不是推翻现有 `[Plugin]` / `[Tool]` / Generator / `PluginSettings` 规则。

## 2. 核心需求

插件可能需要大量设置，例如 API Key、服务地址、默认模型、开关项、路径、限额、账号参数、功能策略等。

期望的用户体验是：

1. 插件声明自己需要哪些设置。
2. 主程序根据声明生成或展示设置界面。
3. 用户在主程序里填写和保存配置。
4. 插件启动或重新加载时，主程序把有效配置通过初始化参数注入给插件。
5. 插件只消费配置，不需要自己提供设置界面，也不要求用户手动编辑配置文件。

## 3. 关键约束：不污染 AI 上下文

插件配置必须和 AI 上下文严格隔离。

### 3.1 禁止进入 AI 的内容

以下内容不得写入系统提示词、智能体提示词、会话上下文、长期记忆、工具描述或工具参数 Schema：

- API Key、Token、Cookie、账号密码
- 服务端点、内部端口、数据库连接串
- 本地路径、插件数据目录、工作区绝对路径
- 插件私有开关、默认参数、限额策略
- 运行时授权摘要、内部协议字段
- 任何不需要 AI 决策的执行环境信息

### 3.2 AI 可以看到的内容

AI 只应该看到工具能力和业务参数：

- 工具名称
- 工具描述
- 工具业务参数
- 参数说明、是否必填、类型

示例：

```json
{
  "name": "google_search",
  "description": "搜索网页内容",
  "parameters": [
    {
      "name": "query",
      "type": "string",
      "description": "搜索关键词",
      "required": true
    }
  ]
}
```

AI 不需要知道该搜索工具使用哪个 `apiKey`、`endpoint`、`region` 或 `maxResults`。这些值由插件在内部读取运行时配置后自行组合。

### 3.3 三条通道隔离

| 通道 | 消费者 | 内容 | 是否进入 AI 上下文 |
|------|--------|------|--------------------|
| 配置声明通道 | 主程序设置 UI | 字段名、类型、默认值、校验规则、是否敏感 | 否 |
| 配置值通道 | 主程序与插件 | 用户保存的真实配置值、运行时合并后的有效配置 | 否 |
| 工具调用通道 | AI 与插件工具 | 用户意图参数，如 `query`、`fileName`、`city` | 是，仅限工具 Schema 和调用参数 |

### 3.4 AI 自我调节工具的边界

§3.1 / §3.3 的硬约束是"配置项不作为 AI 工具参数"，但代码现状里有两种**接近但不违规**的用法需要单独区分：

**反模式（明确禁止）** — 把环境性、敏感性配置当作工具参数让 AI 处理：

```text
google_search_set_config(api_key, search_engine_id)   ❌
db_connect(connection_string)                         ❌
plugin_set_endpoint(url, token)                       ❌
```

这类配置应迁移到 §6 的 `settingsSchema`，由用户在主程序设置页填写，永远不进 AI 视野。

**允许（AI 自我调节用户偏好）** — 让 AI 通过工具读写**插件运行时偏好**，AI 根据用户对话意图调整业务策略：

```text
memory_get_settings()         ✅  AI 查看记忆体系当前策略
memory_update_setting(...)    ✅  根据"记忆太多了""召回不够精准"调整阈值
memory_supply_set_topk(n)     ✅  上下文供应数量
```

判定规则（同时满足才允许暴露给 AI）：

1. **不含敏感凭据**：参数与返回都不能含 API Key、Token、Cookie、连接串、绝对敏感路径。
2. **业务语义**：调整的是插件业务策略（阈值、开关、限额、行为模式），不是环境/连接信息。
3. **用户意图驱动**：典型触发词是"记得太多""不够精准""关闭推荐"——AI 是把用户语言翻译成业务参数，不是替用户做隐私决策。
4. **可观测**：调整后用户在主程序设置页能看到结果（与 `settingsSchema` 双向同步），AI 不会在用户不知情的情况下改写设置。

**实现约束**：

- 这类工具暴露的字段应当与 `settingsSchema` 中标记为 `sensitive: false` 的字段子集一一对应。
- 敏感字段（`sensitive: true`）即使语义合理也不能由 AI 工具读写——例如不能让 AI 调用 `memory_update_setting("api_key", "...")` 改 API Key。
- 插件作者实现这类工具时，应在工具内部对入参做白名单过滤：把不在白名单里的 key 直接拒绝。

## 4. 设计边界

### 4.1 插件负责

- 声明配置 Schema。
- 使用 `PluginSettings` 或强类型 Options 读取运行时配置。
- 在插件内部完成配置校验、默认值兜底和错误翻译。
- 避免在工具返回、异常消息和日志中泄露敏感配置。

### 4.2 主程序负责

- 读取插件声明的配置 Schema。
- 生成或组织插件设置界面。
- 保存配置值。
- 按作用域合并配置。
- 在插件初始化时通过私有运行时通道注入配置。
- 确保配置值不进入 AI 上下文、提示词、长期记忆和工具描述。

### 4.3 AI 负责

- 根据工具描述选择工具。
- 提供业务参数。
- 不参与插件运行配置的选择、保存、展示和传递。

## 5. 与当前插件开发规范的兼容关系

本规划是增量能力，不改变现有插件开发主线。

| 当前规范 | 保持方式 |
|----------|----------|
| Native / Process 仍通过 `[Plugin]` 声明入口 | 保持，不要求插件作者改成手写协议 |
| 工具仍通过 `[Tool]` 类和 `[Tool]` 方法暴露 | 保持，配置项不作为工具参数暴露给 AI |
| `plugin.json` 由 Generator 输出 | 保持，不要求开发者手写 `plugin.json` |
| Process 插件仍由 Generator 生成消息循环、工具路由和 Debugger | 保持 |
| Native 插件仍由 Generator 生成导出函数、工具路由和清单 | 保持 |
| 插件目录、数据目录、工作区目录仍由宿主注入 | 保持，继续通过 `PluginSettings` 访问 |
| `PluginSettings.Extensions` 继续作为 init 扩展槽位 | 保持，但需要区分宿主运行时字段和用户配置字段。02 文档 §0.1 的 Process 通道读取兼容已补齐：SDK 优先读 `pluginBusEndpoint` 系列，缺失时回退 `chatWsEndpoint` / `conversationFeedEndpoint` 系列 |
| MCP 插件不走 Native / Process 包安装规则 | 保持，MCP 配置仍由主程序连接配置管理 |

## 6. 配置声明模型

插件配置声明只描述“需要什么配置”，不包含真实配置值。

建议字段：

| 字段 | 说明 |
|------|------|
| `key` | 配置键，插件内唯一 |
| `label` | 设置界面显示名称 |
| `description` | 给用户看的说明，不给 AI |
| `type` | `string` / `number` / `boolean` / `enum` / `path` / `secret` / `json` |
| `defaultValue` | 默认值，敏感字段默认不建议写入 |
| `required` | 是否必填 |
| `sensitive` | 是否敏感，敏感值不回显、不写日志 |
| `scope` | 支持的配置作用域 |
| `validation` | 长度、范围、格式、枚举项等校验规则 |
| `restartRequired` | 修改后是否必须做插件级重启（强制提示用户）。当通道默认 reload 路径（杀子进程重启）已经可以应用新配置时不需声明；声明后会跳过自动 reload，详见 §14.P6 |

示例：

```json
{
  "settingsSchema": [
    {
      "key": "apiKey",
      "label": "API Key",
      "type": "secret",
      "required": true,
      "sensitive": true,
      "scope": ["global", "workspace", "agent"],
      "validation": {
        "minLength": 8,
        "maxLength": 256
      }
    },
    {
      "key": "maxResults",
      "label": "默认结果数量",
      "type": "number",
      "defaultValue": 5,
      "validation": {
        "min": 1,
        "max": 20
      }
    }
  ]
}
```

## 7. 配置值模型

配置值由主程序私有保存，不进入插件公开元数据。

### 7.1 长期目标作用域

理论上配置值合并存在以下作用域，由低优先级到高优先级覆盖：

1. 插件默认值（来自 Schema）。
2. 全局插件配置。
3. 工作区覆盖配置。
4. 智能体覆盖配置。
5. 本次运行临时配置。

合并后的结果称为“有效配置”。只有有效配置会在插件初始化时注入给插件。

### 7.2 初版收敛范围（与现状对齐）

主程序当前的 `SystemSettingsService` 是平 KV 存储，没有工作区/智能体维度（参考 `PluginModelCapabilityService.ReadSettings` 已经按 `Plugin:{pluginId}:Capability:llm` 单层前缀写值）。一次到位实现五层覆盖会同时改动设置存储、UI、合并算法和插件 init 通道，工程量过大。

因此初版只落地两层：

| 阶段 | 作用域 | 存储位置 |
|------|--------|----------|
| P1–P4 初版 | 插件默认值 + 全局插件配置 | 复用 `SystemSettingsService`，新前缀 `Plugin:{pluginId}:Config:{key}` |
| 后续阶段 | 追加工作区、智能体、临时覆盖 | 由对应作用域服务接管，新表或新前缀 |

§16 待确认问题已不再列入"作用域支持范围"——本节已经给出分阶段口径。

## 8. Init 注入方式

当前已有 `InitConfig.Extensions` 和 `PluginSettings.Extensions`，可以继续使用，但建议做命名空间分区，避免把所有字段都混在同一层。

### 8.1 当前兼容字段

Native 通道（`ExternalProcessPluginHostBase`）下发的字段：

```json
{
  "extensions": {
    "pluginBusEndpoint": "ws://localhost:65321/internal",
    "pluginBusPort": "65321",
    "pluginBusProtocol": "cortana.plugin-bus",
    "pluginBusVersion": "1.2.0"
  }
}
```

Process 调试通道（`PluginDebugger`）当前处于迁移期，会同时写新旧两套 key：

```json
{
  "extensions": {
    "pluginBusEndpoint": "ws://localhost:65321/internal",
    "pluginBusPort": "65321",
    "pluginBusPath": "/internal",
    "pluginBusProtocol": "cortana.plugin-bus",
    "pluginBusVersion": "1.2.0",
    "chatWsEndpoint": "ws://localhost:65321/ws/",
    "conversationFeedEndpoint": "ws://localhost:65321/internal/conversation-feed/",
    "conversationFeedProtocol": "conversation-feed",
    "conversationFeedVersion": "1.0.0"
  }
}
```

两通道字段命名分裂是历史遗留。本规划只**沿用**当前两套字段，不在此处推动统一。当前 Process 端已进入迁移期：`PluginDebugger` 同时下发新旧两套 key，`PluginSettings` 优先读取 `pluginBusEndpoint` 体系，缺失时回退旧名，避免存量插件被破坏。后续如果要彻底废弃旧名，应由 init 通道命名规范的独立提案承载，不阻塞配置声明能力。

### 8.1.1 Native 与 Process 在 extensions 字典上的协议差异

两通道的 init extensions 字典对值类型的支持不一致：

| 通道 | 值类型 | 嵌套对象处理 |
|------|--------|--------------|
| Process | `Dictionary<string, string>`，仅 string（参考 `InitConfig.cs` 中 `InitExtensions`） | 不能直接放嵌套 JSON 对象，必须由宿主先序列化为字符串 |
| Native | dictionary 值实际经过 `PluginSettings.ReadExtensions`，对非 string 走 `GetRawText()` | 能直接吃嵌套 JSON 对象 |

为避免两通道协议规则不对等，本规划下发的所有新字段（包括 §8.2 的 `pluginConfigJson`、02 文档定义的 `hostCapabilityGrantsJson`）**统一约定值类型为 JSON 字符串**：宿主负责序列化，插件侧负责反序列化。这样：

- 不需要扩张 Process 端 `InitExtensions` 字典的值类型；
- 不依赖 Native 端 `GetRawText()` 行为；
- 两通道可以共用同一段 `extensions["pluginConfigJson"] = JsonSerializer.Serialize(...)` 注入代码。

### 8.2 新增配置字段建议

新增用户配置建议使用独立前缀或 JSON 字符串，避免和宿主运行时字段冲突。

方案 A：扁平前缀。

```json
{
  "extensions": {
    "config.apiKey": "***",
    "config.maxResults": "5",
    "config.safeSearch": "true"
  }
}
```

方案 B：单字段 JSON。

```json
{
  "extensions": {
    "pluginConfigJson": "{\"apiKey\":\"***\",\"maxResults\":5,\"safeSearch\":true}"
  }
}
```

建议初版优先采用方案 B：

- 不破坏现有字符串字典结构。
- 复杂配置更容易表达。
- 不需要为每个插件配置项扩展 `PluginSettings` 属性。
- 更符合已有“复杂 JSON 由宿主写入 JSON 字符串，插件侧自行反序列化”的方向。

## 9. 插件侧消费方式

### 9.1 简单读取

小插件可以继续读取：

```csharp
settings.Extensions["pluginConfigJson"]
```

然后反序列化为自己的配置类型。

### 9.2 强类型 Options

复杂插件建议在 Composition 层绑定为强类型 Options：

```csharp
public sealed class SearchPluginOptions
{
    public string ApiKey { get; init; } = string.Empty;
    public int MaxResults { get; init; } = 5;
    public bool SafeSearch { get; init; } = true;
}
```

工具类不直接读取字符串字典，而是依赖应用服务或 Options：

```csharp
[Tool]
public sealed class SearchTools(SearchService searchService)
{
    [Tool(Description = "搜索网页内容")]
    public Task<string> SearchAsync(
        [Parameter(Description = "搜索关键词")] string query)
        => searchService.SearchAsync(query);
}
```

这样工具参数保持干净，AI 只提供 `query`。

### 9.3 AOT 插件的反序列化注意事项

Native AOT 插件不能直接调用 `JsonSerializer.Deserialize<T>(json)`，否则 Trim 与 AOT 警告会阻断发布。插件作者必须为 Options 类型显式提供 `JsonSerializerContext`：

```csharp
[JsonSerializable(typeof(SearchPluginOptions))]
internal partial class PluginConfigJsonContext : JsonSerializerContext;

// 反序列化
var options = JsonSerializer.Deserialize(
    settings.Extensions["pluginConfigJson"],
    PluginConfigJsonContext.Default.SearchPluginOptions);
```

Process 插件可以放宽：JIT 进程允许使用反射式 `Deserialize<T>`，但仍建议沿用 Source Generator 路径，保持两通道开发体验一致。

宿主侧序列化时同样使用 `JsonSerializerContext`，统一从单一 schema 走 round-trip，避免命名策略不一致。

## 10. 配置 Schema 的承载方式

需要避免破坏“不要手写 `plugin.json`”规则。

可选方案：

### 10.1 Attribute 声明

新增 `[PluginSetting]` 等 Attribute，由 Generator 扫描后写入 `plugin.json` 与 `get_info`（**plugin.json 为权威载体**，详见 §11.1.1）。

由于 Attribute 参数只能是常量，复杂 Schema 需要按"每字段一个 Attribute"展开：

```csharp
[Plugin(Id = "google_search", Name = "Google 搜索")]
[PluginSetting(Key = "apiKey", Type = PluginSettingType.Secret, Required = true, Sensitive = true)]
[PluginSetting(Key = "maxResults", Type = PluginSettingType.Number, DefaultValue = "5", ValidationMin = 1, ValidationMax = 20)]
public static partial class Startup;
```

优点：

- 贴合当前 Generator 模式。
- 插件作者体验统一。
- 不要求手写清单。

风险：

- Attribute 参数只能是 const / typeof / 数组字面量等基本类型，复杂 `validation` 规则要拆成扁平字段（如 `ValidationMin` / `ValidationMax` / `ValidationPattern`），表达力受限。
- Generator 需要新增分析逻辑。

### 10.2 静态方法声明

插件入口提供一个可选静态方法，例如：

```csharp
public static IReadOnlyList<PluginSettingDescriptor> ConfigureSettings()
```

**约束**：该方法仅作为 Source Generator 的语法分析对象，Generator 在编译期通过 `SyntaxNode` 扫描方法体内的常量初始化和集合表达式提取 Schema。**不允许在运行期调用**——任何运行期调用方案都违反 §11.1 的 AOT 约束（运行期反射插件类型）。

如果方法体超出 Generator 静态分析能力（例如循环构造、调用其它方法），Generator 必须报错而不是回退到运行期调用。

优点：

- 表达力强于 Attribute。
- 复杂 Schema 更容易组织成对象字面量。

风险：

- Generator 静态分析门槛高，需要配套诊断（如 CPPG 系列）告诉作者哪些写法不被接受。
- 如果作者写出 Generator 无法分析的表达式，必须 fail-fast 而非降级到反射，否则 AOT 边界被打破。

### 10.3 独立配置 Schema 文件

允许插件包携带 `settings.schema.json`，但不要求用户手写 `plugin.json`。

优点：

- 表达力强。
- 与主程序 UI 生成天然匹配。

风险：

- 多一个文件，插件开发和发布脚本需要纳入校验。
- 需要避免回到“开发者维护手写清单”的旧问题。

### 10.4 初版建议

初版建议优先选择 Attribute 或静态方法，并由 Generator 合并到插件元数据中。

独立文件可以作为高级扩展，但不作为初版主路径。

## 11. 设置 UI 生成与 AOT 边界

主程序根据插件配置声明生成设置界面，本身不会必然影响 AOT。风险点不在“动态生成 UI”，而在“运行时通过反射扫描插件类型、读取配置类、调用插件内部方法来推断界面”。

因此设置 UI 必须采用数据驱动模型：

```text
插件源码声明配置 Schema
  -> Generator 在编译期提取
  -> 输出到插件元数据
  -> 主程序读取元数据
  -> 主程序按字段类型生成设置 UI
```

主程序不应该在运行时做：

- 反射扫描插件程序集里的 Options 类型。
- 反射读取插件类属性来生成 UI。
- 反射调用插件内部方法来获取配置项。
- 依赖 `Type.GetProperties()`、`Assembly.GetTypes()` 这类动态发现能力推导配置界面。
- 为了 UI 生成而要求插件暴露运行时配置对象给宿主。

允许的做法是：

- 主程序只读取插件元数据中的 `settingsSchema`。
- `settingsSchema` 是普通 JSON / DTO 数据。
- UI 控件由 `type`、`validation`、`required`、`sensitive` 等字段决定。
- 插件配置值由主程序保存并在 init 时注入。
- 插件内部如果要绑定强类型 Options，应在插件自己的 Composition 层完成，不能反过来让主程序反射这个 Options 类型。

### 11.1 对 Native AOT 的影响

Native AOT 插件尤其要避免运行时反射。配置 Schema 的提取应发生在编译期，由 Source Generator 完成。

推荐路径：

```text
[PluginSetting] / 配置声明方法
  -> Generator 编译期分析
  -> get_info / plugin.json / 插件元数据包含 settingsSchema
  -> 主程序读取 settingsSchema JSON
```

这样主程序看到的是静态元数据，不需要加载插件类型，也不需要反射插件代码。

### 11.1.1 settingsSchema 在 Native 通道上的载体选择

Native 通道当前两条静态/动态元数据路径并不对等：

| 载体 | 当前内容（参考 `PluginJsonEmitter` / `InfoJsonEmitter`） | 读取时机 |
|------|----------------------------------------------------------|----------|
| `plugin.json`（落盘） | id / name / version / description / runtime / libraryName / minHostVersion | 不加载插件即可读 |
| `cortana_plugin_get_info` 导出函数返回 JSON | id / name / version / description / instructions / tags / tools | 必须 LoadLibrary 后调用导出函数 |

也就是说现状下 tags / tools 这类“富元数据”并不在 plugin.json 里，而在 dll 的 get_info 返回里。Process 通道的 plugin.json 已经写 tags / capabilities，两通道 plugin.json 的承载范围本身就不对称。

为不破坏 §11 “主程序读取静态元数据，不必加载插件”的硬约束，本规划采用以下方案：

- **Native plugin.json 必须扩展**，由 `PluginJsonEmitter` 输出 `tags` / `capabilities` / `settingsSchema` / `requiredHostCapabilities`，使其成为完整静态元数据。落地工作在 P1。
- `get_info` 同时返回这些字段，作为 Native dll 加载后的二次校验通道；二者**不一致时以 plugin.json 为准**（因为 UI 渲染只读 plugin.json）。
- Process 通道 plugin.json 已有 tags / capabilities，按同样方式扩展 `settingsSchema` / `requiredHostCapabilities`。
- 插件 Attribute / Generator 模型同步扩展：
  - Native 端 `PluginAttribute` 当前**没有 `Capabilities`**（Process 端有），需在 P1 阶段补齐。
  - Native Generator 的 `PluginClassInfo` 同步增加 `Capabilities` 字段并被 `PluginJsonEmitter` / `InfoJsonEmitter` 读取。

只有这样，主程序设置 UI 才能在“仅扫描 plugin.json”的前提下渲染插件配置界面，不依赖加载插件本体。

### 11.1.2 Native plugin.json 通过 `AddSource` + `.targets` 落盘的字符串注意点

Native 通道生成 plugin.json 的链路是：

```text
NativePluginGenerator.Execute
  -> PluginJsonEmitter.Emit  // 拼接 "//{ ... //}" 注释包裹的 C# 源码
  -> SourceProductionContext.AddSource("plugin.json", source)
  -> Roslyn 把 generated/.../plugin.json.cs 落盘
  -> Netor.Cortana.Plugin.Native.Generator.targets 在 Build / Publish 阶段调用 StripCommentPrefix Task
  -> 把每行的 "// " 前缀去掉后写到 OutputPath/plugin.json
```

settingsSchema 中的字段（如 `description`、`defaultValue`、`enum` 选项）允许出现自然语言、URL、JSON 字面量等任意字符。这条机制有两个边界：

- 整个 JSON 必须在生成时**全部以 `//`+空格前缀逐行包裹**，否则 `.targets` 的去前缀不会触达。
- 字段值若包含独立成行的 `//` 字符（典型如多行 description 中带有注释样写法），去前缀步骤会错误删除它，导致最终 plugin.json 损坏；C# 编译期也可能因为 `//`+空格包裹的内容重新进入注释模式而打断后续行。

为避免这两个问题，Generator 的 `PluginJsonEmitter` 在新增 settingsSchema 输出时必须遵守：

- 所有字符串值在序列化时按 JSON 规则 escape，特别是 `"`、`\`、控制字符和 `//`；
- 嵌套对象（settingsSchema 数组、validation 对象）建议**单行紧凑 emit**，不要按可读性换行——多行越多，落到 `.targets` 去前缀环节出错的概率越高；
- `PluginSettingType.Json` 的 `DefaultValue` 已在 Native / Process Generator 分析阶段做 fail-fast 校验；非法 JSON 会分别报 `CNPG021` / `CPPG021`，不再继续生成可能损坏的 `plugin.json` 或 get_info 元数据；
- 单元测试或 Generator snapshot 测试中加入"description 含 `//`、`"`、换行"的样例，校验最终 plugin.json 仍能被 `JsonSerializer.Deserialize` 反序列化。

Process 通道目前也走同一注释包裹机制（参考 `Process.Generator.PluginJsonEmitter`），同样适用本节约束。

### 11.1.3 Native Debugger / 快速开发框架的 AOT 边界豁免

`Netor.Cortana.Plugin.Native.Debugger`（目录名 `Src/Plugins/Netor.Cortana.Plugin.Native.Debuger`，少一个 g）是 Native 通道的**开发期快速调试框架**，给插件作者提供 REPL 与零配置启动：

```csharp
await PluginDebugRunner.RunAsync(options => options.WsPort = 12841);
```

它**整体走运行期反射**：

- `PluginDebugRunner.DiscoverPluginAssembly`（参考 `Src/Plugins/Netor.Cortana.Plugin.Native.Debuger/PluginDebugRunner.cs:46-66`）扫输出目录所有 dll，`Assembly.Load` 后用反射找 `[Plugin]`；
- `PluginScanner.TryScan`（同包 `Discovery/PluginScanner.cs:48`）走 `assembly.GetTypes()` + `GetCustomAttribute<PluginAttribute>()`；
- `DebugPluginHost`（`Hosting/DebugPluginHost.cs:59-62`）反射调用 `Configure(IServiceCollection)` 静态方法。

这与 §11 "主程序读取静态元数据，不必加载插件"的硬约束**看似冲突**，但实际**不在硬约束的边界内**：

| 角色 | AOT 边界 |
|------|----------|
| Cortana 主程序 / `PluginAuthorizationPage` / `PluginLoader` | **必须**走 plugin.json 静态元数据，不允许反射插件类型 |
| `Cortana.NativeHost.exe` 子进程 | 由 `NativeLibrary.Load` 加载 dll；这是 dll 自己的导出函数调用，本来就不走托管反射 |
| `Netor.Cortana.Plugin.Native.Debugger`（开发期工具） | **豁免**——只在插件作者本地的 console 应用里用，不进生产部署 |

实施约定：

- Debugger 包**不应**被主程序、`Cortana.NativeHost.exe` 引用；只允许插件作者的测试/调试 console 项目引用。
- Debugger 自己**不需要** AOT 兼容；保留运行期反射是合理的。
- 插件作者发布生产构建时，应当走 Native AOT 路径（dll 由 NativeHost 加载），不带 Debugger 包。
- 关于"Generator 必须 fail-fast 不允许降级到反射"（§10.2）的约束**不适用于 Debugger**——那是规约 Generator 阶段的，Debugger 是独立工具链。

`PluginDebugRunner.IsFrameworkAssembly`（同文件第 84 行）对 `Netor.Cortana.Plugin.Native.*` 命名空间整体做前缀过滤——如果未来在该命名空间下添加业务代码，Debugger 会**误过滤**为框架程序集。文档约定：业务代码走 `Cortana.Plugins.*` / `Netor.Cortana.Plugin.<业务名>`，不要占用 `Netor.Cortana.Plugin.Native.*` 子空间。

### 11.2 对 Process 插件的影响

Process 插件虽然可以是 JIT exe，但也应沿用同一规则：

- 不因为 Process 能反射就引入反射式设置发现。
- 继续由 Generator 或明确的元数据输出配置 Schema。
- 保持 Native / Process 两条通道的开发体验一致。

### 11.3 对主程序的影响

主程序设置页可以是动态表单，但它的动态性来自 Schema 数据。

示例映射：

| Schema type | UI 控件 |
|-------------|---------|
| `string` | 单行输入框 |
| `secret` | 密码/密钥输入框，默认遮蔽 |
| `number` | 数字输入框或步进器 |
| `boolean` | 开关 |
| `enum` | 下拉框或分段选择 |
| `path` | 路径输入 + 选择按钮 |
| `json` | 多行编辑器，可选 JSON 校验 |

这属于主程序 UI 层的数据驱动渲染，不要求插件侧反射，也不破坏 AOT。

### 11.4 结论

设置界面生成不会天然破坏 AOT；只要遵守下面规则即可：

> 配置界面基于插件元数据 Schema 生成，不基于运行时反射生成。

这条规则应作为插件配置系统的硬约束。

## 12. 日志与错误处理

需要增加统一脱敏规则：

- 敏感字段不写日志。
- 敏感字段不回显到设置界面明文。
- 工具异常不能返回完整连接串、Token、Cookie、绝对敏感路径。
- 插件向 AI 返回错误时，只返回用户可理解的业务错误。
- 详细诊断进入宿主日志时也需要脱敏。

示例：

```text
错误：搜索服务未配置 API Key，请到插件设置中完成配置。
```

不要返回：

```text
错误：请求 https://xxx?key=真实密钥 失败。
```

## 13. 权限与授权关系

配置注入不等同于工具授权。

需要保持两件事分离：

- 插件是否启用、是否绑定给某个智能体：由主程序工具列表和授权系统决定。
- 插件如何执行：由插件运行时配置决定。

不要通过提示词告诉 AI“某插件启用了某配置”。AI 能否调用工具，应该由主程序实际注入给模型的工具列表决定。

## 14. 分阶段落地建议

### P0：文档与边界确认

- 确认配置不进入 AI 上下文的硬约束。
- 确认 `PluginSettings.Extensions` 继续作为运行时注入槽位。
- 确认配置 Schema 与配置 Value 分离。
- 确认设置 UI 只能基于元数据 Schema 生成，不能运行时反射插件类型。

### P1：配置声明元数据

实施状态：基础链路已落地。Native / Process SDK 已新增 `[PluginSetting]` 与 `PluginSettingType`，Generator 会把声明写入 `plugin.json` 与 `get_info` 的 `settingsSchema`；plugin.json 仍作为权威静态载体。

- 为 Native / Process 设计配置 Schema 声明方式（Attribute 优先，见 §10.4）。
- **补齐 Native 通道 Capabilities 字段**：在 `Netor.Cortana.Plugin.Native.PluginAttribute` 上新增 `Capabilities`，让 Native 与 Process 的 PluginAttribute 在 capability 维度对齐（参考 02 文档 §11.1）。
- **扩展 Native plugin.json 输出**：让 `PluginJsonEmitter` 输出 tags / capabilities / settingsSchema / requiredHostCapabilities，使 plugin.json 成为完整静态元数据载体。
- Generator 同步把 settingsSchema 写入 plugin.json 与 get_info；二者不一致时以 plugin.json 为准。
- 主程序能读取 Schema，但暂不生成复杂 UI。
- 验证配置 Schema 输出路径对 Native AOT 友好。

### P2：主程序配置存储

实施状态：全局插件配置存储已落地。配置仍使用 `Plugin:{pluginId}:Config:{key}` 前缀写入 `SystemSettingsService`；`type: secret` 或 `sensitive: true` 的字段保存时会转换为带版本前缀的本地受保护值，运行时注入前再还原为明文 JSON 值；历史明文值继续兼容读取。

- 增加插件配置存储。**初版只落地"插件默认值 + 全局插件配置"两层（§7.2）**，前缀 `Plugin:{pluginId}:Config:{key}`。
- 工作区、智能体、临时三层覆盖**不在初版范围**，留作后续阶段，由对应作用域服务接入。
- 敏感字段加密或走安全存储。

### P3：设置 UI

实施状态：基础 UI 已落地到插件管理页。当前支持 string / secret / number / boolean / enum / path / json 的基础编辑、保存、敏感字段不回显；保存前已支持 `required` 必填校验、number `validation.min/max` 范围校验、文本类字段 `validation.minLength/maxLength` 长度校验、`validation.pattern` 正则校验、json 格式校验与 enum 选项合法性校验。`type: secret` 与 `sensitive: true` 字段会按敏感输入处理并写入受保护存储。字段依赖和更复杂的格式校验仍留作后续增强。

- 插件详情页展示配置项。
- 支持校验、保存、敏感字段遮蔽。
- 修改后按 §14.P6 reload 路径处理。
- UI 生成只读取 Schema DTO，不加载插件类型、不反射插件 Options。

### P4：运行时注入

- 主程序合并有效配置。
- 通过 `extensions.pluginConfigJson` 注入插件，**值类型固定为 JSON 字符串**（§8.1.1）。
- 插件侧提供读取辅助方法或 Options 绑定工具。

### P4.1 配置注入的具体落地点（与现有代码对齐）

注入链路涉及以下现有类型，落地时按顺序改造：

| 步骤 | 现有代码 | 改造方向 |
|------|----------|----------|
| 1. 配置存储 | `SystemSettingsService`（平 KV） | 按 §7.2 的前缀 `Plugin:{pluginId}:Config:{key}` 读写 |
| 2. 配置 Provider | 已落地 `IPluginRuntimeConfigProvider` / `PluginRuntimeConfigProvider` | `BuildPluginConfigJson(pluginId, manifest)` 合并 `settingsSchema` 默认值与 `SystemSettingsService` 中的 `Plugin:{pluginId}:Config:{key}` |
| 3. 上下文携带 | `Netor.Cortana.Plugin.PluginContext`（持有 dataDir / loggerFactory / httpClientFactory / appPaths / pluginBusPort） | 通过 DI 让 `PluginLoader.LoadProcessPluginAsync` / `LoadNativePluginAsync` 拿到 `IPluginRuntimeConfigProvider`；**不在 `PluginContext` 上加新字段**，避免污染现有上下文契约 |
| 4. init 注入点 | `ExternalProcessPluginHostBase.InitializePluginAsync`（构造 `NativePluginInitConfig.Extensions`） | 在构造 extensions 字典时，调用 `IPluginRuntimeConfigProvider.BuildPluginConfigJson(info.Id, Manifest)`，写入 `extensions["pluginConfigJson"]` 与 `extensions["hostCapabilityGrantsJson"]` |
| 5. 插件侧消费 | `PluginSettings.Extensions` | §9 已规定：插件按需读取 `Extensions["pluginConfigJson"]` 并自行反序列化，不为每个字段加强属性 |

注入发生在 `get_info` 之后、`init` 之前——这一时序在 `InitializePluginAsync` 里已经存在（先 get_info 拿到 plugin id，再用 id 构造 init config）。配置 provider 的查询入参也只能是 plugin id，不依赖 manifest，因为在这个时点 manifest 已经从 plugin.json 读出，但配置归属应当用 `info.Id`（来自 get_info）作为权威 id。

**调试器路径**（`PluginDebugger`）不走 `PluginLoader` 与 `ExternalProcessPluginHostBase`，而是通过 `Pipe` 直连插件循环（参考 `Src/Plugins/Netor.Cortana.Plugin.Process/Debugging/PluginDebugger.cs:84-105`）。`InitAsync(InitConfig)` 的重载允许调用方手动注入测试用 `pluginConfigJson` / `hostCapabilityGrantsJson`，**不强制经过 `IPluginRuntimeConfigProvider`**——避免 self-test 反过来依赖宿主侧 SystemSettingsService。

**Native Debugger / 快速开发框架路径**（`Netor.Cortana.Plugin.Native.Debugger`）也不走 `PluginLoader` 与 `Cortana.NativeHost.exe`，而是通过反射在同一 console 进程内直接构建插件 DI 容器（参考 `Src/Plugins/Netor.Cortana.Plugin.Native.Debuger/Hosting/DebugPluginHost.cs:88-100`）。历史上 `RegisterPluginSettings` 写的 JSON 只含 `dataDirectory` / `workspaceDirectory` / `pluginDirectory` / `wsPort`，**没有 extensions 字段**，导致 Debugger 与生产宿主行为不一致。该项已落地：`DebugOptions.Extensions` 会透传到 init JSON 的 `extensions` 节，插件作者可在 Debugger 中模拟 `pluginConfigJson` / `hostCapabilityGrantsJson`。

| 历史现状 | 当前结果 |
|----------|----------|
| `DebugOptions` 持 `DataDirectory` / `WorkspaceDirectory` / `PluginDirectory` / `WsPort` | 已新增 `IDictionary<string, string>? Extensions` 字段，允许调用方写入 `pluginConfigJson` / `hostCapabilityGrantsJson` |
| `DebugPluginHost.RegisterPluginSettings` 历史上只写目录与端口字段 | 已把 `options.Extensions` 透传进 `extensions` 节，与 `ExternalProcessPluginHostBase.InitializePluginAsync` 输出格式对齐 |
| `PluginDebugRunner.RunAsync(options => ...)` 调用约定 | 使用方可写 `options.Extensions = new Dictionary<string,string> { ["pluginConfigJson"] = "{...}" }` 模拟生产配置 |

约束与 Process Debugger 一致：

- 调用方手动注入测试值，**不强制经过 `IPluginRuntimeConfigProvider`**——Debugger 是开发期工具，不应反向依赖宿主 SystemSettingsService。
- 注入的字段名与生产路径完全一致（`pluginConfigJson` / `hostCapabilityGrantsJson`），保证调试通过的代码路径与生产一致。
- §11.1.3 已豁免 Debugger 的 AOT 反射约束；本节改造不破坏 Debugger 的运行期反射方式。

### P6：配置变更后的 reload 路径

代码现状：当前 Native 与 Process 通道**都通过 `ExternalProcessPluginHostBase` 启动子进程**（Native 启动 `Cortana.NativeHost.exe` 子进程加载 dll，Process 启动插件 exe）——**Cortana 主进程内不存在直接 LoadLibrary 的路径**。所以两个通道的 reload 难度其实相同：杀子进程并重启即可。

| 通道 | 子进程托管方式 | 初版策略 |
|------|----------------|----------|
| Process 插件 | `ExternalProcessPluginHostBase` 启动插件 exe | 配置保存后自动 reload，提示用户进度 |
| Native 插件 | `ExternalProcessPluginHostBase` 启动 `Cortana.NativeHost.exe` 子进程，由它 `NativeLibrary.Load` 加载 dll | 配置保存后自动 reload，提示用户进度 |

`PluginSettingDescriptor.RestartRequired` 字段保留，但**不再以"Native AOT 不能卸载"为论据**。该字段的语义改为"插件本身的内部资源（连接池、缓存模型、文件句柄、长链接）改不了配置"——由插件作者按需声明，与通道类型无关。

### P6.1 reload 触发器（SystemSettings → PluginLoader 事件链）

实施状态：UI 直连触发器已落地。`PluginLoader` 已新增 `ReloadPluginByIdAsync(pluginId)`；插件管理页保存非 `restartRequired` 配置后会调用该入口重载插件，`restartRequired` 配置仅提示下次启动生效。reload 结果会回传给 UI：配置值保存后不做自动回滚；若插件目录加载失败、manifest 无效或进程未成功暴露插件实例，则提示"配置已保存，但插件重载未成功"，避免把失败 reload 误报为成功。

历史现状中 `PluginLoader` 的 reload 入口只有两个：

- `ReloadPluginAsync(string pluginDirName)` — 按目录名 reload，由 `FileSystemWatcher` 触发
- `ReloadAllPluginsAsync()` — 工作目录切换时全量重扫

**不存在"配置变更 → reload 单个插件"的链路**。落地 P6 时需要新增：

1. `PluginLoader` 增加按 `pluginId` reload 的入口（现有按目录名 reload 不够，因为配置 UI 拿到的是插件 id 而不是目录名）；
2. `PluginAuthorizationPage` / 配置保存按钮 → 取得 `pluginId` → 调用 `PluginLoader.ReloadPluginByIdAsync(pluginId)`；
3. 若插件 `RestartRequired` 为 true，则不自动 reload，显示"修改将在下次启动 Cortana 后生效"提示。

事件链不必走 EventHub，因为 reload 是 UI 直接发起的同步动作，不是后台事件订阅场景。

## 15. 当前不做的事

初版不建议做：

- 不让插件自己提供设置窗口。
- 不把配置项变成 AI 工具参数（"AI 自我调节用户偏好"是例外，详见 §3.4）。
- 不把配置值拼进智能体提示词。
- 不要求插件作者手写 `plugin.json`。
- 不大面积修改现有 `[Plugin]` / `[Tool]` 开发方式。
- 不为每个配置字段新增 `PluginSettings` 强属性。
- 不在工具描述中暴露配置细节。
- 不通过运行时反射扫描插件类型来生成设置界面。
- 不要求主程序理解插件内部 Options 类型。
- 不在初版同时落地工作区/智能体/临时作用域（§7.2）。
- 不在初版统一 Native 与 Process 通道 init extensions key 命名（属于另一独立提案，§8.1）。

## 16. 待确认问题

以下是仍未做出决策的开放问题。已经做出决策的项目（如作用域分阶段、配置 Schema 用 Attribute、`pluginConfigJson` 作为初版统一注入字段、统一以 plugin.json 为权威、敏感配置初版使用本地受保护值、reload 失败后保留配置并提示未成功重载）已分别在 §7.2 / §10.4 / §8.2 / §11.1.1 / §14.P2 / §14.P6.1 给出结论，不再列入待确认。

1. MCP 通道是否复用同一套配置 Schema，还是继续沿用 MCP 连接配置 UI。
2. 配置 Schema 是否允许声明“测试连接”动作；如果允许，该动作应由主程序调用插件私有能力，还是暴露为普通工具。
3. Attribute 声明能否覆盖足够多的 UI 场景；复杂场景是否需要在 P1 之后新增可选的 Schema Builder（运行期不可用，仅 Generator 静态分析）。
4. 是否需要在 Schema 中表达字段间的依赖（例如 `enableAdvanced = true` 时才显示 `advancedTimeoutMs`）。

## 17. 初步结论

本需求可以定义为“插件配置声明与运行时注入机制”。

最重要的边界是：

> 插件提供配置模型，主程序提供配置体验；AI 只看到工具能力，不看到插件配置值。

按这个边界推进，可以同时满足：

- 插件不需要维护设置界面。
- 用户不需要手改配置文件。
- 不污染 AI 提示词和上下文。
- 不泄露密钥和运行环境。
- 不破坏当前插件开发主线。
