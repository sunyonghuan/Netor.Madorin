# 02-修改方案

## 一、设计原则

1. **不破坏对话/专家模式现有正常链路**：所有改动只针对 `Work*` 与 `Meeting*` 系列事件、protocol 字段、relay 序列化。
2. **不改 Memory 插件协议版本号**：插件已经声明 `protocol = 1.3.0` 并预留好可选字段读取。所有新加字段对 Memory 来说都是"原本就期望但读不到"的字段，向后兼容自动生效。
3. **不动 schema、不动抽取算法、不动召回打分**。
4. **优先动事件参数 record + 发布点；其次动 relay 与 history dispatcher 序列化**。

## 三、问题 1 修复：扩 `WorkTaskCompletedArgs` + 同时修问题 3

### 3.1 事件参数（`Src/Netor.Cortana.Entitys/Events.cs`）

将 `WorkTaskCompletedArgs` 从 2 字段扩到 8 字段：

```csharp
public record WorkTaskCompletedArgs(
    string TaskId,
    string FinalReport,
    string ManagerAgentId,
    string ManagerAgentName,
    string SourceSessionId,
    string WorkspaceId,
    long CompletedAt,
    bool AllowMemoryIngest) : EventArgs;
```

字段语义：

| 字段 | 含义 | 来源 |
|---|---|---|
| `ManagerAgentId` | 发起任务的总经理 agent 文件名 | `WorkTaskEntity.AgentName`（schema 里就是这个名字承载） |
| `ManagerAgentName` | 显示名 | 通过 `AgentService.GetByName(task.AgentName)` 取 `AgentEntity.Name` |
| `SourceSessionId` | 关联的对话会话 | `WorkTaskEntity.SessionId` |
| `WorkspaceId` | 工作区哈希 | `WorkTaskEntity.WorkspaceId` |
| `CompletedAt` | 完成时间 Unix 毫秒 | `WorkTaskEntity.CompletedAt`；缺失时 fallback 当前时间 |
| `AllowMemoryIngest` | 是否允许写入长期记忆 | `AgentEntity.AllowWorkflowMemory`（按 `AgentName` 查） |

### 3.2 发布点（`ProjectLeadService.cs:93-95`）

新增依赖：构造函数注入 `AgentService`（host 已注册服务；当前 UI host 中为 transient）。

```csharp
public async Task RunAsync(string taskId, CancellationToken cancellationToken = default)
{
    ...
    plan.Status = WorkTaskPlanStatuses.Done;
    fileService.SavePlan(plan);
    var finalReport = BuildSummary(plan);
    taskService?.RecordExecutionCompleted(taskId, finalReport);
    Touch(taskId);
    await CreateTaskEventAsync(taskId, WorkTaskEventKinds.Completion, "计划已全部完成。").ConfigureAwait(false);

    // ── 改造点：从 WorkTaskEntity + AgentEntity 取齐字段 ──
    var task = taskService?.GetById(taskId);
    var agent = task is null ? null : agentService.GetByName(task.AgentName);
    var completedAt = task?.CompletedAt ?? DateTimeOffset.Now.ToUnixTimeMilliseconds();

    await publisher.PublishAsync(
        Events.OnWorkTaskCompleted,
        new WorkTaskCompletedArgs(
            TaskId: taskId,
            FinalReport: finalReport,
            ManagerAgentId: task?.AgentName ?? string.Empty,
            ManagerAgentName: agent?.Name ?? task?.AgentName ?? string.Empty,
            SourceSessionId: task?.SessionId ?? string.Empty,
            WorkspaceId: task?.WorkspaceId ?? string.Empty,
            CompletedAt: completedAt,
            AllowMemoryIngest: agent?.AllowWorkflowMemory ?? true)).ConfigureAwait(false);
    return;
}
```

> 注意：`taskService` 在当前签名是可空的（兼容老测试），新逻辑读不到时退化为空字符串，不抛异常。

### 3.3 Failed / Cancelled 事件保持原样

`WorkTaskFailedArgs / WorkTaskCancelledArgs` 不需要改，因为 Memory 插件本来就只对 `Completed` 入库（其它两个仅 LogDebug，没有副作用）。

### 3.4 JsonContext 同步

`WebSocketJsonContext` 已经为 `WorkTaskCompletedArgs` 注册了序列化；扩字段后 source generator 自动覆盖，无需手动改 [JsonSerializable] 列表。

### 4.3 兼容性

`MemoryMeetingEventHandler` 现在期望读到的字段全部进入 payload，原本的兜底逻辑（`AgentName="会议主持人"`、`CreatedAt=UtcNow`）会自动让路。Memory 插件代码无须修改。

### 4.4 会议历史回放分页加固

`PluginBusMeetingHistoryDispatcher` 的历史补偿同样要避免单时间戳游标漏数据。会议历史批次同时导出最终总结和阶段 summary，两类记录可能共用同一个 `UpdatedAt` 毫秒时间戳，因此分页改成 `(UpdatedAt, CursorId)` 复合游标：

- final 记录 `CursorId = "final:" || MeetingSessions.Id`
- summary 记录 `CursorId = "summary:" || MeetingMessages.Id`
- SQL 分支内可先按 `UpdatedAt/CreatedAt >= @Since` 预过滤，外层再统一做精确游标过滤：`WHERE UpdatedAt > @Since OR (UpdatedAt = @Since AND CursorId > @LastCursorId) ORDER BY UpdatedAt, CursorId`
- `MeetingExportRecord.CursorId` 仅服务端分页使用，标记 `[JsonIgnore]`，不改变 PluginBus payload 协议

## 五、问题 4 修复：让工作模式历史回放查正确的表

### 方案选择

有两种修法：

**方案 A**：把 `PluginBusWorkflowHistoryDispatcher` 改成查 `WorkTasks` 表（**推荐**）。
**方案 B**：保留 `OrchestrationTask` schema 并补齐运行时写入。

### 选择 A 的理由

- `OrchestrationTask` 是早期"多智能体编排模式"策划阶段产物；工作模式三层架构落地后实际表是 `WorkTasks`，没人写 `OrchestrationTask` 已经存在很久
- 另起 `OrchestrationTask` 写入意味着同一份数据写两次，存在双源同步成本与漂移风险
- 从 `WorkTasks` 表已经能拿到记忆插件需要的全部字段（`Id / SessionId / WorkspaceId / AgentName / FinalReport / CompletedAt / IsActive`），无字段缺口

### A 落地

修改 [Src/Netor.Cortana.Networks/WebSockets/PluginBusWorkflowHistoryDispatcher.cs](../../../Src/Netor.Cortana.Networks/WebSockets/PluginBusWorkflowHistoryDispatcher.cs)：

- SQL `FROM OrchestrationTask` → `FROM WorkTasks`，按 `(LastActiveAt, Id)` 复合游标分页，并限制为 `CompletedAt IS NOT NULL AND ErrorMessage IS NULL AND IFNULL(FinalReport, '') <> ''`
- 字段映射调整：
  - `ManagerAgentId / ManagerAgentName` ← 通过 `AgentService.GetByName(WorkTasks.AgentName)` 在 dispatcher 构造函数注入 `AgentService` 后填充
  - `SourceSessionId` ← `WorkTasks.SessionId`
  - `WorkspaceId` ← `WorkTasks.WorkspaceId`
  - `Status` ← 固定为 `"completed"`；SQL 已提前排除失败 / 空报告任务，历史入库只发送 Memory 插件真正会消费的成功任务
  - `TraceId` ← 不存在则为 `""`（Memory 插件容忍空值）
  - `StartedAt / CompletedAt / LastActiveTimestamp` ← `WorkTasks.CreatedAt / CompletedAt / LastActiveAt`
  - `AllowMemoryIngest` ← `AgentEntity.AllowWorkflowMemory`（与问题 3 联动）

分页 SQL 需要使用 `WHERE (LastActiveAt > @Since OR (LastActiveAt = @Since AND Id > @LastId)) ORDER BY LastActiveAt, Id`。不能只用 `LastActiveAt >= @Since` 后在代码里 `last + 1`，否则同一毫秒内多条完成任务分页时可能被跳过。

### 5.1 `WorkflowExportRecord` 加字段

[Src/Netor.Cortana.Networks/WebSockets/Serialization/WebSocketJsonContext.cs:181-200](../../../Src/Netor.Cortana.Networks/WebSockets/Serialization/WebSocketJsonContext.cs) 中的 `WorkflowExportRecord` 增加 `AllowMemoryIngest` 字段。

### 5.2 删空表的 schema？

**不删**。`OrchestrationTask` 等几张表存在 schema 但无数据，删 schema 等于做数据库迁移，超出本次范围。保留空表，dispatcher 改写后这些表自然边缘化，不影响运行。后续单独评审是否清理。

## 八、风险点与对策

| 风险 | 概率 | 影响 | 对策 |
|---|---|---|---|
| `WorkTaskCompletedArgs` 是 record，扩字段改变构造函数签名，可能影响测试 | 高 | 编译错误 | 全代码库 grep `new WorkTaskCompletedArgs(`，逐处补字段；所有引用都在 host 内 |
| `MeetingMessageCompletedArgs` 同上 | 高 | 编译错误 | 全代码库 grep `new MeetingMessageCompletedArgs(`，含 UI 订阅端反序列化 |
| 发布点取 `MeetingSessionEntity` 时遇到 race（会话已删） | 低 | payload 字段为空 | `?? string.Empty` 兜底，不抛异常 |
| `WorkTaskCompletedArgs` 从 2 字段变 8 字段，外部反序列化（旧版本插件）失败 | 极低 | 历史插件断连 | 协议版本仍为 1.3.0；插件侧用宽松 JSON 读取（`TryGetProperty`），新增字段对老插件透明 |
| 扩字段后 `WebSocketJsonContext` source generator 没刷新 | 中 | 序列化字段缺失 | 后续验证阶段执行构建以强制重生成；本轮按要求不编译构建 |
| `OrchestrationTask` 表突然没人查后是否有遗留代码依赖？ | 低 | 链路断 | grep 全代码库已确认仅 dispatcher 一处使用 |

## 九、验证矩阵

| 路径 | 验证方法 | 预期 |
|---|---|---|
| Workflow 实时 | 跑一个工作模式任务到完成，看插件 `observation` 表新增记录的 `AgentId / SessionId / WorkspaceId` 字段是否非空 | 非空 |
| Workflow 实时 → 抽取 | 上一步后等 30s，看 `memory_fragments` 表是否新增条目 | 至少 1 条 |
| Workflow `AllowMemoryIngest=false` | UI 关掉某 agent 的开关再跑工作模式，看 `observation` 表 | 不应新增（被 handler 跳过） |
| Workflow 历史回放 | 重启应用，看 dispatcher 日志是否回放出已存在的 `WorkTasks` | 数量与 `SELECT COUNT(*) FROM WorkTasks WHERE CompletedAt IS NOT NULL AND ErrorMessage IS NULL AND IFNULL(FinalReport, '') <> ''` 一致 |
| Meeting 实时 | 走完一次会议，看 `observation` 表的 `WorkspaceId / SessionId` 是否非空 | 非空 |
| Meeting 召回 | 在会议结束后立即调 `memory_recall`，按 topic 过滤是否能命中 | 命中 |
| 对话 / 专家模式 | 走一轮对话 | 与改动前完全一致（无回归） |
