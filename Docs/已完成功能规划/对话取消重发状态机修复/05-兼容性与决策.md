### 8.2 IAiOutputChannel 接口（破坏性变更，已拍板）

**决策**：**破坏性变更** — 接口所有方法首参加 `string turnId`，删除旧签名，编译器强制所有实现处理 turnId。

**理由（v7 §决策记录）**：

- "截"是 v7 的硬要求 #4 — 旧 turn 不再产生新内容必须从根上做到。**默认实现转发会让"截"沦为可选契约**（旧 channel 默认丢弃 turnId，仍是合法实现），这恰恰是当前 bug 的根源被模板化
- 接口存在两个 OnTokenAsync 重载会让未来阅读者不知道该实现哪个 — 接口腐烂的开始
- 本仓库 IAiOutputChannel 只有 4 个实现且全部在仓库内（无第三方）；破坏性成本可控
- 与"turn 一等公民"哲学一致 — turnId 既然是核心概念就不该是可选

**新接口签名**：

```csharp
public interface IAiOutputChannel
{
    string Name { get; }
    bool IsActive { get; }

    Task OnTokenAsync(string turnId, string token, string sessionId, CancellationToken ct);
    Task OnDoneAsync(string turnId, string sessionId, CancellationToken ct);
    Task OnCancelledAsync(string turnId);
    Task OnErrorAsync(string turnId, string message, CancellationToken ct);
}
```

`IRealtimeProcessOutput.OnProcessEventAsync` **接口签名不变**（保留 `(RealtimeProcessEvent evt, CancellationToken ct)` 一字不动）— `RealtimeProcessEvent` 类已经有 `TurnId` 字段（[Src/Netor.Cortana.Entitys/Models/RealtimeProcessEvent.cs:9](../../../Src/Netor.Cortana.Entitys/Models/RealtimeProcessEvent.cs#L9)），实现端**按 `evt.TurnId` 字段做路由**即可。

**为什么不像 IAiOutputChannel 那样把 turnId 提到方法首参**：

- `IAiOutputChannel` 当前签名**没有任何 turnId 携带**，必须破坏性变更才能让"截"成强制契约
- `IRealtimeProcessOutput` 携带的是 `RealtimeProcessEvent` 整体对象，TurnId 已是字段；改首参等于把同一信息冗余在签名和字段两处
- 调用方如 [PowerShellProvider.cs:309](../../../Src/Netor.Cortana.Plugin/BuiltIn/PowerShell/PowerShellProvider.cs#L309) 已经在通过 `new RealtimeProcessEvent { TurnId = ..., ... }` 传入 turnId — 改签名等于强制所有插件改调用方代码（破坏面非零）

**实现端责任**（实施时务必守住）：

- `UiChatOutputChannel.OnProcessEventAsync(evt, ct)` 内部首行：`if (_cancelledTurnIds.Contains(evt.TurnId)) return Task.CompletedTask;`
- `evt.TurnId == ""`（如 [PowerShellProvider.cs:311](../../../Src/Netor.Cortana.Plugin/BuiltIn/PowerShell/PowerShellProvider.cs#L311) 当前设的空字符串）按"全局/未分配 turn"语义处理：不参与 `_cancelledTurnIds` 守卫，直接渲染（保持现状行为）
- `NonExpertSuppressingRealtimeOutput.OnProcessEventAsync` 不动（首行的 `NonExpertProcessScope.Active` 短路是工作/会议模式的现有保护）

**结论**：阶段 1 改造清单里 `IRealtimeProcessOutput` 是**接口签名不变 + 实现端按字段路由**，不是"接口破坏性变更"。把它误归到 IAiOutputChannel 同等级的接口改造会强制所有插件调用方改代码（包括 [Src/Netor.Cortana.Plugin/BuiltIn/PowerShell/PowerShellProvider.cs](../../../Src/Netor.Cortana.Plugin/BuiltIn/PowerShell/PowerShellProvider.cs)），无收益。

**为什么不留旧重载兼容**：

- 旧重载 + 默认转发会让"忘记 turnId"成为编译期合法的"默认行为" — 把 bug 模板化

- 在"修接口忘记 turnId 是 bug 根源"的情境下，**只有破坏性变更才是从根上修复**

## 十、不做这次改造的代价

| 风险 | 说明 |
| --- | --- |
| 用户每次取消重发丢部分回复 | 主路径触发，不是边角；用户感觉"刚才聊的白聊了" |
| 旧 turn 残余 token 污染新气泡 | "截"违反；用户看到诡异的内容混合 |
| 必须重启软件 | "停"违反（死循环）；体验级灾难 |
| 多智能体编排做不出 | 需要 turn 级隔离和 IAgentOrchestrator 抽象，当前 service 字段层级做不到 |
| 图片/视频生成同病 | 三个 turn 执行器复制粘贴；不拆永远三处同步改 |
| 测试覆盖永远不上来 | 字段共享导致单元测试需要构造复杂初始化状态，团队会放弃写 |

## 十一、核心论点（v7.3 终版）

> **专家模式取消语义是"停 + 留 + 截"三段。当前代码：**
>
> - **"停"** 靠 HTTP/MCP 自然结束 + 无超时轮询，会卡死 → **阶段 1** 加 5s 兜底超时
> - **"留"** 主路径失败 — `ChatInputVm.SubmitAsync` 每次无条件 `RebuildAgent` 清空 `_session` / `_agent`，旧 turn catch 块的 null 守卫拦截 SavePartialResponseAsync → **阶段 2** 让 `Change*` 不再清空字段
> - **"截"** 失败 — `UiChatOutputChannel` 单例 + 实例字段，旧 turn 残余 token 污染新 turn → **阶段 1（破坏性接口契约）+ 阶段 3（ChatTurnContext 一等公民）** 让 turn-aware 在编译期就强制
>
> **而硬要求 #5（新消息基于已有上下文继续）不是回灌路径缺失** — `ChatHistoryDataProvider.ProvideChatHistoryAsync` 是 AF 框架钩子，每次推理前自动从 DB 拉历史（含压缩段落 + 尾部原始消息）。**只要阶段 2 修好"留"，部分回复落进 ChatMessages 表，AF 钩子下一轮自然读到，整条链路打通**。
>
> **所以本次改造完全不动现有压缩链路** — 拆解出来的新组件全部继续依赖 AF 钩子机制读取历史，不重新实现历史回灌。
>
> **核心制度保障**：阶段 1 把 `IAiOutputChannel` 接口做**破坏性变更**强制 turn-aware — "截"从此是接口契约不可绕过的部分，未来任何新增的 channel 实现都必须显式处理 turnId（编译错误而非运行时 bug）。这是从根上修复 vs 修补丁的关键分界。
>
> **对工作模式 / 会议模式 / Networks / Voice 的破坏面：6 条被打断 + 6 条不打断 + 1 条不实现**（v7.3 不再用"零破坏"绕过问题）：
>
> - 工作 / 会议模式的事件流走 EventHub 独立 topic（`OnWorkAssistantDelta` / `OnMeetingMessageDelta` 等），**不实现也不调用 IAiOutputChannel**，接口破坏性变更对它们透明
> - 工作 / 会议模式的取消机制走自有 `WorkTaskCancellationRegistry` / `MeetingCancellationRegistry`，与 `_isRunning` / `_streamCts` 完全独立，阶段 1 的 5s 超时和事件去重守卫只针对 `OnConversationTurnCompleted`
> - `AiChatHostedService` 的所有公共方法（11 个）和公共访问器（5 个）签名**一字不动**，被外部调用的 23 处全部通过转发到新组件保持稳定（详见 [04-链路修复矩阵.md §7.3](04-链路修复矩阵.md)）
> - 阶段 5 删除字段时严格区分"turn 私有"（删）vs"全局默认配置"（迁移到 ChatAgentResolver / ChatSessionService 内部，对外保留访问器签名）
> - **6 条真正被打断的链路**（取消传播 / 持久化 / 配置同步 / SessionCreated / Workflow→Chat 回灌 / 工具上下文版本）每条都有架构级修复方案接通（详见 [04-链路修复矩阵.md §7.2.A 至 §7.2.I](04-链路修复矩阵.md)）
>
> **架构级修复 vs 修补丁的判断标准**：
>
> | 反例（修补丁） | 正解（架构级） |
> | --- | --- |
> | 保留旧字段 + 加新机制双写 → 状态分裂 | 字段单一所有者；公共契约转发暴露 |
> | 接口加默认转发兼容 → "忘记 turnId"被模板化 | 破坏性变更让"忘记"成为编译错误 |
> | 把同类方法迁到新组件 → 跨业务耦合 | 职责分离（AF 钩子/turn 取消/workflow 回灌 各自路径） |
> | 在 4 处都加版本检查 → 散布检查 | 检查内聚到 BuildAgentForTurn 一处 |
> | 转发后再 publish 一次 → 重复事件 | publish 代码跟随业务行为迁移 |
>
> **改一次彻底改完 + 整体链路接通 + 不制造任何新错误** — 这是 v7.3 对用户问题的完整答复。
