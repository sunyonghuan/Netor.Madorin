## 一、专家模式取消语义（用户校正定型）

### 1.1 三段语义

> "停止就等于立即停下当前的任务和对话，已经保存的、持久化的就要保存。不发送新的文、新的内容，之前的内容必须立即停止。"

| 段 | 含义 | 现有代码已实现 |
| --- | --- | --- |
| **停** | 立即停下当前任务和对话 | ❌ 取决于 HTTP/MCP 是否响应取消 token；最坏情况死循环 |
| **留** | 已产出的内容必须持久化 — 数据库 + UI 气泡 | ⚠️ **主路径失败** — `SavePartialResponseAsync` 实现存在但被 `_session is not null` 守卫拦截（见 §2.2） |
| **截** | 截断后续输出 — 旧 turn 残余 token / 事件 / 数据库写入必须全部丢弃 | ❌ `UiChatOutputChannel` 是单例 + 实例字段，旧 turn 的 `OnTokenAsync` 仍会污染 |

### 1.2 用户视角的可观察行为（5 条硬要求）

| # | 要求 | 解释 |
| --- | --- | --- |
| 1 | 动效立即停（< 50ms） | 走马灯停转 + 按钮切换 |
| 2 | 流式输出立即停 | 已显示气泡不再有新 token 进入 |
| 3 | 已生成内容必须保留 | DB 有部分回复行；UI 气泡停留在已渲染状态 |
| 4 | 旧 turn 不再产生任何新内容 | 后续 token / process event / 数据库写入全部截断 |
| 5 | 输入框立即可用，新消息基于已有上下文 | AI 能引用刚才被打断那段 |

### 1.3 三模式取消语义对比

| 模式 | 取消单元 | "停" | "留" | "截" | 是否需"插话/排队" |
| --- | --- | --- | --- | --- | --- |
| **专家模式** | turn | 立即 | 部分回复 + UI 气泡 | 输出管道关闭 | **不需要** |
| **工作模式** | task（含阶段产出物） | 立即 | 已完成步骤 + 阶段产出 + 上下文 | 当前步骤截断 | 需要 |
| **会议模式** | meeting | 立即 | 已发言记录 + 主持人状态 | 当前发言截断 | 需要 |

## 二、为什么这三段都做不到 — 真正的架构债

### 2.1 输出通道不按 turnId 隔离 → "截"失败

`UiChatOutputChannel`（[Src/Netor.Cortana.UI/Channels/UiChatOutputChannel.cs](../../../Src/Netor.Cortana.UI/Channels/UiChatOutputChannel.cs)）是 Singleton + 实例字段：

```csharp
private readonly StringBuilder _buffer = new();
private MarkdownRenderer? _currentPresenter;
private string? _currentTurnId;  // 字段，但只取首次 evt.TurnId
```

旧 turn 取消后，假设 HTTP 流隔了 2 秒才真正断开：

- 旧 turn 的 `OnTokenAsync` 仍可能被调用 → 累加到 `_buffer`
- 此时新一轮已开始，新 turn 的 `EnsureBubbleCreated` 用的是 `_currentPresenter` 字段 → **新 chunk 追加到旧 buffer，UI 气泡里出现两个 turn 的内容混合**
- 新一轮的 `OnDoneAsync` 调用 `Reset(...)` 清 buffer/presenter — 但**此时 UI 上已经渲染过混合内容**（FlushRender 已把混合 markdown 显示出来）

> **修正说明**：`UiChatOutputChannel.OnDoneAsync`（[UiChatOutputChannel.cs:71](../../../Src/Netor.Cortana.UI/Channels/UiChatOutputChannel.cs#L71)）只做 UI 刷新 + Reset 内部状态，**不写数据库**。Chat 历史持久化由 AF 框架的另一个钩子 `ChatHistoryDataProvider.StoreChatHistoryAsync`（[ChatHistoryDataProvider.cs:58](../../../Src/Netor.Cortana.AI/Providers/ChatHistoryDataProvider.cs#L58)）负责，在 `RunStreamingAsync` 完成时由 AF 自动触发，存的是 AF 内部的 `ResponseMessages`（不依赖 channel 的 buffer）。**只有图片/视频生成路径**才在 `AiChatHostedService.GenerateImageAsync` / `GenerateVideoAsync` 内显式调 `SaveAssistantMessage`。
>
> 因此本节描述的污染是 **UI 视觉污染**（用户看到混合气泡），不是 DB 数据污染。但视觉污染本身已经违反硬要求 #4（"截"），仍是必须修的架构债。

### 2.2 字段每次被无条件清空 → "留"主路径失败

[ChatInputVm.cs:301-306](../../../Src/Netor.Cortana.UI/ViewModels/ExpertMode/ChatInputVm.cs#L301-L306) 每次 SubmitAsync 都**无条件**调三次 Change：

```csharp
if (_selectedAgent is not null) _chatService.ChangeAgent(_selectedAgent.Id);
if (_selectedProvider is not null) _chatService.ChangeProvider(_selectedProvider.Id);
if (_selectedModel is not null) _chatService.ChangeModel(_selectedModel.Id);
```

每个 Change 内部 → [`RebuildAgent()`](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L1983) → `_agent = null; _session = null`。

旧 turn catch 块 [line 644](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L644)：

```csharp
if (!string.IsNullOrWhiteSpace(fullResponse.ToString())
    && _session is not null && _agent is not null)  // ← 几乎总是 false
{
    await chatHistoryProvider.SavePartialResponseAsync(...);
}
```

**结论**：这是**主路径触发**，不是边角。哪怕用户没切配置，每次"AI 跑偏 → Stop → 输入新方向 → 发送"都会丢部分回复。

### 2.3 死循环 → "停"失败

[AiChatHostedService.cs:1667-1673](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L1667-L1673) `WaitForCurrentRunToStopAsync` 是无超时轮询 `_isRunning`。如果旧 turn 因 HTTP/MCP 不响应取消而 `_isRunning` 永久为 true，新一轮卡在这死循环里直到重启。

### 2.4 关键澄清：DB→AgentSession 回灌路径已存在（v6 误判修正）

> v6 主张"必须新增 ChatHistoryReplayService 解决回灌缺失"。**v7 撤回此论断。**

代码事实：

[ChatHistoryDataProvider.cs:381](../../../Src/Netor.Cortana.AI/Providers/ChatHistoryDataProvider.cs#L381) `ProvideChatHistoryAsync` 是 **AF 框架钩子方法**（重写自 AF SDK 的 `ChatHistoryProvider` 基类）。AF 在每次 `RunStreamingAsync` 之前会自动调用它从 DB 拉历史，注入给推理。

通过 [AIAgentFactory.cs:213-214](../../../Src/Netor.Cortana.AI/AIAgentFactory.cs#L213-L214) 注册到每个 chat agent：

```csharp
ChatHistoryProvider = enableChatHistory
    ? services.GetRequiredService<ChatHistoryDataProvider>()
    : null
```

钩子内部逻辑：

```text
ProvideChatHistoryAsync(InvokingContext context) [按 sessionId]
  ├─ 优先：CompactionSegmentService.GetBySessionId
  │    取压缩段落 → "[对话摘要 #N]" 系统消息
  │    + 最后段落之后的原始尾部消息（从 ChatMessages 表）
  ├─ 老版兼容：ChatSessions.CompactedContext 缓存 + 之后的原始消息
  └─ 都没有时：ChatMessages 表全量加载
```

`SavePartialResponseAsync` 把部分回复以 `Role=assistant` 写进 `ChatMessages` 表（[line 251-262](../../../Src/Netor.Cortana.AI/Providers/ChatHistoryDataProvider.cs#L251-L262)），同 sessionId。`BuildChatHistoryQuery`（[line 519](../../../Src/Netor.Cortana.AI/Providers/ChatHistoryDataProvider.cs#L519)）是简单的 `SELECT * FROM ChatMessages WHERE SessionId = @SessionId ORDER BY CreatedTimestamp ASC` — **只要 SavePartialResponseAsync 真的写了，下一轮 AF 钩子自然能读到。**

**所以"AI 看到上一轮被打断那段"的真正瓶颈不是回灌缺失，是 §2.2 的字段清空让 SavePartialResponseAsync 根本没机会执行。**

### 2.5 现有压缩链路（不动）

```text
"压给 AI"那端：
  AI 推理时
    → AF 自动调 ChatHistoryDataProvider.ProvideChatHistoryAsync
    → 优先返回 (压缩段落摘要 + 尾部原始消息)
    → AF 注入给 RunStreamingAsync 的 chat history
  压缩触发：StoreChatHistoryAsync → CompactAndReplaceAsync
    → 后台用 IChatCompactionClientResolver 解析的小模型压缩
    → 写入 CompactionSegments 表

"详给 UI"那端：
  切换会话/启动恢复
    → MainWindow.SwitchToSession
    → ChatMessageService.GetBySessionId
    → 全量原始消息渲染气泡
```

**v7 完全不动这条链路。** 拆解出来的所有新组件（ChatSessionService / ChatAgentResolver / ChatTurnExecutor 等）都不重新实现历史回灌，全部继续依赖 AF 钩子。
