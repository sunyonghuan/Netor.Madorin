## 六、阶段路线（v7 终版，5 阶段，4 周）

> 每阶段独立可上线、独立验收；中途可停。
> **阶段 1 含 IAiOutputChannel 接口破坏性变更**（一次性同步本仓库 4 个实现，无外部破坏面）；其它阶段保持向后兼容。

### 阶段 1：止血 + 接口契约一次到位（0.5 周）

**目标**：消除"必须重启"的灾难；同时**一次性**把 IAiOutputChannel 接口契约改为强制 turn-aware（破坏性变更，详见 [05-兼容性与决策.md §8.2](05-兼容性与决策.md)）。

**改动**：

- `WaitForCurrentRunToStopAsync` 加 5s 超时；超时强制 `_isRunning=false` + Dispose CTS
- 5s 超时事件**复用** `OnConversationTurnCompleted(Status=Failed, ErrorMessage="zombie killed: HTTP/MCP 未响应取消")` 上报 — **不新增 EventHub 事件类型**（与 [05-兼容性与决策.md §8.4](05-兼容性与决策.md) "Events.cs 零改动"一致）；同时打 `LogWarning` 便于本地观测
- **`IAiOutputChannel` 接口破坏性变更** — 所有方法首参加 `string turnId`，删除旧签名（详见 [05-兼容性与决策.md §8.2](05-兼容性与决策.md)）
- **`IRealtimeProcessOutput` 接口签名不变** — `RealtimeProcessEvent.TurnId` 字段已存在，实现端按字段路由即可；`PowerShellProvider:309` / `WebSocketChatOutputChannel` 等调用方零改动（详见 [05-兼容性与决策.md §8.2](05-兼容性与决策.md) "实现端责任"段）
- **同步改造 4 个 IAiOutputChannel 源码实现 + 1 个 IRealtimeProcessOutput 实现**（**4 源码实现 / 3 DI 注册**口径，VoiceChatOutputChannel 未注册但仍要改源码以编译通过）：
  - `UiChatOutputChannel` — `ConcurrentDictionary<turnId, TurnRenderState>` 替代实例字段；`_cancelledTurnIds` 60s LRU 守卫；所有方法（含 OnProcessEventAsync）首行 turnId 拦截
  - `WebSocketChatOutputChannel` — turnId 透传到 PluginBus（简化代码）
  - `TtsPluginOutputChannel` / `VoiceChatOutputChannel` — 加 turnId 作日志字段（**VoiceChatOutputChannel 未在 DI 注册，但破坏性接口变更要求源码编译通过**）
  - `NonExpertSuppressingRealtimeOutput` — **签名不变**（OnProcessEventAsync(evt, ct) 一字不动），首行 `NonExpertProcessScope.Active` 短路保留；evt.TurnId 透传到内部 expertChannel
- 上游 `AiChatHostedService` 调用处传入 `_currentTurnId` 字段（阶段 3 后变 `context.TurnId`）
- **新增 turn 终止事件去重守卫** — 同一 turnId 的 `OnConversationTurnCompleted` 只能 publish 一次（详见下方"事件去重"段）

**事件去重（阶段 1 必做）**：

当前 `SendMessageAsync` 的 catch 块在 [AiChatHostedService.cs:655](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L655) 已经会 publish `OnConversationTurnCompleted(Cancelled)`。如果取消入口（`CancelCurrentTaskAsync`）也立即 publish 一次，**同一 turnId 会发两次终止事件**，VM 大概率能容忍但 PluginBus / WebSocket feed 会重复，破坏外部订阅方语义。

修复方式（轻量）：

```csharp
// 在 _streamCts 旁边加一个 turn 终止状态字段
private int _turnCompletedPublished; // 0 未发，1 已发，Interlocked 保护

// publish 终止事件统一走守卫方法
private void PublishTurnCompletedOnce(...)
{
    if (Interlocked.CompareExchange(ref _turnCompletedPublished, 1, 0) != 0)
        return;
    publisher.Publish(Events.OnConversationTurnCompleted, ...);
}

// 新 turn 启动时重置：
_turnCompletedPublished = 0;  // 与 _cancelNotificationRequested 重置同一时机
```

阶段 3 拆 `ChatTurnExecutor` 后，这个标志改成 `ChatTurnContext.IsCompletionPublished` 字段，按 turnId 隔离更干净 — 但阶段 1 先用 service-level 字段过渡。

**为什么阶段 1 必须捆绑接口契约改造**：

1. 单独加 5s 超时但通道仍是全局字段会放大串流污染（旧 turn 晚到的 OnCancelledAsync 全局 Reset，可能 nullify 新 turn 的 _currentPresenter）
2. 接口契约改造延后会让"截"暂时是软约束 — 等于把 v7 的核心硬要求 #4 推迟兑现
3. 一次到位避免接口腐烂的过渡态（先加默认转发、再删的两阶段方案 = 中间存在"接口有两个重载且语义重叠"的窗口期）

**总改动量**：~245 行（详见 [05-兼容性与决策.md §8.2](05-兼容性与决策.md) 表格） + 事件去重 ~30 行，合计 ~275 行，0.5 周可完成。

**验收**：

- 取消后不再"必须重启"；超时后服务自恢复
- 旧 turn HTTP 慢断 3 秒期间，新 turn 气泡不被污染
- **任何新增的 IAiOutputChannel 实现都必须显式处理 turnId（编译器强制）**
- **同一 turnId 的 `OnConversationTurnCompleted` 只发一次**（PluginBus / WebSocket 订阅方零重复）
- 4 个实现的单元测试通过

### 阶段 2：根除"留"主路径丢失（0.5 周）

**目标**：让"留"对所有取消场景都成立。

**改动**：

- 新增 `ChatAgentResolver`（持有职责 2/3/4，比阶段 3 提前）
  - **持有字段**：`_currentProvider` / `_currentAgent` / `_currentModel` / `_builtToolContextVersion`（从 AiChatHostedService 迁过来）
  - **暴露方法**：`ChangeProvider/Agent/Model` / `BuildAgentForTurn` / `InvalidateAgentIfToolContextChanged`
  - **暴露访问器**：`CurrentProvider` / `CurrentAgent` / `CurrentModel`
- `Change*` 不再调 `RebuildAgent` 清空 `_agent` / `_session`，只更新内部"下一轮默认值"
- 旧 turn 的 catch 块改为读 SendMessageAsync 内的局部 `session`/`agent` 变量（本阶段还没拆 ChatTurnContext，先用局部变量过渡）
- **`AiChatHostedService` 的公共契约保持稳定**（详见 [04-链路修复矩阵.md §7.3](04-链路修复矩阵.md)）：
  - `CurrentProvider` / `CurrentAgent` / `CurrentModel` 改为 `=> _agentResolver.CurrentX`（转发，签名不变）
  - `ChangeProvider(string)` / `ChangeModel(string)` / `ChangeAgent(string)` 改为 `=> _agentResolver.ChangeX(id)`（转发，签名不变）
- `ChatInputVm.SubmitAsync` 维持 `Change*` 调用不变（无侵入）
- `WorkModeInputVm:406-408, 698-711` 读 `CurrentAgent/Provider/Model` 仍正常工作（外部签名不变 + 转发到 ChatAgentResolver）

**为什么单独一周提前**：这是用户感知最强的 bug（每次取消重发都丢回复），且改动范围小、可独立验证、立刻见效。同时它解锁了 AF 钩子下一轮自动读取部分回复的整条链路 — 间接让硬要求 #5 真正成立。

**验收**：

- 取消后无论是否换 Provider/Model/Agent 重发，DB 里都有部分回复行
- 新一轮发送时，AI 引用了刚才被打断那段的内容（验证 AF 钩子链路）
- 切换历史会话时，AF 钩子仍能正确加载历史（回归测试）
- **工作模式回归**：`WorkModeInputVm` 读 `_chatService.CurrentAgent/Provider/Model` 行为零变化（验证转发正确）
- **会议模式回归**：会议启动 / 切换正常（虽然不读这三个但同步验证）

### 阶段 4：VM 事件驱动（0.5 周）

**目标**：删除 VM 乐观更新；UI 状态由事件单源驱动。

**事件方案**：A — 复用 `ConversationTurnCompletedArgs.Status` 枚举（用户拍板）

**前置事实**（已代码核对）：

`AiChatHostedService` 三条路径都同时发 `OnAiStarted/Completed` (VoiceSignalArgs) **和** `OnConversationTurnStarted/Completed`：

- 聊天路径：[line 320 + 708](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L320) (OnAiStarted/Completed) + [line 357 + 624/655/668](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L357) (PublishConversationTurn*)
- 图片生成：[line 755 + 945](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L755) + [line 794 + 880/901/923](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L794)
- 视频生成：[line 981 + 1182](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L981) + [line 1020 + 1117/1138/1160](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L1020)

所以阶段 4 切换 VM 事件源到 `OnConversationTurn*` 后，**三条路径自动覆盖**。但实施前必须显式验证（见验收）。

**改动**：

- `ChatInputVm.CancelAsync` 删除 `IsRunning = false` 那行
- 订阅 `OnConversationTurnStarted` → IsRunning=true
- 订阅 `OnConversationTurnCompleted` → IsRunning=false（不分 Status，三个原因都对应"turn 终止"）
- 删除现有 `OnAiStarted`/`OnAiCompleted`（VoiceSignalArgs）订阅
- `OnSendClick` 加 `SemaphoreSlim(1, 1)` 互斥
- `InputAreaView.axaml`：把 SendButton/StopButton 改成单值 IsVisible 切换

**验收**：

- 多次点击发送不再堆积孤儿 task
- UI 状态与服务真实状态严格同步
- **三条路径全覆盖**（必做）：
  - 聊天发送 → IsRunning=true → 流式输出 → IsRunning=false ✅
  - 图片生成 → IsRunning=true → 生成完成 → IsRunning=false ✅
  - 视频生成 → IsRunning=true → 生成完成 → IsRunning=false ✅
  - 任意一条路径 IsRunning 不切换 = 阶段 4 不通过

## 九、阶段间依赖关系

```text
阶段 1 (止血 + IAiOutputChannel 破坏性接口契约)
   │
   ├──→ 阶段 2 (ChatAgentResolver 修字段重置) ←─ 可独立验证主路径修复
   │      │
   │      └──→ 阶段 3 (完整拆分 + ChatTurnContext)
   │             │
   │             └──→ 阶段 4 (VM 事件驱动)
   │                    │
   │                    └──→ 阶段 5 (清理与文档)
   │
   └──→ 也可以直接跳到阶段 3（合并阶段 2 进 3.6 ChatTurnExecutor），
        但拆开能更早交付主路径修复给用户
```

**推荐推进顺序**：1 → 2 → 3 → 4 → 5。阶段 1+2 合计 1 周，能解决用户感知最强的两个问题（必须重启 + 取消重发丢回复），后续阶段是清理架构债。
