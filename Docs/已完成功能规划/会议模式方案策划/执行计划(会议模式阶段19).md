## 当前对齐结论
- 本阶段修复没有改变会议业务模型：老板仍不是参会者；主持人仍可先发言、澄清或征询；`ask_user` 仍是程序层通用工具名。
- 用户已确认会议模式策划整体完成，本阶段运行阻塞修复收口，会议模式方案可归档到已完成功能规划。
- 已确认一个真实逻辑错误：执行器终止判断过宽，`workflowEvent is WorkflowOutputEvent` 会同时匹配 `AgentResponseUpdateEvent` 和 `AgentResponseEvent`。正确终止条件必须只接受 GroupChatHost 的最终工作流输出，不能把单个 Agent 的输出事件当成会议结束。
- 用户复测后仍然出现主持人长时间卡住，日志证明不是模型/网络卡住：没有生成 AI trace，也没有任何主持人选择日志。`Workflow` 只收到 `GroupChatHost` 的 `ExecutorInvokedEvent -> ExecutorCompletedEvent -> SuperStepCompletedEvent`，说明首轮消息被积累但没有触发 `TakeTurnAsync`。
- AF 源码确认：`RunStreamingAsync<TInput>` 只入队输入，不会像 `RunAsync` 那样在 chat protocol 下自动追加 `TurnToken`；而 `GroupChatHost` 的 `AutoSendTurnToken=false`。会议模式使用流式监听时必须显式发送开场 `ChatMessage` 和 `TurnToken(emitEvents: true)`。
- 卡住的核心风险点是不同模型/驱动的流式事件粒度不同：工具调用可能不在 `AgentResponseUpdateEvent` 出现，而只在最终 `AgentResponseEvent` 的 `ChatMessage.Contents` 出现。会议层现在两种路径都处理。
- 输入框动画问题有明确日志：`fatal.log` 记录 Avalonia `Looping animations must not use the Run method.`。已改为 `DispatcherTimer` 驱动停止按钮旋转，并保持输入框霓虹边框与运行态同生命周期。
- 主持人首轮职责已按文档加强：主题不清晰必须先说明澄清点并 `ask_user`；主题清晰也必须先用主持人发言说明会议目标和第一位发言人的理由，再进入讨论。
- 思维卡片空内容的 UI 根因是 `RealtimeProcessCard.AppendContent` 异步 Post 后可能被紧随其后的 `Complete` 抢先停止刷新；已改成 UI 线程内同步追加，并让会议卡片 margin 对齐工作模式嵌套过程卡。
- 无限循环问题已加硬终止：`MeetingHostManager.ShouldTerminateAsync` 现在把会议 `Status=2` 视为当前工作流轮次的硬终止信号，避免 `confirm_meeting_end` 已写库后工作流继续选择发言人重启原话题；同时 `output_summary` / `confirm_meeting_end` 工具返回文案明确禁止继续原始话题。注意：这里的硬终止只约束本轮工作流，不代表 UI 进入永久只读；用户后续输入时应基于会议历史重新开启续接执行。
- 右上角加号无效是入口缺失：`MainWindow.OnNewSessionClick` 在 `groupchat` 分支为空。现在会议模式加号会调用 `MeetingView.StartNewMeeting()`，清空当前会议视图、解除只读、重置输入 VM 的 active meeting，让下一次输入按新会议创建处理。
- 两位参会者只看到一位发言的风险点在主持人选人偏置：选择器可能连续返回已发言参会者。现在保留模型判断，但在已有参会者发言且存在未发言参会者时做最小补位，优先让未发言者参与第一轮讨论。
- 主持人或参会者“只有思考没有正文”的根因是流处理器允许 thinking-only accumulator 持久化为正式消息。现在无正文、无有效工具的内部响应会发布 `OnMeetingMessageDiscarded` 并跳过落库，UI 同步移除对应空泡泡，思维过程仍只作为过程卡出现。
- 会议思考卡片现在复用 `RealtimeProcessCard` 的统一完成折叠能力：新增 `CompleteCollapsed`，会议模式在消息完成、部分保存、历史回放时都强制折叠过程卡；同时移除主持人切换时的临时“主持人正在组织下一步...”气泡，只保留真实 reasoning 增量创建的思考卡，避免生命周期偏离专家/工作模式。
- 会议过程卡布局已按专家/工作模式调整：思考卡、工具调用卡不再作为聊天气泡内部的 `PrependedCardsHost` 子控件，而是通过 `MeetingView.AddProcessCard` 作为消息流独立项显示，外层容器使用与专家模式一致的 `Margin=0,-18,0,0`，卡片自身使用 `RootBorder.Margin=50,0`。正式文本到来或消息完成时才创建聊天气泡，避免出现空气泡包过程卡。
- 本轮复核发现思考卡不折叠还有一个事件归并风险：部分模型/驱动可能不提供稳定 `ResponseId`，导致 reasoning 增量和最终 response 被归到不同 `MessageId`，UI 完成事件无法命中原思考卡。现在 `MeetingStreamProcessor.GetAccumulator` 在缺少 `ResponseId` 时按同一发言者复用未完成 accumulator，确保同一次发言的思考、正文、完成事件共用同一个 `MessageId`。
- 新会议唯一约束报错的直接修复是每次创建会议前先创建新的 ChatSession，并在当前 Session 仍存在活跃会议时再次换新 Session；同时补齐 UI 状态同步：`MeetingView.SetActiveMeeting(null)` 会同步清空 `MeetingInputVm.ActiveMeetingId`，避免右上角加号清空视图后输入 VM 仍把下一条输入当作旧会议插话。
- 多参会者只见一个智能体发言的修复保持业务边界：不强制抢走主持人的首次澄清/安排权，但当已有参会者发言且仍有未发言参会者时，`MeetingHostManager` 会优先安排未发言者，保证第一轮讨论覆盖所选参会者。
- 会议记录恢复只显示老板消息的根因不是 UI 回放过滤，而是运行中会议只在 `AgentResponseEvent` 最终响应时落库；当主持人调用 `ask_user` 后进入等待老板回复，部分模型/框架可能没有立刻产出最终响应，导致 UI 已经流式显示主持人文字但数据库仍没有主持人消息。现在 `MeetingStreamProcessor` 在正文增量到达时先按同一 `MessageId` 写入 `IsPartial=1` 草稿，后续增量持续更新；最终响应到达后用 `CompleteDraft` 转为正式消息。异常保存 partial 时也复用同一草稿，避免重复消息。
- 专家模式历史中出现大量会议相关"新会话"的数据库实查结论：会议内容没有写入 `ChatMessages`，但旧实现为了给 `MeetingSessions.SessionId` 找外键，调用了专家模式 `AiChatHostedService.NewSessionAsync()`，从而创建并切换普通 `ChatSessions`，污染专家历史列表。现在会议改为通过 `MeetingSessionService.CreateBackingChatSession` 创建归档支撑会话，不发布 `OnSessionCreated`，不切换专家当前会话；历史旧数据启动时通过迁移把被会议引用且无 ChatMessages 的支撑会话归档。会议记录面板改为按 `WorkspaceId` 列出会议，不再依赖当前专家会话。
- 会议是否可以结束的业务判定当前依赖主持人提示词，而非程序规则引擎。已把原先抽象的"议题成熟"拆成明确条件：老板核心问题已回应、适合主题的参会者已覆盖、无新增关键分歧/风险/待确认事项、老板插话已处理、能整理出结论/理由/风险/下一步。总结内容也明确要求覆盖主题目标、各参会者观点、共识或推荐方案、风险分歧、下一步建议。总结后仍必须 `check_pending_user_input` 并 `ask_user` 征询老板，老板明确同意后才允许 `confirm_meeting_end`。
- 停止按钮此前等价于取消会议，会直接 `MarkAsAdjourned` 并禁用输入，导致老板无法人工收口后要求总结。现在新增 `meeting.paused` 事件和 `MeetingExecutor.PauseAsync`：停止按钮只取消当前执行轮次，会议保持可继续，输入框显示可继续输入总结或讨论指令。真正散会仍保留 `/end` 路径。
- 历史会议恢复后如果原执行轮次已不存在，普通插话只入 pending 队列会无人消费。现在恢复出的 `Status=0/3` 会议在老板输入新指令后，会追加老板消息并重新调用 `ExecuteAsync`，主持人基于 `MeetingMessages` 历史继续讨论或生成总结；旧的已散会会议会先恢复为进行中再继续。
