## 一、编排核心：GroupChat + 自定义 GroupChatManager

### 1.1 为什么用 GroupChat 而非 Magentic / Handoff

| 模式 | 是否合适 | 原因 |
|------|---------|------|
| Sequential | ✗ | 会议是动态决策，不是流水线 |
| Concurrent | ✗ | 需要有序对话，不是并行 |
| **GroupChat** | **✓** | 主持人 = `GroupChatManager`，单点决策；天然支持"轮转 + 终止条件" |
| Handoff | ✗ | `@` 会变成 `handoff_to_X()` 工具，把决策权下放到智能体；与"主持人控场"冲突 |
| Magentic | ✗ | 任务规划/重规划机制太重；会议没有 plan ledger 概念 |
| WriterCritic | ✗ | 无质量门禁循环 |

**结论**：`AgentWorkflowBuilder.CreateGroupChatBuilderWith(...)` + 自定义 `MeetingHostManager : GroupChatManager`。

### 1.2 顶层装配

```csharp
public sealed class MeetingExecutor
{
    private const int MinParticipants = 2;     // 修复缺陷 22:最少参会者
    private const int MaxParticipants = 8;     // 软上限警告
    private readonly AIAgentFactory _factory;
    private readonly MeetingSessionService _sessions;
    private readonly MeetingMessageService _messageService;
    private readonly MeetingCancellationRegistry _cancellationRegistry;
    private readonly IAppPaths _appPaths;
    // ...

    public async Task ExecuteAsync(
        string meetingId,
        string? fallbackProviderId,
        string? fallbackModelId,
        CancellationToken ct = default)
    {
        var session = _sessions.GetById(meetingId)
            ?? throw new InvalidOperationException($"会议 {meetingId} 不存在");

        // 修复缺陷 22:参会者数量校验
        var participantCount = session.Participants.Count;
        if (participantCount < MinParticipants)
        {
            _sessions.MarkAsAdjourned(meetingId);
            await _publisher.PublishAsync(
                Events.OnMeetingCancelled,
                new MeetingCancelledArgs(meetingId, "participant_count_less_than_2"));
            throw new InvalidOperationException(
                $"会议至少需要 {MinParticipants} 个参会者(当前 {participantCount} 个)");
        }
        if (participantCount > MaxParticipants)
        {
            _logger.LogWarning(
                "会议 {MeetingId} 参会者超过软上限 {Max}(当前 {Count}),可能影响体验",
                meetingId, MaxParticipants, participantCount);
        }

        // 修复缺陷 15:CTS 注册,使能 CancelAsync 真正中断 RunStreamingAsync
        using var linkedCts = CancellationTokenSource.CreateLinkedTokenSource(ct);
        if (!_cancellationRegistry.TryRegister(meetingId, linkedCts))
        {
            throw new InvalidOperationException(
                $"会议 {meetingId} 已有运行中的执行轮次");
        }

        try
        {
            // 装配顺序:manager 先构造,工具引用 manager,hostAgent 后构造再回填
            var manager = new MeetingHostManager(/* ... */, meetingId, /* ... */);
            var hostAgent = await BuildHostAgentAsync(manager, meetingId, /* ... */, linkedCts.Token);
            manager.SetHostAgent(hostAgent);

            var participants = await Task.WhenAll(
                session.Participants.Select(p =>
                    BuildParticipantAgentAsync(p, meetingId, /* ... */, linkedCts.Token)));

            var workflow = AgentWorkflowBuilder
                .CreateGroupChatBuilderWith(_ => manager)
                .AddParticipants(participants)
                .WithName($"meeting-{meetingId}")
                .Build();

            var attachments = await _attachmentService.GetByMeetingIdAsync(meetingId, linkedCts.Token);
            var openingMessage = BuildOpeningMessage(session, attachments, _appPaths);

            await foreach (var evt in InProcessExecution.RunStreamingAsync(
                workflow, openingMessage, linkedCts.Token))
            {
                await DispatchEventAsync(meetingId, evt, linkedCts.Token);
            }
        }
        catch (OperationCanceledException) when (linkedCts.IsCancellationRequested)
        {
            // 用户取消或外部取消 → 散会
            _sessions.MarkAsAdjourned(meetingId);
            await _publisher.PublishAsync(
                Events.OnMeetingCancelled,
                new MeetingCancelledArgs(meetingId, "user_cancel"));
        }
        finally
        {
            _cancellationRegistry.Unregister(meetingId);
        }
    }

    /// <summary>
    /// 修复缺陷 25:用户重复点发送时,backend 必须幂等。
    /// 检查 PendingRequestId + TryClearPending 乐观锁 + 写消息 + 唤醒 TCS。
    /// </summary>
    public async Task ResumeAsync(string meetingId, string userReply, CancellationToken ct = default)
    {
        var session = _sessions.GetById(meetingId);
        if (string.IsNullOrEmpty(session?.PendingRequestId))
        {
            _logger.LogWarning(
                "会议 {MeetingId} 没有挂起的征询,忽略 ResumeAsync(可能是用户重复点击)",
                meetingId);
            return;    // 静默忽略
        }

        // 用 PendingRequestId 做乐观锁,WHERE PendingRequestId = @expected
        var expectedRequestId = session.PendingRequestId;
        var rowsAffected = _sessions.TryClearPending(meetingId, expectedRequestId);
        if (rowsAffected == 0)
        {
            // 期间被另一次调用清掉 — 多次并发 ResumeAsync 的最后保护
            _logger.LogWarning(
                "会议 {MeetingId} ResumeAsync 乐观锁失败(并发清除),忽略",
                meetingId);
            return;
        }

        // 写 user 消息 + 唤醒 TCS
        await _messageService.AppendAsync(new MeetingMessageEntity
        {
            MeetingId = meetingId,
            SpeakerKind = "user",
            SpeakerId = "user",
            SpeakerName = "我",
            ContentMd = userReply,
            MessageRole = "normal",
        }, ct);

        await _publisher.PublishAsync(
            Events.OnMeetingUserSpoke,
            new MeetingUserSpokeArgs(meetingId, /* messageId */ "...", userReply, "reply"));

        _manager.OnUserReplied();    // _userReplyTcs.TrySetResult(true)
    }

    public Task CancelAsync(string meetingId, CancellationToken ct = default)
    {
        _cancellationRegistry.Cancel(meetingId);
        return Task.CompletedTask;
    }
}
```

**关键设计说明**：

- **缺陷 22**：参会者 < 2 时立刻抛异常 + 散会。UI 层也必须做提交前校验，但 backend 不能依赖 UI 正确（详见 [04 §3.2](./04-界面交互设计.md)）
- **缺陷 25**：`ResumeAsync` 入口检查 `PendingRequestId` + `TryClearPending` 乐观锁，重复调用静默忽略。`TryClearPending` 详见 [03 §4.1](./03-数据模型与持久化.md)
- **缺陷 26**：`MeetingSessions.Provider` / `MeetingSessions.Model` 在会议建立时锁定，**ExecuteAsync 中读 session.Provider / session.Model 而非传入参数**——传入参数仅作为"会议建立时无 Provider 配置"的兜底。会议进行中即使输入区切了 Model，也不影响当前会议（详见 [03 §3.1](./03-数据模型与持久化.md)）
- **装配顺序**：先构造 manager 占位 → 用 manager 构造工具 → 构造 hostAgent → 回填到 manager（详见 §三.8）

### 1.3 主持人 Agent 与参会者 Agent 的差异

| | 主持人 Agent | 参会者 Agent |
|--|------------|------------|
| 加入方式 | 不进 `AddParticipants`，由 `MeetingHostManager` 持有 | 进 `AddParticipants` |
| 提示词 | `prompts/meeting/host.md` | 各自 AgentEntity 的提示词 |
| 工具 | `ask_user` + `confirm_meeting_end` + `check_pending_user_input` + 系统默认只读工具 | 仅系统默认只读工具 + 绑定的只读插件（详见 §四） |
| 是否被 LLM 选中 | ✗（永远轮不到） | ✓（由主持人选） |

### 1.4 BuildOpeningMessage 规约（修复缺陷 5 + 19 + 28）

会议启动时，`MeetingExecutor` 把用户输入和附件清单组装成第一条 `ChatMessage`（角色 `User`），传入 `RunStreamingAsync` 作为工作流初始消息。**附件不内联到消息中**（避免 token 爆炸），而是把附件**绝对路径**以文本形式列出，让智能体按需用 `file_read` 工具读取。

**修复缺陷 19**：附件清单超过 N=10 个时截断显示，参会者通过 `list_meeting_attachments` 工具查询完整清单。

**修复缺陷 28**：`MeetingAttachments.StoredPath` 是相对路径（便于 workspace 迁移），但**对外暴露给 LLM 的总是绝对路径**——智能体不需要、也不应该理解 workspace 概念。

```csharp
private const int OpeningMessageAttachmentCap = 10;

private static ChatMessage BuildOpeningMessage(
    MeetingSessionEntity session,
    IReadOnlyList<MeetingAttachmentEntity> attachments,
    IAppPaths appPaths)
{
    var sb = new StringBuilder();
    sb.AppendLine($"会议主题：{session.Topic}");
    sb.AppendLine();

    if (attachments.Count > 0)
    {
        sb.AppendLine("可参考的附件（请按需调用 file_read 工具读取）：");

        // 修复缺陷 19:超过 N 个附件时截断,避免 openingMessage token 爆炸
        var displayCount = Math.Min(attachments.Count, OpeningMessageAttachmentCap);
        for (int i = 0; i < displayCount; i++)
        {
            var att = attachments[i];
            // 修复缺陷 28:对外暴露绝对路径,DB 仍存相对路径
            var absPath = Path.Combine(appPaths.WorkspaceResourcesDirectory, att.StoredPath);
            sb.AppendLine($"- {att.FileName} (绝对路径: {absPath}, 类型: {att.MimeType}, 大小: {att.SizeBytes} 字节)");
        }

        if (attachments.Count > displayCount)
        {
            sb.AppendLine($"- 等共 {attachments.Count} 个文件,如需查看完整附件清单,调 list_meeting_attachments 工具");
        }

        sb.AppendLine();
    }

    sb.AppendLine("会议参与者：");
    foreach (var p in session.Participants)
    {
        sb.AppendLine($"- {p.Name}（agentId: {p.AgentId}）");
    }

    return new ChatMessage(ChatRole.User, sb.ToString());
}
```

**关键约束**：

- 附件路径用文本形式，不内联 `DataContent`（10MB Excel 不能塞进 token）
- 智能体被装载了通用文件读取工具（`file_read` 等），自己判断需要时调用
- **暴露绝对路径**给 LLM 一致性最高（智能体不需要知道 workspace 概念）；DB 存相对路径便于 workspace 迁移
- N=10 截断后参会者用 `list_meeting_attachments` 工具拿完整清单（详见 §三.7）—— 该工具同样返回绝对路径

## 二、MeetingHostManager 实现

### 2.0 关键认知：AF GroupChat 没有"自然挂起"

**AF GroupChat 的内部模型**：

- `GroupChatHost` 维护一份内部 message buffer
- 每轮调 `SelectNextAgentAsync` → 选 agent → 喂 buffer → agent 生成 → 结果回填 buffer
- 调 `ShouldTerminateAsync` → 决定是否结束循环
- **没有任何"挂起 / 等待外部输入"机制**

这意味着：仅靠 `ask_user` 工具写 DB + 发事件，**完全无法暂停 AF 循环**。主持人本轮结束后，AF 会立刻进入下一轮，重新调 `SelectNextAgentAsync` —— 主持人会再选一个发言者，会议根本停不下来。

**正确做法**：在 `SelectNextAgentAsync` 入口处用 `TaskCompletionSource` **真正阻塞**，直到外部 `ResumeAsync` 调 `TrySetResult` 唤醒。

**另一个关键认知**：AF 的内部 buffer 与我们的 `MeetingMessages` DB 是两份不同步的数据。压缩段（`MeetingCompactionSegments`）只存在于 DB 里，AF 一无所知。所以 `UpdateHistoryAsync` 必须**完全无视**传入的 `history` 参数，直接从 DB 重建（含压缩段 + 尾部原文 + 用户插话队列）。

### 2.1 类骨架

```csharp

### 2.2 UpdateHistoryAsync —— 从 DB 重建历史（修复缺陷 3）

**完全无视 AF 传入的 `history` 参数**，直接从 DB 重建。理由见 §2.0。

```csharp
protected internal override async ValueTask<IEnumerable<ChatMessage>> UpdateHistoryAsync(
    IReadOnlyList<ChatMessage> history,    // 完全无视
    CancellationToken ct = default)
{
    // 1. 从 DB 重建历史（压缩段摘要 + 尾部原始消息）
    var rebuilt = await _historyProvider.BuildLlmHistoryAsync(_meetingId, ct);

    // 2. 消费用户插话队列，按入队时间穿插到合适位置
    //    （入队顺序与会议消息顺序天然一致，直接 append 到末尾即可）
    var pending = _pending.DrainAsUserMessages(_meetingId);
    if (pending.Count > 0)
    {
        rebuilt.AddRange(pending);
    }

    return rebuilt;
}
```

**重点**：

- `MeetingHistoryProvider.BuildLlmHistoryAsync` 详见 [03-数据模型与持久化.md §三-bis](./03-数据模型与持久化.md)，输出已经是"压缩段摘要 + 尾部原文"
- 用户插话队列由 `_pending.DrainAsUserMessages` 标记 Consumed=1 + 返回 `ChatRole.User` 消息
- AF 传入的 `history` 是它内部 buffer 的快照，**对我们没用**——我们的真相在 DB

### 2.3 SelectNextAgentAsync —— 入口阻塞 + 主持人决策（修复缺陷 1, 12, 17）

```csharp
private string? _lastSpeakerId;    // 缺陷 17: 防止主持人连续发言

protected internal override async ValueTask<AIAgent> SelectNextAgentAsync(
    IReadOnlyList<ChatMessage> history,
    CancellationToken ct = default)
{
    // —— A. 入口阻塞：如果 PendingRequestId 非空（主持人在等用户回复），等待 ——
    if (HasPendingUserRequest())
    {
        _userReplyTcs = new TaskCompletionSource<bool>(TaskCreationOptions.RunContinuationsAsynchronously);
        try
        {
            await _userReplyTcs.Task.WaitAsync(ct);
        }
        finally
        {
            _userReplyTcs = null;
        }

        if (_terminationFlag)
        {
            return _hostAgent;    // 占位:终止由 ShouldTerminate 决定
        }
    }

    // —— B. 主持人 LLM 决策选下一发言者 ——
    var freshHistory = await UpdateHistoryAsync(history, ct);
    var prompt = BuildSelectorPrompt(freshHistory, _participants);

    // 修复缺陷 20：LLM 推理层本身需要重试网络抖动
    var response = await InvokeWithLlmRetryAsync(
        () => _hostAgent.RunAsync(prompt, ct),
        nameof(SelectNextAgentAsync),
        ct);

    var pickedRaw = response.Messages.LastOrDefault()?.Text ?? string.Empty;

    // —— C. 防御性解析（修复缺陷 12）——
    var picked = ResolveAgent(pickedRaw);

    // —— D. 防止主持人连续发言（修复缺陷 17）——
    if (picked == _hostAgent
        && _lastSpeakerId == HostSpeakerId
        && _participants.Count > 0)
    {
        _logger.LogWarning(
            "主持人尝试连续发言两次,强制切换到第一个参会者 {AgentId}",
            _participants[0].Id);
        picked = _participants[0];
    }

    _lastSpeakerId = picked == _hostAgent ? HostSpeakerId : picked.Id;
    return picked;
}

private const string HostSpeakerId = "HOST";

/// <summary>
/// 防御性 ID 解析:去 markdown 围栏/引号/空白,模糊匹配,失败兜底返回首个参会者。
/// 修复缺陷 12:主持人 LLM 输出格式不规范不能让工作流崩溃。
/// </summary>
private AIAgent ResolveAgent(string raw)
{
    // 1. 清洗
    var cleaned = raw.Trim().Trim('`', '"', '\'', ' ', '\n', '\r');
    // 去除 ``` 围栏
    if (cleaned.StartsWith("```"))
    {
        var firstNewline = cleaned.IndexOf('\n');
        var lastFence = cleaned.LastIndexOf("```", StringComparison.Ordinal);
        if (firstNewline > 0 && lastFence > firstNewline)
            cleaned = cleaned.Substring(firstNewline + 1, lastFence - firstNewline - 1).Trim();
    }

    // 2. 精确匹配
    if (string.Equals(cleaned, HostSpeakerId, StringComparison.OrdinalIgnoreCase))
        return _hostAgent;

    var exact = _participants.FirstOrDefault(p =>
        string.Equals(p.Id, cleaned, StringComparison.OrdinalIgnoreCase));
    if (exact is not null) return exact;

    // 3. 模糊匹配:输出包含某个 agent ID
    if (cleaned.Contains(HostSpeakerId, StringComparison.OrdinalIgnoreCase))
    {
        _logger.LogWarning("主持人输出格式不规范 '{Raw}',模糊匹配到 HOST", raw);
        return _hostAgent;
    }

    var fuzzy = _participants.FirstOrDefault(p =>
        cleaned.Contains(p.Id, StringComparison.OrdinalIgnoreCase));
    if (fuzzy is not null)
    {
        _logger.LogWarning("主持人输出格式不规范 '{Raw}',模糊匹配到 {AgentId}", raw, fuzzy.Id);
        return fuzzy;
    }

    // 4. 兜底:返回第一个参会者
    _logger.LogError("主持人输出无效 '{Raw}',兜底选第一个参会者 {AgentId}", raw, _participants[0].Id);
    return _participants[0];
}
```

**输出格式约束**：主持人 LLM 必须返回纯 ID 字符串（`HOST` / `agent-id-xxx`）。提示词约束在 §五 + §4.2 主持人提示词关键约束.C。即使 LLM 不规范，`ResolveAgent` 三级回退保证工作流不崩。

### 2.4 ShouldTerminateAsync —— 终止标志 + 迭代上限兜底（修复缺陷 2 + 9）

```csharp
protected internal override async ValueTask<bool> ShouldTerminateAsync(
    IReadOnlyList<ChatMessage> history,
    CancellationToken ct = default)
{
    // 1. 终止标志(由 confirm_meeting_end 工具置位)
    if (_terminationFlag) return true;

    // 2. 迭代上限兜底(修复缺陷 9):override 后丢失了 AF 默认实现,必须显式补回
    if (IterationCount >= MaximumIterationCount)
    {
        _logger.LogWarning(
            "会议 {MeetingId} 达到最大迭代次数 {Max},强制结束",
            _meetingId, MaximumIterationCount);

        // 强制让主持人输出一段总结,否则 FinalSummary 是空的
        await ForceFinalSummaryAsync(ct);
        _terminationFlag = true;
        return true;
    }

    return false;
}

/// <summary>
/// 迭代上限触发时,强制让主持人输出一段总结写入 MeetingMessages(MessageRole=summary)。
/// 这样 confirm_meeting_end 路径下游能找到最终总结。
/// </summary>
private async Task ForceFinalSummaryAsync(CancellationToken ct)
{
    try
    {
        var freshHistory = await UpdateHistoryAsync(Array.Empty<ChatMessage>(), ct);
        var forcePrompt = string.Join("\n", new[]
        {
            "会议达到最大迭代次数(40 轮),请立刻产出一份会议总结,不要再追问、不要再选发言者。",
            "总结要求:覆盖每位参会者的关键观点、达成的共识、待办事项。",
            "调用 output_summary 工具提交总结(详见你的工具列表)。",
        });

        await InvokeWithLlmRetryAsync(
            () => _hostAgent.RunAsync(
                freshHistory.Append(new ChatMessage(ChatRole.System, forcePrompt)),
                ct),
            nameof(ForceFinalSummaryAsync),
            ct);
    }
    catch (Exception ex)
    {
        // 强制总结失败不抛异常:即便没有 summary 也要终止,避免无限循环
        _logger.LogError(ex, "强制生成最终总结失败,会议仍然终止但 FinalSummary 可能为空");
    }
}
```

**关键**：`_terminationFlag` 不是用 `ask_user` 的回复内容做关键词匹配置位，而是**等主持人 LLM 自己确认用户同意结束后调用 `confirm_meeting_end` 工具**置位。这把"理解用户意图"和"标记终止"解耦：

- LLM 理解语义（包括"嗯""对啊""可以呀""差不多了""结束吧"等无穷多种表述）
- 工具调用作为机器可识别的明确动作

### 2.5 用户插话（不打断当前发言者）

老板在任何时刻输入 → 进入 `MeetingPendingInputs` 队列 → `UpdateHistoryAsync` 在下一轮发言前消费。

**为什么不实时打断**：当前 superstep 内已经在跑某位 agent 的流式生成，强行打断会导致 `history` 中残留半截 assistant 消息，下一轮 superstep 上下文不自洽。让当前发言者说完，再让主持人决定如何应对老板的话——这恰好对应现实公司会议（"等张总说完我接老板的问题"）。

**重要补充**（修复缺陷 4）：主持人在调用 `ask_user` 之前，**必须先用 `check_pending_user_input` 工具检查队列**。如果队列里有未消费的插话，应优先处理插话，不要冒然征询结束。详见 §三的工具说明和 §五的提示词约束。

### 2.6 LLM 调用层重试（修复缺陷 20）

**问题**：智能体调用 LLM 时可能遇到瞬时网络错误、模型超时、5xx 网关错误。如果直接抛异常，AF 会触发 `ExecutorFailed` 让整个会议崩溃。会议是长流程，发言者多，单点失败概率显著增加。

**已有基础设施**（工作模式）：

- [FailureClassifier](../../../Src/Netor.Cortana.AI/WorkMode/Reliability/FailureClassifier.cs) —— 分类异常并返回最大重试次数（Network=5 / Tool=3 / ModelOutput=2 / Cancel/Config=0）
- [RetryingFunctionWrapper.InvokeWithRetryAsync](../../../Src/Netor.Cortana.AI/WorkMode/Tools/RetryingFunctionWrapper.cs#L49) —— 指数退避重试模板

**会议模式的扩展**：把 `FailureClassifier` 从 WorkMode 命名空间提到公共的 `Netor.Cortana.AI.Reliability`，让会议模式也能复用。然后**两层重试**：

#### A. LLM 推理层（主持人 / 参会者所有发言）

会议中所有 LLM 调用（`hostAgent.RunAsync` / `participantAgent.RunStreamingAsync`）都套一层重试。在 `MeetingHostManager` 内提供：

```csharp
private async Task<TResult> InvokeWithLlmRetryAsync<TResult>(
    Func<Task<TResult>> action,
    string operationName,
    CancellationToken ct)
{
    var attempt = 0;
    while (true)
    {
        try
        {
            return await action();
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            throw;
        }
        catch (Exception ex)
        {
            attempt++;
            var (category, maxRetries) = FailureClassifier.Classify(ex, ex.Message);

            if (category != FailureCategory.Network    // 仅网络瞬时错误重试
                || attempt >= maxRetries)
            {
                _logger.LogError(ex,
                    "LLM 调用 {Op} 失败({Category}, 第 {Attempt}/{Max} 次),不再重试",
                    operationName, category, attempt, maxRetries);
                throw;
            }

            var delay = TimeSpan.FromSeconds(Math.Pow(2, attempt - 1));
            _logger.LogWarning(ex,
                "LLM 调用 {Op} 网络错误第 {Attempt} 次,{Delay}s 后重试",
                operationName, attempt, delay.TotalSeconds);

            await _publisher.PublishAsync(
                Events.OnMeetingLlmRetrying,
                new MeetingLlmRetryingArgs(_meetingId, operationName, attempt, maxRetries, ex.Message));

            await Task.Delay(delay, ct);
        }
    }
}
```

**为什么只重试 Network**：

- `ModelOutput`（JSON 解析失败）—— 重试也大概率失败，应让主持人 LLM 自己重写
- `Tool`（工具执行错误）—— 已经被工具层 `RetryingFunctionWrapper` 重试过
- `Configuration` / `Cancel` —— 不应重试

调用点：

```csharp
// SelectNextAgentAsync 内
var response = await InvokeWithLlmRetryAsync(
    () => _hostAgent.RunAsync(prompt, ct),
    nameof(SelectNextAgentAsync),
    ct);

// ForceFinalSummaryAsync 内同样套用
```

#### B. 参会者 Agent 流式调用层

参会者的 `RunStreamingAsync` 由 AF GroupChatHost 调用，无法在 `MeetingHostManager` 拦截。改为**包装 AIAgent 实例**：

```csharp
public sealed class RetryingAgent : DelegatingAIAgent
{
    private readonly AIAgent _inner;
    private readonly ILogger _logger;
    private readonly IPublisher _publisher;
    private readonly string _meetingId;

    public override async IAsyncEnumerable<AgentRunResponseUpdate> RunStreamingAsync(
        IEnumerable<ChatMessage> messages,
        AgentThread? thread = null,
        AgentRunOptions? options = null,
        [EnumeratorCancellation] CancellationToken ct = default)
    {
        var attempt = 0;
        while (true)
        {
            attempt++;
            IAsyncEnumerable<AgentRunResponseUpdate>? stream = null;
            try
            {
                stream = _inner.RunStreamingAsync(messages, thread, options, ct);
            }
            catch (Exception ex) when (ShouldRetry(ex, attempt, out var delay))
            {
                await Task.Delay(delay, ct);
                continue;
            }

            // 流式枚举本身的异常需要单独处理(枚举器不能 try/catch yield)
            await foreach (var update in EnumerateWithRetry(stream, attempt, ct))
            {
                yield return update;
            }
            yield break;
        }
    }
}
```

> 注意：流式枚举中途网络断（缺陷 14）由 [03-数据模型与持久化.md §3.2](./03-数据模型与持久化.md) 的 `IsPartial` 字段处理——保存已收到的部分文本作为残留消息。重试只覆盖"还没开始流式" / "建立连接失败"这种 head-fail 情况。

#### C. 工具调用层（已有，仅需启用）

会议模式 Agent 装载工具时套一层 `RetryingFunctionWrapper.Wrap`：

```csharp
// MeetingAgentBuilder 内

var wrappedTools = _retryingWrapper.WrapAll(rawTools);   // 工具层重试
```

#### D. 重试事件 → UI 反馈

新事件 `meeting.llm.retrying` 让 UI 在重试时显示"网络抖动，正在重试..."状态文字（StatusHintBar）。详见 [03 §5.2](./03-数据模型与持久化.md) 事件契约。

### 三.5 会议特有工具：confirm_meeting_end（修复缺陷 2 + 10）

### 三.6 会议特有工具：check_pending_user_input（修复缺陷 4）

**用途**：主持人在调用 `ask_user` 之前必须先检查用户插话队列。如果队列里有未消费的插话，应优先处理插话——不要在用户已经表达了新观点的情况下还冒然征询"是否结束"。

```csharp
public AIFunction CreateCheckPendingUserInputTool()
{
    [Description("查询当前是否有用户的插话尚未被消费。" +
                 "在你即将调用 ask_user 征询会议结束前,必须先调用此工具检查。" +
                 "如果有未处理的用户插话,优先处理插话内容,不要冒然征询。")]
    Task<string> CheckPendingAsync(CancellationToken ct)
    {
        var pending = _pendingService.PeekUnconsumed(_meetingId);
        if (pending.Count == 0)
        {
            return Task.FromResult("没有未处理的用户插话,可以继续。");
        }

        var summary = string.Join("\n", pending.Select((p, i) =>
            $"{i + 1}. [{DateTimeOffset.FromUnixTimeMilliseconds(p.EnqueuedAt):HH:mm}] {p.Content}"));
        return Task.FromResult(
            $"有 {pending.Count} 条用户插话尚未处理:\n{summary}\n\n" +
            "请先处理这些插话,而不是征询会议结束。");
    }

    return AIFunctionFactory.Create(CheckPendingAsync, new()
    {
        Name = "check_pending_user_input",
        Description = "检查用户插话队列,在调用 ask_user 前必须先调用。",
    });
}
```

**注意 `PeekUnconsumed` 与 `DrainAsUserMessages` 的区别**：

- `PeekUnconsumed` —— 只读查询，**不标记 Consumed**。工具返回信息给主持人决策用
- `DrainAsUserMessages` —— 标记 Consumed=1 + 返回消息。在 `UpdateHistoryAsync` 中下一轮真正注入历史时调用

这样主持人在调 `ask_user` 之前能看见队列内容，但不会"消费"它——后续 `UpdateHistoryAsync` 仍会把这些消息注入到正确的 history 位置。

## 四、参会者 Agent 构建

### 4.1 工具集来源（**只读约束 - 修复缺陷 8**）

会议是"出主意"的场合，不是"动手干"的场合。参会者**只装载只读 / 查询类工具**（`file_read` / `web_search` / `db_query` 等），**不装载可变操作工具**（发邮件 / 写文件 / 发布 / 部署 / 数据库写入等）。后续真正动手的工作由会议结论驱动，转交给工作模式去做。

**为什么严格限制**：会议模式遵循"零浮窗交互"原则（[README §1.2](./README.md)），不能弹 `ApprovalFloatPopup`。如果允许敏感工具，要么跳过审批（危险），要么每次审批中断会议节奏（破坏体验）。最干净的设计就是从源头上不装载——会议要写邮件 → 给会议总结一条"待办：发邮件给 X" → 用户接着开工作模式跑这条总结即可。

[AIAgentFactory.Build](Src/Netor.Cortana.AI/AIAgentFactory.cs) 现有签名：

```csharp

#### 工具是否只读的判定

1. 工具被 `[ApprovalRequired]` 或类似元数据标记（已有的 `ApprovalRequiredAIFunction` 包装）
2. 工具名匹配可变动词前缀：`send_*` / `write_*` / `delete_*` / `create_*` / `update_*` / `publish_*` / `deploy_*` / `execute_*` / `run_*`（保守清单，可微调）
3. 工具的 `Description` 中包含"修改 / 写入 / 发送 / 删除 / 创建 / 部署 / 执行"等可变动词

    //   - 部分工具被禁用是正常约束,不是错误
    //   - 自己想问老板时应当在发言里说出问题,主持人会代为询问
    //   - 发言对象是会议室所有人,不是 1 对 1 问答
    var contextHeader = await _promptProvider.GetPromptAsync("meeting.participant_header", ct)
        ?? throw new InvalidOperationException("找不到参会者 header 提示词 meeting.participant_header");

    var clonedAgent = new AgentEntity
    {
        Id = agent.Id,
        Name = agent.Name,
        SystemPrompt = contextHeader + "\n\n---\n\n" + agent.SystemPrompt,
        // ... 其他字段从 agent 复制
    };

    // 只读模式:系统默认只读工具 + 绑定的只读插件,可变工具被过滤
    var listAttachmentsTool = _meetingControlTools.CreateListAttachmentsTool();
    return _factory.Build(
        clonedAgent,
        provider,
        model,
        extraTools: new[] { listAttachmentsTool },    // 参会者只装载只读的附件查询工具
        toolFilterMode: ToolFilterMode.ReadOnly);
}

```markdown

- 你只能发表观点和提供建议，**不能执行实际的可变操作**（发邮件 / 写文件 / 部署 / 修改数据等已被禁用）

- 如果讨论涉及需要实际操作，请把它作为待办建议写进发言中，会议结束后由用户在工作模式下执行

### 4.2 主持人 Agent 构建（特殊）

主持人不是用户配置的智能体，而是固化的系统 Agent。提示词通过 `IPromptProvider` 加载，**优先读 `<UserData>/prompts/meeting/host.md`，没有时回退到 EmbeddedResource 内的默认值**（详见 [05-实施路线图.md §2.B](./05-实施路线图.md)）：

```csharp
private async Task<AIAgent> BuildHostAgentAsync(
    MeetingHostManager manager,
    string meetingId,
    AiProviderEntity fallbackProvider,
    AiModelEntity fallbackModel,
    CancellationToken ct)
{
    // 通过 IPromptProvider 加载主持人提示词
    // 链路: LocalFilePromptProvider (文件系统覆盖层) → EmbeddedResourcePromptProvider (默认兜底)
    var hostPrompt = await _promptProvider.GetPromptAsync("meeting.host", ct)

    hostPrompt = hostPrompt.Replace("{participants}", BuildParticipantsBlock());

    {
        Id = "system-meeting-host",
        Name = "主持人",

    };

    var hitlTools = new HitlTools(_meetingHitlContext, _meetingNotifier);

    {
        hitlTools.CreateAskUserTool(),                          // 通用 ask_user
        meetingControlTools.CreateConfirmMeetingEndTool(),      // 标记会议结束
        meetingControlTools.CreateCheckPendingUserInputTool(),  // 检查用户插话队列
    };

        hostAgentEntity,
        fallbackProvider,

#### 主持人提示词关键约束

写在 `<UserData>/prompts/meeting/host.md` 或内嵌默认值，运行时 `{participants}` 占位符被替换。提示词覆盖以下七个主题：

##### A. 角色与权限

- 你是会议主持人，参会者是：`{participants}`
- 你只能从参会者中选发言者；**绝对不能要求 user 发言**
- user 是老板，会主动插话或回应你的征询；你不能"点 user 的名"

##### B. 启动会议（修复缺陷 6 + 主题对齐）

会议刚开始时（history 中只有 1 条用户消息），你应该被选为第一个发言者（返回 `HOST`）。

读完用户的输入后，做**主题清晰度判断**：

- 议题对象是否明确？（讨论的是什么事 / 什么人 / 什么决策）
- 期望产出是否明确？（要意见？要方案？要决策？）
- 信息约束是否充分？（背景、范围、时间、参与者立场）

**主题清晰** → 输出开场白（复述议题、说明流程、明确目标产出），然后下一轮选某个参会者发言。

**主题模糊** → 输出引导对话（指出哪个维度不清楚、给出几个可能的理解供 user 选择），然后**立刻调用 `ask_user` 工具**等用户回复。

不要假设主题。不要替用户补全主题。如果不清楚就问。

##### C. 选发言者（每轮 SelectNextAgentAsync）

- 看到自己上一轮说了 `@某某` → 优先选某某
- 看到 user 在 history 里说了 `@某某` → 倾向选某某，但保留判断权（被点的人若完全不熟悉话题，可先让其他人铺垫）
- 议题成熟时，选 `HOST` 自己发言收尾（输出总结）
- 讨论卡住或重复 → 主动选 `HOST` 自己介入收尾或问 user

**输出格式**：纯 ID 字符串（`HOST` / `agent-id-xxx`），不要任何解释、不要 markdown、不要标点。

##### D. 收尾流程（修复缺陷 1+2+4+13 的提示词侧）

当你判断议题已充分讨论，按以下顺序操作：

1. **调用 `output_summary` 工具**（修复缺陷 13）—— 不要直接 markdown 输出总结。`output_summary(content)` 会把总结作为 `MessageRole=summary` 落库，UI 用突出样式显示。
   - 总结要求：覆盖每位参会者的关键观点、达成的共识、待办事项
   - 调用此工具后**不要再 markdown 输出**，直接进入下一步
2. **调用 `check_pending_user_input` 工具**（修复缺陷 4）—— 检查用户插话队列
   - 如果队列有未处理的用户插话 → **不要调 ask_user**，转而把插话作为新讨论点处理（选合适的参会者发言或自己回应）
   - 如果队列为空 → 进入下一步
3. **调用 `ask_user` 工具**（修复缺陷 1）—— 参数 = "我们今天的讨论是否可以告一段落了？" 或类似征询语

> **顺序不可调换**：output_summary → check_pending_user_input → ask_user。如果你跳过 output_summary 直接 ask_user，confirm_meeting_end 会因找不到 summary 而失败；如果你跳过 check_pending_user_input，可能错过用户已经插话的新议题。

##### E. 处理用户对征询的回复（修复缺陷 18 的提示词侧）

**回复前必查**：先回头读 history 中你最近一次 `ask_user` 的 question 内容，明确用户在回应**哪种征询**。如果实在记不清（罕见情况），可以再调一次 `ask_user` 问"您是想[A]还是[B]？"

`ask_user` 在会议中有三种使用场景：

1. **主题对齐征询**（§B 启动时）—— 用户回复用于补全主题，进入正式讨论
2. **修改总结征询**（罕见，由用户上一轮的修改要求触发）—— 重写总结后再次走 D 流程
3. **是否结束征询**（§D 收尾流程）—— 用户回复决定终止 / 修改 / 继续

用户对 §D 收尾征询的回复有四种语义可能，你需要理解后采取行动：

| 用户语义 | 你要做的 |
|---------|---------|
| 同意结束（"可以""好的""结束吧""差不多了"等任何形式的肯定） | **调用 `confirm_meeting_end` 工具**正式标记会议结束（工具会自动取最近 summary 写入 FinalSummary） |
| 要求修改总结（"你漏了 X""不对，重点是 Y") | 不调 `confirm_meeting_end`；重新走 D 流程：output_summary（新版） → check_pending → ask_user |
| 要求继续讨论（"再聊聊 Z""我想听听 X 怎么看") | 不调 `confirm_meeting_end`；选合适的参会者发言 |
| 临时模糊化主题（"等等，方向不对，应该是…") | 不调 `confirm_meeting_end`；像 §B 那样重新对齐主题 |

**关键**：理解用户意图是你的职责。不要靠关键词匹配——用户可能用任何措辞表达同意。理解后用工具调用作为机器可识别的动作。

##### F. 处理用户插话与代为询问（修复缺陷 30 的提示词侧）

`UpdateHistoryAsync` 会自动把用户插话注入到 history。当你看到 history 末尾有新的 user 消息（不是对你 ask_user 的回复），按以下原则处理：

- 用户对当前话题有补充 → 选合适的参会者基于补充继续发言
- 用户表达不同意见 → 选某个参会者回应该意见，或自己介入引导讨论
- 用户提出新议题 → 判断是否在原议题范围内：在 → 顺势讨论；不在 → 礼貌告知"这是个好问题，要不要单开一个会议讨论？"，然后选回原议题

**代为询问机制（修复缺陷 30）**：

参会者**没有 `ask_user` 工具**——只有你有。当你看到参会者发言里出现以下信号，说明他们需要你代为询问老板：

- "我需要老板确认 X 才能继续"
- "在不知道 Y 的情况下，我无法给出更精确的方案"
- "如果老板倾向 A 还是 B，我的建议会很不一样"
- "请问老板对这个数字 / 方向 / 偏好的态度是什么"

处理：

1. 评估是否值得问老板（避免每个参会者的小疑问都打扰老板）
2. 值得 → **走简版征询**：直接调 `ask_user(question)` 把参会者的问题转述给老板。**不要走 §D 的完整收尾流程**（因为这不是要结束会议）
3. 不值得 → 选另一个参会者发言，或自己介入引导（"小李，没有这个数据时你能给个范围估计吗？"）

收到老板回复后，回到讨论上下文，让原参会者继续。

##### G. 死循环兜底

- 单次 ask_user 之后再次 ask_user 应至少间隔 3 轮普通发言（避免反复打扰用户）
- 同一参会者连续被选 3 次以上需要换人（除非用户明确要求）
- 主持人自己不能连续发言两次（会话顺序：HOST → 参会者 → HOST → 参会者...）；如果你违反，框架会强制切换到第一个参会者
- AF 的 `MaximumIterationCount=40` 是硬上限，不靠你保证；触顶时框架会强制让你输出最终总结并终止

#### 主持人提示词分层（修复缺陷 29）

主持人提示词总长度 ~250 行 / ~3000 token，每次 `SelectNextAgentAsync` 决策都送过去会让 token 成本失控（30 轮会议主持人决策 ~120K token）。

**分层策略**（v1.1 演进，v1.0 先全量注入）：

| 层 | 内容 | 注入时机 |
|----|------|---------|
| **SystemPrompt（一次性 + ChatClient prompt cache）** | A 角色与权限 / C 选发言者通用规则 / G 死循环兜底 | Agent 构造时设置一次,LLM provider 缓存命中后续调用 |
| **DecisionPrompt（每轮按需注入）** | B 启动判断（仅首轮）/ D 收尾流程（仅议题成熟时）/ E 处理征询（仅有 inquiry 待回复时）/ F 处理插话（仅有 user 消息在尾部时） | `MeetingHostManager.BuildSelectorPrompt` 检测当前 history 状态,只注入对应小段 |

**判断逻辑示例**：

```csharp
private string BuildSelectorPrompt(IEnumerable<ChatMessage> history, ...)
{
    var sb = new StringBuilder();

    var historyList = history.ToList();

    // 首轮:仅注入 §B
    if (_lastSpeakerId is null)
    {
        sb.AppendLine(LoadDecisionSection("B_startup_topic_alignment"));
    }
    else
    {
        // 后续轮:按 history 状态选择性注入
        var lastMsg = historyList.LastOrDefault();
        if (lastMsg?.Role == ChatRole.User)
        {
            // 用户在 history 末尾说了话 — 可能是插话或回复
            if (HasPendingUserRequest())
                sb.AppendLine(LoadDecisionSection("E_handle_inquiry_reply"));
            else
                sb.AppendLine(LoadDecisionSection("F_handle_user_interrupt"));
        }

        // 议题成熟启发式:同一议题讨论超过 X 轮且无新增信息
        if (IterationCount > 8 && DetectTopicMaturity(historyList))
        {
            sb.AppendLine(LoadDecisionSection("D_closing_flow"));
        }
    }

    sb.AppendLine("---");
    sb.Append(historyList.LastN(20).ToText());    // 仅最近 N 条原文(更早的从压缩段拿)
    return sb.ToString();
}
```

**v1.0 简化做法**：DecisionPrompt 全量注入（不分层），但 SystemPrompt 用 prompt cache（如 OpenAI / Anthropic 提供商支持）。**v1.1+ 再做精细分层**。

**收益估算**：典型决策 token 减半（4000 → 2000），主持人响应更快。代价：BuildSelectorPrompt 状态判断逻辑复杂度上升，需要单元测试覆盖各分支。

## 五、流式事件分发

### 5.1 总览

参考 [WorkModeStreamProcessor](Src/Netor.Cortana.AI/WorkMode/WorkModeStreamProcessor.cs) 的 chunk 解析模式，但事件名换成 `meeting.*`。

```csharp
public sealed class MeetingStreamProcessor
{
    public async Task DispatchAsync(string meetingId, WorkflowEvent evt, CancellationToken ct)
    {
        switch (evt)
        {
            case ExecutorInvokedEvent invoked:
                // 一位发言者开始 → 推 meeting.speaker.changed
                await _publisher.PublishAsync(Events.OnMeetingSpeakerChanged,
                    new MeetingSpeakerChangedArgs(meetingId, invoked.ExecutorId, ResolveKind(invoked.ExecutorId)));
                break;

            case AgentResponseUpdateEvent delta:
                // 流式 token → meeting.message.delta
                await DispatchUpdateContentsAsync(meetingId, delta.Update.Contents, ct);
                break;

            case AgentResponseEvent completed:
                // 一条发言定稿 → meeting.message.completed + INSERT MeetingMessages
                await OnMessageCompletedAsync(meetingId, completed, ct);
                break;

            case WorkflowOutputEvent output:
                // 会议正式结束 → meeting.completed
                await OnMeetingCompletedAsync(meetingId, output, ct);
                break;
        }
    }
}
```

### 5.2 思维链 / 工具调用拆分

`AgentResponseUpdateEvent.Update.Contents` 的处理与工作模式 1:1 一致：

| AIContent 类型 | 处理 |
|---------------|------|
| `TextReasoningContent` | → `meeting.thinking.delta`（带 messageId, speakerId） |
| `FunctionCallContent` | → `meeting.tool.call`（带 callId, name, args） |
| `FunctionResultContent` | → `meeting.tool.result`（带 callId, result/exception） |
| `TextContent` | → `meeting.message.delta`（累积 markdown） |

**唯一例外**：当 `FunctionCallContent.Name == "ask_user"` 且发言者 = 主持人时，工具调用的特殊处理由 `HitlTools` 自身完成（已经写库 + 发 `meeting.askuser.requested` 事件）；处理器把它再额外发一次 `meeting.tool.call` 是冗余的，可以跳过。

### 6.1 关键不变量

| 不变量 | 说明 |
|--------|------|
| TCS 单例 | 同一时间只有一个 `_userReplyTcs`，`SelectNextAgentAsync` 入口 new + finally 置 null |
| 历史真相在 DB | `UpdateHistoryAsync` 永远从 `MeetingMessages` 重建，AF 内部 buffer 仅作"调用喂数据"的载体，不作真相 |
| 终止标志单调 | `_terminationFlag` 一旦 true 不再回 false；下次 ShouldTerminate 必然返回 true |
| ResumeAsync 三件事 | 写 MeetingMessages → 清 PendingRequestId → 唤醒 TCS。三步顺序不可调换（写库先于唤醒，唤醒先于…无所谓） |
| Workflow 真正终止由 LLM 调工具决定 | 不靠 `ResumeAsync` 解析用户回复关键词；主持人 LLM 自己理解后调 `confirm_meeting_end` |

### 6.2 正常 vs 异常路径对照

| 路径 | 是否会卡死 |
|------|----------|
| 主持人调 ask_user → user 回复 → 主持人调 confirm_meeting_end | 正常终止 |
| 主持人调 ask_user → user 回复 "继续讨论" → 主持人选下一个发言者 | TCS 唤醒后正常进入下一轮 |
| 主持人调 ask_user → user 长时间不回复 → app 关闭 | session 状态保持 Status=1，下次启动 MeetingStartupService 把它置 Status=3 已散会（详见 [05-实施路线图.md §3.7](./05-实施路线图.md)） |
| 主持人忘了调 confirm_meeting_end，用户已经说"结束吧" | _terminationFlag 不被置位 → ShouldTerminate 返回 false → 主持人下一轮再有机会调（提示词强约束应避免，AF MaximumIterationCount=40 兜底） |
| `ResumeAsync` 调用时 `_userReplyTcs` 为 null（罕见竞态） | `?.TrySetResult` 无副作用；下一轮 SelectNext 读 PendingRequestId 已为空，不再阻塞，自然进入正常决策 |
