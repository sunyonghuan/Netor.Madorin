# 渐进式计划与动态专家问题记录

**记录时间**：2026-05-29
**状态**：问题落盘，后续单独制定详细方案

---

## 一、问题背景

真实业务任务并不总是能在开始时一次性拆出完整子步骤。

例如：

- 创建大型项目时，开始只能确定需求、架构、模块边界，具体子步骤需要进入某个阶段后才能明确。
- 服务器故障排查时，用户往往不知道问题在哪里，总经理也不能直接规划最终修复步骤，需要先收集日志、检查环境、定位异常。
- 数据分析、代码重构、系统迁移、线上事故处理等场景，都可能先需要“调查计划”，等信息足够后才能生成“执行计划”。

因此，工作模式不能只支持“一次性完整计划 → 按计划执行”，还需要支持：

- 先规划大步骤，执行到某个阶段后再展开子步骤。
- 执行中追加、替换或重排尚未执行的子步骤。
- 先进行信息收集，再制定真正可执行的解决方案。
- 必要时由总经理调度专业子智能体或临时专家完成调查与分析。

## 二、问题 1：渐进式计划

### 当前能力

当前系统已经具备一部分基础能力：

- `set_plan` 可以重新写入完整计划。
- `dispatch_step` 每次执行时读取当前最新计划。
- 已执行过程写入 `WorkExecutionLogs`，不会因为计划覆盖而删除历史记录。

这意味着：总经理理论上可以通过再次调用 `set_plan` 来“重新规划”后续步骤。

### 当前不足

当前实现仍然不适合真实业务里的渐进式计划：

- `set_plan` 是整体覆盖，不支持只展开某个主步骤。
- `WorkPlan` 要求每个主步骤必须有 `sub_steps`，不适合“先只有大步骤，子步骤待调查后生成”的场景。
- 没有计划修订记录，用户无法清楚看到“什么时候、为什么调整过计划”。
- 如果整体覆盖后步骤序号变化，后续 `dispatch_step(stepIndex, subStepIndex)` 可能出现语义错位。
- 当前 UI 更适合展示已确定计划，不够适合展示“待展开主步骤”。

### 后续方向

后续需要单独设计“渐进式计划”能力。方向包括但不限于：

- 允许主步骤暂时没有完整子步骤，或只有一个“调查并展开本阶段”的占位子步骤。
- 新增局部计划调整工具，例如：
  - 展开某个主步骤的子步骤。
  - 追加某个主步骤的子步骤。
  - 替换未执行子步骤。
  - 记录计划修订原因。
- 区分“调查计划”和“执行计划”。
- 历史时间线中展示计划修订节点。
- UI 上明确区分“已确定子步骤”和“待展开阶段”。

## 三、问题 2：动态专家 / 临时子智能体

### 当前能力

当前系统支持调用已有子智能体：

- 用户通过 `@` 提及已有智能体。
- 总经理可以调用同步子智能体工具 `agent_*`。
- 长任务可以使用 `start_subagent_*` / `wait_for_subagent` / `cancel_subagent`。

这适合用户已经知道要找哪个专家、并且该专家已经存在的情况。

### 当前不足

真实业务里，用户经常不知道需要哪些专家，总经理也可能需要根据任务临时组织调查分工。

例如服务器故障排查可能需要：

- 日志收集智能体。
- 批量日志读取与摘要智能体。
- Linux 运维分析智能体。
- 解决方案专家智能体。

当前工作模式还不支持总经理在任务中临时创建这些专业角色，也不支持为临时专家动态限制工具范围、传入专门指令、收集结构化结果。

### 后续方向

后续需要评估“动态专家 / 临时子智能体”能力。方向包括但不限于：

- 允许总经理启动临时专家任务，而不是要求用户提前创建并 `@` 提及。
- 临时专家只在当前工作任务内有效，不一定持久化为全局智能体。
- 总经理为临时专家指定：
  - 角色名称。
  - 调查目标。
  - 可用工具范围。
  - 输入材料。
  - 输出格式。
- 临时专家输出结构化调查结果，总经理再汇总为正式执行计划。
- 对高风险工具仍然走授权机制。

## 四、初步产品判断

这两个问题应该分阶段处理。

优先级建议：

1. **先做渐进式计划**  
   这是基础能力。没有它，动态专家收集到信息后也很难优雅地更新后续步骤。

2. **再做调查型任务流程**  
   明确“先调查，后执行”的任务形态，让总经理不要过早生成最终方案。

3. **最后做动态专家 / 临时子智能体**  
   动态专家很有价值，但需要工具权限、输出格式、生命周期、UI 展示和安全边界一起设计。
