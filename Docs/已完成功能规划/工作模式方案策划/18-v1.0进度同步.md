## 实施过程中的偏离与新增

### 偏离 1：从 `RunAsync`（一次性）改为 `RunStreamingAsync`（流式）

**计划原文（13 文档 §6）**：未明确指定流式 / 非流式
**实际选择**：流式

**原因**：用户体验要求实时显示思考过程、工具调用过程，与专家模式一致。非流式 `RunAsync` 一次性返回完整结果，中间过程不可见。

**新增组件**：[WorkModeStreamProcessor.cs](../../../Src/Netor.Cortana.AI/WorkMode/WorkModeStreamProcessor.cs)
**职责**：消费 `RunStreamingAsync` 的 chunk，按内容类型（`TextReasoningContent` / `FunctionCallContent` / `FunctionResultContent` / `TextContent`）发布对应的 `work.*` 事件。
**架构层次**：
```
WorkflowExecutor（执行编排 + 历史维护）
    ↓ chunk
WorkModeStreamProcessor（流→事件转换）
    ↓ work.* events
WorkModeViewController（事件→UI 卡片渲染）
```

### 偏离 2：UI 卡片复用 `RealtimeProcessCard`，不新建 ThinkingCard / ToolCard

**计划原文（13 文档 §6）**：未指定具体控件
**实际选择**：复用专家模式的 `RealtimeProcessCard`

**原因**：
- `RealtimeProcessCard` 已支持流式 `AppendContent` + `Complete` 状态切换
- 视觉风格与专家模式统一
- 避免重复造轮子

**注意点**：`RealtimeProcessCard` 默认 `RootBorder.Margin="50,0"`，工作模式中通过 `WorkModeViewController.ApplyWorkModeCardMargin` 覆盖为 `(16, 2, 16, 0)`，使其与用户气泡同宽并紧贴。

### 偏离 3：总经理提示词从"先追问"改为"主动规划"

**计划原文（11 文档 §2.6）**：未具体规定追问 vs 主动规划风格
**实际版本 1**：先充分追问需求再制定计划
**用户反馈**：不符合"一人公司"定位 — 用户是老板，只做决策（做/不做），方案应由总经理出
**修正版本 2**：[prompts/work_mode/general_manager.md](../../../Src/Netor.Cortana.AI/prompts/work_mode/general_manager.md) — 主动规划，第一轮尽快形成计划；允许先查模板、历史、最近任务，必要时先询问关键决策

### 新增：2026-05-29 真实场景推演后的取消链路修正

- 场景问题：用户在任务执行中输入“取消/停止/不要继续”时，原逻辑会把它当作软抢占插话排队，必须等总经理下一次调用 `check_pending_user_input` 才可能处理，体验上像“取消不生效”。
- 已修正：`WorkModeInputVm` 在活跃任务存在时先识别取消指令，命中后直接调用 `WorkflowExecutor.CancelAsync`，不再进入 `WorkPendingInputs` 队列。
- 场景问题：`WorkflowExecutor.CancelAsync` 之前只修改数据库状态并发布事件，没有取消正在运行的 `RunStreamingAsync`，AI 仍可能继续输出或调用工具。
- 已修正：新增 `WorkTaskCancellationRegistry`，`WorkflowExecutor` 每轮执行注册 linked cancellation token；UI 停止按钮、用户取消输入和 `cancel_task` 工具都会触发同一个运行时取消信号。
- `TaskControlTools.cancel_task` 现在除了标记任务取消和发布事件，也会通过取消注册表停止当前执行轮次。
- 仍需后续验证：不同模型/供应商对流式取消的响应速度不一定一致，长工具调用内部是否及时响应取消还取决于具体工具实现。

### 新增：2026-05-29 测试问题集中修正

- `WorkModeViewController` 在新增消息、追加步骤、工具结果、授权提示、并行/嵌套/子智能体事件后都会滚动到底部，修复长页面增长时需要用户手动下拉的问题。
- `set_plan` 与 `load_plan_from_template` 保存计划后会写入 `PendingRequestKind=plan_confirmation` 并发布“工作计划已制定，确认后我再开始执行。”提示。

- `general_manager.md` 已同步：计划制定或模板加载后必须等待用户明确确认开始，再派发任何执行步骤。

## 已知问题

### 1. UI 样式：思考卡片与气泡间距过宽（已处理）

**根因**：`OnWorkTaskCreated` 过早把空 `TimelineBlock` 插入 `MessageList`。空时间线没有步骤，但 `StepsHost.Margin="16,8,16,8"` 仍会占用高度，夹在用户气泡和思考卡片之间。
**处理**：
- `WorkModeViewController.OnWorkTaskCreated` 只创建时间线对象，不立即加入消息流。
- 第一个 `OnWorkStepStarted` 到达时才插入时间线。
- 工作模式 `RealtimeProcessCard.RootBorder.Margin` 覆盖为 `(16, 2, 16, 0)`，与用户气泡保持 2px 间距。

### 2. 时间线主/子步骤层级错误（已处理）

**根因**：`dispatch_step` 事件中的 `StepTitle` 是子步骤标题，旧 UI 直接把它作为主步骤加入 `TimelineBlock`，导致“圆点 + 子步骤名”，不符合 09 文档“圆点 + 主步骤名，主步骤下挂多个子步骤卡片”的结构。
**处理**：
- `WorkModeViewController.OnWorkStepStarted` 现在将 `Department` 按主步骤标题使用，将 `StepTitle` 按子步骤标题使用。
- 同一主步骤内只创建一个主步骤行，后续 `dispatch_step` 创建新的 `SubStepCard`。
- 思考卡片、工具卡片、验收卡片优先追加到当前 `SubStepCard` 内。
- `dispatch_step` 工具调用卡片先于 `OnWorkStepStarted` 到达时，先暂存，子步骤创建后再归入卡片内部。

### 3. 子智能体调用过程未拦截输出
