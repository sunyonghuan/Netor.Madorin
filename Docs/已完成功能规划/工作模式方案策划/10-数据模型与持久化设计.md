# 10 - 数据模型与持久化设计

> 工作模式的数据库表结构与持久化策略
>
> **核心原则**：AOT 安全（JsonSerializerContext）、轻量持久化、AF Workflow 状态作为唯一真相

---

## 一、设计原则

### 1.1 状态归属（不重复定义）

工作模式涉及两类状态，分别由不同方负责：

| 状态 | 谁拥有 | 怎么读 |
|------|--------|--------|
| Workflow 运行时状态（Plan / Ledger / 工具调用历史） | **AF 框架**（通过 ICheckpointStore 自动持久化） | `InProcessExecution.ResumeAsync(workflow, runId)` |
| 任务元数据（Title / SessionId / RunId / IsActive） | **Cortana**（WorkTasks 表） | `SELECT FROM WorkTasks WHERE Id = ?` |
| 用户可见的对话内容 | **ChatHistoryDataProvider**（ChatMessages 表） | 已有机制 |
| 任务过程明细（工具调用 / 验收记录） | **Cortana**（WorkExecutionLogs 表） | UI 重建时间线时读 |

**不要再设计** `WorkTaskStatus { Clarifying / Planning / PlanReview / Executing ... }` 这种语义状态字段——这种状态由"主 Agent 的对话历史"表达，是 AI 行为，不是数据库状态。

### 1.2 与 ChatSession 的关系

工作模式 Tab **共享**对话模式 Tab 的 `ChatSession`，原因：

- 永续对话要求："任务完成后用户继续说'再做一份 5 月的'"——只有共享会话才能让 AI 看到上一个任务的总结
- 现有 `ChatSession.Categorize` 按 `WorkspaceDirectory.Md5Encrypt()` 分组，工作模式的会话同样按 workspace 分组
- 任务完成后总结写入 `ChatMessages`，同一 Session 的用户在专家模式 / 工作模式都能看见

**唯一区别**：工作模式 Tab 的输入会先走 `WorkModeInputRouter`，普通对话还是走 `IAiChatEngine`。详见 [12-输入路由与状态机设计.md](./12-输入路由与状态机设计.md)。

### 1.3 AOT 安全

- 所有持久化的复合对象（`WorkPlan` / `ToolCallRecord` 等）都注册到 `WorkModeJsonContext`
- 数据访问保持 Cortana 既有风格（`CortanaDbContext.Execute` + `SqliteCommand` 显式参数）
- 不使用 ORM、不使用反射映射

## 二、数据边界

### 2.1 复用的现有表

| 表 | 工作模式如何使用 |
|----|----------------|
| `ChatSessions` | 工作模式任务通过 `WorkTasks.SessionId` 关联到此表，与对话模式共享 |
| `ChatMessages` | 用户输入、需求补齐对话、计划展示、`ask_user` 提问、最终总结都写入此表（与现有专家模式一致） |
| `ChatMessageAssets` | 用户附件、AI 生成的图片，复用现有机制 |

### 2.2 新增表

| 表 | 用途 | 行数级别 |
|----|------|---------|
| `WorkTasks` | 任务元数据 + RunId | 每任务 1 条 |
| `WorkExecutionLogs` | 工具调用 / 验收 / 错误明细 | 每任务 N 条 |
| `WorkflowCheckpoints` | AF Workflow Checkpoint（自定义 ICheckpointStore 后端） | 每 superstep 1 条，多任务复用 |
| `WorkPendingInputs` | 用户在执行中插话的输入队列 | 短暂存活 |
| `WorkPlanTemplates` | 可复用的工作流模板 | 用户/系统主动创建 |
| `WorkBackgroundJobs` | **仅服务"主软件托管的背景任务"**（v1.0 即子智能体）。**不服务插件长任务** | 每个 [LONG] 子智能体调用 1 条 |

> **重要边界**：`WorkBackgroundJobs` 只记录主软件托管的背景任务（`IBackgroundJobExecutor` 实现）。**插件长任务由插件子进程自管**——插件提供查询类工具（如 PowerShell 的 `sys_get_session_status`）让 AI 直接查询，主软件不写入这个表。详见 [16 文档 §八](./16-长任务可靠性与重试策略.md)。

### 2.3 废弃的旧表

- `OrchestrationTask` / `OrchestrationStep` / `OrchestrationMessage` / `OrchestrationParticipant` — 旧的多智能体编排方案，不在工作模式中使用。
  - 建议处理：保留表结构（兼容旧数据），但工作模式不写入。后续若旧功能下线，再迁移/删除。
- 现有 `WorkflowCheckpoints` 表（在 `CortanaDbContext.cs` 中已存在，按 `(TaskId, CheckpointId)` 主键）：**可继续复用，但需扩展为符合 AF JsonCheckpointStore 接口的形态**（详见 §3.4）。

## 三、表结构

### 3.1 WorkTasks 表

```sql
CREATE TABLE IF NOT EXISTS WorkTasks (
    Id              TEXT PRIMARY KEY,            -- GUID(N)
    SessionId       TEXT NOT NULL,               -- 关联 ChatSessions.Id
    WorkspaceId     TEXT NOT NULL DEFAULT '',    -- workspace MD5（与 ChatSession.Categorize 一致）

    Title           TEXT NOT NULL DEFAULT '',    -- 任务标题（AI 生成或用户手输）
    InitialInput    TEXT NOT NULL DEFAULT '',    -- 触发任务的第一条用户输入（用于回看）

    -- 与 AF Workflow 的关联（关键）
    RunId           TEXT,                        -- AF StreamingRun.RunId，恢复时必需
    IsActive        INTEGER NOT NULL DEFAULT 1,  -- 1=活跃（含运行/HITL等待），0=终结

    -- 计划快照（最新覆盖式，旧版本不保留 —— 用户已确认"不需要版本管理"）
    CurrentPlanJson TEXT,                        -- WorkPlan 的 JSON（WorkModeJsonContext）

    -- HITL 待响应请求（一个任务最多一个挂起请求）
    PendingRequestId    TEXT,                    -- AF RequestInfo.RequestId
    PendingRequestKind  TEXT,                    -- "approval" / "ask_user"
    PendingRequestData  TEXT,                    -- 请求载荷的 JSON 快照（用于 UI 重建授权浮窗）

    -- 终态字段
    CompletedAt     INTEGER,                     -- Unix 毫秒
    FinalReport     TEXT,                        -- final_report 工具的输出
    ErrorMessage    TEXT,                        -- 失败原因

    -- 元数据
    Provider        TEXT NOT NULL DEFAULT '',    -- AiProviders.Id（任务启动时锁定）
    Model           TEXT NOT NULL DEFAULT '',    -- AiModels.Id
    AgentId         TEXT NOT NULL DEFAULT '',    -- Agents.Id（"总经理"角色）
    MentionsJson    TEXT,                        -- 任务启动时 @ 的子智能体列表

    SourceTaskId    TEXT,                        -- "再做一份"复用上一任务时的来源 ID
    ParentTaskId    TEXT,                        -- 嵌套子工作流：指向父任务（v1.0 嵌套深度上限 2）

    -- 长任务可靠性字段（详见 16 文档）
    IsOrphaned          INTEGER NOT NULL DEFAULT 0,  -- 应用重启检测：上次未正常关闭
    OrphanedDetectedAt  INTEGER,                     -- 标记为孤儿的时刻
    HeartbeatAt         INTEGER,                     -- 最近一次活动时间（用于死循环检测）

    -- 软抢占（详见 12 文档 §三）
    HasPreemption       INTEGER NOT NULL DEFAULT 0,  -- 用户输入了"立刻停"等抢占性指令

    -- 进度估算（详见 16 文档 §八）
    TotalSubStepsEstimate     INTEGER,           -- 计划阶段确定的子步骤总数
    CompletedSubSteps         INTEGER NOT NULL DEFAULT 0,
    CurrentSubStep            TEXT,              -- 当前正在做的子步骤标题
    EstimatedCompletionAt     INTEGER,           -- 预计完成时间

    CreatedAt       INTEGER NOT NULL,
    UpdatedAt       INTEGER NOT NULL,
    LastActiveAt    INTEGER NOT NULL,            -- 用于"当前会话最近活跃任务"查询

    FOREIGN KEY (SessionId) REFERENCES ChatSessions(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS IX_WorkTasks_Session_Active
    ON WorkTasks(SessionId, IsActive, LastActiveAt DESC);
CREATE INDEX IF NOT EXISTS IX_WorkTasks_Workspace_Active
    ON WorkTasks(WorkspaceId, IsActive);
CREATE INDEX IF NOT EXISTS IX_WorkTasks_Source
    ON WorkTasks(SourceTaskId);
CREATE INDEX IF NOT EXISTS IX_WorkTasks_Parent
    ON WorkTasks(ParentTaskId);
CREATE INDEX IF NOT EXISTS IX_WorkTasks_Orphaned
    ON WorkTasks(IsOrphaned) WHERE IsOrphaned = 1;
```

#### 字段说明（重点）

| 字段 | 设计原因 |
|------|---------|
| `RunId` | AF Workflow 的恢复必需。任务启动后 `WorkflowExecutor.SetRunIdAsync` 写入 |
| `IsActive` | 替代复杂状态机。1 = Workflow 还能 Resume 或正在跑，0 = 已 Completed/Failed/Cancelled |
| `CurrentPlanJson` | `set_plan` 工具调用时覆盖。最新版本就是当前计划，不做版本管理 |
| `PendingRequest*` | HITL 挂起的请求快照。让 UI 在刷新后能重建授权浮窗 |
| `MentionsJson` | 任务启动时锁定的 @ 子智能体。后续步骤复用相同的子智能体集合，避免中途变化 |
| `SourceTaskId` | 用户说"再做一份"时，新任务通过这个字段指向上一任务，便于追溯链路 |

### 3.2 WorkExecutionLogs 表

```sql
CREATE TABLE IF NOT EXISTS WorkExecutionLogs (
    Id          INTEGER PRIMARY KEY AUTOINCREMENT,
    TaskId      TEXT NOT NULL,
    Sequence    INTEGER NOT NULL,                -- 同任务内单调递增
    LogType     TEXT NOT NULL,                   -- 见 WorkExecutionLogType 枚举
    Content     TEXT NOT NULL,                   -- 类型相关 JSON（WorkModeJsonContext）
    CreatedAt   INTEGER NOT NULL,
    FOREIGN KEY (TaskId) REFERENCES WorkTasks(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS IX_WorkExecutionLogs_Task_Seq
    ON WorkExecutionLogs(TaskId, Sequence);
```

#### LogType 枚举与 Content 对应

```csharp
public enum WorkExecutionLogType
{
    StepStart,           // dispatch_step 调用，记录主步骤开始
    StepComplete,        // 主步骤完成（dispatch 工具返回时）
    ToolCall,            // 任意工具调用开始（含子智能体内部工具）
    ToolResult,          // 工具调用结束
    Acceptance,          // verify_step 工具调用，记录验收结果
    Error,               // 工具失败、Workflow 失败
    UserInterrupt,       // 用户在执行中插话（写入 WorkPendingInputs 时同步打一条）

    // 长任务可靠性相关（详见 16 文档）
    SelfEvaluation,      // self_evaluate 工具的评估结果
    RetryAttempt,        // 自动重试（任意类型，重试详情在 Content）
    DeadlockDetected,    // 死循环检测命中

    // 并行与嵌套（详见 11 文档 §3.7 / §3.9）
    ParallelBlockStart,  // dispatch_parallel 开始，多个步骤同时启动
    ParallelBlockEnd,    // dispatch_parallel 结束
    NestedWorkflowStart, // dispatch_nested_workflow 开始
    NestedWorkflowEnd,   // dispatch_nested_workflow 结束
}
```

```csharp
// 对应的 record 类型，全部注册到 WorkModeJsonContext

public sealed record StepStartRecord(string StepTitle, string Department, string Context);

public sealed record ToolCallRecord(string CallId, string ToolName, string? ParametersJson);
```

> **不入库的内容**：流式 token 增量（`AgentResponseUpdateEvent` 文本部分）、思维过程（`TextReasoningContent`）。这些只走 EventHub 给 UI，不持久化。

### 3.3 WorkPendingInputs 表

用户在任务执行过程中插话时，输入塞进这个队列；主 Agent 通过 `check_pending_user_input` 工具消费。

```sql
CREATE TABLE IF NOT EXISTS WorkPendingInputs (
    Id          INTEGER PRIMARY KEY AUTOINCREMENT,
    TaskId      TEXT NOT NULL,
    Content     TEXT NOT NULL,
    EnqueuedAt  INTEGER NOT NULL,
    Consumed    INTEGER NOT NULL DEFAULT 0,
    ConsumedAt  INTEGER,
    FOREIGN KEY (TaskId) REFERENCES WorkTasks(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS IX_WorkPendingInputs_Task_Pending
    ON WorkPendingInputs(TaskId, Consumed, EnqueuedAt);
```

> 设计要点：用 `Consumed` 软删除而非物理删除，便于 UI 时间线显示"用户在第 N 步说了 X"。

### 3.4 WorkflowCheckpoints 表（AF ICheckpointStore 后端）

AF 的 `JsonCheckpointStore` 抽象类要求一个简单的 `key → JsonElement` KV 存储。我们用 SQLite 实现：

```sql
CREATE TABLE IF NOT EXISTS WorkflowCheckpoints (
    [Key]       TEXT PRIMARY KEY,                -- AF 内部生成的 checkpoint key（含 runId）
    Payload     TEXT NOT NULL,                   -- JSON 序列化的 Checkpoint
    UpdatedAt   INTEGER NOT NULL,

    -- 反向索引到 WorkTasks（便于清理）
    RunId       TEXT,                            -- 从 Key 解析出的 RunId
    TaskId      TEXT                             -- 通过 RunId 反查 WorkTasks
);

CREATE INDEX IF NOT EXISTS IX_WorkflowCheckpoints_RunId ON WorkflowCheckpoints(RunId);
CREATE INDEX IF NOT EXISTS IX_WorkflowCheckpoints_TaskId ON WorkflowCheckpoints(TaskId);
```

> **与现有 `WorkflowCheckpoints` 表的差异**：当前 `CortanaDbContext.EnsureTables()` 里已有同名表（主键 `(TaskId, CheckpointId)`，BLOB Payload）。两种结构不冲突——可以**保留旧表**给旧编排功能用，**新建表**（如改名 `WorkflowJsonCheckpoints`）给 AF JsonCheckpointStore 用。或者迁移：把旧表改为 AF 兼容的结构，旧编排代码下线。
>
> **建议**：实施时先 grep `WorkflowCheckpoints` 是否还在被旧代码使用。若不再使用，直接重建为上面的结构。

### 3.5 WorkPlanTemplates 表（计划复用）

支持"保存当前任务的计划为模板"和"从模板加载计划"。

```sql
CREATE TABLE IF NOT EXISTS WorkPlanTemplates (
    Id              TEXT PRIMARY KEY,
    Name            TEXT NOT NULL,               -- 用户可见的模板名
    Description     TEXT NOT NULL DEFAULT '',
    Category        TEXT NOT NULL DEFAULT '',    -- 自定义分类（"销售月报" / "代码审查" 等）

    PlanJson        TEXT NOT NULL,               -- WorkPlan 的 JSON

    -- 来源（可追溯）
    SourceTaskId    TEXT,                        -- 从哪个 WorkTask 抽出来的（NULL = 用户/系统直接创建）
    SourceKind      TEXT,                        -- "task" / "chat" / "groupchat" / "manual"

    -- 使用统计
    UseCount        INTEGER NOT NULL DEFAULT 0,
    LastUsedAt      INTEGER,

    -- 范围
    Scope           TEXT NOT NULL DEFAULT 'user',  -- "user" / "workspace" / "system"
    WorkspaceId     TEXT,                          -- Scope=workspace 时关联

    CreatedAt       INTEGER NOT NULL,
    UpdatedAt       INTEGER NOT NULL
);

CREATE INDEX IF NOT EXISTS IX_WorkPlanTemplates_Scope ON WorkPlanTemplates(Scope);
CREATE INDEX IF NOT EXISTS IX_WorkPlanTemplates_Category ON WorkPlanTemplates(Category);
CREATE INDEX IF NOT EXISTS IX_WorkPlanTemplates_LastUsed ON WorkPlanTemplates(LastUsedAt DESC);
```

#### 计划复用的三个来源

| SourceKind | 触发方式 | 实现路径 |
|-----------|---------|----------|
| `task` | 用户主动"保存当前任务为模板" | UI 操作 → `WorkPlanTemplateService.CreateFromTask(taskId, name, ...)` |
| `chat` | 总经理调用 `load_plan_from_chat_history` 工具，用 `plan_extractor` Agent 从专家模式对话提取 | 见 [11 文档](./11-AF框架集成方案.md) §3.2 |
| `groupchat` | 同上，源是会议模式（GroupChat）的对话 | 同上 |
| `manual` | 用户在设置页直接编辑 JSON 创建 | UI 操作 |

> **设计要点**：模板加载只产生 `WorkPlan`，不会"自动开始执行"。Agent 加载后仍需要：用户确认 → `set_plan` 写入 `WorkTasks.CurrentPlanJson` → 进入执行。

### 3.6 WorkBackgroundJobs 表（仅服务主软件托管的背景任务）

支持子智能体背景执行（v1.0）以及未来 v1.1+ 扩展的其他主软件托管背景任务（批量分析、异步审核等）。

```sql
CREATE TABLE IF NOT EXISTS WorkBackgroundJobs (
    Id                  TEXT PRIMARY KEY,                        -- jobId（GUID）
    TaskId              TEXT NOT NULL,                           -- 父 WorkTask
    JobKind             TEXT NOT NULL,                           -- 'subagent' | (v1.1+ 扩展)
    OwnerName           TEXT,                                    -- 子智能体显示名 / 任务来源标识

    State               TEXT NOT NULL DEFAULT 'pending',
        -- pending（已创建未启动）/ running（执行中）
        -- completed（成功完成）/ failed（失败）/ cancelled（用户/系统取消）

    InputJson           TEXT NOT NULL,                           -- 启动参数（按 JobKind 解析）
    ProgressDescription TEXT,                                    -- "正在分析第 12 个文件..." 给 AI 看
    ResultJson          TEXT,                                    -- State=completed 时
    Error               TEXT,                                    -- State=failed 时

    CreatedAt           INTEGER NOT NULL,                        -- Unix 毫秒
    UpdatedAt           INTEGER NOT NULL,
    CompletedAt         INTEGER,

    FOREIGN KEY (TaskId) REFERENCES WorkTasks(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS IX_WorkBackgroundJobs_Task_State
    ON WorkBackgroundJobs(TaskId, State);
CREATE INDEX IF NOT EXISTS IX_WorkBackgroundJobs_Kind
    ON WorkBackgroundJobs(JobKind);
CREATE INDEX IF NOT EXISTS IX_WorkBackgroundJobs_Active
    ON WorkBackgroundJobs(State) WHERE State IN ('pending', 'running');
```

#### 字段说明

| 字段 | 设计原因 |
|------|---------|
| `JobKind` | 让一个表服务多种背景任务类型（v1.0 仅 `subagent`，v1.1+ 可扩展），各类型有自己的 `IBackgroundJobExecutor` 实现 |
| `State` | 状态机式简单流转：`pending → running → completed`/`failed`/`cancelled`，不可逆 |
| `InputJson` / `ResultJson` | 按 `JobKind` 用不同 record 反序列化（统一在 `WorkModeJsonContext`） |
| `ProgressDescription` | 给 AI 看的人话进度（不是百分比），`wait_for_subagent` 工具返回时附带 |

#### 边界（不可越线）

| ✅ 写入此表的操作 | ❌ 不写入此表的操作 |
|----------------|------------------|
| `[LONG] start_subagent_<id>` 工具调用（v1.0） | 任何插件长会话的状态（PowerShell ExecutionSession 等） |
| 未来 `IBackgroundJobExecutor` 的其他实现（v1.1+） | 普通同步工具调用（写入 `WorkExecutionLogs` 即可） |

#### 应用启动时的清理

应用崩溃后重启，可能留下 `State='running'` 但实际 Task 已死的记录。`WorkModeStartupService` 启动时统一清理：

```sql
UPDATE WorkBackgroundJobs
SET State = 'failed', Error = '应用上次未正常关闭，背景任务被中断',
    UpdatedAt = strftime('%s','now') * 1000
WHERE State IN ('pending', 'running');
```

清理策略与 `WorkTasks.IsOrphaned` 一致——不自动重启，等用户在 `TaskResumePromptCard` 选"继续"后由总经理 Agent 决定要不要重新启动子智能体（一般是重新调用 `start_subagent_*`）。

## 四、关键查询场景

### 4.1 当前会话的活跃任务（输入路由首要操作）

```sql
SELECT *
FROM WorkTasks
WHERE SessionId = @SessionId
  AND IsActive = 1
ORDER BY LastActiveAt DESC
LIMIT 1;
```

> **唯一性**：由 `WorkModeInputRouter` 在创建新任务前的事务中检查"当前 Session 没有活跃任务"。

### 4.2 应用启动时检查待恢复任务

```sql
SELECT *
FROM WorkTasks
WHERE IsActive = 1
  AND PendingRequestId IS NOT NULL  -- HITL 挂起的，等用户回应
ORDER BY LastActiveAt DESC;
```

> 没有 `PendingRequestId` 的活跃任务（理论上不该存在，除非异常崩溃）按"失败"处理。

### 4.3 UI 重建时间线

```sql
SELECT Sequence, LogType, Content, CreatedAt
FROM WorkExecutionLogs
WHERE TaskId = @TaskId
ORDER BY Sequence ASC;
```

UI 端按 `LogType` 分发到对应的卡片构造逻辑（参考 13 文档 §六）。

### 4.4 找上一个任务作为"再做一份"的参照

```sql
SELECT *
FROM WorkTasks
WHERE SessionId = @SessionId
  AND IsActive = 0
  AND CompletedAt IS NOT NULL
ORDER BY CompletedAt DESC
LIMIT 1;
```

> 总经理调用 `get_recent_completed_task_plan` 工具时用到。

### 4.5 模板搜索

```sql
SELECT Id, Name, Description, Category, UseCount
FROM WorkPlanTemplates
WHERE (Scope = 'system' OR (Scope = 'user') OR (Scope = 'workspace' AND WorkspaceId = @Ws))
  AND (@Keyword IS NULL OR Name LIKE '%' || @Keyword || '%' OR Description LIKE '%' || @Keyword || '%')
  AND (@Category IS NULL OR Category = @Category)
ORDER BY UseCount DESC, LastUsedAt DESC
LIMIT 20;
```

## 五、生命周期事务

### 5.1 创建任务

```text
WorkModeInputRouter 判断为新任务
  ↓
事务开始
  ├─ INSERT WorkTasks (IsActive=1, CurrentPlanJson=NULL, ...)
  ├─ INSERT ChatMessages (Role=User, Content=userInput)  ← 复用现有 SaveUserMessage 路径
  └─ Publish work.task.created
事务结束
  ↓
WorkflowExecutor.ExecuteAsync(taskId, userInput)
  ↓
事件流处理（写 WorkExecutionLogs / 发 EventHub）
```

### 5.2 工具调用 / 步骤执行

```text
AF 触发 FunctionCallContent
  ↓
WorkflowEventDispatcher.OnAgentDeltaAsync
  ├─ INSERT WorkExecutionLogs (LogType=ToolCall, Content=ToolCallRecord JSON)
  └─ Publish work.tool.called
  ↓
工具执行（含 set_plan / dispatch / verify 等）
  ↓
工具返回 → FunctionResultContent
  ↓
WorkflowEventDispatcher.OnAgentDeltaAsync
  ├─ INSERT WorkExecutionLogs (LogType=ToolResult)
  └─ Publish work.tool.completed
```

### 5.3 set_plan 工具的特殊路径

```text
set_plan 工具调用
  ↓
PlanTools.SetPlanAsync
  ├─ UPDATE WorkTasks SET CurrentPlanJson = @PlanJson WHERE Id = @TaskId
  └─ Publish work.plan.updated (UI 在消息流追加计划 Markdown)
```

### 5.4 HITL 挂起

```text
ApprovalRequiredAIFunction 拦截 / ask_user 抛 HitlRequestException
  ↓
AF 产出 RequestInfoEvent
  ↓
WorkflowEventDispatcher.OnRequestInfoAsync
  ├─ UPDATE WorkTasks SET PendingRequestId=?, PendingRequestKind=?, PendingRequestData=? WHERE Id=?
  └─ Publish work.approval.requested 或 work.ask_user
  ↓
WorkflowExecutor.ConsumeEventsAsync 检测到 RequestInfoEvent → 退出循环（任务挂起）
  ↓
等待用户操作（点授权按钮 / 回复输入框）
  ↓
WorkflowExecutor.ResumeAsync(taskId, userResponse)
  ├─ UPDATE WorkTasks SET PendingRequestId=NULL, PendingRequestKind=NULL, PendingRequestData=NULL
  ├─ run.SendResponseAsync(...)
  └─ 继续 ConsumeEventsAsync
```

### 5.5 任务完成

```text
final_report 工具调用
  ↓
PlanTools.FinalReportAsync
  ├─ ChatHistoryDataProvider.AppendAssistantMessageAsync(SessionId, reportMarkdown)
  ├─ UPDATE WorkTasks SET IsActive=0, CompletedAt=NOW(), FinalReport=?
  └─ Publish work.task.completed
  ↓
AF 产出 WorkflowOutputEvent
  ↓
WorkflowExecutor.ConsumeEventsAsync 检测到 → 退出循环
```

### 5.6 用户插话（执行中说话）

```text
用户在输入框提交（Workflow 还在跑）
  ↓
WorkModeInputRouter 检测到当前会话有活跃任务且无 PendingRequest
  ↓
WorkflowExecutor.EnqueueUserInputAsync
  ├─ INSERT WorkPendingInputs (TaskId, Content, Consumed=0)
  ├─ INSERT WorkExecutionLogs (LogType=UserInterrupt) ← 让时间线能显示
  └─ Publish work.pending_input
  ↓
（无中断 Workflow，主 Agent 在下次决策点调用 check_pending_user_input 工具消费）
```

每次 Serialize/Deserialize 都必须传 Context：

```csharp
// ✅
var json = JsonSerializer.Serialize(plan, WorkModeJsonContext.Default.WorkPlan);
var plan = JsonSerializer.Deserialize(json, WorkModeJsonContext.Default.WorkPlan);

// ❌ 反射 → AOT 报错或运行时崩溃
var json = JsonSerializer.Serialize(plan);
```
