# 03 - 通信协议

## 总体原则

本方案不新增专用 STT/TTS/KWS WebSocket 协议。

语音插件通信复用现有插件体系：

| 通信内容 | 复用机制 |
| --- | --- |
| 生命周期 | Process 插件协议 `get_info` / `init` / `destroy` |
| 控制命令 | Process 插件协议 `invoke` |
| 长期/流式事件 | 插件通过 `init` 中已有 `wsPort` 回连宿主，复用现有 PluginBus 上报通道 |
| 前端广播 | 继续由 EventHub → `Netor.Cortana.Networks` 广播，事件名尽量不变 |

## 为什么不新增语音专用协议

原方案定义了：

- `ws://localhost:12858/` STT 服务协议；
- `ws://localhost:12859/` TTS 服务协议。

但现有 Process 插件协议已经提供：

- 插件进程启动与销毁；
- `plugin.json` 描述；
- `get_info` 工具清单；
- `init` 运行时配置；
- `invoke` 命令调用；
- `wsPort` 回连宿主能力（[ExternalProcessPluginHostBase.cs:197-211](Src/Netor.Cortana.Plugin/Core/ExternalProcessPluginHostBase.cs#L197-L211)）。

继续新增语音专用端口和协议会带来重复的生命周期管理、重连、心跳、端口占用处理，不符合"能不添加新协议就不添加新协议"的原则。

## Process 插件协议复用边界

现有 `invoke` 是请求-响应模型，并且存在调用超时（当前宿主读取子进程响应超时为 30 秒）。因此：

> `invoke` 只用于短命令：启动、停止、配置、查询状态。
> `invoke` 不承载长期监听、持续录音、流式 partial、字幕流、播放完成事件。

长期事件由插件主动通过 PluginBus 上报给宿主，再由当前已新增的 `PluginBusVoiceEventDispatcher` 映射到 EventHub。后续 `*PluginAdapter` 主要负责控制命令调用和状态协同。

当前实现复查：`voice_tts_enqueue` / `voice_tts_finish` / `voice_tts_speak` / `voice_tts_greeting_play` 已按该边界改为短命令，真实合成、播放、字幕和完成事件由后台 Channel / 播放任务处理，避免长文本或声卡阻塞触发 invoke 超时。

## 插件生命周期

```text
宿主启动插件进程
  │
  ├─ get_info：读取插件元数据和工具清单
  ├─ init：传入 dataDirectory / workspaceDirectory / pluginDirectory / wsPort
  ├─ invoke：按需调用 start / stop / configure 等工具
  ├─ 插件通过 wsPort 回连宿主，上报语音事件
  └─ destroy：宿主关闭或卸载插件时释放资源
```

## 能力声明

**当前实现状态**：[PluginManifest.cs](Src/Netor.Cortana.Plugin/Core/PluginManifest.cs) 已支持 `capabilities` 和 `tags` 字段；`VoiceCapabilityRegistry` 已能识别 `voice.kws` / `voice.stt` / `voice.tts`。推荐新插件使用 `capabilities`，短期可用 `tags: ["voice", "stt"]` 等方式兼容。

```json
{
  "id": "madorin.voice.tts.melo",
  "name": "Melo TTS 语音合成",
  "version": "1.0.0",
  "runtime": "process",
  "command": "Madorin.Voice.Tts.Melo.exe",
  "capabilities": ["voice.tts"]
}
```

| 能力 | capability ID |
| --- | --- |
| KWS | `voice.kws` |
| STT | `voice.stt` |
| TTS | `voice.tts` |

## 麦克风互斥协议（KWS ↔ STT）

> 这是原稿缺失的关键一节。Win32 `waveIn*`（[AotWaveRecorder.cs](Src/Netor.Cortana.Voice/AotWaveRecorder.cs)）通常不允许两个进程同时独占同一物理输入设备。当前实现里 KWS 与 STT 由同一进程串行打开/关闭；拆分为两个独立进程后，必须由宿主显式协调让渡。

让渡时机由 `VoiceOrchestrator` 负责：

```text
唤醒后准备启动 STT
  ├─ 调 KWS 插件 voice_kws_pause
  │     插件应在 100ms 内：
  │       - 关闭 waveIn
  │       - 释放音频缓冲
  │       - 上报 voice.kws.paused
  ├─ 等待 voice.kws.paused（最长 500ms 兜底）
  ├─ 调 STT 插件 voice_stt_start
  ├─ STT 完成或被取消
  └─ 调 KWS 插件 voice_kws_resume
        插件应：
          - 重新打开 waveIn
          - 上报 voice.kws.resumed
```

错误恢复：

- 若 `voice_stt_start` 失败，宿主必须立即调 `voice_kws_resume`，否则永久无法再次唤醒；
- `voice_stt_cancel` 与 `voice_kws_resume` 应被 Coordinator 视为**必须配对**调用（详见 [07-接口与命名变更.md](07-接口与命名变更.md) 中 `CancelEverythingAsync` 的实现要求）。

## 会议模式语义复刻

当前 [VoiceChatOutputChannel.cs:27](Src/Netor.Cortana.Voice/VoiceChatOutputChannel.cs#L27) 与 [SpeechRecognitionService.cs:94](Src/Netor.Cortana.Voice/SpeechRecognitionService.cs#L94) 都通过 `IWindowController.IsMainWindowVisible()` 来回避会议视图正在使用主窗时被语音通道打扰：会议视图属于主窗 → 主窗一定可见 → `IsActive=false` → AI token 不会进 TTS、续杯不会发生。

拆分后这条隐性门控必须显式迁入：

| 新组件 | 必须复刻的判断 |
| --- | --- |
| `TtsPluginOutputChannel.IsActive` | `!IWindowController.IsMainWindowVisible()` |
| `VoiceOrchestrator` 续杯条件 | `!IWindowController.IsMainWindowVisible()` && 当前轮次未取消 |

否则会议进行中收到唤醒或 AI 回复时，TTS 插件会越权播报，造成功能回归。本协议要求所有 `*PluginOutputChannel` 实现都不得直接调 TTS 插件而绕过 `IsActive` 判断。

已参与当前 AI 回复的输出通道必须继续收到收尾事件。当前宿主侧会记录本轮已接收 token 的通道，AI 完成或异常时通知“已参与 + 当前活跃”的通道并集；因此 `IsActive` 中途从 `true` 变为 `false` 时，不会导致 TTS 插件漏掉 `voice_tts_finish` / `voice_tts_stop`。

## 问候语缓存归属

原稿"插件内部缓存欢迎语音频"是合理的，但需要明确两件事：

- **欢迎语文本**仍由主程序维护（[`SystemSettings`] 的 `Tts.WelcomeGreeting`），通过 `voice_tts_greeting_regen` 下发给插件；
- **音频缓存**只存活于插件进程内，主程序不直接读写音频字节。
- 用户在设置中改欢迎语后，主程序必须立即调 `voice_tts_greeting_regen`，等 `voice.tts.greeting_ready` 上报后再视为生效；首次安装插件后，主程序也应主动调一次。

`voice_tts_greeting_play` 在缓存未就绪时应返回错误，宿主侧由 Orchestrator 回退为不播问候、直接进 STT。

当前宿主侧已落地：插件扫描完成后 `App.LoadPluginsAsync()` 会通过 `TtsPluginAdapter` 主动调用 `voice_tts_configure` 与 `voice_tts_greeting_regen`；设置页保存 TTS 语速、欢迎语或 TTS 插件选择后，也会热下发配置。`TtsPluginAdapter` 会解析工具返回中的 `ok/code/message`，插件不可用时不阻断保存，但会提示配置将在插件可用后生效。

## KWS 插件工具约定

| 工具名 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `voice_kws_start` | 可选配置 JSON | 成功/失败 | 开始监听唤醒词，立即返回 |
| `voice_kws_stop` | 无 | 成功/失败 | 完全停止监听并释放设备（用于禁用能力） |
| `voice_kws_pause` | 无 | 成功/失败 | 临时让出麦克风，不卸载模型，配套 `voice_kws_resume` 使用 |
| `voice_kws_resume` | 无 | 成功/失败 | 重新打开麦克风，恢复监听 |
| `voice_kws_configure` | 阈值、关键词、模型配置 | 成功/失败 | 更新配置，通常下次 start 生效 |
| `voice_kws_status` | 无 | 状态 JSON：`idle / listening / paused / error` | 查询当前状态 |

| `voice.kws.started` | 日志/状态 | 监听已启动 |
| `voice.kws.paused` | 日志/状态 | 已让出麦克风（Orchestrator 等待此事件再启动 STT） |

## TTS 插件工具约定

下表列出的是语音编排层使用的**短工具名**。Process 插件运行时会在实际 `toolName` 前加插件 ID 前缀，例如 `voice_tts_melo_voice_tts_status`；`TtsPluginAdapter` 应从插件 `get_info` 返回的工具元数据中按 `shortName` 找到完整工具名再调用。

| 工具名 | 参数 | 返回 | 说明 |
| --- | --- | --- | --- |
| `voice_tts_speak` | 完整文本 | 成功/失败 | 合成并播放完整文本，立即返回，完成靠事件通知 |
| `voice_tts_enqueue` | 一句话文本 | 成功/失败 | 流式入队 |
| `voice_tts_finish` | 无 | 成功/失败 | 标记文本输入结束 |
| `voice_tts_stop` | 无 | 成功/失败 | 立即停止合成和播放 |
| `voice_tts_greeting_play` | 可选问候语 | 成功/失败 | 停止旧播放并播放问候语；缓存未就绪时返回错误码 `greeting_not_ready` |
| `voice_tts_greeting_regen` | 新问候语文本 | 成功/失败 | 重新生成问候语缓存，完成时上报 `voice.tts.greeting_ready` |
| `voice_tts_configure` | 语速、音色、模型配置 | 成功/失败 | 更新合成配置 |
| `voice_tts_status` | 无 | 状态 JSON | 查询当前状态 |

TTS 事件：

| 插件事件 | EventHub 映射 | 说明 |
| --- | --- | --- |
| `voice.tts.started` | `Events.OnTtsStarted` | 开始播放 |
| `voice.tts.subtitle` | `Events.OnTtsSubtitle` | 当前播放句子 |
| `voice.tts.completed` | `Events.OnTtsCompleted` | 播放完成 |
| `voice.tts.greeting_ready` | 日志/状态 | 问候语缓存已就绪，可调 `voice_tts_greeting_play` |
| `voice.tts.error` | 日志 + 错误状态 | 合成/播放异常 |

当前 `Cortana.Plugins.Voice.Tts.Melo` 已上报上述事件。模型文件缺失时，`started/subtitle/completed` 仍按工具调用生命周期模拟；模型文件齐全时，`voice_tts_speak` / `voice_tts_greeting_*` / `voice_tts_enqueue` / `voice_tts_finish` 都已走后台播放路径，字幕由播放线程切换音频段时上报，完成由播放循环自然结束时上报。推演后修正的约束：`started` 只在空闲→播放时上报一次；PluginBus 客户端必须响应宿主 `ping`，避免长连接超时。插件侧已迁入文本清洗与断句，完整朗读、流式入队和问候语播放都必须先整体清理 Markdown，再拆为可合成片段，避免代码块、链接和纯格式文本被误播。

单次播放工具与流式工具的完成语义不同：`voice_tts_speak` / `voice_tts_greeting_play` 不会再等待额外 `voice_tts_finish`；`voice_tts_enqueue` 仍需由宿主在 AI done 时调用 `voice_tts_finish`，再由插件后台播放循环发布 `completed`。模型齐全时，`speak` / `greeting_play` / 流式 `finish` 都只启动或标记后台工作并返回，不等待播放完成。

模型目录归属：宿主 `init` 会把 `pluginDirectory` 传给 Process 插件。TTS 插件默认模型目录为 `{pluginDirectory}/models/TTS`；`voice_tts_configure.model_directory` 传入相对路径时也必须按插件目录解析，传入绝对路径时可作为显式覆盖。当前 Melo TTS 已完成路径解析，并在 `voice_tts_status` / 工具返回 `status` 中上报 `modelFilesReady`、`missingModelFiles` 与 `modelLoaded`；`modelFilesReady` 要求必需文件存在且非空，`modelLoaded=true` 表示插件进程内已成功创建 Sherpa `OfflineTts` 实例。`RuleFsts` 只传入实际存在且非空的 FST 文件，避免把缺失 FST 交给 Sherpa native 校验。

播放基础件归属：`AotWavePlayer`、`SegmentedWaveProvider` 与 WinMM 播放结构体已迁入 Melo TTS 插件项目，并由插件项目独立开启 `AllowUnsafeBlocks`。当前单次播放与流式播放均可以使用插件内 `AotWavePlayer` 输出 PCM；流式 `voice.tts.subtitle` 已由 `SegmentedWaveProvider` 在声卡读取新音频段时触发，而不是在文本入队时提前触发。

## 事件载荷建议

事件载荷保持简单，优先复用已有 `VoiceTextArgs` / `VoiceSignalArgs` 所需信息。

当前宿主已支持两类 envelope：

```json
{
  "type": "event",
  "eventType": "voice.stt.partial",
  "sourcePluginId": "madorin.voice.stt.sherpa",
  "payload": {
    "text": "正在识别的内容",
    "sessionId": "可选轮次 ID"
  }
}
```

以及直接事件类型：

```json
{
  "type": "voice.stt.partial",
  "text": "正在识别的内容",
  "sourcePluginId": "madorin.voice.stt.sherpa",
  "sessionId": "可选轮次 ID"
}
```

```json
{
  "type": "voice.tts.subtitle",
  "text": "当前播放的句子",
  "sourcePluginId": "madorin.voice.tts.melo",
  "sessionId": "可选轮次 ID"
}
```

`sessionId` 由 `VoiceOrchestrator` 在每次唤醒时生成，KWS/STT/TTS 收到后回填，便于过滤过期回调（例如二次唤醒时丢弃上一轮的 `voice.tts.completed`）。

当前宿主侧已将 `IAiOutputChannel.OnTokenAsync` 扩展为携带 `sessionId`，`AiChatHostedService` 在 AI 文本 token 和图片 Markdown token 广播时都会传入当前轮次 ID。`TtsPluginOutputChannel` 在收到 token 时先记录 session，再调用 `voice_tts_enqueue`，因此流式入队、`finish`、`stop` 三类工具都可以带上同一轮次 ID。

## AOT 要求

语音插件仍需遵守项目 AOT 约束：

- JSON 序列化使用 `System.Text.Json` Source Generator；
- 不依赖运行时反射发现复杂类型；
- Native 音频与模型调用需要明确处理资源释放；
- stdout 只能输出 Process 插件协议响应，日志必须走 stderr 或日志文件。

## 兼容性要求

- `Netor.Cortana.Networks` 当前订阅的语音 EventHub 事件尽量不变；
- 前端收到的 `stt_partial` / `stt_final` / `tts_subtitle` 等广播尽量不变；
- 旧 `OnTtsEnqueue` / `OnTtsFinish` 在过渡期保留，但插件化后主流程直接调用 TTS 插件工具，不再发布 `OnTtsEnqueue`。
