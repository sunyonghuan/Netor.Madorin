# 产品形态与交互设计：面向工作的多任务并发工作台

> 状态：设计草案（产品形态 + 交互 + 工作量估算，含代码核实结论）
> 关联文档：`Docs/多任务并发体系/架构决策：当前版商用化与并发版重建.md`
> 定位：那份文档讲"底层怎么支撑"，本文讲"用户看到什么、怎么用"，以及"复用边界与真实工作量"。

## 1. 产品定位

一句话：**让一个人像经营一家公司一样，用 AI 完成本该多个部门协作或单部门独立完成的全部工作。**

老板（用户）不必事必躬亲。他把任务丢给"部门"（智能体/智能体组），部门之间自动协作或各自独立推进；老板只在关键节点介入决策，其余时间监督进度。

典型场景（电商板块）：

- 营销部接到"获客"任务 → 需要技术部配合处理数据、多媒体运营部处理图片/视频 → 处理好的内容分发到各社交媒体账号 → 营销部回收评论/咨询 → 向客户推送对应产品 → 客户下单后调用售后服务部发货。
- 老板也可单独给某个部门下**定时任务**：多媒体运营部每天定时更新博客/论坛/文档/多媒体；技术部每天产出 N 个视频和图片。
- 编排既可由智能体自动完成（总经理拆解计划），也可由老板手工编排：步骤 1/2/3/4，用不同提示词指派不同智能体，每个智能体完成后触发事件驱动下一步。

当老板需要介入时，可同时开多个分栏、多个工作并行处理，最后由他决策下一步。例如软件工程师同时开多个项目，每个项目内有不同的工作、不同智能体协作，他只负责监督进度与拍板。

## 2. 核心概念模型

三层结构，与架构文档的三级并发一一对应，术语就此统一：

| 本文术语 | 架构文档术语 | 本质 | 基数 |
|---|---|---|---|
| **工作台 Workbench** | 工作区 Workspace（= 一个目录 / 一套文件结构） | 隔离边界、`.cortana` 落地点 | 顶层，N 个并行 |
| **工作 Work** | 对话 / 任务 | 有目标、有产出的执行单元 | 一个工作台 → N 个工作 |
| **智能体 Agent** | streaming run | 模型 + 角色 + 工具 + 权限 的实例 | 一个工作 → 1..N 个智能体 |

**工作台 = 工作区目录**（已确认成立），隔离边界与术语由此统一。

每个工作在创建时选择一种**模式**（沿用现有三种，直接复用）：

- **专家模式（ExpertMode）**：单智能体、单轮/多轮对话，最轻。
- **工作模式（WorkMode）**：总经理编排 → 形成工作计划（`WorkPlan`）→ 交给对应部门（子智能体）执行，一个工作可多步骤、由不同智能体完成。
- **会议模式（Meeting）**：主持人编排 → 挑选发言人轮流发言 → 主持人判断会议是否结束或询问用户。

## 3. UI 形态与交互

### 3.1 整体三栏布局

```
┌────────────┬───────────────────────────────────┬────────────┐
│ 左栏         │              中间分栏区                │ 右栏         │
│ 工作台树      │  (每个分栏 = 一个工作的一个视图)          │ 工作台文件树   │
│              │                                    │            │
│ ▸ 工作台A     │  ┌─────────┐  ┌─────────┐          │ 工作台A/     │
│   ▸ 工作1 🟢  │  │ 工作1     │  │ 工作3     │          │  ├ src/     │
│     · 智能体x │  │ 对话流     │  │ 文件diff  │          │  └ docs/    │
│   ▸ 工作2 ⏸  │  │          │  │          │          │            │
│ ▸ 工作台B     │  └─────────┘  └─────────┘          │ 工作台B/     │
│   ▸ 工作3 🟢  │                                    │  └ ...      │
│  [可折叠]     │                                    │  [可折叠]    │
└────────────┴───────────────────────────────────┴────────────┘
```

- **左栏、右栏均可折叠**，折叠后把更多空间让给中间分栏区。
- **左栏 = 工作台树**：工作台 → 工作 → 正在工作的智能体，三级展开。每个工作旁实时显示状态标记。
- **右栏 = 工作台文件树**：不同工作台各有独立文件结构；支持从系统拖入文件、拖入文件夹。
- **中间 = 分栏区**：核心工作面，见下。

### 3.2 分栏（Pane）是"视图"，不是"工作"本身

关键区分：**工作在后台跑，分栏只是它的一个视图，可开、可关、可重开，不影响工作运行。**

- **一个工作可对应多个分栏**：如会议模式一栏看总转录、发言人各一栏；工作模式一栏对话、一栏看文件 diff。
- **分栏内容多态**：对话流 / 文件 diff / PowerShell 输出 / 进度计划视图 / 产出物预览。
- **分栏可自由布局**：分割方向、大小、位置可调；布局可保存，重启恢复。
- **关掉分栏后**：工作继续跑；左栏点该工作可重新挂回一个新分栏。
- **每个分栏有独立输入区**：输入框、附件、文件拖入。

### 3.3 输入语义

分栏输入框打的字，**喂给整个工作 / 协调者**（沿用现有专家/工作/会议三模式的输入路由，直接照抄）。

- 专家模式：喂给该对话的智能体。
- 工作模式：喂给总经理（协调者）。
- 会议模式：作为用户插话喂给主持人。

### 3.4 文件拖入的两种语义（须区分）

- **拖进输入框** → 作为**上下文/参考**给智能体看，不改变工作台目录。
- **拖进右侧文件树** → 作为**文件**真正复制进该工作台目录。

智能体改动文件后，右侧树实时刷新（文件监听已具备）；应能看出**哪个工作/智能体改了哪个文件**，可看 diff、可回退（并发多智能体改文件时的必需保障）。

### 3.5 工作状态（左栏实时上报）

左栏每个工作显示当前状态即可，不需复杂通知：

- 🟢 **进行中**
- ✅ **已完成**
- ⚠️ **需要人工介入**（HITL：智能体在等用户拍板）
- ⏸ **被打断**
- ⛔ **被阻断**

> "需要人工介入"最关键：并发工作一多，用户必须一眼看出哪个在等他。

## 4. 编排与隔离（核心新增工作）

这是整套产品真正要造的齿轮，也是架构文档第 5 节点名的重心。分三个层次，成熟度差别极大——**以下结论均经代码核实**。

### 4.1 工作内编排：✅ 已有且成熟（复用）

- 工作模式 `ProjectLeadService` 是确定性 C# 主循环：加载计划 → 找下一个可执行步骤 → 派发给对应角色智能体 → 回写状态 → 发事件；支持步骤展开、里程碑、暂停/取消/用户抢占。
- 会议模式主持人调度参会者轮流发言。
- **均按 `taskId` / `meetingId` 隔离，多个工作并发跑零改动。**

### 4.2 定时调度：⚠️ 已有（插件 + WS），但缺工作隔离

**定时能力已经存在**，以**插件**形式实现（独立进程），通过 WebSocket 插件总线向主程序注入调度。这一点之前因为它不在主仓库源码里而被漏判，此处更正。

**真正的缺口是"工作隔离"**，根因已用代码定位：

- 定时插件走 WS 发 `"send"` 消息 → 落到 `WebSocketInputChannel` → 调用 `chatEngine.SendMessageAsync(...)`。
- `IAiChatEngine` 是**全局单引擎**，`SendMessageAsync` 只认全局"当前会话"（`ChatSessionService._currentSessionId`）。
- WS 消息里唯一的路由信息是 `requestContext.ActiveClientId`——它标识**WS 客户端**，不是工作/工作台。

**结论**：定时任务能触发，但**无法指定"注入到哪个工作台的哪个工作"**，只会打到全局当前会话。这正是"没有针对工作进行隔离"的症结。

**关键推论：这个隔离缺口与"专家模式多对话并发"是同一个根因**——都是 `ChatSessionService` 全局单会话。因此修复方案共享：

- WS 注入消息需**携带目标工作/工作台 id**；
- `IAiChatEngine` / `ChatSessionService` 改为**会话池按 id 路由**，而非全局"当前"。
- 一次改造，同时解决"定时任务打到指定工作"和"多专家对话并发"两个问题。

### 4.3 跨工作编排：🔮 未来畅想（暂不纳入成本）

电商愿景里"营销部完成 → 自动触发多媒体部 → 再触发售后部"这类**跨工作、跨部门的事件链**，是**远期方向，本期不做**，仅在此登记以免遗忘：

- `TaskEngine`（带 `DependsOn`、并行 ready steps、`await_user` 门控的 DAG 调度器）目前**只有测试、无源码**，是未实现的设计草稿——将来做跨工作编排时可从它起步。
- `OnWorkTaskCompleted` 等事件目前只被 UI / WS 中继订阅刷界面；未来接一个"编排消费者"即可把工作完成事件驱动到下一个工作。事件总线已就绪，链路留待将来接。

### 4.4 隔离（去全局化）：⚠️ 部分需改造

| 隔离点 | 现状 | 工作量 |
|---|---|---|
| `App.WorkspaceDirectory` 全局静态 | 152 处引用，89% 纯读路径；`IAppPaths` 接口 + 事件切换机制已存在 | 去全局化约 **35 小时，低风险** |
| 专家模式并发 + 定时任务工作路由（同一根因：`ChatSessionService._currentSessionId` / `ChatTurnCancellationRegistry._currentTurn` 全局单值） | 只支持一个活跃对话；WS 注入的定时消息只能打到全局当前会话 | 改会话池 + 按 turnId 字典 + WS 消息携带目标工作 id，**中等**（一次修复两个问题） |
| `ChatInputVm` 硬编码 `App.Services` | 无法多实例 | 改构造函数注入，**低** |
| PowerShell 快速执行全局 `SemaphoreSlim(1,1)` | 串行化；会话模式已支持多进程 | 快速执行改按会话加锁，**低**（可选） |
| 工作/会议模式、Provider 客户端、历史/压缩层 | 已按作用域隔离 | ✅ 无需改 |

| 层 | 处理 | 说明 |

| `ChatInputVm` | **改造** | 去 `App.Services`，改构造注入 |

| 专家模式并发 | **改造** | 会话池 + turn 字典 |

## 6. 工作量估算（单人开发）

### 6.1 MVP：现有能力并发化 + 多工作台外壳

约 **6–9 周**

1. 新组合根 + DI 作用域 + `WorkspaceContext` 去全局化 + `ChatInputVm` 改造：2–3 周
2. 多工作台外壳 + 分栏系统 + 右侧文件树拖拽 + 左栏状态上报：3–5 周（最大块，纯新 UI）
3. 工作/会议模式挂入并发运行：基本零改动，以验证为主

### 6.2 完整版：在 MVP 之上叠加

- 专家模式多对话并发 + 定时任务工作路由（会话池 + turn 字典 + WS 消息携带目标工作 id）：2–4 周（一次改造解决两个问题）
- 单工作台内多对话资源隔离（PowerShell 会话池 + 插件状态按对话作用域）：2–3 周

**完整版合计约 3–4 个月**（定时能力已复用、跨工作编排本期不做，比先前估算下调）。

> 校准一：架构文档"七八成复用、两三成重建"对**底层**成立；主要新增成本是"多工作台 + 分栏"这层 UI 外壳，属"新建"。
> 校准二：定时不是新建——它已插件化（独立进程 + WS），本期只需补"工作路由"；跨工作编排属未来畅想，不在本期成本内。这两点较初版估算显著下调。

## 7. 推荐路线（阶段化，各阶段可独立交付）

1. **阶段 0** — 文件化 + 每工作台 Channel/索引（当前工程内完成）→ 商用条件 + 并发地基。
2. **阶段 1** — 当前版商用发布 → 稳定营收基座，为重建争取从容空间。
3. **阶段 2** — 新组合根 + DI 作用域 + `WorkspaceContext` + `ChatInputVm` 改造（对应 6.1-1）。
4. **阶段 3** — 多工作台外壳 + 分栏系统 + 文件树拖拽 + 状态上报（对应 6.1-2）；工作/会议模式并发接入。
5. **阶段 4** — 专家模式多对话并发 + 定时任务工作路由（同一根因，一并解决）。
6. **阶段 5** — 单工作台内多对话资源隔离（难度最高，最后做）。
7. **未来** — 跨工作编排引擎（DAG / 事件链驱动跨部门自动协作），从 `TaskEngine` 草稿起步。本期不做。

## 8. 待用户拍板的决策项

- [ ] 定时任务工作路由是否纳入 MVP（阶段 4）？它与专家模式多对话并发同根因，一并做成本增量小。
- [ ] 分栏布局是否需要保存/恢复？多窗体是否要（还是只做界面内分栏）？
- [ ] 智能体的**工具权限**（只读/可写/可跑 PowerShell/可删文件）是否第一版就要按智能体配置？
- [ ] 危险操作（删文件、跑 PowerShell）在无人盯守时的策略：自动执行 vs 挂起等审批？（定时任务无人盯守时尤其重要）
