# 16 - 长任务可靠性与重试策略

> 一人公司模式下，工作模式必须支持视频剪辑（6-8 小时）、网站开发（30+ 小时）等长周期不中断任务
>
> **核心承诺**：在用户离开时持续运行；网络/API/工具瞬时故障自动重试；崩溃可恢复；不进入死循环

---

## 一、问题陈述

### 1.1 一人公司的长任务画像

工作模式定位是"一人公司"——用户是唯一的决策者和审批人，AI 是全部"员工"。这种定位决定了长任务的几个核心特征：

| 特征 | 含义 | 对架构的要求 |
|------|------|------------|
| **持续时间长** | 视频剪辑 6-8 小时、网站开发 30+ 小时 | 不能依赖用户全程在场 |
| **自评迭代多** | "做出来 → 看效果 → 改 → 再看"反复 N 次 | AI 要会自己看自己的产出，不打扰用户 |
| **依赖外部稳定性差** | 模型 API 502 / 网络抖动 / 工具偶发失败 | 瞬时失败自动重试，不要把 6 小时的进度因为一次 API 超时全部废掉 |
| **决策点稀疏** | 只在主步骤完成、需要用户判断的歧义、高风险操作时打扰用户 | 默认"不打扰"，但出现真正的歧义就必须停下来问 |
| **崩溃概率不低** | 30 小时跨度里电脑死机、应用崩溃、断电至少有一次概率 | 崩溃恢复必须是设计目标，不是事后补救 |

### 1.2 当前文档的缺口

10-15 文档对长任务可靠性几乎没有专门设计：

- ❌ 工具失败重试没有上限策略
- ❌ 模型 API 错误（限流、超时、502）没有处理
- ❌ AI 死循环（同一工具反复失败）没有检测
- ❌ 应用崩溃后的恢复策略只在 12 文档提了一句"标记 Failed"
- ❌ 自评循环（AI 看自己的产出再改）没有机制
- ❌ 长任务进度估算和心跳没有

本文档填补这些空白。

## 二、可靠性的五层防护

```text
┌──────────────────────────────────────────────────────────┐
│ Layer 5: 死循环检测                                       │
│   同一工具/同一参数连续失败 N 次 → 强制 ask_user           │
└──────────────────────────────────────────────────────────┘
                           ↑
┌──────────────────────────────────────────────────────────┐
│ Layer 4: 分类型重试上限                                    │
│   ├─ 网络/API 错误 5 次（指数退避）                        │
│   ├─ 工具执行失败 3 次                                     │
│   └─ 模型输出格式错误 2 次                                 │
└──────────────────────────────────────────────────────────┘
                           ↑
┌──────────────────────────────────────────────────────────┐
│ Layer 3: 自评循环                                         │
│   AI 调用 self_evaluate 自己看产出 → 不满意自动改         │
│   达到可接受阈值 / 迭代上限才向用户展示                    │
└──────────────────────────────────────────────────────────┘
                           ↑
┌──────────────────────────────────────────────────────────┐
│ Layer 2: AF Workflow Checkpoint                          │
│   每个 superstep 自动落盘 → 应用内崩溃 / 异常自动续跑      │
└──────────────────────────────────────────────────────────┘
                           ↑
┌──────────────────────────────────────────────────────────┐
│ Layer 1: 应用崩溃恢复                                      │
│   重启后恢复最后一个对话/任务，不自动续跑，等用户决策       │
└──────────────────────────────────────────────────────────┘
```

> **设计原则**：能自动恢复的绝不打扰用户（Layer 1-4），但确实需要用户判断的就必须停下来（Layer 5 + Layer 1 用户重启场景）。

## 三、Layer 1：应用崩溃恢复

### 3.1 设计决策

**应用进程内的异常**（如未捕获 Exception、Workflow 内部错误）：

- AF Checkpoint 已经在 superstep 边界自动保存
- `WorkflowExecutor` 顶层 try/catch 捕获后**自动 Resume**（在 §4 详述）
- 用户无感知

**应用外的故障**（电脑死机、断电、用户强行结束进程、操作系统崩溃）：

- 应用重启时**不自动续跑**（决策已确认）
- 重启时恢复"最后一个对话/任务"作为当前焦点
- 用户在 UI 上看到"任务在 X 时间中断（执行到 X 步骤），是否继续？"
- 用户选择"继续"才走 Resume 路径
- 用户选择"放弃"则标记任务为 `Cancelled`

### 3.2 启动流程

```csharp
public sealed class WorkModeStartupService : IHostedService
{
    private readonly WorkTaskService _taskService;
    private readonly IPublisher _publisher;
    private readonly ILogger<WorkModeStartupService> _logger;

    public async Task StartAsync(CancellationToken ct)
    {
        // 查找所有"上次没正常关闭"的任务
        var orphanedTasks = await _taskService.GetActiveTasksAsync(ct);

        foreach (var task in orphanedTasks)
        {
            // 注意：不区分 PendingRequestId 是否存在
            // - 有 PendingRequest → 上次挂在 HITL 上正常等待
            // - 无 PendingRequest → 上次正在执行中崩溃
            // 两种情况都不自动恢复，统一标记为"待用户决定"

            await _taskService.MarkOrphanedAsync(task.Id, ct);
            //                ↑ 不改 IsActive，但加一个 IsOrphaned=1 标记

            _logger.LogInformation(
                "Task {TaskId} found orphaned (last activity: {Time}), awaiting user decision",
                task.Id, task.LastActiveAt);
        }
    }
}
```

### 3.4 UI 端恢复展示

用户重启应用、切到工作模式 Tab、加载最近会话时：

```csharp
// WorkModeViewController 加载会话时

### 3.5 用户决策

**继续**（`ContinueOrphanedAsync`）：

```csharp
public async Task ContinueOrphanedAsync(string taskId)
{
    await _taskService.ClearOrphanedFlagAsync(taskId);

    // 走 ResumeAsync 或 ContinueAsync 路径
    // 取决于任务原本是 HITL 挂起还是正在执行
    var task = await _taskService.GetByIdAsync(taskId);
    if (!string.IsNullOrEmpty(task.PendingRequestId))
    {
        // 上次挂在 HITL 上 → 等用户在输入框给出回应
        // UI 已经把 HITL 的浮窗或问题重新展示
        return;
    }
    else
    {
        // 上次在执行中崩溃 → 注入"继续"提示让 AI 接着做
        await _executor.ContinueAsync(taskId, "继续上次未完成的工作", CancellationToken.None);
    }
}
```

**放弃**（`AbandonOrphanedAsync`）：

```csharp
public async Task AbandonOrphanedAsync(string taskId)
{
    await _taskService.MarkCancelledAsync(taskId, "用户放弃恢复");
    // UI 把 ResumeCard 替换为"任务已取消"卡片
}
```

## 四、Layer 2：AF Workflow Checkpoint（应用内自愈）

### 4.1 当前 AF 的能力

AF 的 `JsonCheckpointStore` 在每个 superstep 完成时自动保存（[04 文档 §2.2](./04-长任务与持久化.md)）。这意味着：

- 主 Agent 每次完成一轮"对话→工具调用→工具返回"循环，状态都会被保存
- 单次工具失败抛异常，AF 内部能从最近 checkpoint 重新尝试该 superstep（**取决于 RetryPolicy 配置**）

### 4.2 启用 AF 自动重试

`WorkflowExecutor.ExecuteAsync` 的 `RunOptions` 要配置：

```csharp
var run = await InProcessExecution.RunStreamingAsync(
    workflow,
    new ChatMessage(ChatRole.User, userInput),
    new RunOptions
    {
        CheckpointManager = new CheckpointManager(_checkpointStore),
        // 关键：启用 superstep 级别的重试
        // RetryPolicy 的具体 API 名称需在 AF 验证 sample 里确认
        RetryPolicy = new SuperstepRetryPolicy
        {
            MaxAttempts = 3,
            BackoffStrategy = BackoffStrategy.Exponential,
            InitialDelay = TimeSpan.FromSeconds(2),
            MaxDelay = TimeSpan.FromSeconds(30),
        },
    },
    cancellationToken: ct);
```

> **实施前验证项**（写入 14 文档 §五）：AF v1.6 是否提供 `SuperstepRetryPolicy`，如不提供则在 `WorkflowExecutor` 顶层用 try/catch + 指数退避包装。

### 4.3 顶层异常自愈

不论 AF 是否提供原生重试，`WorkflowExecutor.ConsumeEventsAsync` 顶层都要有自愈逻辑：

```csharp
private async Task ConsumeEventsAsync(string taskId, StreamingRun run, CancellationToken ct)
{
    var attemptCount = 0;
    const int MaxAttempts = 3;
    var backoff = TimeSpan.FromSeconds(2);

    while (attemptCount < MaxAttempts)
    {
        try
        {
            await foreach (var evt in run.WatchAsync().WithCancellation(ct))
            {
                await _eventDispatcher.HandleAsync(taskId, run, evt, ct);

                if (evt is WorkflowOutputEvent or WorkflowErrorEvent)
                {
                    await _taskService.SetActiveAsync(taskId, false, ct);
                    return; // 任务完成 / 失败，正常退出
                }
                if (evt is RequestInfoEvent reqEvt)
                {
                    await _hitlService.PersistPendingRequestAsync(taskId, run.RunId, reqEvt.Request, ct);
                    return; // HITL 挂起，正常退出
                }
            }

            // 事件流自然结束（一轮对话完成）
            return;
        }
        catch (OperationCanceledException) when (ct.IsCancellationRequested)
        {
            // 用户取消（不是抢占），不重试
            throw;
        }
        catch (Exception ex) when (IsTransientError(ex) && attemptCount < MaxAttempts - 1)
        {
            attemptCount++;
            _logger.LogWarning(ex,
                "Task {TaskId} transient error (attempt {N}/{Max}), retrying after {Delay}s",
                taskId, attemptCount, MaxAttempts, backoff.TotalSeconds);

            // 写入日志让 UI 显示"正在重试"
            await _logService.AppendAsync(taskId, new WorkExecutionLog
            {
                LogType = WorkExecutionLogType.RetryAttempt,
                Content = JsonSerializer.Serialize(
                    new RetryAttemptRecord(attemptCount, MaxAttempts, ex.Message, ex.GetType().Name),
                    WorkModeJsonContext.Default.RetryAttemptRecord),
            }, ct);
            _publisher.Publish(Events.OnWorkRetryAttempt,
                new WorkRetryAttemptArgs(taskId, attemptCount, MaxAttempts, ex.Message));

            await Task.Delay(backoff, ct);
            backoff = TimeSpan.FromTicks(Math.Min(backoff.Ticks * 2,
                                                  TimeSpan.FromSeconds(30).Ticks));

            // Resume 重新开始事件循环（AF 会从最近 checkpoint 恢复）
            run = await InProcessExecution.ResumeAsync(
                _workflow, run.RunId,
                new RunOptions { CheckpointManager = new CheckpointManager(_checkpointStore) },
                ct);
            continue;
        }
        catch (Exception ex)
        {
            // 不可恢复的错误，标记任务失败
            _logger.LogError(ex, "Task {TaskId} failed unrecoverably", taskId);
            await _taskService.MarkFailedAsync(taskId, ex.Message, ct);
            throw;
        }
    }

    // 重试用尽
    await _taskService.MarkFailedAsync(taskId,
        $"任务在 {MaxAttempts} 次重试后仍失败", ct);
}

private static bool IsTransientError(Exception ex) => ex switch
{
    HttpRequestException                => true,
    TaskCanceledException               => true,   // 通常是超时
    SocketException                     => true,
    IOException io                      => true,
    JsonException                       => true,   // 模型输出 JSON 解析失败
    _ when ex.Message.Contains("429")   => true,   // 限流
    _ when ex.Message.Contains("502")
        || ex.Message.Contains("503")
        || ex.Message.Contains("504")   => true,
    _                                   => false,
};
```

### 4.4 重试与用户体验

UI 看到 `OnWorkRetryAttempt` 事件后，在当前正在运行的卡片上显示"重试中 (2/3)"，**不打扰用户**。重试成功后状态恢复"运行中"。重试用尽才向用户展示错误。

## 五、Layer 4：分类型重试上限

> 之所以先讲 Layer 4 再讲 Layer 3：自评循环（Layer 3）是上层应用，依赖底下的重试机制。

### 5.1 三类失败与对应上限（用户已确认）

| 失败类型 | 触发条件 | 上限 | 退避策略 | 处理 |
|---------|---------|------|---------|------|
| **网络/API 错误** | 模型 API 502/503/504/429、网络超时 | 5 次 | 指数退避 2s→4s→8s→16s→30s | 自动重试，UI 显示"重试中" |
| **工具执行失败** | 工具方法抛异常 | 3 次 | 指数退避 1s→3s→8s | 自动重试，第 3 次失败转 `verify_step` 让 AI 决定 |
| **模型输出格式错误** | 反序列化失败、缺必需字段 | 2 次 | 立即重试 | 第 2 次失败把错误信息塞回提示词重试一次，仍失败转 ask_user |

### 5.2 失败分类器

```csharp
namespace Netor.Cortana.AI.WorkMode.Reliability;

public enum FailureKind
{
    NetworkOrApi,        // 网络/API 错误（5 次上限）
    ToolExecution,       // 工具执行失败（3 次上限）
    ModelOutputFormat,   // 模型输出格式错误（2 次上限）
    Unrecoverable,       // 不可恢复（不重试，直接失败）
}

public sealed class FailureClassifier
{
    public static FailureKind Classify(Exception ex) => ex switch
    {
        // 网络/API 类
        HttpRequestException                 => FailureKind.NetworkOrApi,
        TaskCanceledException tc when !tc.CancellationToken.IsCancellationRequested
                                             => FailureKind.NetworkOrApi,
        SocketException                      => FailureKind.NetworkOrApi,
        IOException                          => FailureKind.NetworkOrApi,
        _ when ex.Message.Contains("429") || ex.Message.Contains("rate_limit")
                                             => FailureKind.NetworkOrApi,
        _ when Regex.IsMatch(ex.Message, @"\b50[234]\b")
                                             => FailureKind.NetworkOrApi,

        // 模型输出格式
        JsonException                        => FailureKind.ModelOutputFormat,
        InvalidOperationException ioe when ioe.Message.Contains("schema")
                                             => FailureKind.ModelOutputFormat,

        // 工具执行
        ToolExecutionException               => FailureKind.ToolExecution,

        // 用户取消（不重试）
        OperationCanceledException oce when oce.CancellationToken.IsCancellationRequested
                                             => FailureKind.Unrecoverable,

        // 默认按工具执行处理（保守策略）
        _                                    => FailureKind.ToolExecution,
    };

    public static int GetMaxAttempts(FailureKind kind) => kind switch
    {
        FailureKind.NetworkOrApi      => 5,
        FailureKind.ToolExecution     => 3,
        FailureKind.ModelOutputFormat => 2,
        _                             => 0,
    };

    public static TimeSpan GetBackoff(FailureKind kind, int attempt) => kind switch
    {
        FailureKind.NetworkOrApi      => TimeSpan.FromSeconds(Math.Min(2 * Math.Pow(2, attempt - 1), 30)),
        FailureKind.ToolExecution     => TimeSpan.FromSeconds(Math.Min(1 * Math.Pow(3, attempt - 1), 10)),
        FailureKind.ModelOutputFormat => TimeSpan.Zero,  // 立即重试
        _                             => TimeSpan.Zero,
    };
}
```

### 5.3 工具调用重试包装

工具失败的重试在工具调用层面做，不让 AF 感知：

```csharp
namespace Netor.Cortana.AI.WorkMode.Tools;

/// <summary>
/// 把任意 AIFunction 包装为带重试能力的版本。
/// 包装后的工具对 AI 透明（只看到最终结果），但内部会做分类型重试。
/// </summary>
public static class RetryingFunctionWrapper
{
    public static AIFunction Wrap(AIFunction inner, string taskId, IServiceProvider sp)
    {
        var logService = sp.GetRequiredService<WorkExecutionLogService>();
        var publisher = sp.GetRequiredService<IPublisher>();
        var logger = sp.GetRequiredService<ILogger<AIFunction>>();

        // AF 提供 DelegatingAIFunction 模式（具体 API 在实施前从 AF 源码确认）
        return new DelegatingAIFunction(inner, async (args, ct) =>
        {
            var attempt = 0;
            while (true)
            {
                try
                {
                    return await inner.InvokeAsync(args, ct);
                }
                catch (Exception ex)
                {
                    var kind = FailureClassifier.Classify(ex);
                    var maxAttempts = FailureClassifier.GetMaxAttempts(kind);
                    attempt++;

                    if (kind == FailureKind.Unrecoverable || attempt >= maxAttempts)
                    {
                        // 失败上限到达，把异常往上抛
                        // AI 会看到工具结果是 FunctionResultContent.Exception
                        // 总经理 Agent 通过 verify_step 或 ask_user 决定下一步
                        logger.LogWarning(ex,
                            "Tool {Name} failed after {Attempt} attempts (kind: {Kind})",
                            inner.Name, attempt, kind);
                        throw;
                    }

                    var backoff = FailureClassifier.GetBackoff(kind, attempt);
                    logger.LogInformation(
                        "Tool {Name} attempt {N}/{Max} failed ({Kind}), retrying after {Delay}",
                        inner.Name, attempt, maxAttempts, kind, backoff);

                    publisher.Publish(Events.OnWorkRetryAttempt,
                        new WorkRetryAttemptArgs(taskId, attempt, maxAttempts, ex.Message));

                    if (backoff > TimeSpan.Zero)
                        await Task.Delay(backoff, ct);
                }
            }
        });
    }
}
```

### 5.4 在 WorkModeToolset 应用包装

```csharp
// WorkModeToolset.BuildTools 末尾追加
var rawTools = new List<AIFunction>
{
    /* ... 所有原始工具 ... */
};

// 全部用 RetryingFunctionWrapper 包装
return rawTools
    .Select(t => RetryingFunctionWrapper.Wrap(t, taskId, _serviceProvider))
    .ToList();
```

> **注意**：`set_plan` / `final_report` 这种纯数据库操作的工具失败概率低，重试对它们也不会有副作用（写库幂等），统一包装是安全的。

### 5.5 子智能体调用的重试

子智能体通过 `BuildWithSubAgents` 注入为 `agent_*` 工具。这些工具内部会调用模型 API，重试逻辑和普通工具一样——**统一在工具包装层做**，不需要在子 Agent 层重复做。

## 六、Layer 3：自评循环（自主迭代改进）

### 6.1 设计目标

视频剪辑场景核心流程：

```text
AI: 调用 export_video 生成片段 v1
AI: 调用 self_evaluate 看 v1 → 评估"15 秒处卡顿"
AI: 调整参数，调用 export_video 生成 v2
AI: 调用 self_evaluate 看 v2 → 评估"过渡生硬"
AI: 调整参数，调用 export_video 生成 v3
AI: 调用 self_evaluate 看 v3 → 评估"达标"
AI: 把 v3 作为本子步骤的产出
```

整个迭代过程**不打扰用户**。用户只看到主步骤完成时的最终产出。

### 6.2 self_evaluate 工具

```csharp
[Description(
    "对当前子步骤的产出做自我评估。如果产出是图片/视频/音频，会调用多模态模型查看；" +
    "如果是文本/代码，会调用模型审阅。返回评分（0-100）和问题清单。")]
public async Task<SelfEvaluationResult> SelfEvaluateAsync(
    [Description("产出的描述（让评估器知道在评估什么）")] string artifactDescription,
    [Description("产出文件路径（可空）")] string? artifactPath,
    [Description("评估标准（来自计划里的验收标准）")] string acceptanceCriteria,
    [Description("当前是第几次迭代（从 1 开始）")] int iteration,
    CancellationToken ct)
{
    // 1. 加载评估器 Agent（动态构建，提示词来自 work_mode.self_evaluator.md）
    var evaluator = await _evaluatorBuilder.BuildAsync(ct);

    // 2. 组装输入：附件 + 评估上下文
    var contents = new List<AIContent>
    {
        new TextContent($"评估标准：{acceptanceCriteria}\n产出描述：{artifactDescription}"),
    };
    if (!string.IsNullOrEmpty(artifactPath) && File.Exists(artifactPath))
    {
        var mime = MimeHelper.GuessFromPath(artifactPath);
        if (mime.StartsWith("image/") || mime.StartsWith("video/") || mime.StartsWith("audio/"))
        {
            contents.Add(await DataContent.LoadFromAsync(artifactPath, mime, ct));
        }
    }

    // 3. 调用评估
    var msg = new ChatMessage(ChatRole.User, contents);
    var response = await evaluator.RunAsync([msg], cancellationToken: ct);

    // 4. 解析（评估器提示词约束输出 JSON）
    return ParseSelfEvaluationResult(response.Messages.Last().Text);
}

public sealed record SelfEvaluationResult(
    int Score,                                        // 0-100
    string Verdict,                                   // "pass" / "fail" / "marginal"
    IReadOnlyList<string> Issues,                     // 具体问题列表
    IReadOnlyList<string> Suggestions);               // 改进建议
```

```markdown

严格的 JSON：

```json

## 评分指引

- 90-100 = pass（达标）
- 70-89 = marginal（边缘，列出问题但建议进入下一步）
- < 70 = fail（必须改进后重做）

## 评估原则

- **客观**：只评估产出本身，不评估"努力程度"
- **具体**：问题要可执行（"第 30 秒画面闪烁"，不是"质量不行"）
- **不挑刺**：90+ 分不要硬找问题；判 pass 就让它过
- **不放水**：< 70 分要明确说理由

## 七、Layer 5：死循环检测

### 7.1 死循环典型形态

| 形态 | 表现 |
|------|------|
| **同工具反复失败** | 重试 N 次都失败，AI 还在调同一工具同一参数 |
| **自评震荡** | self_evaluate 反复在 fail / marginal 之间切换，每次 issues 不同 |
| **进度停滞** | 一个子步骤超过 30 分钟还没完成，且无新事件 |

### 7.2 检测器

```csharp
public sealed class DeadlockDetector
{
    private readonly WorkExecutionLogService _logService;
    private readonly WorkTaskService _taskService;
    private readonly ILogger<DeadlockDetector> _logger;

    // 在每次工具调用前检查（接到 OnWorkToolCalled 事件后）
    public async Task<DeadlockDetectionResult> CheckAsync(string taskId, string toolName, string paramsJson)
    {
        var recent = await _logService.GetRecentLogsAsync(taskId, take: 30);

        // 形态 1：同工具同参数连续失败
        var sameToolSamArgs = recent
            .Where(l => l.LogType == WorkExecutionLogType.ToolResult)
            .Take(5)
            .Select(l => JsonSerializer.Deserialize(l.Content, WorkModeJsonContext.Default.ToolResultRecord))
            .ToList();

        if (sameToolSamArgs.Count >= 5
            && sameToolSamArgs.All(r => r is { Status: "failed" }))
        {
            return DeadlockDetectionResult.RepeatedToolFailure(toolName);
        }

        // 形态 2：自评震荡
        var recentEvals = recent
            .Where(l => l.LogType == WorkExecutionLogType.SelfEvaluation)
            .Take(5)
            .Select(l => JsonSerializer.Deserialize(l.Content, WorkModeJsonContext.Default.SelfEvaluationRecord))
            .ToList();

        if (recentEvals.Count >= 5)
        {
            var verdicts = recentEvals.Select(e => e!.Verdict).Distinct().ToHashSet();
            if (verdicts.SetEquals(new[] { "fail", "marginal" })
                || verdicts.Contains("fail") && recentEvals[0]!.Iteration >= 5)
            {
                return DeadlockDetectionResult.SelfEvaluationOscillation();
            }
        }

        // 形态 3：进度停滞（用心跳检测，§6.x 描述）
        var task = await _taskService.GetByIdAsync(taskId);
        if (task is not null && task.HeartbeatAt is not null)
        {
            var stalled = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() - task.HeartbeatAt;
            if (stalled > TimeSpan.FromMinutes(30).TotalMilliseconds)
            {
                return DeadlockDetectionResult.ProgressStalled(TimeSpan.FromMilliseconds(stalled));
            }
        }

        return DeadlockDetectionResult.Healthy();
    }
}

public sealed record DeadlockDetectionResult(bool IsDeadlock, string? Reason)
{
    public static DeadlockDetectionResult Healthy() => new(false, null);
    public static DeadlockDetectionResult RepeatedToolFailure(string tool) =>
        new(true, $"工具 {tool} 连续失败 5 次以上");
    public static DeadlockDetectionResult SelfEvaluationOscillation() =>
        new(true, "自评循环震荡，可能陷入完美主义陷阱");
    public static DeadlockDetectionResult ProgressStalled(TimeSpan duration) =>
        new(true, $"任务停滞超过 {(int)duration.TotalMinutes} 分钟");
}
```

### 7.3 检测命中后的处理

`WorkflowEventDispatcher.OnAgentDeltaAsync` 收到 `FunctionCallContent` 时调用 `DeadlockDetector.CheckAsync`：

    if (deadlock.IsDeadlock)

## 八、长任务编排模式（架构核心）

> 这一章是工作模式架构的核心契约。**任何"耗时超过 60 秒的工具调用"都必须按这套模式执行**，不允许主智能体直接 await 长操作。

### 8.1 三层职责模型

```text
┌─────────────────────────────────────────────────────────────┐
│ Layer 3 — 主智能体（总经理 Agent）                            │
│   职责：决策"用什么工具"，对长操作主动 poll 查进度             │
│   - 不区分"插件 vs 子智能体"——都是工具                       │
│   - 看到 [LONG] 前缀的工具就走 start → poll → use 模式         │
│   - 由 Instructions（提示词）强制约束行为                     │
└─────────────────────────────────────────────────────────────┘
                       ↑ 工具集（AIFunction[]）
┌─────────────────────────────────────────────────────────────┐
│ Layer 2 — 工具注入层（AIAgentFactory + WorkModeToolset）      │
│   职责：把异构后端统一暴露为 AIFunction                       │
│   工具来源：                                                 │
│     A. 普通插件工具                  → PluginContextProvider │
│     B. 长任务插件                    → 同上（插件自管会话）   │
│     C. 同步子智能体（短查询）        → BuildWithSubAgents     │
│     D. 背景子智能体（长任务）        → 子智能体背景执行框架    │
└─────────────────────────────────────────────────────────────┘
                       ↑ 实现支撑
┌─────────────────────────────────────────────────────────────┐
│ Layer 1 — 执行后端                                            │
│  ┌──────────────────────────┬──────────────────────────────┐ │
│  │ 插件自治（已有，零改造）  │ 主软件托管（v1.0 新增）       │ │
│  │                          │                              │ │
│  │ ExternalProcessPluginHost│ IBackgroundJobExecutor       │ │
│  │   ↳ stdin/stdout JSON    │   ↳ SubAgentJobExecutor (核心)│ │
│  │   ↳ PluginBus WS 推送    │   ↳ 未来扩展点 (v1.1+)        │ │
│  │                          │                              │ │
│  │ 状态：插件子进程内自管     │ 状态：WorkBackgroundJobs 表  │ │
│  │ 进度：插件提供查询工具     │ 进度：通过 EventHub 发事件    │ │
│  │ 主软件 DB 不参与           │                              │ │
│  └──────────────────────────┴──────────────────────────────┘ │
└─────────────────────────────────────────────────────────────┘
```

### 8.2 职责边界（不可越线）

| 边界项 | 插件自治（A/B 类工具） | 主软件托管（D 类工具） |
|-------|---------------------|---------------------|
| 状态存储 | 插件子进程内（如 PowerShell `SessionRegistry`） | `WorkBackgroundJobs` 表 |
| 进度查询机制 | 插件提供查询类工具（如 `sys_get_session_status`） | `wait_for_subagent` 工具读 SQLite |
| 进程崩溃边界 | 插件子进程崩溃 ≠ 主软件崩溃 | 与主进程同生死（由 `ChildProcessTracker` 决定） |
| 主软件 DB 写入 | **零写入**（不要写 WorkBackgroundJobs） | 写 WorkBackgroundJobs |
| 跨主进程重启 | 插件被 Kill（受 ChildProcessTracker 影响） | 主进程崩溃 = Task 丢，重启走 `IsOrphaned` 路径 |
| 实施工作 | **无**（已存在） | v1.0 新建 |

> **架构原则**：插件已经是一个**自治的状态边界**——它有自己的进程、自己的会话存储、自己的查询接口。主软件不要侵入这个边界。如果插件需要持久化能力，是插件自己的实现细节，不是主软件的责任。

### 8.3 工具命名约定

为了让主智能体统一识别"哪些工具不能直接 await"，所有长任务工具用 `[LONG]` 前缀（**写入名称的 Description 部分，不是 name 本身**——AF 的工具 name 字段限制为 `[a-zA-Z0-9_-]`）：

```csharp
// AIFunctionFactory.Create 时的 Description
"[LONG] 启动后台渲染任务，立即返回 jobId"
"[LONG] 查询后台渲染进度，最多等待 max_seconds 秒"
"[LONG] 启动背景子智能体，立即返回 sub_task_id"
"[LONG] 等待背景子智能体的进度，最多 60 秒返回当前状态"
```

主智能体在 Instructions 里被引导：

```markdown
看到工具 Description 以 [LONG] 开头的，必须走以下模式之一：
- 启动型工具：调用后立即拿到 jobId/sessionId/taskId，不要等结果
- 查询型工具：可以阻塞调用，但工具内部会限定最长等待时间（一般 30-60 秒）
- 关闭型工具：使用完后必须调用，释放资源

错误用法：以 await 一次性等到底（即使工具不限时间，也禁止主智能体连续 poll 超过 60 秒不放手——
应当让 wait_for_X 自然返回，进入下一个 superstep 让 Checkpoint 落盘）
```

### 8.4 IBackgroundJobExecutor — 主软件托管的扩展抽象

为了让主软件托管的"背景执行"具备框架级可扩展性（v1.0 只做子智能体，未来可加视频处理、批量分析等），定义统一抽象：

```csharp
namespace Netor.Cortana.AI.WorkMode.Background;

/// <summary>
/// 主软件托管的背景任务执行器抽象。
/// 适用场景：执行体本质是"主进程内的 AI 推理或 .NET 计算"，需要主软件管理生命周期。
///
/// 不适用：插件长任务（插件自治，由插件子进程管理）。
/// </summary>
public interface IBackgroundJobExecutor
{
    /// <summary>执行器类型，对应 WorkBackgroundJobs.JobKind。</summary>
    string JobKind { get; }

    /// <summary>启动一个背景任务，立即返回 jobId。</summary>
    Task<string> StartAsync(BackgroundJobStartRequest request, CancellationToken ct);

    /// <summary>查询任务状态（不阻塞）。</summary>
    Task<BackgroundJobStatus> GetStatusAsync(string jobId, CancellationToken ct);

    /// <summary>等待任务进展，最多等待 maxWait 秒后返回当前状态。</summary>
    Task<BackgroundJobStatus> WaitAsync(string jobId, TimeSpan maxWait, CancellationToken ct);

    /// <summary>取消任务（向执行体发取消信号，不保证立即停止）。</summary>
    Task CancelAsync(string jobId, CancellationToken ct);
}

public sealed record BackgroundJobStartRequest(
    string TaskId,                  // 父 WorkTask
    string? OwnerName,              // 子智能体名 / 任务来源标识
    string InputJson,               // 启动参数（按 JobKind 解析）
    IReadOnlyDictionary<string, string>? Metadata);

public sealed record BackgroundJobStatus(
    string JobId,
    BackgroundJobState State,       // pending / running / completed / failed / cancelled
    string? ProgressDescription,    // "正在分析第 12 个文件..." 给 AI 看
    string? ResultJson,             // State=completed 时
    string? Error);                 // State=failed 时

public enum BackgroundJobState { Pending, Running, Completed, Failed, Cancelled }

#### v1.0 实现：SubAgentJobExecutor

```csharp
public sealed class SubAgentJobExecutor : IBackgroundJobExecutor
{
    public string JobKind => "subagent";

    private readonly ConcurrentDictionary<string, RunningJob> _running = new();
    private readonly WorkBackgroundJobsService _jobService;
    private readonly WorkExecutionLogService _logService;
    private readonly AIAgentFactory _agentFactory;
    private readonly IPublisher _publisher;

    public async Task<string> StartAsync(BackgroundJobStartRequest req, CancellationToken ct)
    {
        var input = JsonSerializer.Deserialize(req.InputJson,
            WorkModeJsonContext.Default.SubAgentJobInput)!;

        // 构建子智能体（同步版 BuildWithSubAgents 已有逻辑复用）
        var subAgent = _agentFactory.BuildSubAgent(input.AgentEntity, input.Provider, input.Model);

        // 入库 + 启动 Task
        var job = await _jobService.CreateAsync(req.TaskId, JobKind, req.OwnerName, req.InputJson, ct);

        var task = Task.Run(async () => await RunSubAgentLoopAsync(job.Id, subAgent, input.Query));
        _running[job.Id] = new RunningJob(task, /* CTS */);

        return job.Id;
    }

    private async Task RunSubAgentLoopAsync(string jobId, AIAgent subAgent, string query)
    {
        await _jobService.SetRunningAsync(jobId);
        try
        {
            var sequence = 0;
            await foreach (var update in subAgent.RunStreamingAsync(
                [new ChatMessage(ChatRole.User, query)]))
            {
                // 关键约束：子智能体的对话只写 WorkExecutionLogs，不写 ChatMessages
                await _logService.AppendAsync(/* taskId from job */, new WorkExecutionLog
                {
                    LogType = WorkExecutionLogType.SubAgentDelta,
                    Content = JsonSerializer.Serialize(
                        new SubAgentDeltaRecord(jobId, update.AuthorName, update.Text),
                        WorkModeJsonContext.Default.SubAgentDeltaRecord),
                });
                _publisher.Publish(Events.OnWorkSubAgentProgress,
                    new WorkSubAgentProgressArgs(jobId, update.Text));
            }

            var finalText = /* 收集完成的最终结果 */;
            await _jobService.SetCompletedAsync(jobId, finalText);
        }
        catch (Exception ex)
        {
            await _jobService.SetFailedAsync(jobId, ex.Message);
        }
    }

    public Task<BackgroundJobStatus> GetStatusAsync(string jobId, CancellationToken ct)
        => _jobService.GetStatusAsync(jobId, ct);

    public async Task<BackgroundJobStatus> WaitAsync(string jobId, TimeSpan maxWait, CancellationToken ct)
    {
        var deadline = DateTime.UtcNow + maxWait;
        while (DateTime.UtcNow < deadline)
        {
            var status = await _jobService.GetStatusAsync(jobId, ct);
            if (status.State is BackgroundJobState.Completed or BackgroundJobState.Failed
                or BackgroundJobState.Cancelled)
                return status;
            await Task.Delay(2000, ct);
        }
        return await _jobService.GetStatusAsync(jobId, ct);  // 到期返回当前状态
    }

    public Task CancelAsync(string jobId, CancellationToken ct)
    {
        if (_running.TryGetValue(jobId, out var job))
            job.Cancel();
        return _jobService.SetCancelledAsync(jobId);
    }
}

        ↓
        SubAgentJobExecutor.WaitAsync 轮询 SQLite 60 秒
        子智能体还在跑 → 返回 status=running, progress="正在分析第 3 季度数据"
        子智能体完成 → 返回 status=completed, result=完整报告 JSON

AI 拿到结果作为 FunctionResultContent 注入主对话历史
```

两种模式对 AI 来说**用法完全一致**——都是"start → wait/check → use result"。区别只在 Layer 1 的实现，Layer 3 不需要知道。

### 9.6 不属于本框架的能力（明确边界）

以下能力**不在主软件托管范围内**，由插件自己提供：

- 插件长任务的会话状态存储 → 插件子进程内自管（如 PowerShell 插件的 `SessionRegistry`）
- 插件长任务的进度查询 → 插件提供查询类工具（如 `sys_get_session_status`）
- 插件长任务的进度事件推送 → 插件通过 `IPluginBusBroadcaster` 推 WebSocket 给 UI
- 插件子进程崩溃恢复 → 插件自己的实现细节，主软件不介入

主软件**禁止**做的事：

- ❌ 在 `WorkBackgroundJobs` 写入 JobKind="plugin" 的记录
- ❌ 用 PID/sessionId 跟踪插件后台任务
- ❌ 主软件层调用插件的内部状态接口（破坏插件自治边界）

## 十二、最终承诺

工作模式上线后，**用户可以做以下事**：

- ✅ 周五晚上启动一个网站开发任务，关掉 Cortana 窗口去睡觉，周六中午回来看进度
- ✅ 视频剪辑过程中模型 API 限流，Cortana 自动等待退避后继续，用户无感知
- ✅ 30 小时任务跑了 20 小时电脑死机，重启 Cortana 后选"继续"接着跑，已完成的 20 小时不重做
- ✅ AI 卡在某一步反复失败，5 次后停下来问用户怎么办，不会无限烧 token
- ✅ 视频剪辑里 AI 自己看 5 次都不满意，停下来问用户"我觉得这一段一直处理不好，你来看看"

**用户不会遇到以下事**：

- ❌ 一次模型 502 让 8 小时进度全废
- ❌ 30 小时任务的最后 1 步失败让前面 29 小时进度也丢
- ❌ AI 在某一步上无限循环烧光 API 配额
- ❌ 应用崩溃恢复后默默继续做高风险操作（应用外的崩溃恢复必须经用户确认）
