# 20 - 工作模式上下文压缩设计

> 本文只负责工作模式的运行上下文压缩方案。
> 目标是解决长任务、多轮确认、多次工具调用后，总经理智能体上下文无限增长的问题。
>
> 设计原则：复用系统设置中已有的 `Compaction.*` 参数，不新增一套用户可见配置。

---

## 一、当前代码现状

### 1.1 普通对话已有压缩链路

普通对话已经有完整的压缩能力：

| 位置 | 当前能力 |
|------|----------|
| `ChatHistoryDataProvider` | 保存 `ChatMessages` 后触发 `CompactAndReplaceAsync` |
| `CompactionSegmentService` | 读写 `CompactionSegments` 表 |
| `Compaction.ModelId` | 指定摘要/压缩模型 |
| `Compaction.SegmentSize` | 每多少条消息生成一个压缩段落 |
| `Compaction.RawTailSize` | 保留最近多少条原始消息 |
| `Compaction.MaxDisplaySegments` | 加载历史时最多携带多少个摘要段落 |

普通对话的加载方式是：

```text
压缩段落摘要 + 尾部原始消息
```

这条链路已经能避免普通聊天历史无限增长。

### 1.2 工作模式没有接入压缩链路

当前工作模式的运行上下文由 `WorkflowExecutor` 自己维护：

```csharp
ConcurrentDictionary<string, List<ChatMessage>> _chatHistories
```

执行时直接把完整内存列表传给模型：

```csharp
await foreach (var chunk in aiAgent.RunStreamingAsync(history, cancellationToken: linkedCts.Token))
```

这意味着：

- 不经过 `ChatHistoryDataProvider.ProvideChatHistoryAsync`
- 不读取 `CompactionSegments`
- 不调用 `CompactAndReplaceAsync`
- 不使用 `Compaction.SegmentSize / RawTailSize / MaxDisplaySegments`
- 进程重启后，`_chatHistories` 会丢失
- 长任务多轮执行后，上下文会持续膨胀

### 1.3 不能把普通对话压缩直接当成工作模式压缩

工作模式和普通对话共享 `ChatSession`，但两者压缩对象不同：

| 类型 | 作用 | 是否应压缩 |
|------|------|------------|
| `ChatMessages` | 用户可见的普通对话历史、任务完成总结 | 继续使用现有普通对话压缩 |
| `WorkExecutionLogs` | 执行过程事实记录、工具调用、验收、错误 | 不压缩，不删除，作为审计和恢复真相 |
| 工作模式运行上下文 | 总经理下一轮推理要读的上下文 | 需要单独压缩 |

工作模式压缩不能覆盖执行日志，也不能把 UI 时间线当成模型上下文。

---

## 二、设计目标

1. **复用现有压缩设置**
   - 不新增工作模式专属的压缩配置页面。
   - 直接使用 `Compaction.ModelId / SegmentSize / RawTailSize / MaxDisplaySegments`。

2. **限制总经理上下文长度**
   - 每次调用模型前，构造“摘要段落 + 尾部原文”的上下文。
   - 不再把 `_chatHistories[taskId]` 从头到尾全部传给模型。

3. **支持崩溃恢复**
   - 工作模式运行上下文不能只放内存。
   - 至少要持久化“可回灌给模型的轻量消息”和“压缩段落”。

4. **保留执行真相**
   - `WorkExecutionLogs` 是完整执行事实，不参与压缩删除。
   - 压缩只影响“下一轮喂给模型的上下文”，不影响历史回放。

5. **避免大工具结果污染上下文**
   - 工具完整结果可以保留在日志或文件中。
   - 模型上下文只放工具名、状态、关键摘要、错误信息、输出文件路径。

## 三、推荐数据模型

### 3.1 新增 `WorkTaskContextMessages`

存储工作模式中“可以喂回模型”的轻量上下文消息。

```sql
CREATE TABLE IF NOT EXISTS WorkTaskContextMessages (
    Id           TEXT PRIMARY KEY,
    TaskId       TEXT NOT NULL,
    MessageIndex INTEGER NOT NULL,
    Role         TEXT NOT NULL,        -- user / assistant / system / tool
    AuthorName   TEXT NULL,
    Content      TEXT NOT NULL,
    ContentKind  TEXT NOT NULL DEFAULT 'text',
    CreatedAt    INTEGER NOT NULL,

    FOREIGN KEY (TaskId) REFERENCES WorkTasks(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS IX_WorkTaskContextMessages_Task_Index
ON WorkTaskContextMessages(TaskId, MessageIndex);
```

写入原则：

- 用户输入写入 `user`。
- 总经理自然语言回复写入 `assistant`。
- 计划确认、授权请求、用户确认写入轻量文本。
- 工具结果只写摘要，不写完整大结果。
- 大文件读取、批量日志、长工具输出只记录路径、标题、状态、关键结论。

### 3.2 新增 `WorkTaskContextSegments`

存储工作模式运行上下文的压缩段落。

```sql
CREATE TABLE IF NOT EXISTS WorkTaskContextSegments (
    Id                   TEXT PRIMARY KEY,
    TaskId               TEXT NOT NULL,
    SegmentIndex         INTEGER NOT NULL,
    StartMessageIndex    INTEGER NOT NULL,
    EndMessageIndex      INTEGER NOT NULL,
    Summary              TEXT NOT NULL,
    OriginalMessageCount INTEGER NOT NULL,
    ModelName            TEXT NOT NULL DEFAULT '',
    CreatedAt            INTEGER NOT NULL,

    FOREIGN KEY (TaskId) REFERENCES WorkTasks(Id) ON DELETE CASCADE
);

CREATE INDEX IF NOT EXISTS IX_WorkTaskContextSegments_Task_Index
ON WorkTaskContextSegments(TaskId, SegmentIndex);
```

这张表不要复用 `CompactionSegments`，原因是：

- `CompactionSegments` 以 `SessionId` 为主键范围，面向普通 `ChatMessages`。
- 工作模式运行上下文以 `TaskId` 为主键范围。
- 一个 `ChatSession` 可以有多个工作任务。
- 工作任务可以被历史记录恢复，必须能按任务独立重建上下文。

配置复用，存储隔离。

## 四、配置复用规则

工作模式不新增配置项，直接复用：

| 系统设置 | 工作模式含义 |
|----------|--------------|
| `Compaction.ModelId` | 工作模式上下文摘要使用的模型。为空时跟随当前总经理模型。 |
| `Compaction.SegmentSize` | 每多少条 `WorkTaskContextMessages` 生成一个工作上下文摘要段落。 |
| `Compaction.RawTailSize` | 每次调用总经理时保留多少条最近原始上下文消息。 |
| `Compaction.MaxDisplaySegments` | 每次调用总经理时最多加载多少个最近摘要段落。这里不是 UI 展示，而是“最多回灌摘要段落数”。 |

建议默认值继续沿用当前系统设置：

```text
SegmentSize = 30
RawTailSize = 20
MaxDisplaySegments = 15
```

如果工作模式后续发现任务上下文更长，可以只调系统设置，不加新 UI。

## 五、运行流程

### 5.1 每轮执行前构造上下文

`WorkflowExecutor.ExecuteAsync` 不再直接使用无限增长的 `_chatHistories`。

推荐流程：

```text
输入 taskId + userInput
  ↓
从 WorkTaskContextSegments 读取最近 MaxDisplaySegments 个摘要段落
  ↓
从 WorkTaskContextMessages 读取最后 RawTailSize 条原始消息
  ↓
组装 ChatMessage 列表
  ├─ system: [工作上下文摘要 #n] ...
  ├─ user / assistant / tool: 最近原始消息
  └─ user: 本轮用户输入
  ↓
RunStreamingAsync(messages)
```

### 5.2 每轮执行后写入轻量上下文

每轮结束后写入：

```text
WorkTaskContextMessages:
  user      本轮用户输入
  assistant 本轮总经理最终回复摘要或完整短回复
```

工具调用事件不要原样全部塞进上下文。应由 `WorkModeStreamProcessor` 或专门服务写入轻量消息：

```text
tool 调用工具：read_file
tool 结果：成功，读取 README.md，正文已省略，关键输出见 WorkExecutionLogs
tool 错误：失败，文件不存在：xxx
```

### 5.3 触发压缩

每轮结束后调用：

```text
CompactWorkTaskContextAsync(taskId)
```

触发条件沿用普通对话逻辑：

```text
未压缩消息数 > Compaction.SegmentSize + Compaction.RawTailSize
```

只压缩最早的一段 `SegmentSize` 条未压缩消息。

### 5.4 压缩提示词

工作模式压缩提示词应区别于普通聊天摘要，重点保留执行状态：

```text
你是工作模式上下文压缩助手。
请把以下工作任务上下文压缩成可供总经理继续执行任务的摘要。

必须保留：
- 用户最终目标和明确约束
- 已确认的计划、计划变更、用户批准或拒绝
- 当前任务状态、正在等待什么
- 已完成的主步骤、子步骤、验收结论
- 工具调用的关键结果、失败原因、输出文件路径
- 用户插话、补充要求、临时修改
- 未完成事项、下一步应做什么

可以压缩：
- 重复确认、寒暄、过程性废话
- 大段工具输出正文
- 已被后续修正覆盖的中间错误尝试

输出要求：
- Markdown
- 按“目标 / 已完成 / 当前状态 / 关键证据 / 待办”组织
- 不要编造未发生的执行结果
```

## 六、服务设计

建议新增服务：

```text
Src/Netor.Cortana.Entitys/Services/WorkTaskContextService.cs
Src/Netor.Cortana.AI/WorkMode/WorkTaskContextCompactor.cs
```

### 6.1 `WorkTaskContextService`

职责：

- `AppendMessage(taskId, role, content, authorName?, contentKind?)`
- `GetRawTail(taskId, rawTailSize)`
- `GetSegments(taskId, maxSegments)`
- `GetMaxCoveredMessageIndex(taskId)`
- `AddSegment(...)`
- `BuildRuntimeMessages(taskId, userInput, settings)`

### 6.2 `WorkTaskContextCompactor`

职责：

- 读取 `SystemSettingsService` 中的 `Compaction.*`
- 通过 `IChatCompactionClientResolver` 获取摘要模型
- 生成工作模式上下文摘要
- 写入 `WorkTaskContextSegments`
- 失败时不推进覆盖索引

### 6.3 `WorkflowExecutor` 接入点

现有：

```csharp
var history = _chatHistories.GetOrAdd(taskId, _ => new List<ChatMessage>());
history.Add(new ChatMessage(ChatRole.User, userInput));
await foreach (var chunk in aiAgent.RunStreamingAsync(history, ...))
```

目标：

```csharp
var messages = _contextService.BuildRuntimeMessages(taskId, userInput);
await foreach (var chunk in aiAgent.RunStreamingAsync(messages, ...))
{
    ...
}

_contextService.AppendMessage(taskId, "user", userInput);
_contextService.AppendMessage(taskId, "assistant", assistantText);
await _contextCompactor.CompactAsync(taskId, aiAgent, cancellationToken);
```

`_chatHistories` 可以先保留作兼容缓存，但不能再作为唯一上下文来源，也不能无限增长。

## 七、和现有普通对话压缩的关系

### 7.1 普通对话继续按 `ChatSession` 压缩

任务完成后的最终总结仍然写入 `ChatMessages`。

这部分继续由现有 `ChatHistoryDataProvider` 压缩，不需要工作模式再处理。

### 7.2 工作任务运行上下文按 `TaskId` 压缩

工作任务执行期间的计划确认、工具调用摘要、用户插话、运行状态，写入 `WorkTaskContextMessages`。

这部分由工作模式自己的压缩器处理。

### 7.3 两者不能混在一张压缩表

原因：

- 普通对话是会话级别。
- 工作模式运行上下文是任务级别。
- 一个会话可以包含多个任务。
- 工作模式历史恢复要能按任务独立恢复。

---

## 八、边界规则

### 8.1 不压缩执行日志

`WorkExecutionLogs` 是审计和 UI 恢复真相，不删除、不覆盖、不摘要替代。

压缩段落只用于模型上下文，不用于 UI 历史回放。

### 8.2 不把大工具结果塞进上下文

例如：

- 文件全文
- 批量日志
- ERP 查询大结果
- 视频分析输出

应该写入：

```text
工具：read_file
状态：成功
对象：README.md
摘要：读取项目说明，发现启动命令为 ...
完整内容：保留在 WorkExecutionLogs 或外部文件引用中
```

### 8.3 HITL 必须进入上下文

授权、确认计划、用户拒绝、用户提出其他建议，都是影响任务走向的关键信息，必须进入 `WorkTaskContextMessages`。

### 8.4 压缩失败不能造成数据丢失

如果摘要模型失败：

- 不写 `WorkTaskContextSegments`
- 不推进覆盖范围
- 继续保留原始 `WorkTaskContextMessages`
- 记录日志

当原始消息过多且持续压缩失败时，允许在 UI 或系统日志提示“上下文压缩失败，长任务可能消耗更多上下文”。

## 九、实施顺序建议

### 阶段 1：数据模型与服务

- 新增 `WorkTaskContextMessages`
- 新增 `WorkTaskContextSegments`
- 新增 `WorkTaskContextService`
- 注册 DI
- 补齐索引和级联删除

### 阶段 2：执行器接入

- `WorkflowExecutor` 改为从 `WorkTaskContextService` 构造运行上下文。
- 每轮结束后写入 user / assistant 轻量消息。
- 工具调用摘要进入轻量上下文。

### 阶段 3：压缩器接入

- 新增 `WorkTaskContextCompactor`
- 复用 `Compaction.*` 设置
- 复用 `IChatCompactionClientResolver`
- 每轮结束后触发压缩

### 阶段 4：恢复与验收

- 应用重启后恢复任务时，能从摘要段落 + 尾部消息恢复总经理上下文。
- 长任务 100+ 轮对话不会无限增长。
- 压缩失败不丢上下文。

---

## 十、验收标准

- [ ] 工作模式不再依赖无限增长的 `_chatHistories` 作为唯一上下文来源。
- [ ] 工作模式每轮模型输入由“工作上下文摘要段落 + 原始尾部消息 + 当前用户输入”组成。
- [ ] 工作模式复用 `Compaction.ModelId` 选择摘要模型。
- [ ] 工作模式复用 `Compaction.SegmentSize` 控制每段压缩消息数。
- [ ] 工作模式复用 `Compaction.RawTailSize` 控制尾部原始消息数。
- [ ] 工作模式复用 `Compaction.MaxDisplaySegments` 控制最多加载摘要段落数。
- [ ] 工作模式上下文压缩失败时，不删除、不覆盖任何原始上下文消息。
- [ ] `WorkExecutionLogs` 不被压缩替代，历史时间线仍可完整恢复。
- [ ] 工具大结果不会原样进入模型上下文，只进入摘要或引用。
- [ ] 任务完成后的最终总结继续写入 `ChatMessages`，普通对话压缩链路照常工作。

---

## 十一、结论

工作模式上下文压缩应该采用“配置复用、存储隔离、运行上下文独立压缩”的方案：

```text
普通对话：
ChatMessages + CompactionSegments + ChatHistoryDataProvider

工作模式：
WorkTaskContextMessages + WorkTaskContextSegments + WorkTaskContextCompactor

共同配置：
Compaction.ModelId
Compaction.SegmentSize
Compaction.RawTailSize
Compaction.MaxDisplaySegments
```

这样既不破坏现有普通对话压缩能力，也能解决工作模式长任务上下文无限增长的问题。
