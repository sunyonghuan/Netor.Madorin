## 一、为什么做这次重构

### 1.1 核心问题（按优先级）

| 优先级 | 问题 | 表现 |
|-------|------|------|
| **主** | **流程中断** | AI 在长任务中途停下，需要用户手动 ping 才继续。一旦模型在语义边界（写完一卷、做完一阶段）输出"X 已完成，将继续 Y"这种汇报性纯文本，AF 触发 `WorkflowOutputEvent`，任务被判定结束。 |
| **次** | **上下文爆炸** | 长任务历史越积越大，最终模型推不动。压缩可缓解但不能根治。 |

**主次顺序很重要**：这次重构的动机是流程中断，上下文爆炸是顺带解决的。

### 1.2 根因

总经理一身二职：既要跟用户对话，又要持续调度执行。

- 跟人对话时输出"汇报性纯文本"是合法行为
- 调度执行时输出"汇报性纯文本"会让循环死掉
- 同一个智能体里这两种行为无法同时正确

### 1.3 解决思路

**把"对话/规划"和"执行/调度"在架构上拆成两个独立角色，各自用提示词锚死职责**。

对应公司管理体系：

- 总经理负责对外谈业务、定战略、拍板
- 项目组长负责按战略推进，不和客户聊天，只看进度

## 二、三层角色

### 2.1 角色定义

| 层 | 角色 | 公司类比 | 唯一职责 |
|---|------|---------|---------|
| **A** | 总经理 GeneralManager | 业务总监 | 跟用户对话；理解需求；制定/修订计划与环境；接收阶段汇报；处理用户打断 |
| **B** | 项目组长 ProjectLead | 项目经理 PM | 看 plan 推进进度；调度专员；把进度汇报给 A；进度没走完就一直推 |
| **C** | 专员 SubAgent | 一线员工 | 执行单个步骤；产出物；返回 summary |

### 2.2 边界（非常严格）

- **只有 A 跟用户对话**。B 永远不接收用户输入；C 永远不直接对用户说话
- **只有 A 改 plan 和 environment**。B 和 C 只读
- **只有 B 调度 C**。A 不直接 dispatch
- **只有 C 产出物**。A 和 B 不写代码、不写小说、不剪视频
- **C 返回的 summary 不进 B 的工具结果以外的任何地方**——B 看完决策完就该让它在上下文里被压缩或丢弃

### 2.3 角色行为约束

**A 的行为靠提示词约束，B 的行为靠代码控制**（依据 D1）：

- **A** 是 AF Agent，用 prompt.md 里的系统提示词约束行为
- **B** 是 `ProjectLeadService`（C# 类），主循环写在代码里，仅 2 个 LLM 决策点；这 2 个决策点用极短的提示词模板（保存在 prompt.md，由 ProjectLeadService 加载）
- **C** 是 AF Agent，prompt.md 决定它的角色定位、技术选型、思维模式

**A 的提示词要点**：

```text
你是项目总经理。
- 你的职责：和用户对话，理解需求，制定 plan 和 environment，处理用户中途插话。
- 你不执行任何具体工作（不写代码、不写小说、不调外部系统）。
- 当需求清晰后，调 finalize_plan 把计划交给项目组长。
- 之后你的角色是"用户的对接人"：用户问进度时你查 plan 答；用户改需求时你修 plan 或重新规划。
- 你可以输出任何形式的回答给用户，包括"任务已交付，预计 X 小时完成"这种自然语言。
```

**B 的提示词只用于 2 个决策点**（不是给 Agent 当系统提示词用）：

```text
[决策点 1：选 role]
给定 step 描述和已注册 Agent 列表，输出最合适的 role 名（仅 name，无解释）。
若都不合适，输出 NONE。

[决策点 2：分类异常]
给定一次 dispatch 失败的异常信息，输出 RETRY / ESCALATE / SKIP 之一。
- RETRY：临时性故障（网络超时、限流），可重试
- ESCALATE：业务问题（参数错误、能力不足），需 A 介入
- SKIP：可接受失败（非关键步骤），跳过继续
```

每次决策只用小模型（haiku 级），输出强制结构化结果，不存在"输出汇报性文本导致循环退出"的可能。

**C 的提示词** 由 C 自己的 manifest + prompt.md 决定，参见 [执行计划(Agent数据文件化迁移).md](执行计划(Agent数据文件化迁移).md)。

### 2.4 智能体的来源

A、B、C 三层都是 Madorin 智能体体系里的注册项，**统一一套机制**，差异仅在 manifest 和 prompt：

| 角色 | 来源 | manifest 标记 |
|------|------|--------------|
| A `general-manager` | 系统内置（工厂目录拷贝到用户目录） | `kind: builtin/manager` |
| B `project-lead` | 系统内置 | `kind: builtin/orchestrator` |
| C `novel-writer` / `dotnet-developer` / ... | 系统内置 + 用户自建 + 应用市场下载 | `kind: agent` |

**存储位置**：用户级全局目录（不放项目内）

```text
%APPDATA%/Madorin/agents/        # Windows
~/.madorin/agents/               # macOS/Linux
  ├─ general-manager/
  │   ├─ manifest.yaml
  │   └─ prompt.md
  ├─ project-lead/
  ├─ novel-writer/
  └─ ...
```

**注册时机**：应用启动时扫描目录建索引；`FileSystemWatcher` 监听运行时变更，触发工具上下文版本号递增（已解决 [智能体创建时机与工具上下文刷新问题讨论.md](../智能体创建时机与工具上下文刷新问题讨论.md)）。

**缺失 role 的处理**（A 在 finalize_plan 前校验）：

```text
A 整理出 plan 草稿
A 校验每个 step.role 是否在已注册 Agent 列表里
  ├─ 全部命中 → finalize_plan，启动 B
  └─ 任何一个缺失 → 中断，告知用户
       "当前任务需要专员 image-processor，但系统中没有。
        请你手动创建该智能体，或从应用市场下载，
        完成后告诉我继续。"
```

**不回退、不降级、不自动生成**——系统中没有合适的 Agent 直接停下来让用户处理。理由：

- 自动用通用助手兜底 → 效果不可预期，用户也不知道是降级方案
- 运行时自动生成 Agent → 提示词质量、能力边界、安全审计都不可控
- 中断让用户决策 → 行为可预测，用户透明

详细的文件 schema、迁移策略、UI 改造点见独立文档 [执行计划(Agent数据文件化迁移).md](执行计划(Agent数据文件化迁移).md)。

## 三、两份共享数据

整个体系只有两份共享数据，三层角色都看同一份。

### 3.1 plan：要做什么

任务的步骤列表与状态。存为 task 工作区下的 `plan.yaml`（或类似结构化文件）。

最小字段：

```yaml
- id: ch-01
  title: 第一章 起源
  role: novel-writer        # 派给哪类专员
  status: pending           # pending / running / done / failed
  summary: null             # 完成后由 C 返回的摘要文本
  is_milestone: false       # 是否完成时通知 A
```

**只有 A 写**（通过 `finalize_plan` / `update_plan` 工具）。**B 只调用 `update_plan_status`** 更新某个 step 的 status 和 summary，不能新增/删除 step。**C 完全不碰 plan**。

> 渐进式展开（[19 文档](../工作模式方案策划/19-渐进式计划与动态专家问题记录.md)）由 B 在执行到 expandable step 时调 `expand_plan` 触发，写入子步骤。这是 plan 的扩展玩法，本方案 §九 阶段 3 落地。

### 3.2 environment：在哪做、按什么规格

任务的环境变量与路径约定。存为 task 工作区下的 `environment.yaml`。

**字段不预定义**，A 跟用户对话时填什么就是什么。例子：

```yaml
# 写小说
working_dir: D:/Novels/超级科幻
chapters_dir: D:/Novels/超级科幻/chapters
style: 第一人称、悬疑科幻
target_words: 800000

# 剪视频
material_dir: E:/Videos/raw/2026-06
output_dir: E:/Videos/output
specs: 1080p / 30fps / h264

# 上传商品
images_dir: F:/Products/winter-2026/images
target_store: shopify://my-store
credential_ref: keychain://shopify/api-key   # 引用而非真值
```

**只有 A 写**（`set_environment` / `update_environment`）。**框架在 dispatch 时自动把 environment 拼进 C 的系统提示词**，C 一开干就知道路径、规格、凭证。

这解决了 C "先查路径再干活"浪费 token 和 "信息不全卡住"两个问题。

### 3.3 plan 与 environment 的区别

| 维度 | plan | environment |
|---|------|------|
| 内容 | 步骤、状态、摘要 | 路径、规格、凭证引用 |
| 谁更新频繁 | B（每完成一步更新 status） | 几乎不变（任务期间稳定） |
| 用途 | B 决定调度顺序 | C 知道在哪干、怎么干 |
| 注入对象 | B 每轮 read_plan 主动读 | dispatch 时框架自动注入 C |

## 四、一个协议：C 的 summary

C 完成步骤后，返回**一段自由格式自然语言文本**，里面自己说清两件事：

1. 做了什么
2. 产出在哪里能找到

例子：

- 完成第三章撰写，1.2 万字。文件位于 D:/Novels/超级科幻/chapters/03.md。
- 修复了登录卡顿问题。改动文件 Src/Foo.cs、Src/Bar.cs。已提交，commit a1b2c3d。
- 商品「冬季外套」已上架。Shopify 商品 ID prod_xxx，可在 https://... 查看。

**就这。** 没有 schema、没有 kind 分类、没有 output_refs。

### 为什么这样够用

- **B 看 summary 就够调度**——它只需要知道"这一步完成了"
- **A 想看细节自己取**——A 本来就有读文件、跑 git、调浏览器/MCP 的通用工具，按 summary 里的自然语言指针自己查就行
- **用户问起也直接转给用户**——summary 本身就是人类可读的

### 不需要新增什么

- 不需要 read_artifact 工具
- 不需要产出形态分类
- 不需要 output_refs 结构化引用
- 不需要"危险产出"标记——危险操作走现有 HITL 工具授权

## 五、典型流程

### 5.1 任务发起

```text
User → A："写一部 80 万字的科幻小说"
A 与 User 多轮对话：澄清主题、风格、卷数、存放位置
A 调 set_environment(...)        ← 写 environment.yaml
A 调 finalize_plan(...)          ← 写 plan.yaml + 启动 B
A → User："计划已交付项目组长执行，预计 X 小时完成"
```

### 5.2 B 推进循环（核心）

B 是 `ProjectLeadService`（C# 类），不挂 AF Workflow（依据 D1）。主循环纯代码：

```text
[B 启动后进入 while 循环，每轮只做一件事]

read_plan(taskId)
  ├─ 找到下一个 pending step
  │    → 选 role（step.role 或 LLM 决策点 1）
  │    → dispatch C：AIAgent.RunStreamingAsync(input) 拿到 summary
  │    → update_plan_status(step.id, "done", summary)
  │    → Heartbeat()
  │    → 若 step.is_milestone → 写 WorkTaskEvents + EventBus.Publish
  │    → 进入下一轮
  ├─ 没有 pending 了 → 写 Completion 事件 → OrchestratorState=done → 退出
  └─ dispatch 异常 → LLM 决策点 2 分类 → Retry / Escalate / Skip
```

B 不会"自己输出文本结束"——它根本不调模型生成回复（只用模型做 2 个语义决策点），不会触发 `WorkflowOutputEvent`。流程中断在 B 这层从架构上消除。

### 5.3 用户中途打断

```text
User → A："等等，第三卷改成悲剧结局"
A 判断意图：
  ├─ 闲聊 / 询问进度 → A 直接回答（必要时 read_plan 看实时状态）
  ├─ 计划微调（改未完成 step）→ A 调 update_plan(...)
  │                              B 下一轮 read_plan 时自然读到新版
  └─ 重大变更 → A 调 pause_orchestrator → 与用户深入讨论
                → finalize_plan(new_plan) → resume_orchestrator
```

**关键点**：用户中断**不直接打到 B**。B 不知道用户存在，它只看 plan。A 把用户意图翻译成对 plan 的修改，B 自然适应。

> 用户改的是已完成的 step 怎么办？放到 §十.Q4 讨论。MVP 先只允许改未完成的。

### 5.4 任务完成

```text
B 走到 plan 末尾 → notify_gm("ALL_DONE")
A 收到通知 → 可选调 read_plan / 读 artifact 做一份总结
A → User："任务已完成。第一卷在 ..., 第二卷在 ..."
```

A 是否需要做最终汇报由 A 自己判断（提示词引导）。

## 六、上下文如何各自独立

| 角色 | 上下文规模 | 内容构成 | 与任务规模的关系 |
|------|----------|---------|----------------|
| A | 与用户对话长度成正比 | 用户对话 + plan 摘要 + 阶段汇报 | **解耦**（不随 C 的产出膨胀） |
| B | **几乎为零**（不是 Agent，无对话历史） | plan.yaml 文件 + 当前 step 上下文 | **完全解耦** |
| C | 单步执行的局部上下文 | environment + step.input + 必要时主动读的 artifact | 短，跑完即销毁 |

> B 不挂 AF Workflow（D1）——它没有"对话历史"概念，"上下文"就是 plan.yaml 文件本身。这进一步压实了次问题（上下文爆炸）的解决。

[20 文档](../工作模式方案策划/20-工作模式上下文压缩设计.md) 描述的"按 TaskId 压缩"改为**"按 Run 压缩"**——A、B、C 各自的 Run 独立压缩。这是个简单的扩展，不是新机制。

> 上下文爆炸问题就此自然解决。这是这次重构的"副产品"。

## 七、为什么这能解决两个核心问题

### 主问题：流程中断

原架构下中断的根因是"调度智能体在语义边界输出汇报性纯文本"，AF 自动触发 `WorkflowOutputEvent`，循环结束。新架构下：

- **B 不是 AF Agent，根本不进 AF Workflow**（D1）——它就是个 C# 服务类，没有"输出文本就结束"这件事
- B 的主循环 `while` 由代码控制，不依赖模型判断"该不该继续"
- B 用模型只做 2 件事：选 role、分类异常。这两件事都返回结构化结果，不存在"模型输出汇报性文本导致循环退出"的可能
- B 崩溃由看门狗（§九 阶段 4）发现 `OrchestratorHeartbeatAt < now-N分钟` 自动重启
- A 输出汇报性文本是**合法的**——它在跟用户说话，本来就应该这样

简言之：**用代码层面的确定性换 AI 智能体的灵活性**，B 这层从架构上不可能"自己停下"。

### 次问题：上下文爆炸

- **A 的上下文**：用户对话 + plan 摘要 + 阶段汇报，规模与对话长度成正比
- **B 没有上下文**：状态就是 plan.yaml 文件本身
- **C 的上下文**：单步执行的局部上下文，跑完即销毁

任务规模再大，三层上下文都不爆。

## 九、分阶段实施

| 阶段 | 内容 | 解决什么 |
|------|------|---------|
| **0. Agent 体系文件化**（前置） | Agent 数据从数据库迁移到文件；统一智能体注册体系；A/B/C 都用文件版 Agent；缺失 role 时中断让用户处理 | 三层架构的注册基础；详见独立文档 [执行计划(Agent数据文件化迁移).md](执行计划(Agent数据文件化迁移).md) |
| **1. 架构骨架** | 拆分提示词；A 是 AF Agent + Workflow，B 是 `ProjectLeadService`（C# 类，不挂 Workflow），C 单 Agent 模式；新增 plan.yaml/environment.yaml；A 工具（finalize_plan/set_environment/pause/resume/cancel/update_plan）；B 实现主循环 + 2 个 LLM 决策点；旧任务直接清空（D6） | 三层架构跑得起来；流程中断在 B 这层从根上消除 |
| **2. 上下文隔离** | `WorkTaskContextService` 改为按 Run 压缩（仅 A、C）；environment 自动注入 C 的 system 消息 | 上下文爆炸 |
| **3. 渐进式计划** | plan schema 加 expandable/expander；B 增加 expand_plan/collapse_plan 调度逻辑；planner 类专员 | 大型计划上下文进一步压缩；按需展开 |
| **4. 可靠性兜底** | 看门狗服务扫 `OrchestratorState=running AND OrchestratorHeartbeatAt < now-N分钟` 自动重启 B；WorkTaskEvents 表 + EventBus 让 UI 实时看到进度 | 流程中断的最后一道防线 |

> 阶段 5（迁移与清理）依据 D6 决策已不再需要——旧任务直接清空，老代码本次直接删除。

**阶段 0 是阶段 1 的硬前置**——三层架构的"按 role 名查 Agent"必须基于文件版 Agent 体系。阶段 0 影响范围超出工作模式（聊天模式、会议模式都会涉及），独立文档管理。

每个阶段独立可上线。**MVP 是阶段 0 + 阶段 1 + 阶段 2**，能解决主问题 + 次问题各 80%；阶段 3+4 是把另外 20% 也吃掉。

## 十、已拍板决策

§二–§九 的所有内容均依据本节决策展开。

### D1：B 是混合实现，不挂 AF Workflow

**B 是普通的 .NET 服务类 `ProjectLeadService`**，不是 AF Agent，不进 AF Workflow。

主循环纯代码，仅 2 个 LLM 决策点（用小模型 haiku 级即可）：

- **决策点 1**：plan 中 step.role 缺失或写错时，扫已注册 Agent 列表选最合适的
- **决策点 2**：dispatch 异常时分类（重试 / 升级到 A / 跳过）

```csharp
public sealed class ProjectLeadService
{
    public async Task RunAsync(string taskId, CancellationToken ct)
    {
        UpdateState(taskId, "running");
        while (!ct.IsCancellationRequested)
        {
            var plan = await _planFile.LoadAsync(taskId);
            var pending = plan.FindNextPending();
            if (pending is null)
            {
                await _eventBus.PublishAsync(new TaskCompletedEvent(taskId));
                UpdateState(taskId, "done");
                break;
            }

            var role = pending.Role
                ?? await _decisionPoint.SelectRoleAsync(pending, _agentRegistry);

            try
            {
                Heartbeat(taskId);
                var summary = await _dispatcher.DispatchAsync(role, pending.Input);
                pending.MarkDone(summary);
                await _planFile.SaveAsync(taskId, plan);
                if (pending.IsMilestone)
                    await _eventBus.PublishAsync(new MilestoneEvent(taskId, summary));
            }
            catch (Exception ex)
            {
                var decision = await _decisionPoint.ClassifyFailureAsync(pending, ex);
                ApplyFailureDecision(pending, decision, ex);
                await _planFile.SaveAsync(taskId, plan);
            }
        }
    }
}
```

**关键效果**：

- B 不会"自己输出纯文本结束"——它根本不调用模型生成回复，只用模型做判断
- 主循环 `while` 由代码控制，不是 AF Workflow 的事件循环
- B 崩溃恢复 = 重启 ProjectLeadService 读 plan，发现 status=running 但无活跃子任务的 step 标记为可重试

**对 AF 框架的取舍**（与本决策配套）：

| AF 层 | 用法 |
|---|---|
| **A 层（总经理）** | ✅ 完整使用 AF Agent + Workflow（A 是聊天型 Agent，AF 这套抽象正合适）|
| **B 层（项目组长）** | ❌ 不使用 Workflow / 不作为 Agent；仅使用 ChatClient 抽象做 2 个决策点 |
| **C 层（专员）** | ✅ 单 Agent 模式：`AIAgent.RunStreamingAsync(input)` 直接拿结果；❌ 不挂 Workflow、不用 Magentic/GroupChat |

> AF 工作流编排（Workflow + Magentic + GroupChat）这一层在本架构下不使用——它假设的"多 Agent 平等对话"模式与公司管理体系（清晰层级 + 调度）不匹配。AF 底层（AIAgent + ChatClient + 工具适配）继续保留。

### D2：plan.yaml 的最小 schema

```yaml
version: 1
task_id: <uuid>
created_at: 2026-06-07T10:00:00Z
status: planning             # planning / running / paused / done / failed
steps:
  - id: ch-01
    title: 第一章 起源
    role: novel-writer
    kind: leaf               # 预留扩展位：leaf（默认，叶子步骤）/ sub_task（未来任务树，触发 fork 子 WorkTask）
    input:
      chapter_outline: ...
      target_words: 8000
    status: pending          # pending / running / done / failed
    summary: null
    is_milestone: false
    attempts: 0
    last_error: null
    created_at: 2026-06-07T10:00:00Z
    updated_at: 2026-06-07T10:00:00Z
```

不加 `depends_on`（用顺序表达依赖）、不加 `retryable`（HITL 已覆盖危险操作）、不加 `expandable/expander`（阶段 3 渐进式计划再加）。

> **`kind` 字段是预留位**：当前代码（`WorkTaskPlanStepFile` / `WorkTaskPlanFileYaml`）**不解析此字段**，B 也不消费。仅在 schema 文档登记，写在 plan.yaml 里也无副作用（yaml parser 容忍 unknown 字段）。未来 ERP 级"多模块并行项目"出现时，再在代码层加 `Kind` 属性 + B 的"`kind=sub_task` 时 fork 子 WorkTask"逻辑——届时复用现有 `WorkTasks.ParentTaskId` 字段即可（数据库 schema 已就位）。详见 [../../未来版本策划/工作模式三层架构重构/README.md](../../未来版本策划/工作模式三层架构重构/README.md) "已预留扩展点"。

### D3：notify_gm 走 EventBus + WorkTaskEvents 表

B 触发里程碑/异常时：

1. **持久化**：写入 `WorkTaskEvents` 表（taskId / kind / message / created_at / read_at）
2. **发布事件**：通过 EventBus 推送 `WorkTaskEventCreated` 事件
3. **UI 实时订阅**：进度面板订阅事件，立即刷新里程碑/异常徽标
4. **A 主动消费**：A 下次被用户激活时，代码扫描 unread 事件，合并成一条 system 消息注入 A 的上下文（多个里程碑合并成一句汇报，避免污染）

事件类型：

```csharp
public enum WorkTaskEventKind
{
    Milestone,    // step.is_milestone=true 完成
    Error,        // dispatch 异常或 escalate
    Completion    // 整个 plan 完成
}
```

UI 通道：复用现有 `Publisher.Publish` + 订阅事件。MVP 不做"系统级 notification"（用户不在线时主动弹通知），等真需要时再做。

### D4：用户改已完成 step → MVP 拒绝 + 协商新增

A 检测到用户想改已完成 step 时，按以下话术回应：

> 第三卷已完成。我可以新增一个步骤"重新撰写第三卷为悲剧结局"，原版保留作为参考。这样可以吗？

用户同意 → A 调 `update_plan` 新增 step（不动旧 step）。

不实现：
- 删 artifact + 重置 step + 重做（涉及级联回滚和副作用，复杂）
- 自动 superseded 标记（下个版本可升级）
