# 对话记录文件化存储方案

> 状态：方案设计（未涉及代码修改）
> 日期：2026-07-15
> 目标读者：本项目开发者

## 1. 背景与目标

当前专家模式、工作模式、会议模式的对话记录（原始内容 + 压缩内容 + 文档/代码修改内容）全部持久化到单一 SQLite 数据库 `madorin.db`。长期使用后暴露两个真实痛点：

- **抗崩溃差 / 爆炸半径大**：所有模式、所有工作区的数据集中在一个库文件里，库损坏会导致整个历史全部不可用。
- **单点体积膨胀**：库文件随对话只增不减，越来越大，也让"加载即读大字段"的内存压力上升。

明确的**非目标**：

- 不是为了节省磁盘空间（JSON 文件不会比数据库更省，反而略大）。
- 不追求历史数据的富查询能力。长期历史检索已由**记忆插件**承担——它另外备份了全部对话并做了缩略/提取，强制搜索是低频操作。

因此本方案的核心诉求是：**降低数据库单点风险 + 控制库体积 + 保持上层几乎零改动**。

## 2. 核心设计原则

1. **索引在库、内容在文件**。数据库只保留会话/任务/会议的**元数据与简介**（用于列表、排序、恢复定位）；真正的大块内容（消息正文、结构化内容、压缩上下文）落到工作区 `.cortana` 目录下的文件。需要读内容时，按索引定位文件再读取。
2. **不迁移旧数据**。当前用户量极少，旧库数据由用户自行删除。新逻辑从启用之日起直接写文件，**不做存量迁移，不做双读兼容**，实现大幅简化。
3. **上层接口不动，只换下层存储后端**。VM 层、AI 层调用的服务接口（如 `ChatMessageService.GetBySessionId`、`ChatSessionService` 系列）签名与语义保持不变，改造集中在这些服务的内部实现。
4. **只做内容分流，不改运行时状态存储**。工作/会议模式的运行时活状态（`RunId`、`ManagerRunId`、`OrchestratorState`、`PendingRequest*`、`IsActive` 等）继续留在数据库，事务安全与跨工作区启动恢复能力完全保留。文件化只针对"对话内容"这类以追加为主的数据。

## 3. 存储布局

### 3.1 数据库侧（保留）

各表结构维持现状，但大文本字段的角色转变为"可空的冗余/兜底"，正常读取路径不再依赖它们：

| 表 | 保留字段（索引/元数据） | 内容外移到文件的字段 |
|----|----------------------|-------------------|
| ChatSessions | Id、Categorize、Title、Summary、AgentName、SourceTaskId、IsArchived、IsPinned、LastActiveTimestamp、TotalTokenCount、CompactedAtCount 等 | RawDiscription、CompactedContext |
| ChatMessages | Id、SessionId、Role、AuthorName、TokenCount、ModelName、CreatedAt、AgentId、AgentName（作为索引/回放骨架） | Content、ContentsJson |
| CompactionSegments | SessionId、SegmentIndex、范围、ModelName | Summary |
| MeetingSessions | 全部元数据 + 运行时状态 | FinalSummaryMd |
| MeetingMessages | MeetingId、Sequence、Speaker*、MessageRole、时间 | ContentMd、ThinkingMd、ToolCallsJson、AttachmentsJson |
| WorkTaskContextMessages | TaskId、RunId、Sequence、Role、时间 | Content |
| WorkTaskContextSegments | TaskId、RunId、范围、ModelName | Summary |

> 说明：数据库里"每条消息一行元数据"仍然保留，是为了保住按会话回放的顺序骨架和轻量列表。真正省下来、也是膨胀主因的大文本移到文件。若希望库更瘦，可进一步只在文件侧保留逐条消息、库里仅存会话级摘要——见 §8 可选深化。

### 3.2 文件侧（`.cortana`）

```
<Workspace>/.cortana/
  └── conversations/
        ├── expert/
        │     ├── {sessionId}.jsonl       # 对话正文，一轮往复一行
        │     └── {sessionId}.compact.json # 压缩上下文，同名不同扩展名
        ├── meeting/
        │     ├── {meetingId}.jsonl
        │     └── {meetingId}.compact.json
        └── work/
              ├── {taskId}.{runId}.jsonl
              └── {taskId}.{runId}.compact.json
```

- **文件名即索引**：与数据库主键一致（`sessionId` / `meetingId` / `taskId`），无需在库里额外存路径列，路径由 ID + 模式约定推导。
- **压缩记录同 ID、扩展名区分**：`.jsonl` 是给人看的往复正文，`.compact.json` 是给智能体看的压缩上下文，符合"压缩记录单独保存、ID 相同"的设想。

### 3.3 单文件格式

**头部（文件第一行，固定结构）**：

```json
{"type":"header","schema":1,"id":"<guid>","mode":"expert","title":"会话简要标题","createdAt":"2026-07-15T10:00:00+08:00","updatedAt":"2026-07-15T10:42:00+08:00","agentName":"..."}
```

**正文（后续每行一个对象，一轮往复为一行）**：

```json
{"seq":1,"role":"user","author":"我","content":"...","ts":"..."}
{"seq":2,"role":"assistant","author":"Cortana","content":"...","contents":[...],"tokens":123,"model":"...","ts":"..."}
```

采用 **JSONL（行分隔 JSON）**而非单个大 JSON 数组，原因：

- **追加即写**，新一轮对话只 append 一行，不需读回整文件再重写。
- **崩溃容错好**：进程在写一行中途被杀，最多末尾一行不完整；读取时跳过无法解析的末行即可，前面已落盘的内容不受影响。

## 4. 读写分离：Channel 队列 + 单写线程

用 .NET `System.Threading.Channels` 做读写分离，解决"写入不阻塞热路径 + 单点顺序落盘"两个问题。

### 4.1 拓扑

```
[对话产生侧] --写入(可含压缩/序列化)--> [Channel<WriteJob>] --单个后台消费线程--> [按 ID 追加写文件] --全部写完--> [更新数据库索引行]
```

- **生产者**：AI/会话层在生成一轮往复后，把"写任务"（目标文件 + 序列化后的行数据 + 关联的 DB 索引更新）投递到 Channel，立即返回，不阻塞对话流。可在投递前完成 JSON 序列化/压缩，把 CPU 开销从热路径挪到调用方线程或队列。
- **单消费者**：一个长期运行的后台任务从 Channel 读取，**串行**写文件。单写线程天然规避了同文件并发写的锁问题；`Channel` 的有界/无界配置可按需选择（建议无界或大容量有界 + 背压）。
- **顺序保证**：同一会话的多轮往复按投递顺序进入队列、按顺序落盘，`seq` 单调递增。

### 4.2 "写完再存库"的次序（关键）

消费线程处理一个写任务的顺序**固定为**：

1. 先把正文行 append 到 `.jsonl`（并 flush）。
2. 需要时更新 `.compact.json`（整块替换，用临时文件 + rename 原子替换）。
3. **文件确认落盘后**，再更新数据库里的索引行（`LastActiveTimestamp`、`TotalTokenCount`、`CompactedAtCount`、`updatedAt` 等）。

这样保证**数据库索引永远不指向尚未落盘的内容**。即便在第 1 步和第 3 步之间崩溃，最坏情况是"文件里多了一行、库里索引还没更新"——下次读取以文件为准即可自愈，不会出现"库说有、文件没有"的悬空引用。

### 4.3 原子性的实际含义

用户已明确：程序整体崩溃时丢失最新几条是可接受的，不为此过度设计。据此本方案的原子性目标收敛为两条，都很轻量：

- **不破坏已落盘的旧内容**：追加写（append）本身不动旧字节；整块替换的 `.compact.json` 用"写临时文件 → `File.Move` 覆盖"完成原子替换，避免写一半覆盖坏。
- **末行截断可识别**：读取 `.jsonl` 时逐行解析，遇到最后一行 JSON 不完整就丢弃该行。丢的就是崩溃瞬间那一条，符合预期。

> 注意：`Channel` 解决的是**并发与顺序**，不等于文件写入的原子性。真正的"不写坏旧数据"由 append + 临时文件 rename 这两个廉价手段保证。二者配合即可，无需引入 WAL/事务式复杂机制。

## 5. 工作目录切换时的加载流程

切换工作区后：

1. 查数据库索引，按 `LastActiveTimestamp` 倒序取该工作区（`Categorize` / 模式）最新的 **10~20 条**会话/任务/会议，填充专家、工作、会议三个列表。**此步只读库里的元数据+简介，不碰文件、不读大内容**，因此列表加载恒定轻量。
2. 用户点击某条记录时，才按 ID 定位对应 `.jsonl` 文件、逐行读取还原对话；需要压缩上下文时读同 ID 的 `.compact.json`。
3. 恢复在途会话/任务的运行时状态仍走数据库（`RunId` 等未外移），逻辑不变。

## 6. 改造范围（下层存储后端）

上层接口不变，改造集中在这些服务的内部实现，让它们从"读写 SQLite 大字段"改为"读写文件 + 读写库索引"：

- `ChatMessageService`（`GetBySessionId` 等）——正文读取改为读 `.jsonl`。
- `ChatHistoryDataProvider`（`StoreChatHistoryAsync` 等）——写入改为投递 Channel 写任务。
- `ChatSessionService`（`GetVisibleExpertSessions`、`ResumeSessionAsync`、`LoadOrCreateSessionAsync` 等）——列表走库索引、恢复时按需读文件。
- `CompactionSegmentService` / `MeetingCompactionService`——压缩内容读写 `.compact.json`。
- `MeetingSessionService` / `MeetingMessage` 存取——会议正文读写文件。
- 工作模式 `WorkTaskContextMessages` / `WorkTaskContextSegments` 的正文/摘要读写文件。

新增基础设施：

- `ConversationFileStore`：封装 `.jsonl` / `.compact.json` 的追加、整块替换、按 ID 读取、头部维护。
- `ConversationWriteQueue`：`Channel<WriteJob>` + 后台单消费线程，实现 §4 的写完再存库次序。
- 路径推导工具：接入 `AppPaths`，在 `.cortana/conversations/{mode}/` 下按 ID 生成路径。

复用现有：`EntityJsonContext` / `MeetingJsonContext` / `WorkModeJsonContext`（JSON source-gen，AOT 友好）；`WorkTaskFileService` 的文件写模式可作参考。

## 7. 分阶段落地（建议）

风险从低到高分模式推进，每阶段可独立验证、独立回退：

1. **阶段一：专家模式**。正文 → `.jsonl`，压缩上下文 → `.compact.json`。这是追加型、最简单、收益最直接的一块，用来验证 `ConversationFileStore` + `ConversationWriteQueue` 这套地基（含末行截断恢复、写完存库次序）。
2. **阶段二：会议模式**。多了 `ThinkingMd` / `ToolCallsJson` / `AttachmentsJson` 等字段与 `IsPartial` 半截消息，格式扩展但机制复用阶段一。
3. **阶段三：工作模式上下文消息**。文件名带 `RunId`，与现有 `plan.yaml` / `environment.yaml` 同目录体系协调。

## 8. 可选深化（视需要）

- **进一步瘦库**：库里逐条消息元数据也可只保留会话级摘要，逐条骨架完全交给文件。省库更多，但列表/回放要多依赖文件，权衡后再定。
- **文件侧保留策略**：文件同样只增不减，需配套归档/清理上限（如单工作区保留 N 个会话文件、或超期 gzip）。这与文件化正交，是"控制无限增长"的最终解，别遗漏。
- **索引自愈工具**：提供"扫描 `.cortana/conversations` 重建数据库索引"的命令，作为库损坏后的恢复手段——这正是本方案抗崩溃价值的兑现点。

## 9. 结论

- **可行性高**：方向与现有 `.cortana` + 按工作区 + source-gen JSON 基础设施契合；不迁移旧数据、上层接口不动，实现被大幅简化。
- **命中目标**：库瘦身、爆炸半径缩小（内容独立于库、可重建索引）、列表加载恒定轻量；富查询的缺失由记忆插件兜底，可接受。
- **投入产出合理**：靠 `Channel` 读写分离 + append/临时文件 rename 这套廉价机制满足原子性目标，不上重型事务；分模式推进，先做专家模式即可拿到主要收益并验证地基。
- **仍需独立对待**：文件侧的保留/归档策略是"无限增长"的最终解，必须配套，不能只做分流。
