## 1. 框架全景

当前 `Netor.Cortana.AI` 使用的核心 NuGet 包：

| 包名 | 版本 | 作用 |
|---|---|---|
| `Microsoft.Agents.AI` | 1.7.0 | MAF 核心：Agent 抽象、内置工具、运行时循环 |
| `Microsoft.Agents.AI.OpenAI` | 1.7.0 | MAF 的 OpenAI Provider 绑定 |
| `Microsoft.Agents.AI.Workflows` | 1.7.0 | MAF 内置 Workflow/多步骤编排 |
| `Microsoft.Extensions.AI` | 10.6.0 | MEAI：`IChatClient`、`ChatMessage`、`AIFunction` 等统一抽象 |
| `Microsoft.Extensions.AI.OpenAI` | 10.6.0 | MEAI 的 OpenAI `IChatClient` 实现 |
| `Netor.Anthropic` | 12.21.11 | 自有 Anthropic 客户端，未使用 MEAI 官方 Anthropic 包 |

两个框架层级关系：

```text
Microsoft.Agents.AI（MAF）
└── 依赖 Microsoft.Extensions.AI（MEAI）作为底层 IChatClient 抽象
    ├── Microsoft.Extensions.AI.OpenAI   → OpenAI IChatClient
    └── （Anthropic 由 Netor.Anthropic 自行适配 IChatClient）
```

**MEAI 的 `IChatClient`** 是跨 Provider 的统一接口，MAF 的 `IAgent` 在内部通过 `IChatClient` 调用模型。这两层在独立 Runtime 的设计中各有用武之地。

> **关于 Experimental 警告**：`MAAI001`（MAF 核心）、`MAAIW001`（MAF Workflows）、`MEAI001`（MEAI）目前均处于 Experimental 阶段。当前系统通过 `<NoWarn>` 屏蔽。独立 Runtime 同样需要接受这一现状，并在框架正式 GA 后更新 API。

## 2. Provider 抽象边界：`IRuntimeProviderAdapter`

### 2.1 边界接口

`IChatClient`（MEAI）不作为 Runtime 的公开 Provider 接口——它是 MEAI 实验性 API，Runtime 的公开契约不应绑定到外部框架的版本节奏。正确的边界是自有的 `IRuntimeProviderAdapter`：

```csharp
// Netor.AI.Runtime.Providers.Abstractions 中定义，不引用 MEAI
public interface IRuntimeProviderAdapter
{
    string ProviderId { get; }
    ProviderCapabilities Capabilities { get; }
    Task<ProviderModel[]> GetModelsAsync(CancellationToken ct);
    IAsyncEnumerable<RuntimeProviderEvent> CompleteStreamingAsync(
        RuntimeProviderRequest request, CancellationToken ct);
}
```

`IChatClient` 存在于 Adapter 实现层的内部，不暴露到 `Providers.Abstractions` 或 `Services`。

### 2.2 `IChatClient` 的正确生命周期

`IChatClient` 实例**由 DI 容器和 HttpClientFactory 管理**，不在每个 `AgentInvocation` 上创建和销毁。`AgentInvocation` 隔离的是 Agent 对象、`InvocationSnapshot` 和执行上下文，不是底层 HTTP 连接池。

```csharp
// 注册（Server/DI 层）
services.AddHttpClient("openai-provider");
services.AddSingleton<IRuntimeProviderAdapter, OpenAIProviderAdapter>();
// OpenAIProviderAdapter 内部持有 IChatClient（单例或 scoped per Provider Profile）

// AgentInvocation 执行时：通过 DI 获取 IRuntimeProviderAdapter，不 new IChatClient
public class AgentInvocationExecutor(IRuntimeProviderAdapter provider, ...)
{
    // provider 由 DI 注入，生命周期由容器管理
}
```

### 2.3 MEAI 类型与 Runtime 协议的映射

`IRuntimeProviderAdapter` 内部可以使用 MEAI 类型作为实现细节：

| MEAI 类型 | Runtime 协议概念 | 说明 |
|---|---|---|
| `ChatMessage` | CanonicalHistory 中的消息（内部转换） | Adapter 负责规范化历史 → MEAI → Provider 请求 |
| `StreamingChatCompletionUpdate` | `output.delta` 事件（内部拆解） | Adapter 内部处理，外部只看到 `RuntimeProviderEvent` |
| `AIFunction` | 宿主工具目录中的工具定义（内部包装） | Adapter 内部用 `AIFunctionFactory` 包装 |
| `UsageDetails` | `UsageUpdated` 事件 | Adapter 从 MEAI 类型提取并转换为 `RuntimeUsage` |

### 2.4 中间件建议（Adapter 内部）

Adapter 内部包装 `IChatClient` 的中间件，对外不可见：

```csharp
// 这段代码在 OpenAIProviderAdapter 的内部构造中，Services 层看不到
IChatClient internalClient = new OpenAIChatClient(...)
    .AsBuilder()
    .UseLogging(logger)
    .UseOpenTelemetry(tracing)
    .UseRetry(retryPolicy)
    .Build();
```

**限制**：中间件链不在进程间传递；对外通过 `IRuntimeProviderAdapter.CompleteStreamingAsync` 暴露归一化事件流。

## 3. MAF `IAgent` 与 AgentInvocation 的关系

### 3.1 MAF `IAgent` 的职责

MAF 的 `IAgent`（`Microsoft.Agents.AI.IAgent`）封装了"给定工具集和系统提示，执行一轮完整的 Reason-Act 循环"的能力，内部处理工具调用续调（多次 `IChatClient` 请求直到完成原因不是 `tool_use`）。

这与 `03 §1` 定义的 `AgentInvocation` 层级完全对应：

```text
AgentInvocation
  └── 在内部映射为 IAgent.InvokeAsync(...)
       ├── 第一次 IChatClient 请求（ProviderRequest #1）
       ├── 工具调用处理
       ├── 第二次 IChatClient 请求（ProviderRequest #2）
       └── 返回最终结果
```

### 3.2 当前系统的构建方式

`AIAgentFactory.Build`（`Src/Netor.Cortana.AI/Agents/AIAgentFactory.cs`）使用以下步骤构建每轮的 `IAgent`：

1. 从 `AgentRef.promptTemplate` 解析系统提示和用户指令
2. 通过当前 Provider 的 `IChatClient` 创建 `AIAgent`
3. 把宿主注册的 `AIFunction` 列表注入到 `ChatOptions.Tools`
4. 返回可执行的 `IAgent` 实例

独立 Runtime 应保留这一构建模式，但把"从宿主协议获取 AgentRef 和工具目录"作为构建的输入源，而不是从内部 DI 容器直接获取。

### 3.3 独立 Runtime 中 `IAgent` 的生命周期

```text
ExistingSessionRunRequest 到达
  -> AgentInvocationManager 从 NextTurnSelection 解析 AgentRef
  -> AIAgentFactory.Build(agentRef, toolCatalog, chatHistory)
  -> 产生 IAgent 实例（绑定到本次 Invocation）
  -> IAgent.InvokeStreamingAsync(...)
     -> 产生 invocation.started（携带 InvocationSnapshot）
     -> 每个 StreamingChatCompletionUpdate -> output.delta 事件
     -> 工具调用 -> tool.permission.request / tool.call.request
     -> 产生 invocation.completed
  -> IAgent 实例随 Invocation 结束销毁（不跨 Invocation 复用）
```

**关键约束**：`IAgent` 实例按 Invocation 创建，Invocation 结束后销毁（不跨 Invocation 或 Session 复用），以防止 Agent 内部状态泄漏。`IChatClient` 由 DI/HttpClientFactory 管理，生命周期独立于 Invocation，不随 IAgent 一同释放——`IAgent` 持有的是对 `IRuntimeProviderAdapter` 的引用，而非直接持有 `IChatClient`。

## 4. MAF Workflows 与工作模式

### 4.1 `Microsoft.Agents.AI.Workflows` 的能力

MAF Workflows 提供：
- 声明式多步骤编排（类似有向图）
- 步骤间状态传递
- 并行步骤执行
- 检查点和恢复（实验性）

这与 `03 §9.5`（`work_steps` 表）的工作模式存储设计有交集。

### 4.2 V1 使用策略

**V1 结论：仅参考 MAF Workflows 的编排模式，不直接依赖其运行时**。原因：

1. MAF Workflows 目前是 Experimental（`MAAIW001`），API 稳定性不够
2. `02-架构修订` 要求工作模式步骤幂等记录和恢复由 `work_steps` / `work_tool_intents` 表负责——这需要 Runtime 完全控制步骤持久化逻辑，而 MAF Workflows 的内部持久化机制无法直接对接 `.madorin/state.db`
3. 工具权限握手（`tool.permission.request`）是 Runtime 协议层的职责，MAF Workflows 不知道跨进程权限协议

**V2 决策点**：当 MAF Workflows 正式 GA 且 API 稳定后，评估是否将工作模式的编排执行迁移到 MAF Workflows，Runtime 只负责持久化和协议桥接。

### 4.3 参考借鉴点

尽管不直接依赖，工作模式的设计可以参考 MAF Workflows 的以下概念：

| MAF Workflows 概念 | Runtime 工作模式对应 |
|---|---|
| WorkflowStep | `work_steps` 中的一行 |
| StepContext（前序步骤输出） | `work_steps.parent_step_id` + 消息历史 |
| WorkflowPolicy（步骤失败策略） | `WorkOptions.workflowPolicy`（见 `03 §8`） |
| 并行步骤 | `work_steps.depth` 相同的步骤可并发，由总经理调度 |

## 5. 会议模式与 MAF 的关系

会议模式没有直接对应的 MAF 抽象（MAF 主要面向单 Agent 和 Workflow）。会议轮次调度、Speaker Selector、主持人逻辑均需自行实现，以 `IAgent` 为执行单元、`IChatClient` 为底层调用。

参考当前系统：
- `MeetingAgentBuilder.BuildParticipantAgentsAsync`（`Src/Netor.Cortana.AI/MeetingMode/MeetingAgentBuilder.cs`）为每位参与者构建独立 `IAgent`
- `IAgent` 实例绑定参与者的提示词和 Provider 配置
- 会议轮次切换时不销毁 Session，只切换下一轮的 `IAgent`

独立 Runtime 的会议模式沿用这一模式，但构建过程通过协议从宿主获取 `MeetingOptions.participants[]`，而不是直接读内部配置。

## 6. Anthropic Provider 适配

当前系统使用 `Netor.Anthropic`（v12.21.11）而非 Microsoft 官方的 MEAI Anthropic 包。独立 Runtime 的 Anthropic Adapter 应：

1. 继续使用 `Netor.Anthropic` 作为底层 HTTP 客户端（已适配 Streaming、工具调用、thinking 块）
2. 在 Adapter 层将 `Netor.Anthropic` 响应包装为标准 `IChatClient` 接口（如果尚未实现，需要补充适配器），使 MAF 的 `IAgent` 可以透明使用
3. `thinking` 块（Claude 的推理过程）映射到 MEAI 的 `ChatMessage` 时，作为自定义扩展内容保留，并在事件层转换为 `reasoning.delta` 事件

## 7. 版本管理与 Experimental API 策略

### 7.1 当前风险

MAF（`Microsoft.Agents.AI` 1.7.0）和 MEAI（`Microsoft.Extensions.AI` 10.6.0）均标记为 Experimental，存在跨版本破坏性变更风险。

### 7.2 缓解策略

- Provider Adapter SDK（`Netor.AI.Runtime.Providers.Abstractions`）定义自有的 Provider 接口，`IChatClient` 仅作为 Adapter 的实现细节，不暴露在公共契约中
- `Netor.AI.Runtime.Core` 和 `Netor.AI.Runtime.Contracts` **不直接引用** MAF / MEAI 包，只有 `Services` 层及以下可以引用
- 依赖关系：

```text
Contracts          不引用 MAF / MEAI
Core               不引用 MAF / MEAI
Services           引用 MEAI（IChatClient、ChatMessage）
Server             引用 MAF（IAgent、AIAgentFactory）
Providers.*        引用 MEAI + 各 Provider SDK
```

- 每个 MAF / MEAI 版本升级前，在独立分支运行协议一致性测试（`Netor.AI.Runtime.Protocol.Tests`），确认事件输出不变

### 7.3 `NoWarn` 设置

独立 Runtime 解决方案的根 `Directory.Build.props` 应加入：

```xml
<PropertyGroup>
  <NoWarn>$(NoWarn);MAAI001;MAAIW001;MEAI001</NoWarn>
</PropertyGroup>
```

并在注释中说明原因和计划去除时机（等待 GA 版本发布）。

## 8. 与当前 `Netor.Cortana.AI` 的代码复用边界

| 能复用（可参考，需移植） | 不能复用（协议耦合过深） |
|---|---|
| `AIAgentFactory.Build` 的构建逻辑 | `AiChatHostedService`（绑定 Madorin 内部事件总线） |
| `MeetingAgentBuilder.BuildParticipantAgentsAsync` 的参与者构建模式 | `ChatSessionService`（直接依赖内部 Session 对象） |
| `GeneralManagerAgentBuilder.BuildAsync` 的总经理工具隔离逻辑 | `ChatAgentResolver`（依赖内部 ChangeProvider/ChangeModel 接口） |
| Provider 驱动层（Drivers/）对 `IChatClient` 的包装 | 任何引用 `Netor.Cortana.Entitys` 业务实体的代码 |
| `prompts/` 目录中的提示词模板 | 内部 DI 注册和启动流程 |

移植时不应携带对 `Netor.Cortana.Entitys`、`Netor.EventHub` 或任何 Madorin 内部程序集的引用。
