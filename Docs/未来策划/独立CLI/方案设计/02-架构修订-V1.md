## 1. 【阻断】引入 AgentInvocation 层级

### 问题

`README §7.1` 把 Run 与 Turn 混用，`01 §5.4` 只为每个 Run 定义一个 `TurnExecutionSnapshot`。会议模式和工作模式在同一 Run 内切换多个 Agent，单一快照无法描述这种结构。

### 决策：四级层级

```text
Session
└── Run（一次流式任务的生命周期边界）
    └── AgentInvocation（单个 Agent 一次连续调用的边界）
        └── ProviderRequest（向模型 API 发出的单次 HTTP 请求）
```

**Session**：用户可见的连续对话，`sessionId` 跨 Run 不变。  
**Run**：宿主调度的一次任务，有唯一 `runId`、取消源、状态机和事件序列。一个 Run 包含一到多个 AgentInvocation。  
**AgentInvocation**：单个 Agent 从收到输入到产出完整输出的完整过程，有唯一 `invocationId`、对应 `agentId` 和不可变的 `InvocationSnapshot`。会议模式每位参与者/主持人一轮 = 一个 Invocation；工作模式每个子智能体调度 = 一个 Invocation；专家模式每个用户 Turn = 一个 Invocation。  
**ProviderRequest**：Invocation 内部因工具调用续调而产生的每次 HTTP 请求，有唯一 `requestId`，仅用于 Provider 侧追踪，不暴露在公共协议中。

### InvocationSnapshot

```text
invocationId
runId
sessionId
agentId
parentInvocationId         子智能体调用时指向父 Invocation
invocationIndex            在当前 Run 中的顺序编号（0-based）
mode
providerId
providerProfileId
modelId
promptTemplateId
promptTemplateVersion
resolvedPromptHash
generationOptions
toolCatalogVersion
contentPolicyVersion
contextProjectionVersion   见 §7，记录本次投影的裁剪版本号
startedAt
```

`TurnExecutionResolved` 事件改为 `invocation.started`，携带 `InvocationSnapshot`。每个 Invocation 结束时产生 `invocation.completed` 或 `invocation.failed`。

### 事件修订

| 旧事件 | 新事件 | 说明 |
|---|---|---|
| `turn.execution.resolved` | `invocation.started` | 携带 InvocationSnapshot |
| `meeting.participant.started` | `invocation.started`（mode=Meeting） | 统一入口 |
| `meeting.participant.completed` | `invocation.completed` | |
| `subagent.job.started` | `invocation.started`（parentInvocationId 非空） | |
| `subagent.job.completed` | `invocation.completed` | |

Run 级事件（`run.accepted`、`run.completed` 等）不变。

## 2. 【阻断】事件游标模型：全局单调序号

### 问题

`README §6.5` 规定按 `runId + sequence` 排序，但 `01 §5.1` 的 `InitializeRequest` 只有单个 `eventReplayCursor`。多 Run 并发时，一个游标无法精确表达"哪些 Run 的哪些事件已确认"。Delta 丢弃后的序号空洞规则也未定义。

### 决策：全局单调事件序号（GSN）

Runtime 为每个实例维护一个进程内单调递增的全局序号 `gsn`（Global Sequence Number）。事件通道上的每个帧携带 `gsn`，不同 Run 的事件按 `gsn` 顺序发出。

```text
事件帧结构
  gsn              全局单调序号，连续，无间隙（Delta 丢弃用专用事件占位）
  runId            所属 Run
  runSequence      Run 内部的有序编号（0-based，仅用于 Run 内排序）
  messageType
  payload
```

**游标确认**：宿主发送 `events.acknowledge(lastConfirmedGsn)`。Runtime 释放 `gsn ≤ lastConfirmedGsn` 的缓冲，并记录该游标到 `state.db`。

**重连重放**：宿主在 `InitializeRequest` 中携带 `eventReplayCursor: lastConfirmedGsn`，Runtime 从 `gsn = lastConfirmedGsn + 1` 开始重放。

**Delta 丢弃后的空洞处理**：不产生序号空洞。Delta 丢弃时，Runtime 发出一个占位事件：

```text
delta.dropped
  gsn              正常分配（不跳号）
  runId
  runSequence      被丢弃帧的 runSequence 范围 [from, to]
  droppedBytes
```

宿主在重放时收到 `delta.dropped` 后知道对应范围的文本增量不完整，可通过 `run.query` 获取终态快照补全。

**GSN 持久化——Event Outbox 模式（崩溃安全）**

GSN 不能仅在关键检查点持久化。事件在发送前必须先写入 Outbox 表，否则崩溃后可能以旧 GSN 重发新事件，导致同一 GSN 对应不同内容。

```sql
event_outbox (
  gsn          INTEGER PRIMARY KEY,   -- 发送前先分配并落库
  run_id       TEXT NOT NULL,
  run_sequence INTEGER NOT NULL,
  message_type TEXT NOT NULL,
  payload_json TEXT NOT NULL,
  status       TEXT NOT NULL,         -- Pending | Sent | Acknowledged
  created_at   TEXT NOT NULL,
  sent_at      TEXT
)
```

**事件发送流程**：
1. 分配 `gsn = MAX(gsn) + 1`（原子自增，事务内）
2. 在同一事务内写入 `event_outbox (gsn, ..., status=Pending)`
3. 事务提交后发送事件帧到通道
4. 发送成功后更新 `status=Sent`

**崩溃恢复流程**：
- 重启时扫描 `event_outbox WHERE status IN ('Pending','Sent')` 按 `gsn` 升序
- 重放所有未确认事件（幂等：宿主按 gsn 去重）
- 继续从 `MAX(gsn) + 1` 分配新 GSN

宿主确认 `lastConfirmedGsn` 后，可删除 `gsn ≤ lastConfirmedGsn` 且 `status=Acknowledged` 的行。

**delta.dropped 约束修正**：`delta.dropped` 事件只能用于表示已发送但宿主未收到或已丢弃的 Delta 事件的占位——它自身也经过 Outbox，不能用一个新 GSN 填补多个已分配的旧 GSN。如果一批 Delta 事件在溢出时被丢弃，Runtime 不为它们分配 GSN，直接发出一个 `delta.dropped` 事件（携带 `runSequence` 范围，表明那些 Delta 的 Run 内序号），该占位事件本身正常分配一个 GSN。

## 3. 【阻断】Run 启动请求拆分

### 问题

`01 §5.2` 的 `RunStartRequest` 同时承载"新建 Session"和"在已有 Session 中继续"两种语义。继续已有 Session 时，传入配置与保存配置冲突，采用哪份没有定义。新建请求响应丢失后重试可能重复创建 Session。

### 决策：拆成两个独立 DTO

**新建 Session 并启动 Run**：

```text
NewSessionRunRequest
  runIdempotencyKey            宿主生成，用于去重（保留 24 小时）
  sessionIdempotencyKey        宿主生成，用于 Session 去重（保留 7 天）
  mode                         Expert | Meeting | Work
  workspaceRoot                已由进程绑定，此处改为可选校验字段（见 §4）
  defaultSelection
    providerId / providerProfileId / modelId
  modeOptions                  ExpertOptions | MeetingOptions | WorkOptions
  initialContents[]
  attachments[]
  generationOptions
  timeout
  metadata
```

Runtime 收到后：若 `sessionIdempotencyKey` 已存在，返回已存在的 `sessionId` 和 `runAccepted`（幂等）；否则新建 Session 并启动 Run。

**在已有 Session 中启动新 Run**：

```text
ExistingSessionRunRequest
  runIdempotencyKey
  sessionId                    必须存在且 mode 与保存的 mode 一致
  expectedSelectionVersion     可选；提供时做乐观并发检查
  contentsOverride             本轮输入内容
  attachments[]
  turnOverride                 本轮临时配置覆盖
  generationOptions
  timeout
  metadata
```

继续已有 Session 时，配置以 `NextTurnSelection`（由 `session.selection.update` 维护）为准，`ExistingSessionRunRequest` 不传入完整配置——只允许通过 `turnOverride` 做单轮临时覆盖。这消除了"传入配置和保存配置哪个优先"的歧义。

**幂等键保留时间**：`runIdempotencyKey` 保留 24 小时（覆盖合理的网络重试窗口）；`sessionIdempotencyKey` 保留 7 天。超期后同名键视为新请求。

## 4. 【阻断】Runtime-工作区绑定（V1 单绑定）

### 问题

`serve` 模式允许每个 Run 传入不同 `workspaceRoot`，但 `--data-dir` 是进程级参数，`session.get/resume` 只有 `sessionId` 没有 `workspaceId`。多工作区共享同一 Runtime 实例会让数据路由变得不可靠。

### 决策：V1 一个 Runtime 实例绑定一个工作区

`workspaceRoot` 从 Run 级参数提升为**进程级启动参数**：

```text
ai-runtime serve  --workspace <path>  --data-dir <path（可选）>  ...
ai-runtime run    --workspace <path（可选，缺省=当前目录）>  ...
```

- `serve` 模式：`--workspace` 必须提供，所有宿主发来的 Run 均在该工作区下执行。`NewSessionRunRequest` 和 `ExistingSessionRunRequest` 不再携带 `workspaceRoot`；若携带，Runtime 仅验证是否与绑定工作区一致，不一致时拒绝（`WorkspaceMismatch` 错误）。
- `run` 模式：`--workspace` 可选，缺省使用 CLI 启动时的当前目录。
- `--data-dir` 缺省为 `{workspaceRoot}/.madorin`。

`session.list/get/resume` 不需要 `workspaceId`；Runtime 只管理当前绑定工作区的 Session。

**多工作区场景（V2+）**：届时引入 `WorkspaceRegistry`（`state.db` 中的注册表），Session API 增加 `workspaceId` 字段；V1 协议字段预留 `workspaceId`（可空），确保 V2 不破坏协议。

## 5. 【阻断】Agent Prompt 恢复握手

### 问题

`01 §5.2` 允许 Prompt 内容 `isRedacted=true`（脱敏为空），同时 `01 §5.3` 规定 Runtime 不维护模板库。但 `01 §9.4` 的恢复快照要求还原 Agent 快照——如果 Prompt 已被脱敏且 Runtime 没有存储，恢复后无法重建可执行 Agent。

### 决策：恢复配置握手 + 输入 DTO 与快照 DTO 分离

#### 5.1 输入 DTO 与快照 DTO 分离

宿主传入 `AgentRef`（输入 DTO）——包含完整 Prompt 内容或脱敏标记。  
Runtime 保存 `AgentSnapshot`（快照 DTO）——仅存储元数据和哈希，永远不存储完整 Prompt 明文（除非启用可选的加密存储，见下）。

```text
AgentSnapshot（存入 state.db）
  agentId
  promptTemplateId
  promptTemplateVersion
  resolvedPromptHash         sha256(resolved full prompt)
  layerHashes[]              每层独立哈希
  capabilities[]
  providerId / modelId       本次 Invocation 实际使用的值
  invocationId
```

宿主任何时候可以通过 `invocationId` 查询某次 Invocation 使用的 `AgentSnapshot`，获得哈希但不获得明文。

#### 5.2 恢复配置握手——session.rehydrate

`ExistingSessionRunRequest` 不携带 `AgentRef`（该 DTO 只负责启动 Run，不传输 Agent 定义）。Prompt 和 Agent 定义的重新注入通过独立的 `session.rehydrate` 握手完成。

**握手流程**：

```text
1. 宿主调用 session.resume(sessionId)

2. Runtime 返回 SessionResumeResponse：
   sessionId
   mode
   latestSelectionVersion
   neededDefinitions[]          Runtime 没有可执行版本的 Agent 定义列表
     agentId
     resolvedPromptHash         宿主需要提供哈希匹配的 Prompt
     definitionType             SingleAgent | MeetingParticipant | WorkGeneralManager | WorkSubAgent
     participantId?             MeetingParticipant 时提供
   lastGsn
   lastCheckpoint

3. 若 neededDefinitions 不为空：
   宿主调用 session.rehydrate(sessionId, agentDefinitions[])
     每个 AgentDefinition：
       agentId
       participantId?
       agentRef                  完整 AgentRef（含明文 Prompt，或已开启加密存储时可省略）

4. Runtime 验证每个 AgentRef 的哈希，返回 SessionRehydrateResponse：
   sessionId
   status                       Ready | PartiallyReady | Failed
   mismatched[]                 哈希不匹配的 agentId（需要宿主重试或放弃）

5. status=Ready 后，宿主可正常发起 ExistingSessionRunRequest
```

`neededDefinitions` 按模式覆盖范围：
- 专家模式：最多一个 SingleAgent
- 会议模式：返回所有 `meeting_participants` 中 `status=Active/Standby` 且未加密存储的参与者定义
- 工作模式：返回总经理、上次未完成步骤涉及的子智能体定义

若已启用 `--store-encrypted-prompts`，Runtime 自主解密可执行 Prompt，`neededDefinitions` 为空，无需握手。

#### 5.3 可选：加密本地 Prompt 存储

V1 可选功能（由 `--store-encrypted-prompts` 启动参数启用）：Runtime 用 **AES-256-GCM** 加密保存非脱敏 Prompt，允许在宿主不在线时自主恢复。密钥派生使用 PBKDF2（`Rfc2898DeriveBytes`），主密钥来源为运行时随机生成并保存在 `{data-dir}/keys/` 目录下的密钥文件（文件权限设为仅当前用户可读）。

`System.Security.Cryptography.Aes` 是 .NET 标准库的跨平台实现，不依赖 Windows DPAPI、macOS Keychain 或 Linux libsecret，在 Windows、macOS、Linux 上行为一致。

未启用时，每次恢复必须经过 `session.rehydrate` 握手（§5.2）。

## 6. 【阻断】Named Pipe 安全加固

### 问题

`01 §3.2` 的"先探测再创建"不是原子互斥（TOCTOU 竞态），且 `InitializeRequest` 直接携带 `authenticationToken`——恶意进程若抢先占据同名 Pipe，可以接收到原始令牌。

### 决策：三重防护

#### 6.1 Pipe ACL

#### 6.1 传输层安全（跨平台）

.NET `NamedPipeServerStream` 在 Unix 上使用 Unix Domain Socket 实现，安全机制与 Windows 不同，需要平台分支：

**Windows**：在 `PipeOptions` 中通过 `PipeSecurity` 设置 ACL，只允许当前用户 SID 连接：

```csharp
if (OperatingSystem.IsWindows())
{
    var acl = new PipeSecurity();
    acl.AddAccessRule(new PipeAccessRule(
        WindowsIdentity.GetCurrent().User,
        PipeAccessRights.ReadWrite | PipeAccessRights.CreateNewInstance,
        AccessControlType.Allow));
    // 通过 NamedPipeServerStreamAcl.Create 传入 acl
}
```

**macOS / Linux**：Unix Domain Socket 文件创建后，立即设置文件权限为仅所有者可读写（`chmod 600`）：

```csharp
if (!OperatingSystem.IsWindows())
{
    File.SetUnixFileMode(socketPath,
        UnixFileMode.UserRead | UnixFileMode.UserWrite);
}
```

这两段代码封装在 `Transport.NamedPipes` 层，上层只调用 `IControlChannel.CreateServer()`，不感知平台差异。

#### 6.2 服务端 PID 校验（跨平台）

宿主在连接后验证对端进程 PID，与已知的 Runtime 进程 PID 比对：

**Windows**：调用 `GetNamedPipeServerProcessId`

**macOS / Linux**：在 Unix Domain Socket 上通过 `SO_PEERCRED` 选项获取对端进程 PID：

```csharp
if (OperatingSystem.IsWindows())
{
    NativeMethods.GetNamedPipeServerProcessId(pipeHandle, out var serverPid);
    if (serverPid != expectedRuntimePid) Disconnect();
}
else
{
    var cred = socket.GetSocketOption(SocketOptionLevel.Socket,
        SocketOptionName.PeerCredentials);
    // UCred.pid 字段
    if (cred.Pid != expectedRuntimePid) Disconnect();
}
```

PID 不符时立即断开，不发送任何认证信息，记录安全事件，不重试。

#### 6.3 双向挑战响应

当前单向挑战响应只能证明 Runtime 持有 secret；同一用户下的其他进程仍可在 PID 校验通过后伪装宿主，发送 InitializeRequest。必须改为双向认证，并从握手中派生连接会话密钥。

`authenticationToken` 和 `--auth-token-handle` 旧契约废弃——不再传递原始令牌。改用 `--auth-secret-handle` 传递 HMAC 共享密钥。

```text
握手流程（双向 HMAC）：

1. 宿主生成 nonce_c（随机 32 字节）
   发送：MutualAuthRequest { nonce_c }

2. Runtime 生成 nonce_s（随机 32 字节）
   计算：hmac_s = HMAC-SHA256(secret, "runtime" || nonce_c || nonce_s || instanceId)
   返回：MutualAuthChallenge { nonce_s, hmac_s, instanceId, timestamp }

3. 宿主验证：
   - 重算 HMAC-SHA256(secret, "runtime" || nonce_c || nonce_s || instanceId)，与 hmac_s 比对
   - 校验 timestamp 在±30 秒内，instanceId 与预期一致
   - 验证失败：立即断开，不发送任何后续消息

4. 宿主计算：hmac_c = HMAC-SHA256(secret, "host" || nonce_c || nonce_s || hostInstanceId)
   发送：MutualAuthResponse { hmac_c, hostInstanceId }

5. Runtime 验证：
   - 重算 HMAC-SHA256(secret, "host" || nonce_c || nonce_s || hostInstanceId)，与 hmac_c 比对
   - 验证失败：断开连接，记录安全事件

6. 双方从 nonce_c + nonce_s 派生连接会话密钥：
   sessionKey = HKDF-SHA256(secret, nonce_c || nonce_s, info="session-key", length=32)
   后续控制消息的 MAC 使用 sessionKey，不再使用原始 secret

7. 握手完成，发送 InitializeRequest（不含 secret 或 token）
```

`secret` 通过进程句柄（`--auth-secret-handle`）传递，不出现在命令行参数或环境变量中，Runtime 和宿主各自读取后立即清零内存。

## 7. 【高风险】CanonicalHistory 与 ContextProjection 分离

### 问题

`01 §5.6` 描述历史裁剪会产生 `history.trimmed` 事件，但没有说明裁剪是否修改权威历史。"恢复完整规范化历史"（`01 §9.4`）与"裁剪历史"存在直接矛盾：如果裁剪修改了权威历史，就无法完整恢复。

### 决策：严格分离两个概念

#### 7.1 CanonicalHistory（权威历史，不可变）

所有消息按 `(sessionId, sequence)` 永久存储，不因任何原因被修改或删除（仅可显式归档）。UI 显示的始终是 CanonicalHistory。

每条消息的 `role`、`content[]`、`agentId`、`invocationId`、`createdAt` 一旦写入，不得覆盖。工具结果、推理过程、Agent 内部消息均包含在内。

#### 7.2 ContextProjection（上下文投影，每次 Invocation 独立生成）

每次 Invocation 开始时，Content Pipeline 从 CanonicalHistory 中按策略生成 ContextProjection，发送给模型。投影策略包括：

```text
ContextProjectionPolicy
  maxTokens              目标上下文窗口用量（不超过模型限制的 90%）
  strategy               Full | TailWindow | SlidingWindow | SummaryCompressed
  summaryAgentId         strategy=SummaryCompressed 时使用的摘要 Agent
  preserveToolResults    true=保留工具调用/结果；false=仅保留文本
  preserveReasoning      false=投影时丢弃 reasoning 块
```

投影结果只存在于内存中（不写入 state.db），不改变 CanonicalHistory。

#### 7.3 ContextProjection 记录与事件

每个 Invocation 的 `InvocationSnapshot` 记录 `contextProjectionVersion`（投影策略版本）和 `contextTokensEstimate`（投影后的估算 token 数）。

当投影导致消息被裁剪或摘要化时，产生事件：

```text
context.projection.adjusted（替换原 history.trimmed）
  invocationId
  originalMessageCount
  projectedMessageCount
  trimmedTokenEstimate
  strategy
  summaryMessageId       strategy=SummaryCompressed 时，插入的摘要消息 ID
```

宿主和 UI 收到此事件后知道"模型看到的历史比 UI 显示的少"，可以显示压缩标记；但 CanonicalHistory 中的消息数量不变。

#### 7.4 UI 与模型视图的同步说明

| | CanonicalHistory | ContextProjection |
|---|---|---|
| 存储位置 | `messages/{sessionId}.jsonl`（append-only）+ `state.db` 轻量索引 | 内存，每次 Invocation 重建；`.compact.json` 为可选缓存 |
| UI 显示 | ✅ 始终完整 | ❌ 不直接展示 |
| 模型输入 | ❌ 不直接发送 | ✅ 经过裁剪/投影 |
| 可恢复 | ✅ 完整恢复 | 恢复后重新生成 |
| 可修改 | ❌ 不可变 | 每次 Invocation 独立策略 |

## 8. 【高风险】状态机与工具幂等补全

### 8.1 完整状态机

Run 完整状态机（包含所有补充状态）：

```text
Accepted
  -> Preparing
  -> Running
  -> WaitingForTool
  -> WaitingForApproval
  -> WaitingForCredentials   凭据过期/401，等待宿主推送新凭据
  -> Running                 （凭据续期后恢复）
  -> Persisting
  -> Completed | Failed | Cancelled

崩溃后重建：
  -> Interrupted             无终态 Run 在 Runtime 重启后标记为此状态
                             宿主可按策略决定重试（创建新 Run）或放弃
```

状态跳转规则：
- `WaitingForCredentials` 只能由 Runtime 在收到 Provider `401` 或凭据接近过期时触发，不由宿主直接设置
- `Interrupted` 只在 Runtime 重启时批量设置，正常流程不产生此状态
- 从任何非终态进入 `Cancelled` 都需要显式 `run.cancel` 命令或租约到期

**凭据续期重试规则**：
- Runtime 收到 `credentials.update` 后，对原请求重试一次
- 重试后仍 `401`：Run 进入 `Failed`，错误码 `AuthenticationFailed`，`isRetryable=false`
- 等待凭据超时（默认 30 秒）未收到 `credentials.update`：Run 进入 `Failed`，错误码 `CredentialRefreshTimeout`

### 8.2 工具调用幂等：执行前落库

旧设计的问题：`stepHash` 包含 `toolCallsSnapshot`（执行后才有），无法在发送前判断是否已执行。

**决策：工具调用意图在发送前事务性落库，结果内容持久化**

```text
工具调用幂等记录（state.db）
  callId              stable, generated before sending
  invocationId
  runId
  sessionId
  agentId
  toolId
  argumentsHash       sha256(serialized arguments)
  status              Pending | Sent | Succeeded | Failed | Cancelled
  sentAt
  completedAt
  resultHash          sha256(result content)，完成后记录
  resultJson          小型结果内联（≤ maxInlineContentBytes），null 则看 resultBlobId
  resultBlobId        大型结果写入 blobs/，存 blobId
```

`resultHash` 用于完整性校验；`resultJson` 或 `resultBlobId` 是恢复时返回给模型的实际内容。两者至少有一个非 null 时，`status=Succeeded` 才可直接复用已持久化结果。

流程：

```text
1. 模型输出工具调用
2. Runtime 事务性写入 (callId, status=Pending) 到 state.db
3. 发送 tool.permission.request（如无有效 Grant）
4. 获权后更新 status=Sent，发送 tool.call.request
5. 收到 tool.call.response 后更新 status=Succeeded/Failed，记录 resultHash
```

恢复时：
- `status=Succeeded/Failed`：直接使用已持久化的结果，不重发
- `status=Sent`（发送后无响应）：向宿主发送 `tool.result.query(callId)`，宿主返回结果或 `Unknown`；`Unknown` 时由宿主策略决定重发或失败
- `status=Pending`（落库后未发送）：安全重发，无副作用

### 8.3 Work 模式两级幂等键

`stepHash = sha256(invocationId + agentId + toolId + args)` 实际上是工具调用键，不是步骤键——一个步骤可能没有工具调用、也可能触发多个工具调用。步骤和工具意图是两个独立的幂等层级：

**步骤级幂等键**（Work Step）：

```text
stepId        总经理在制定计划时分配的稳定计划步骤 ID（plan step ID）
planVersion   计划版本号（总经理修订计划时递增）
stepInputHash sha256(stepId + planVersion + serializedStepInputs)
              stepInputs = 该步骤的目标描述 + 依赖步骤输出引用 + 参数
```

步骤键与工具调用无关——同一步骤的不同执行尝试（重试）使用相同 `stepId + planVersion`，但每次执行生成新的 `invocationId` 和新的 `callId` 集合。

**工具调用级幂等键**（Tool Intent）：

每个工具调用独立使用 `callId`（在发送前生成），与步骤键正交：

```text
callId        UUID，工具调用发送前生成
stepId        所属步骤（可空，非工作模式调用时为 null）
```

**Work Step 与 Tool Intent 的关系**：
- 步骤 `Completed`：步骤内所有工具意图都已达到终态（Succeeded/Failed）
- 步骤 `Interrupted`：恢复时先查询所有 `status=Sent` 的工具意图结果，再决定是否重新执行步骤

**grant.revoke 命令**（Grant 撤销，Issue 6 补充）：

```text
grant.revoke（Host → Runtime）
  grantId           撤销的 Grant ID
  revokeDescendants 是否同时撤销基于此 Grant 的所有委派（默认 true）

撤销效果：
  尚未发送的工具调用：检查权限时发现 Grant 无效，立即以 PermissionRevoked 失败
  已发送等待响应的工具调用：等待响应后，Runtime 拒绝使用结果继续执行，返回 PermissionRevoked
  已完成的工具调用：不影响，结果已持久化
```

**approval 关联 ID**（Issue 6 补充）：

```text
NeedsUserApproval 流程：
  tool.permission.response(status=NeedsUserApproval, approvalRequestId)
  → Runtime 进入 WaitingForApproval
  → approval.request(approvalRequestId, toolId, callId, agentId, arguments, risk)
  → approval.response(approvalRequestId, approved=true/false, grantId?)
  → 若 approved=true：继续 tool.call.request
  → 若 approved=false：工具调用以 ApprovalDenied 失败
```

`approvalRequestId` 是跨越整个审批生命周期的稳定关联键，宿主按此 ID 追踪 UI 审批状态。

## 9. 三种模式专属存储结构

### 9.1 设计原则

**存储分层**（与 `Docs/未来策划/存储优化/对话记录文件化存储方案.md` 对齐）：

- `state.db`：索引、元数据、事务性状态（可查询、可回滚）
- `messages/{sessionId}.jsonl`：CanonicalHistory 消息正文（append-only，不进 SQLite）
- `messages/{sessionId}.compact.json`：ContextProjection 缓存（可重新生成）

`messages/` 下的文件以 `sessionId` 为文件名，模式不同只影响 `state.db` 的专属结构表，文件布局不区分模式。

会议模式和工作模式的结构化状态（轮次、步骤、依赖图）存入各自的专属表，通过 `sessionId` 与消息文件关联。

### 9.2 统一 CanonicalHistory（消息文件）

所有模式的消息正文统一写入 `messages/{sessionId}.jsonl`，统一记录格式 `ConversationRecordV1`：

```jsonl
{"type":"header","schema":1,"sessionId":"ses_xxx","mode":"expert|meeting|work","createdAt":"..."}
{"messageId":"msg_aaa","seq":1,"invocationId":"inv_xxx","agentId":"agent_xxx","role":"user","content":[{"type":"text","text":"..."}],"ts":"..."}
{"messageId":"msg_bbb","seq":2,"invocationId":"inv_xxx","agentId":"agent_xxx","role":"assistant","content":[{"type":"text","text":"..."},{"type":"reasoning","text":"...","signature":"..."}],"tokens":123,"model":"...","ts":"..."}
{"messageId":"msg_ccc","seq":3,"invocationId":"inv_xxx","agentId":"agent_xxx","role":"assistant","content":[{"type":"tool_call","callId":"call_xxx","toolId":"builtin.fs.read","name":"read_file","arguments":{}}],"ts":"..."}
```

每行必须包含：
- `messageId`（UUID，写入前在内存生成，用于 SQLite 索引的幂等 INSERT OR IGNORE）
- `seq`（从文件末行读取，不从 SQLite 读取）
- `content[]`（ContentBlock 联合类型数组，不使用单一 `content` 字符串）

`state.db` 中保留 `messages` 轻量索引表（只存元数据，不存正文）：

```sql
messages (
  message_id     TEXT PRIMARY KEY,
  session_id     TEXT NOT NULL,
  sequence       INTEGER NOT NULL,
  invocation_id  TEXT,
  agent_id       TEXT,
  role           TEXT NOT NULL,   -- user | assistant | tool_result
  token_count    INTEGER,
  created_at     TEXT NOT NULL,
  UNIQUE(session_id, sequence)
)
```

列表、分页、token 统计通过索引表完成；加载消息正文时才读 `.jsonl` 文件。

### 9.3 专家模式

无额外专属表。Session 状态通过消息文件 + InvocationRecord 还原。

### 9.4 会议模式专属表

```sql

)

-- 参与者池：记录整个会话生命周期内曾经存在的所有参与者及其状态变化
```

**恢复**：`session.resume` 返回 `meeting_sessions`、当前 `meeting_rounds` 状态、`meeting_participants`（含状态和当前 joinOrder）、下一位预定发言者（`Scheduled` 的 `meeting_invocations`）和最后一轮摘要的 `message_id`。宿主据此可还原会议界面上已选参与者列表及其激活/待机状态。

## 10. 上下文压缩处理

### 10.1 问题场景

当 Session 历史超过模型上下文窗口时，系统需要压缩/裁剪历史。压缩后：
- **模型看到的**：ContextProjection（裁剪或摘要化后的内容）
- **UI 显示的**：CanonicalHistory（完整原始内容）

两者必然不同，设计必须显式处理这个差异，而不是让调用方意外发现。

### 10.2 ContextProjection 生成流程

每次 Invocation 开始时，Content Pipeline 执行以下流程：

```text
1. 从 CanonicalHistory 加载完整消息列表
2. 计算当前消息的 token 估算（各 Provider 的 tokenizer 不同，使用 Adapter 提供的估算器）
3. 若总量 ≤ maxTokens * 0.9：使用 Full 策略，不裁剪
4. 若总量 > maxTokens * 0.9：按 ContextProjectionPolicy.strategy 生成投影：
   - TailWindow：保留最近 N 条消息的完整内容
   - SlidingWindow：保留系统提示 + 最近 N 轮完整对话（工具调用/结果作为一个单元不被拆开）
   - SummaryCompressed：调用 summaryAgent 对早期对话生成摘要，插入为单条摘要消息，
     原始消息仍保留在 CanonicalHistory 但不进入本次投影
5. 生成 context.projection.adjusted 事件（如发生裁剪）
6. 将 ContextProjection 发送给 Provider
```

### 10.3 摘要消息的处理

`SummaryCompressed` 策略生成的摘要消息**追加到 CanonicalHistory 末尾**（`seq` 大于所有被摘要消息的 `seq`），而不是插入到被摘要消息之前——插入会破坏 append-only 和 sequence 不可变两个约束。

```text
摘要消息字段
  messageId        UUID
  seq              追加末尾，大于所有被摘要消息
  role             assistant
  agentId          system.summarizer
  content[]        [{ type: "text", text: "摘要内容..." }]
  summarizesThroughSeq   被摘要的最大 seq（用于投影时识别哪些消息可以用摘要替代）
  invocationId     生成该摘要的 Invocation
```

ContextProjection 生成时的使用规则：
- 如果存在 `summarizesThroughSeq=N` 的摘要消息，投影时用该摘要替代 `seq ≤ N` 的所有原始消息
- 摘要消息本身按正常 seq 顺序排在原始消息之后（对模型呈现时调整顺序：摘要先，原始消息后续部分跟）
- CanonicalHistory 中原始消息和摘要消息都保留，互不删除

摘要缓存规则：如果自上次摘要生成以来 CanonicalHistory 没有超过摘要范围的新消息，直接复用已有摘要，不重新调用摘要 Agent。

### 10.4 UI 层同步

宿主收到 `context.projection.adjusted` 事件后，应在 UI 中展示适当标记：

```text
事件字段
  invocationId
  originalMessageCount      CanonicalHistory 消息总数
  projectedMessageCount     实际发送给模型的消息数
  strategy                  使用的投影策略
  trimmedTokenEstimate      未进入投影的估算 token 数
  summaryMessageId          摘要消息的 message_id（strategy=SummaryCompressed 时）
```

UI 可以选择：
- 显示"部分历史已压缩"提示，点击后展示完整 CanonicalHistory
- 在被摘要的消息区域显示摘要消息内容
- 不区分展示（宿主选择忽略此事件）

Runtime 不强制要求 UI 的展示方式，只保证事件的完整性。

### 10.5 会议/工作模式的压缩特殊性

会议模式的 ContextProjection 通常不应裁剪当前 Round 的发言记录（保持会议连贯性）。建议 `MeetingOptions` 增加 `contextPolicy.preserveCurrentRound=true`（默认），使 TailWindow 和 SlidingWindow 以 Round 为单位而非消息为单位进行裁剪。

工作模式的 ContextProjection 通常应保留当前步骤的全部上下文和工具调用历史，以及总经理的计划消息；早期步骤的详细工具结果可以优先裁剪。建议 `WorkOptions` 增加 `contextPolicy.preservePlan=true`（默认）和 `contextPolicy.preserveCurrentStep=true`（默认）。

## 11. 修订后的变更汇总

以下修订需要同步反映到 `01-实施方案-V1.md` 和 `README.md`：

| 章节 | 变更 |
|---|---|
| 层级模型 | Session → Run → AgentInvocation → ProviderRequest；`invocation.started/completed` 替换多个模式事件 |
| 事件游标 | 引入 GSN；单游标确认；`delta.dropped` 占位不产生空洞 |
| Run 启动 | `NewSessionRunRequest` / `ExistingSessionRunRequest` 替换 `RunStartRequest` |

| Prompt 恢复 | `AgentRef`（输入）/ `AgentSnapshot`（快照）分离；恢复握手；可选加密存储 |
| Pipe 安全 | ACL + PID 校验 + 挑战响应；不传原始令牌 |
| 历史模型 | CanonicalHistory（不可变）/ ContextProjection（每次 Invocation 生成）；`context.projection.adjusted` 事件 |
| 状态机 | 补全 `WaitingForCredentials`、`Interrupted`；401 重试规则；工具意图执行前落库 |
| 存储结构 | 专家模式无额外表；会议模式增 3 个专属表；工作模式增 3 个专属表 |
