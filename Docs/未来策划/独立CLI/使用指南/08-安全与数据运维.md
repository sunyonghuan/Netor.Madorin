# Madorin Runtime 安全与数据运维

> 适用版本：Madorin.AI.Runtime V1，协议 1.1，SQLite Schema 14
>
> 本文面向直接使用 CLI 的用户和 Runtime 运维人员。所有命令都通过 Runtime 服务执行，不应手工修改 `.madorin` 内部文件。

## 1. 权限模型

### 1.1 Restricted 是默认策略

每个 Run 都必须绑定规范化的 `workspaceRoot`。Restricted 默认只允许通过受控内置工具读取工作区内容，以及在工作区内新建和写入文件；没有额外 Grant 或审批时，覆盖、移动、删除、任意进程执行、PowerShell 和工具网络访问均被拒绝。Provider 访问仅限已配置的 Provider 端点，不等于向模型工具开放任意网络。

路径校验以 `workspaceRoot` 为唯一基准，并在实际打开文件前处理绝对路径、`..`、UNC、设备路径、备用数据流、符号链接、目录联接点和 Reparse Point。复制、移动和写入会同时校验源、目标及最终父目录，不能用字符串前缀判断路径是否位于工作区内。

Restricted 是 Runtime 的最小权限策略，不是操作系统沙箱。它约束 Runtime 提供的工具入口，但不能把同一用户权限下的任意子进程限制在工作区中。

### 1.2 进程与 Shell

| 模式 | 边界 |
| --- | --- |
| Restricted | 默认模式；不开放任意进程和 PowerShell |
| AllowlistedProcess | 只运行显式允许的程序，参数数组、工作目录和环境变量均受控 |
| SandboxedShell | 依赖低权限账户、AppContainer、Windows Sandbox 或容器提供 OS 级隔离 |
| UnrestrictedShell | 使用当前用户权限运行，必须显式授权，不具备工作区隔离 |

`UnrestrictedShell` 不能因为模型请求而自动开启。它能够访问当前用户本来可以访问的文件、凭据和网络资源，设置 `WorkingDirectory` 也不会形成隔离。阶段 7 尚未闭合完整的 Shell 授权和 OS 沙箱能力，因此不得把 `UnrestrictedShell` 描述为默认可用能力，也不得用 Restricted 的名称暗示它已经受到 OS 级隔离。

允许 PowerShell 时仍应使用 `-NoProfile`、`-NonInteractive`，通过标准输入或受控脚本文件传递脚本，并采用环境变量白名单、输出字节上限、超时、取消和进程树回收。命令和路径始终通过参数数组传递，不拼接 Shell 字符串。

## 2. Secret、日志与数据边界

- 个人 `~/.madorin/config.json` 只用于用户直接启动 CLI。宿主集成通过 Client SDK 和协议提供配置、凭据及 Selection，不读取个人 CLI 配置。
- API Key 只通过无回显输入、受控环境变量或宿主凭据更新接口传入。不要把 Key 写入命令行参数、Prompt、仓库文件、日志或异常消息。
- `config show`、`doctor` 及 JSON 输出必须脱敏。日志默认只记录必要元数据、哈希和诊断 ID，不记录完整 Prompt、工具结果、脚本或密钥。
- Client 启动 Runtime 时通过重定向 stdin 传递一次性握手 secret；secret 不进入命令行、环境变量或实例文件。
- `.madorin` 是 Runtime 保留数据区。AI 文件工具、宿主和普通用户流程都不得直接修改其中的 `state.db`、WAL、`messages/`、`blobs/`、`checkpoints/`、`staging/`、`locks/` 或实例信息。
- `messages/*.jsonl` 是 CanonicalHistory 正文，`state.db` 保存状态和索引，`messages/*.compact.json` 是可重建投影缓存。三者不能互相替代。
- Provider 凭据和宿主业务密钥不得随 Session、数据库备份或 Blob 归档自动写入 `.madorin`。

运维命令应显式指定工作区，自动化场景建议同时固定数据目录：

```powershell
$workspace = 'E:\Projects\demo'
$dataDirectory = 'E:\Projects\demo\.madorin'

madorin doctor --workspace $workspace --data-dir $dataDirectory
```

`--json` 输出只写机器可解析信封到 stdout，诊断和进度写 stderr。非 TTY 或指定 `--no-color` 时不输出 ANSI 控制码。

## 3. 日常检查

按以下顺序进行例行检查：

```powershell
madorin doctor --workspace $workspace
madorin db check --workspace $workspace --verbose
madorin storage check --workspace $workspace
madorin storage check --workspace $workspace --verify-hashes
```

`doctor` 固定检查 Runtime、个人配置、记忆、工作区、数据、Provider、传输、日志和 Blob。`db check` 严格只读，不获取写锁，不截断 JSONL、不修复索引，也不执行迁移。`storage check` 同样只读；默认检查引用、文件名、元数据和已知长度，只有 `--verify-hashes` 才流式读取 Blob 内容并计算 SHA-256。

检查失败时先保存完整 JSON 输出和 `diagnosticId`，再判断问题属于配置、锁、数据库、消息文件还是 Blob。不要通过删除 `state.db` 或清空 `.madorin` 来消除告警。

## 4. 数据库维护

| 命令 | 是否写入 | 锁与保护 | 适用场景 |
| --- | --- | --- | --- |
| `db check` | 否 | 不获取写锁，严格零写入 | 完整性、Schema、WAL、表/索引、JSONL 和消息索引检查 |
| `db repair` | 是 | 确认后获取排他锁，修复前创建恢复点 | 修复已识别的 JSONL 损坏尾行和已有 Session 的消息索引漂移 |
| `db rebuild` | 是 | 确认后获取排他锁，替换前保存数据库恢复点 | SQLite 索引无法继续使用，但 CanonicalHistory 仍可读取 |
| `db vacuum` | 是 | 获取排他锁 | 回收 SQLite 空闲页，不改变逻辑数据 |
| `db backup` | 生成备份 | 仅数据库使用在线备份；包含消息时获取排他锁 | 日常备份、升级或维护前保护 |
| `db migrate` | 是 | dry-run 无锁；实际迁移获取排他锁并先保存恢复点 | 仅向前升级 Schema |

### 4.1 检查与定向修复

先检查，再预览修复计划：

```powershell
madorin db check --workspace $workspace --verbose
madorin db repair --workspace $workspace --dry-run
```

确认诊断属于可修复范围后执行：

```powershell
madorin db repair --workspace $workspace
# 非交互或 JSON 场景：
madorin db repair --workspace $workspace --yes --json
```

`db repair` 不是 `db rebuild` 的别名。它只处理检查器已经识别的损坏尾行和索引漂移；JSONL 中间行损坏、缺失 Session、缺失消息文件、SQLite 损坏和 Schema 不兼容只报告，不自动扩大修复范围。`--dry-run` 不加锁、不备份、不写入；实际修复在展示计划并确认后加锁，恢复点创建失败时不会开始修改。

`doctor --fix` 复用相同的可恢复损坏边界：

```powershell
madorin doctor --workspace $workspace --fix
madorin doctor --workspace $workspace --fix --yes --json
```

它不会把不可恢复问题静默转成成功，也不会自动选择 rebuild 或 migrate。

### 4.2 在线备份

```powershell
madorin db backup --workspace $workspace
madorin db backup --workspace $workspace --output 'E:\Backups\demo-state.db'
madorin db backup --workspace $workspace --output 'E:\Backups\demo-state.db' --include-messages
```

默认目标是数据目录 `backups/` 下的唯一 `.db` 文件。数据库使用 SQLite 在线备份 API，能够包含活动 WAL 中已提交的数据；不要直接复制活动的 `state.db`、WAL 和 SHM 文件拼接快照。

指定 `--include-messages` 时，会在数据库备份旁生成同名 `.messages.zip`，并为保持 SQLite 与 CanonicalHistory 一致而获取工作区排他锁。数据库和消息归档都先写临时文件再原子发布；目标已存在或归档失败时不会覆盖旧文件，也不会返回不完整的备份集。

### 4.3 索引重建

```powershell
madorin db rebuild --workspace $workspace --dry-run
madorin db rebuild --workspace $workspace --confirm
```

rebuild 从 `messages/*.jsonl` 构造新的 `state.db`、Session 元数据和消息索引。它不修改 Canonical JSONL；损坏尾行只读取有效前缀，中间损坏会产生不可恢复诊断。替换前保存现有数据库、WAL 和 SHM，恢复点失败时不会开始重建。

重建只能恢复消息文件中仍有权威数据的部分。Run、Grant、工具意图和 Invocation 快照不能从消息正文推导，恢复后的 Session 标记为 `Recovered`。存在部分不可恢复 Session 时保留已恢复结果并返回 partial/退出码 1，运维人员必须检查诊断后再开放写入。

### 4.4 压缩与迁移

在确认没有活动 Runtime 写入后压缩数据库：

```powershell
madorin db vacuum --workspace $workspace
```

vacuum 获取工作区排他锁，并报告压缩前后大小和回收字节数。数据目录或 `state.db` 缺失时不会隐式创建空数据库。

升级前先预览迁移路径，再执行向前迁移：

```powershell
madorin db migrate --workspace $workspace --dry-run
madorin db migrate --workspace $workspace --to 14 --dry-run
madorin db migrate --workspace $workspace --to 14
```

缺省目标是当前 Runtime 支持的最新 Schema。V1 只允许向前迁移，拒绝降级、负数和高于当前 Runtime 支持版本的目标。实际迁移在锁内重新读取当前版本，有迁移步骤时先保存数据库、WAL 和 SHM；每个已有迁移按事务执行。失败时保留恢复点和原始诊断，不自动回退到空数据库。

## 5. Blob 检查与清理

先检查引用关系；需要内容级校验时再启用哈希：

```powershell
madorin storage check --workspace $workspace
madorin storage check --workspace $workspace --verify-hashes
```

如果 JSONL 或 SQLite 扫描不完整，Runtime 不会把无法证明引用关系的 Blob 归类为可清理对象。缺失引用、非法文件名和元数据冲突必须先处理诊断。

清理始终从 dry-run 开始：

```powershell
madorin storage gc --workspace $workspace --dry-run
madorin storage gc --workspace $workspace --older-than 30 --dry-run
madorin storage gc --workspace $workspace --older-than 30 --confirm
```

默认龄期保护为 7 天；`--older-than` 使用天数且不能为负数。`--dry-run` 与 `--confirm` 互斥。未提供 `--confirm` 时只展示计划且不获取写锁；实际执行获取排他锁并在锁内重新扫描，只移动名称为小写 64 位 SHA-256 的未引用 `.blob` 文件。

清理不是直接删除。候选 Blob 和清单会移动到 `backups/storage-gc-*` 恢复点；活动引用、过新文件、非法文件名和扫描不完整状态始终受保护。中途失败时保留恢复点、尚未移动的文件和原始诊断。

## 6. 锁、确认与并发

同一规范化工作区默认只有一个 Runtime 写实例。`db repair`、`db rebuild`、`db vacuum`、实际 `db migrate`、包含消息的 `db backup` 和实际 `storage gc` 都需要工作区排他锁。锁冲突返回工作区/数据错误，不提供强制绕过参数。

发生锁冲突时：

1. 使用 `madorin ctl status --workspace $workspace` 核对持锁实例和工作区绑定。
2. 停止向该实例分配新 Run，等待活动 Run 完成或通过 Client/`ctl cancel` 按业务策略取消。
3. 由拥有该 Runtime 的终端、服务管理器或 Client 生命周期策略正常关闭进程。
4. 确认实例退出后重新执行检查，再运行维护命令。

不要直接删除锁文件，不要按进程名批量结束 Runtime，也不要终止其他工作区或其他 Client 拥有的实例。SQLite-only 在线备份和只读检查不应为了方便而要求停掉无关实例。

非交互执行必须使用各命令自己的确认参数：

| 操作 | 非交互确认 |
| --- | --- |
| `doctor --fix` | `--yes` |
| `db repair` | `--yes` |
| `db rebuild` | `--confirm` |
| `storage gc` | `--confirm` |

拒绝交互确认返回 130。dry-run 不得与实际确认混用；`storage gc --dry-run --confirm` 会作为参数错误拒绝。

## 7. 故障处置顺序

遇到启动失败、数据库损坏、消息不一致或 Blob 告警时，按以下顺序处理：

1. 停止新的写入和自动重试，记录 Runtime 版本、协议版本、Schema、工作区、数据目录、实例 ID、时间和 `diagnosticId`。
2. 执行 `doctor --json`、`db check --verbose --json` 和 `storage check --json`，分别保存 stdout；不要把 stderr 合并进 JSON 文件。
3. 若只是配置、权限、磁盘空间或锁冲突，先解决外部条件并重新检查，不运行 repair/rebuild。
4. 数据库仍可在线读取时先运行 `db backup`；需要同时保护消息正文时使用 `--include-messages`，并为排他锁安排维护窗口。
5. 只有检查明确标记为可修复时才运行 `db repair --dry-run`，核对计划后执行 repair。
6. Schema 过旧时先运行 `db migrate --dry-run`；只执行当前 Runtime 支持的向前迁移。
7. 只有 SQLite 索引无法继续使用且 Canonical JSONL 可读取时才考虑 `db rebuild --dry-run`。接受 Run、Grant、工具状态和 Invocation 快照不可恢复后再确认重建。
8. 数据库与消息检查恢复健康后再处理 Blob；先 `storage check`，最后执行带龄期保护的 `storage gc`。
9. 维护完成后重新运行全部只读检查，并抽查 Session 列表、详情、消息顺序和 resume/rehydrate。

### 7.1 备份或恢复点失败

备份、恢复点或目标目录创建失败时，写操作不会开始。检查可用空间、目标路径权限、现有同名文件和工作区锁；修复外部条件后从只读检查重新开始。不要关闭保护逻辑，也不要把输出改到 Runtime 数据区中的任意内部目录。

### 7.2 中途故障

repair、rebuild、migrate 或 storage gc 中途失败时，保留命令返回的恢复点路径和原始诊断。不要立即重复执行写命令，也不要删除恢复点；先重新运行只读检查，确认当前数据库、JSONL 和 Blob 状态，再决定继续、回退或人工恢复。

V1 没有通用 `db restore` 命令。恢复数据库备份或维护恢复点属于版本匹配的离线处置，必须先停止目标 Runtime，并由受控运维流程执行；不得把备份覆盖到仍在运行的工作区。恢复后必须再次验证 Schema 14、数据库完整性、消息索引和 Blob 引用。

## 8. 退出码与自动化判定

| 退出码 | 含义 |
| ---: | --- |
| 0 | 成功，或 dry-run/检查完成且结果健康 |
| 1 | 通用错误、检查发现不健康状态或部分恢复 |
| 2 | 参数或配置错误 |
| 3 | 认证错误 |
| 4 | 工作区、数据目录或排他锁错误 |
| 5 | Runtime 连接错误 |
| 130 | 用户拒绝确认或主动中断 |

自动化程序同时检查进程退出码和 JSON 信封的 `success`。不要仅搜索人类输出文本，也不要把“创建了恢复点”误判为维护成功。任何 partial、diagnostic 或 warnings 都应进入运维记录。

## 9. 维护后验证

```powershell
madorin version --json
madorin doctor --workspace $workspace --json
madorin db check --workspace $workspace --verbose --json
madorin storage check --workspace $workspace --verify-hashes --json
madorin session list --workspace $workspace --json
```

确认产品名为 `Madorin.AI.Runtime`、协议为 `1.1`、SQLite Schema 为 `14`，所有 JSON 可独立解析且 stderr 未混入 stdout。至少抽查一个活动 Session 和一个已恢复 Session，确认 Selection、消息顺序、最新 Run 状态以及 resume/rehydrate 行为符合预期，再恢复正常写入。

恢复点和备份应按组织保留策略转移到受控位置；在验证期结束前不要清理。日志、诊断包和工单中继续执行 Key、Prompt、工具参数和业务内容脱敏。
