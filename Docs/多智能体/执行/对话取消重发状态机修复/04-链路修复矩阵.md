**统计**：

- 真正被打断的链路：**6 条**（1, 4, 6, 7, 8, 12）— 每条都给出架构级修复方案
- 新增需求但不实现：**1 条**（9，TTS 物理上不需要 per-turn 队列）
- 不打断的链路：**6 条**（2, 3, 5, 10, 11, 13）

**关键原则**：所有"修复"都是架构级（独立组件 + 显式契约 + 单源事件），不是修补丁（保留旧路径 + 临时桥接 + 复制粘贴）。

### 7.2 6 条打断链路的架构级修复方案详解

#### 7.2.A 取消传播链路 — 单一入口 + Registry 路由

**问题**：旧链路里 `_streamCts` 是 service 字段，`UI/Networks/Voice → IAiChatEngine.Stop → AiChatHostedService._streamCts.Cancel()` 一气呵成。新架构 CTS 在 `ChatTurnContext` 里，外部直接读字段不可能。

**架构级修复**：

```text
取消唯一入口（架构契约）：
   ChatTurnExecutor.CancelCurrentTurnAsync()
     ├─ 内部查 ChatTurnCancellationRegistry 找当前活跃 turnId
     ├─ Registry.CancelAsync(turnId) 取该 turn 的 CTS 并 Cancel
     └─ 立即返回（不等 AF stream 自然结束）

外部 4 个入口都转发到这一个：
   IAiChatEngine.Stop()              → ChatTurnExecutor.CancelCurrentTurnAsync()  fire-and-forget
   IAiChatEngine.CancelCurrentTask() → 同上
   IAiChatEngine.CancelCurrentTaskAsync() → await
   ChatInputVm.CancelAsync()         → IAiChatEngine.CancelCurrentTaskAsync
```

**链路接通性验证**：

- ✅ `WebSocketInputChannel:69 chatEngine.Stop()` → 转发 → ChatTurnExecutor → Registry → 当前 turn CTS Cancel
- ✅ `IVoiceCoordinator:27 chatEngine.CancelCurrentTask()` → 同
- ✅ `SpeechRecognitionService:345 chatEngine.CancelCurrentTask()` → 同
- ✅ `VoicePipelineCoordinator:159 chatEngine.CancelCurrentTask()` → 同
- ✅ `ChatInputVm.CancelAsync` → IAiChatEngine.CancelCurrentTaskAsync → 同

**架构级而非修补丁的体现**：

- 修补丁式做法：保留 `_streamCts` 字段 + 加一个 `Registry.CancelAsync` 双写 → 状态分裂
- 架构式做法：唯一入口 + Registry 单源 → 取消语义有且只有一种实现路径

#### 7.2.C 持久化链路 — 双路径分工

**问题**：旧 catch 块直接调 `chatHistoryProvider.SavePartialResponseAsync`，那是 AF 钩子层的方法。新架构拆出 ChatMessagePersistence 后，是替代还是包装？

**架构级修复**：明确**两条平行路径**，绝不替代：

```text
路径 A（AF 钩子主链路，不动）：
   AF stream 自然完成
     → 触发 ChatHistoryProvider.StoreChatHistoryAsync (AF 钩子)
     → ChatHistoryDataProvider.StoreChatHistoryAsync
     → 写 ChatMessages 表 + 触发 CompactAndReplaceAsync 异步压缩

路径 B（取消时部分持久化，新增薄包装）：
   AF stream 取消
     → ChatTurnExecutor catch 块捕获 OperationCanceledException
     → ChatMessagePersistence.SavePartialResponseAsync(context, fullResponse)
     → 内部转调 chatHistoryProvider.SavePartialResponseAsync(...)（不重新实现）
     → 写 ChatMessages 表

路径 C（Workflow → Chat 回灌，独立平级）：
   WorkflowExecutor 任务完成
     → 直接调 chatHistoryProvider.AppendWorkflowFinalReport(...)
     → 写 ChatMessages + publish OnConversationTurnCompleted
     → 与路径 A、B 互不干扰
```

**链路接通性验证**：

- ✅ AF 钩子 StoreChatHistoryAsync 在 RunStreamingAsync 完成时自动触发，方法不动 → Memory 插件订阅链路完整
- ✅ 取消时部分回复落库 → AF 钩子 ProvideChatHistoryAsync 下一轮自动读到 → AI 看见上下文
- ✅ 工作模式 finalReport 回灌 → SourceTaskId 通过 TraceId 字段透传 → Memory 插件去重逻辑保留

**架构级而非修补丁的体现**：

- 修补丁式做法：把 SavePartialResponseAsync + AppendWorkflowFinalReport 都迁到 ChatMessagePersistence 类 → 跨业务耦合
- 架构式做法：三条路径职责分离（AF 钩子主链路 / turn 取消薄包装 / workflow 回灌独立方法），ChatMessagePersistence 只做 turn 内最薄包装

#### 7.2.E 配置同步链路 — ChatAgentResolver 单源 + 转发暴露

**问题**：`_currentProvider/_currentAgent/_currentModel` 字段从 AiChatHostedService 迁到 ChatAgentResolver 后，外部 12 处读取（WorkModeInputVm 4 处 + MeetingInputVm 1 处 + CurrentSessionResolver 2 处 + UI VM 等）会失效；ChatInputVm 调 `Change*` 也要保持兼容。

**架构级修复**：

```text
ChatAgentResolver（单源）：
   持有 _currentProvider / _currentAgent / _currentModel / _builtToolContextVersion
   暴露：
     CurrentProvider / CurrentAgent / CurrentModel 访问器
     ChangeProvider/Agent/Model 方法（不再清空字段，仅更新内部默认值）
     BuildAgentForTurn(ChatTurnRequest) 方法（每个 turn 调一次，按需重建）
     DefaultsChanged 事件（默认配置变更时触发，UI 可订阅）

AiChatHostedService（薄转发层）：
   public AiProviderEntity? CurrentProvider => _agentResolver.CurrentProvider;
   public AgentEntity?      CurrentAgent    => _agentResolver.CurrentAgent;
   public AiModelEntity?    CurrentModel    => _agentResolver.CurrentModel;
   public void ChangeProvider(string id) => _agentResolver.ChangeProvider(id);
   public void ChangeAgent(string id)    => _agentResolver.ChangeAgent(id);
   public void ChangeModel(string id)    => _agentResolver.ChangeModel(id);
```

**链路接通性验证**：

- ✅ `WorkModeInputVm:406 _chatService.CurrentAgent` → 转发到 _agentResolver.CurrentAgent → 行为不变
- ✅ `WorkModeInputVm:407/702 _chatService.CurrentProvider` → 同
- ✅ `WorkModeInputVm:408/711 _chatService.CurrentModel` → 同
- ✅ `MeetingInputVm:396 _chatService.CurrentWorkspaceId` → 不动（依赖 appPaths，与 ChatAgentResolver 无关）
- ✅ `ChatInputVm:301-306 _chatService.ChangeAgent/Provider/Model` → 转发，且阶段 2 之后**不再清空字段**

**架构级而非修补丁的体现**：

- 修补丁式做法：在 AiChatHostedService 同时维护两份字段 + 同步逻辑 → 双源
- 架构式做法：ChatAgentResolver 是字段唯一所有者；AiChatHostedService 仅做薄转发；事件订阅源单一

#### 7.2.F SessionCreated 联动链路 — publish 跟随 NewSessionAsync 迁移

**问题**：[AiChatHostedService.cs:191](../../../Src/Netor.Cortana.AI/AiChatHostedService.cs#L191) `publisher.Publish(Events.OnSessionCreated, new SessionCreatedArgs(_sessionId))` 在 NewSessionAsync 内部。NewSessionAsync 迁到 ChatSessionService 时如果 publish 代码不迁，工作模式监听会丢事件。

**架构级修复**：

```text
ChatSessionService.NewSessionAsync(...)
   ├─ 创建空 AgentSession (经 ChatAgentResolver 建出来的 agent.CreateSessionAsync)
   ├─ 生成 sessionId
   ├─ session.StateBag.SetValue("sessionid", sessionId)
   ├─ chatHistoryProvider.CreateNewSessionAsync(session, agent)（写 DB）
   ├─ publisher.Publish(Events.OnSessionCreated, new SessionCreatedArgs(sessionId))   ← 必须跟着迁移
   └─ factory.ResetTokenStats()  ← Token 统计重置也跟着迁

AiChatHostedService.NewSessionAsync() => _sessionService.NewSessionAsync()  ← 转发
```

**链路接通性验证**：

- ✅ UI MainWindow.Sessions 调 chatEngine.NewSessionAsync → 转发 → ChatSessionService → publish OnSessionCreated → UI 订阅端收到
- ✅ WorkModeInputVm:378 调 _chatService.NewSessionAsync → 同（工作模式可能监听 OnSessionCreated 做后续动作）
- ✅ Memory 插件订阅 OnSessionCreated → 收到（事件结构 SessionCreatedArgs 不动）

**架构级而非修补丁的体现**：

- 修补丁式做法：在 AiChatHostedService 转发后**也 publish 一次** → 重复事件
- 架构式做法：publish 代码跟随业务行为迁移，单一事件源

#### 7.2.G Workflow → Chat 回灌链路 — 保留 AppendWorkflowFinalReport 不动

**问题**：[ChatHistoryDataProvider.cs:283-374](../../../Src/Netor.Cortana.AI/Providers/ChatHistoryDataProvider.cs#L283-L374) `AppendWorkflowFinalReport` 是工作模式 finalReport 回灌到 Chat 历史的入口，独立于 turn 执行。实施者拆 ChatMessagePersistence 时可能误把它一起拆走。

**架构级修复**：

```text
保留不动的边界：
   ChatHistoryDataProvider 类（AF kit 的扩展）
     ├─ ProvideChatHistoryAsync (AF 钩子)              ← 保留
     ├─ StoreChatHistoryAsync (AF 钩子)                ← 保留
     ├─ SavePartialResponseAsync (turn 取消用)         ← 保留（被 ChatMessagePersistence 包装）
     ├─ AppendWorkflowFinalReport (workflow 回灌用)    ← 保留，独立功能
     └─ AddOrUpdateSessionAsync (内部辅助)             ← 保留

新增的 ChatMessagePersistence 类：
   public sealed class ChatMessagePersistence(ChatHistoryDataProvider provider)
   {
       public Task SavePartialResponseAsync(ChatTurnContext context, string content)
           => provider.SavePartialResponseAsync(content, context.Session, context.Agent,
                                                context.Model.Name, context.AssistantMessageId);
   }
   ←  仅是 turn 内最薄包装，不重新实现持久化
   ←  不接管 AppendWorkflowFinalReport
```

**链路接通性验证**：

- ✅ WorkflowExecutor 调 chatHistoryProvider.AppendWorkflowFinalReport → 写 ChatMessages → publish OnConversationTurnCompleted（带 SourceTaskId）→ Memory 插件消费
- ✅ 工作模式回灌的对话出现在 Chat 历史里 → AF 钩子 ProvideChatHistoryAsync 下一轮自动加载
- ✅ ChatTurnExecutor 取消时调 ChatMessagePersistence.SavePartialResponseAsync → 转调 ChatHistoryDataProvider 同方法（实现唯一）

**架构级而非修补丁的体现**：

- 修补丁式做法：把 AppendWorkflowFinalReport 也迁到 ChatMessagePersistence → 跨业务耦合
- 架构式做法：ChatHistoryDataProvider 是 AF kit 扩展功能（持久化所有 Chat 类消息），ChatMessagePersistence 是专家模式 turn 内薄包装；两者职责清晰分离

#### 7.2.H TTS 跨 turn 截断链路 — 不实现 per-turn 队列（架构决策）

**问题**：TtsPluginOutputChannel.OnCancelledAsync 当前调 `ttsPluginAdapter.StopAsync(_sessionId, cts.Token)` 整把停 sessionId 范围内的 TTS。接口加 turnId 后是否需要按 turn 切播报队列？

**架构级修复（决策不实现）**：

```text
TTS 物理事实：
   - 一次只能播一条音频流
   - 跨 turn 不会同时播报多个 AI 回复
   - "旧 turn 的 token 未播完，新 turn 的 token 又来"在物理上不会发生（因为 OnTokenAsync 串行）

架构决策：
   TtsPluginOutputChannel.OnCancelledAsync(turnId)
     → ttsPluginAdapter.StopAsync(_sessionId, cts.Token)  ← 行为不变
     → turnId 仅用于 LogInformation 日志关联

TtsPluginOutputChannel.OnTokenAsync(turnId, token, sessionId, ct)
   → ttsPluginAdapter.EnqueueAsync(token, sessionId, ct)  ← 行为不变
   → turnId 仅用于日志
```

**链路接通性验证**：

- ✅ AI 流式 → TtsPluginOutputChannel.OnTokenAsync(turnId, ...) → TTS 队列 → 播报
- ✅ 用户取消 → TtsPluginOutputChannel.OnCancelledAsync(turnId) → ttsPluginAdapter.StopAsync(sessionId) → 整把停
- ✅ VoiceChatOutputChannel 同理

**架构级而非修补丁的体现**：

- 这不是回避问题，而是基于物理事实的合理边界 — TTS 不需要 per-turn 队列
- turnId 仍进入接口契约（编译期强制），保留未来加 per-turn 行为的扩展点

#### 7.2.I 工具上下文版本链路 — ChatAgentResolver 接管全链路

**问题**：`InvalidateAgentIfToolContextChanged` 当前在 AiChatHostedService 4 处被调（NewSessionAsync, ResumeSessionAsync, SendMessageAsync, EnsureGenerationSessionAsync），加上 SubscribeConfigChangeEvents 监听 PluginLoader 事件触发的 InvalidateAgent。`_builtToolContextVersion` 字段。整条链路要随 ChatAgentResolver 一起迁移。

**架构级修复**：

```text
ChatAgentResolver 接管全链路：
   持有 _builtToolContextVersion 字段
   构造时订阅 ToolContextVersionService.VersionChanged 事件
     → 触发自身 InvalidateAgent 方法（清空 agent 缓存，下次 BuildAgentForTurn 时重建）
   BuildAgentForTurn(ChatTurnRequest) 内：
     ① 若 _builtToolContextVersion != ToolContextVersionService.Current
        → 重建 agent + 更新版本快照
     ② 返回新 / 缓存的 AIAgent

AiChatHostedService 不再持有 _builtToolContextVersion，不再调 InvalidateAgent*：
   - SendMessageAsync 改为调 ChatTurnExecutor.ExecuteTurnAsync(context)
   - ChatTurnExecutor 内调 ChatAgentResolver.BuildAgentForTurn(context)
   - 工具上下文检查在 BuildAgentForTurn 内自动发生
```

**链路接通性验证**：

- ✅ PluginLoader 加载/卸载插件 → ToolContextVersionService.IncrementVersion → ChatAgentResolver 收到事件 → 下次 BuildAgentForTurn 时重建 → AI 看到新工具集
- ✅ NewSession / ResumeSession 流程：阶段 3.4 拆 ChatSessionService 后，session 服务调 ChatAgentResolver.BuildAgentForTurn 之前会自动检查
- ✅ 图片/视频生成 (EnsureGenerationSessionAsync) 调用相同的 BuildAgentForTurn 路径

**架构级而非修补丁的体现**：

- 修补丁式做法：4 个调用点保留在 AiChatHostedService，每个都加 `_agentResolver.InvalidateIfToolContextChanged()` → 散布检查
- 架构式做法：检查内聚到 BuildAgentForTurn 一处；版本号字段唯一所有者是 ChatAgentResolver；订阅源单一
