# 总览页配置驱动方案

> 让同一套总览页骨架，随品牌切换出不同的仪表盘、介绍与快捷操作，
> 而"继续工作/活跃任务"等通用骨架保持不变。
>
> 关联：[控件清单 · 03 主内容-总览页](界面样板/控件清单/03-主内容-总览页.md) ·
> [品牌发布目录](../../Build/brands/README.md)

> ⚠️ **载体位置未定性。** 本项目后期将整体移出并重建，因此配置文件"放在哪"
> （`Build/brands/{brand}/` 下、还是独立配置仓 / 平台下发 / 应用数据目录）
> 均为**候选方案**，不作最终决定。当前 `Build/brands/madorin/workbench.json`
> 等文件仅作**参考样例**，用于把 schema 与驱动机制先跑通。重建时按第 5 节的
> 候选与权衡另行定稿。**本方案定性的是"配置驱动的机制与 schema"，不是存放路径。**

> 🆕 **v2 升级（当前版本）。** 总览页已重构为五层工作台（KPI / 运行项目 / 继续工作 /
> 新建业务工作 / 行业功能）。前三层通用、由 Runtime 提供；后两层可配置。配置模型从
> v1 的 `command/skill/platform` 三档，升级为 **动作调用模型 `invoke`（四种 kind）+
> 能力别名层 + Agent 内联定义**。完整设计见 **[§9 v2：工作台配置模型](#9-v2工作台配置模型)**。
> §1–§4 的"固定骨架 + 内容槽"原则依然成立；§5–§8 的 v1 KPI/quickActions schema 作为
> 历史保留，实际以 §9 为准。

## 1. 背景与目标

当前总览页（`#pane-overview`）顶部 KPI 与常用操作是**硬编码的电商示例数据**
（今日订单 184、待发布商品 27……）。但本软件以**多品牌发布**方式交付，
两个品牌核心驱动一致，区别只在安装的技能/插件与行业配置：

| 品牌 | ID | 行业 | 仪表盘关注点 |
|------|----|------|------------|
| 玛得令 / Madorin | `madorin` | 软件工程开发 AI 助理 | 任务、对话、审批、产物 |
| 渡海舟 / SreamX | `sreamx` | 跨境电商运维 | 订单、商品、异常、回款 |

目标：**总览页四大板块骨架永远不变，变的只是每个槽位的数据来源**。
切换品牌 = 换一份配置，骨架代码零改动，UI 自动呈现不同样式与快捷入口。

---

## 2. 核心原则：固定骨架 + 配置内容槽

总览页四大板块的**顺序与结构永远不变**：

```
KPI 行（仪表盘）  →  继续工作卡  →  常用操作  →  活跃任务表
```

每个槽位的数据归入三档来源之一：

| 档位 | 含义 | 谁定义 | 举例 |
|------|------|--------|------|
| **通用固定** | 跨品牌完全一致，写死在骨架 | 代码 | 继续工作卡结构、活跃任务表列、常用操作通用段 |
| **品牌配置** | 随行业变，发布时声明 | `workbench.json` | KPI 卡定义、常用操作品牌段、模式介绍文案 |
| **运行时数据** | 按当前工作目录 / run 状态实时算 | Runtime | KPI 数值、继续工作卡内容、活跃任务行 |

> 你提到的"统计根据工作目录或全局配置"，对应关系是：
> **配置声明**（有哪些卡、什么图标、数据从哪取）由品牌层给；
> **数值求值**（具体数字）由运行时针对当前工作目录算。

---

## 3. 四板块拆解（通用 vs 品牌化）

### 3.1 KPI 行（仪表盘）→ 完全品牌化

不再写死"订单/商品/异常"。品牌配置声明一组 KPI 卡描述符，每张卡带
`label / icon / color / source`。`source.type` 决定数字从哪来：

| source.type | 含义 | 适用 |
|-------------|------|------|
| `builtin` | Runtime 针对当前工作目录算的内置指标 | AI 助理：活跃任务数、今日对话、待审批、本周产物 |
| `command` | 跑一条命令，解析输出为数值 | 电商：异常计数等本地脚本可得的指标 |
| `skill` | 调一个技能返回数值 | 需要技能能力才能得到的统计 |
| `platform` | 运营平台 API | 电商：订单、商品、回款 |

每张卡另可带 `trend`（趋势小字），来源同上或 `static`（固定文案）。

### 3.2 继续工作卡 → 通用骨架 + 运行时数据

两品牌结构完全一致（左栏进度 + 右栏业务步骤）。"业务步骤"文案来自任务本身，
无需品牌配置。此板块**不进 workbench.json**。

### 3.3 常用操作 → 半品牌化（通用段 + 品牌段）

- **通用段**（骨架固定，永远在）：新建工作任务、查看历史记录、工作区文件
- **品牌段**（`workbench.json.overview.quickActions` 声明）：
  - AI 助理：代码分析、发起评审会议、运行测试
  - 电商：批量上架、订单同步、异常处理

每个品牌段操作绑定一个 `action`，机制与 KPI 的 `source` 同族：
`builtin`（调内置函数如 `openNewDialog`）/ `command`（跑命令）/ `skill`（调技能）。

### 3.4 活跃任务表 → 通用骨架 + 运行时数据

列结构（标题/模式/状态/进度/主 Agent/耗时）通用，行数据实时。此板块**不进配置**。

---

## 4. 三层配置模型

```
品牌层 (发布时, workbench.json)
   行业默认：KPI 定义 / 常用操作品牌段 / 模式介绍文案
        │  可被覆盖
        ▼
工作区层 (运行时, 当前工作目录)
   真实数据上下文 + 可选覆盖（某工作区想改 KPI 组合）
        │  填充数值
        ▼
运行时层
   KPI 数值 / 继续工作卡 / 活跃任务 实时求值填充
```

- **品牌层**：随发布固化，回答"这个品牌总览页长什么样"。
- **工作区层**：可选，允许单个工作目录覆盖品牌默认（留扩展位，第一版可不实现覆盖）。
- **运行时层**：把描述符里的 `source` / `action` 求值成真实数字与行为。

## 5. 配置载体：`workbench.json`（存放位置为候选，待重建定稿）

界面/业务配置**独立成文件**（不混入承载身份与构建信息的 `{brand}.json`）——
这一点是机制层的决定，稳定。**但文件放在哪里未定性**，下面列候选与权衡。

### 5.0 存放位置候选

| 候选 | 位置 | 优点 | 顾虑 |
|------|------|------|------|
| **A. 品牌目录内**（当前样例） | `Build/brands/{brand}/workbench.json` | 与品牌资产同处，发布链路现成 | 配置与构建目录耦合；重建后目录结构会变 |
| **B. 独立配置仓** | 独立 repo / 配置目录 | 配置与代码解耦，可单独版本化 | 需新增拉取/同步机制 |
| **C. 平台下发** | 运营平台 API 返回 | 不重新发布即可改仪表盘；与电商 platform 源天然一致 | 依赖联网；需缓存与离线降级 |
| **D. 应用数据目录** | 安装后用户/应用数据目录 | 运行时可写，便于工作区层覆盖 | 首次需内置默认；分发要带初始配置 |

> 当前用候选 A 仅因发布链路现成、便于把 schema 跑通。**重建时重新评估**，
> 很可能走 B/C 组合（默认内置 + 平台可覆盖）。选定前不写死任何加载路径。

### 5.1 当前参考样例（候选 A 下的形态）

```
Build/brands/madorin/
  madorin.json      ← 品牌身份 + 构建（现有）
  workbench.json    ← 界面/业务配置（本方案参考样例）
  brand.ico / brand.png
```

发布时 `publish.ps1` 已把品牌目录整体作为来源；若沿用候选 A，`workbench.json`
可随该目录一同同步进产物（发布脚本对接细节见后续 Runtime 排期）。
换作其他候选，则由对应加载器读取——**Runtime 只认 schema，不认路径**。

### 5.2 Schema（`schemaVersion: 1`）

```jsonc
{
  "schemaVersion": 1,
  "brand": "madorin",
  "overview": {
    "intro": "面向软件工程开发的 AI 工作台",   // 模式介绍，两品牌不同
    "kpis": [
      {
        "id": "active_tasks",              // 稳定标识
        "label": "活跃任务",               // 卡片标签
        "icon": "list-checks",             // lucide 图标名
        "color": "ok",                     // 主题色变量：ok/ac/warn/txm...
        "format": "number",                // number(默认) | currency
        "source": { "type": "builtin", "metric": "tasks.active" },
        "trend":  { "type": "builtin", "metric": "tasks.active.delta", "suffix": "较昨日" }
      }
    ],
    "quickActions": [
      {
        "id": "code_analysis",
        "name": "代码分析",
        "desc": "让 Agent 审查代码",
        "icon": "search-code",
        "action": { "type": "skill", "ref": "code-analysis" }
      }
    ]
  }
}
```

### 5.3 `source` / `action` 类型

| type | 字段 | 说明 |
|------|------|------|
| `builtin` | `metric` | 运行时内置指标名（如 `tasks.active`） |
| `command` | `ref` | 命令标识，跑命令解析输出 |
| `skill` | `ref` | 技能标识，调技能取返回值 |
| `platform` | `metric` | 运营平台 API 指标（`action` 不用此型） |
| `static` | `text` | 仅 `trend` 用，固定文案 |

`trend` 额外可带 `prefix` / `suffix` / `color`，用于拼装趋势小字。

## 6. 求值时序（运行时渲染流程）

```
1. 应用启动 / 切换工作区
2. 载入当前品牌 workbench.json  →  得到 KPI 定义、常用操作品牌段、intro
3. 渲染骨架：KPI 行占位卡、常用操作(通用段 + 品牌段)、继续工作、活跃任务
4. 对每个 KPI.source 求值：
     builtin  → 查 Runtime 指标表(按当前工作目录)
     command  → 执行命令、解析输出
     skill    → 调技能、取返回
     platform → 请求平台 API
   求值失败的卡显示占位/降级，不阻塞其他卡
5. 填充数值与 trend，KPI 行完成
6. 继续工作卡 / 活跃任务表 由 Runtime 任务状态实时填充
```

要点（呼应控件清单）：**分类/卡片增删改后，只需配置变 + 重渲染，UI 自动同步，无需改 HTML。**

## 9. v2：工作台配置模型

总览页重构为五层工作台。本节是 v2 的权威定义，取代 §5–§8 的 v1 schema。

### 9.1 五层结构：通用 vs 可配置

| 层 | 区块 | 性质 | 数据来源 |
|----|------|------|---------|
| ① | KPI 统计行 | **通用** | Runtime（运行项目/智能体/文件/待处理） |
| ② | 正在运行的项目 | **通用** | Runtime（当前项目列表 + 任务/文件） |
| ③ | 继续工作 | **通用** | Runtime（当前活跃任务） |
| ④ | 新建业务工作 | **可配置** | `overview.newBusiness` |
| ⑤ | 行业功能 | **可配置** | `overview.industry` |

**只有 ④⑤ 进配置。** ①②③ 由 Runtime 直接提供，配置不涉及。

### 9.2 核心：动作调用模型 `invoke`

④⑤ 里每个可点击动作 = 一个 `invoke` 判别联合，`kind` 四选一：

| kind | 用途 | 关键字段 |
|------|------|---------|
| `skill` | 纯技能（如翻译商品页） | `skill` + 可选 `prompt` / `inputs` |
| `plugin` | 插件 / 技能+插件（如导入商品） | `plugin` + `entry` + 可选 `skills` |
| `command` | 命令 / 简单调用（如检查 DNS） | `command` |
| `task` | **AI 任务**（如购买服务器、新建独立站） | `mode` + `agent` + `needs` + `prompt` + `inputs`；可选 `vendor`/`model` |

`task` 是重点，承载"用谁执行 · 需要什么权限 · 做什么"三元组，直接对接你的 AI 接口（§9.5）。

### 9.3 能力别名层 `capabilities`

动作**不直接写插件 id**，而声明"需要什么能力"（`needs`），能力→实现的映射集中在 `capabilities`：

```jsonc
"capabilities": {
  "服务器管理": { "plugins": ["server-manager"] },
  "域名管理":   { "plugins": ["dns-tools", "domain-registrar"] },
  "商品本地化": { "skills": ["page-translate", "product-clean"] }
}
```

- 换插件实现只改这一处；
- 界面/客户看到的是"服务器管理"能力，而非插件 id；
- 解决"AI 默认无服务器/域名管理权限"——运行时按 `needs` 解析出插件/技能集，授予执行 agent。

### 9.4 Agent 内联定义 `agents`

执行者（agent）在 workbench.json 内联定义。每个 agent 自带厂商/模型/基础能力；
动作里 `vendor`/`model` 可省略（用 agent 绑定的），需要覆盖时再写。

```jsonc
"agents": {
  "infra-ops":    { "displayName": "基础设施运维", "vendor": "anthropic", "model": "claude-opus-4",
                    "capabilities": ["服务器管理", "域名管理"] },
  "content-ops":  { "displayName": "商品内容运营", "capabilities": ["商品本地化", "商品优化"] }
  // content-ops 未写 vendor/model → 用系统 Agent 默认绑定
}
```

> 采用**内联**是本轮决策（单文件自包含）。代价：多品牌各写一份、与"Agent 定义"面板可能重复。
> 重建时若 agent 体系独立，可改为引用外部注册表——届时把此段替换为 `"agents": "ref:registry"` 之类即可，
> 动作里的 `agent` 引用键不变。

### 9.5 与 AI 接口的衔接契约

点击 `kind:"task"` 动作时，前端把配置 + 用户填写的 `inputs` 解析成一次调用，
正是你将实现的 AI 接口入参：

```
createTask({
  mode,                  // work / meeting / expert → 打开哪种工作页
  agent,                 // 解析后的 agent（携带厂商+模型+基础权限）
  vendorOverride?,       // 动作显式覆盖（可空）
  modelOverride?,        // 动作显式覆盖（可空）
  grantedCapabilities,   // needs 经 capabilities 解析出的 { plugins:[], skills:[] }
  prompt,                // 用 inputs 值填好占位符后的提示词
  inputs                 // 用户填写的参数键值
})
```

**配置负责"声明"，你的接口负责"执行"，边界清晰。** ④新建业务工作 与 ③继续工作 都走这个接口
（③继续工作是恢复已存在任务，同样以 agent + prompt 续接）。

### 9.6 完整 schema（v2）

```jsonc
{
  "schemaVersion": 2,
  "brand": "sreamx",
  "intro": "面向跨境电商运维的 AI 工作台",

  "agents": { "<id>": { "displayName", "vendor?", "model?", "capabilities": [] } },

  "capabilities": { "<能力名>": { "plugins?": [], "skills?": [] } },

  "overview": {
    "newBusiness": [
      { "id", "name", "desc", "icon", "invoke": { /* 四种 kind 之一 */ } }
    ],
    "industry": [
      { "id", "name", "desc", "icon",
        "stat": { "source": "builtin", "metric": "<聚合指标名>" },   // 卡片右上统计，Runtime 求值
        "actions": [ { "name", "icon", "color?", "invoke": { /* … */ } } ] }
    ]
  }
}
```

`inputs[]` 项：`{ "key", "label", "type": "text|select|number", "options?": [] }`——
点击动作时 UI 据此弹出参数收集，值填进 `prompt` 占位符并随 `createTask` 传出。

### 9.7 品牌区分

不同品牌换 `agents / capabilities / overview.newBusiness / overview.industry` 四段即可，
①②③ 通用层不动。客户打开就看到本行业的能力矩阵，点哪个直接触发对应 `invoke`。

样例：[`Build/brands/sreamx/workbench.json`](../../Build/brands/sreamx/workbench.json)（跨境电商，与当前界面一一对应）·
[`Build/brands/madorin/workbench.json`](../../Build/brands/madorin/workbench.json)（软件工程对照）。
