## 插件通道架构

项目有两套插件加载机制：

```
Plugin.Native  → 直接加载 .dll，通过 P/Invoke 调用导出函数
Plugin.Process → 启动独立进程，JSON-over-IPC 通信
```

`Plugin.Process` 架构天然跨平台（进程隔离 + JSON），是更推荐的跨平台插件模式。
`Plugin.Native` 在 .NET 层面跨平台，但要求插件开发者为每个目标平台编译对应原生库。

## 详细评估

### 🔴 PowerShell Plugin（阻塞）

**文件**：`BuiltIn/PowerShell/`

问题：

1. **`PowerShellPathHelper.cs`（第16–31行）** — 硬编码 Windows 路径：
   ```csharp
   // %ProgramFiles%/PowerShell/pwsh.exe
   // %SystemRoot%/System32/WindowsPowerShell/v1.0/powershell.exe
   ```

2. **`ExecutionSession.cs`（第66–82行）** — `Process.Kill(entireProcessTree: true)` 在 Linux/macOS 上行为不一致

3. **依赖 `ChildProcessTracker`**（见下）

**修复方向**：
- `pwsh` 在 macOS/Linux 同样存在（`/usr/bin/pwsh` 或 Homebrew 安装），需用 `which pwsh` 探测
- `Process.Kill(entireProcessTree)` 在 .NET 6+ 实际支持三端，但依赖的 `ChildProcessTracker` 仍是阻塞点
- 整体改为条件分支：Windows 用 Job Objects，Unix 用进程组（`kill -SIGTERM -pgid`）

---

### 🔴 ChildProcessTracker（阻塞，影响范围广）

**文件**：`Core/ChildProcessTracker.cs`

```csharp
[SupportedOSPlatform("windows")]  // 第15行，明确标注
// P/Invoke：
[DllImport("kernel32.dll")] CreateJobObject(...)
[DllImport("kernel32.dll")] SetInformationJobObject(...)
[DllImport("kernel32.dll")] AssignProcessToJobObject(...)
```

Windows Job Objects 用于确保子进程跟随父进程退出。Linux/macOS 的对应机制：
- Linux：`prctl(PR_SET_PDEATHSIG, SIGTERM)` 或进程组
- macOS：`kqueue` + `PROC_EVENT_EXIT`

**修复方向**：
```csharp
// 条件编译模式
static partial class ChildProcessTracker
{
    static partial void TrackInternal(Process process);
}

// ChildProcessTracker.Windows.cs
[SupportedOSPlatform("windows")]
static partial void TrackInternal(Process process) { /* Job Objects */ }

// ChildProcessTracker.Unix.cs
[SupportedOSPlatform("linux"), SupportedOSPlatform("macos")]
static partial void TrackInternal(Process process) { /* prctl / kqueue */ }
```

---

### 🟢 FileBrowser Plugin（无问题）

**文件**：`BuiltIn/FileBrowser/`

全部使用标准 .NET 文件 API（`Path`、`File`、`Directory`），无 Windows 特有依赖。
**结论：直接可跨平台，无需修改。**

---

### 🟡 NativeHost（有条件可行）

**文件**：`Plugins/Netor.Cortana.NativeHost/Program.cs`

.NET 层面使用标准的 `NativeLibrary.Load()` + `Marshal`，本身跨平台。
依赖的 C 接口协议：
```c
cortana_plugin_get_info()
cortana_plugin_init(char* configJson)
cortana_plugin_invoke(char* toolName, char* argsJson)
cortana_plugin_free(char* ptr)
cortana_plugin_destroy()
```

**结论**：宿主本身可跨平台，但第三方插件开发者需要为每个目标平台编译原生库（`.dll` / `.dylib` / `.so`），文档需要说明这一要求。

---

### 🟡 Plugin.Native 框架（有条件可行）

源代码生成器（`StartupEmitter.cs`）生成的代码使用标准 `[UnmanagedCallersOnly]` + `Marshal`，.NET 层面跨平台。
同 NativeHost——原生插件 DLL 本身需要各平台分别编译。

---

## 修复优先级

**必须解决（阻塞跨平台发布）：**
1. `ChildProcessTracker` — 拆分为平台特定实现
2. `PowerShellPathHelper` — 改为运行时探测 `pwsh` 路径（支持 PATH 搜索）
3. `ExecutionSession` — 验证 `Process.Kill(entireProcessTree)` 三端行为，补 Unix 回退

**不需要修改：**
- FileBrowser Plugin
- Plugin.Process 框架
- StartupEmitter 代码生成器
- 插件接口定义（IPlugin、IPluginContext）

**需要文档说明（非代码修改）：**
- NativeHost：第三方插件需提供三端原生库
- Plugin.Native：开发者指南需补充跨平台编译要求
